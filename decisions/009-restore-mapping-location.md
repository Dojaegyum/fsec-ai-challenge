# ADR-009. 복원 매핑을 암호화해 서버 볼트에 두고 키는 클라이언트가 갖는다

- 상태: **채택**
- 날짜: 2026-08-16
- 결정: @kth9245
- 관련: [ADR-002](002-project-name.md) (포지셔닝) · `spec/common/08-14-pii-boundary.md`

## 결정

토큰↔원문 매핑을 **암호화된 상태로 서버 볼트에 보관**하고, **복호화 키(세션키)는 클라이언트가** 갖습니다. 복원은 브라우저에서 일어납니다.

`spec/common/08-14-pii-boundary.md` 불변 규칙 1과 `CLAUDE.md` 절대 규칙 3을 이에 맞춰 고쳤습니다.

| | 이전 | 이후 |
| --- | --- | --- |
| 매핑 저장 | 클라이언트 세션에만 | **암호화해 서버 볼트에** |
| 복호화 키 | (해당 없음) | **클라이언트 세션에만** |
| 복원 위치 | 브라우저 | **브라우저** (그대로) |

**규칙 2·4·5·6은 건드리지 않았습니다.** 외부 LLM에는 여전히 토큰화 텍스트만 가고, 서버가 완성된 서류를 만들어 내려주지 않습니다.

## 왜 바꿨나

**이전 규칙이 서비스 정의와 모순됐습니다.**

`CLAUDE.md`는 이 서비스를 "기한과 서류를 **몇 달에 걸쳐** 대신 관리"한다고 정의합니다. 그런데 `spec/04`는 매핑을 클라이언트 세션에만 두고 사건을 24시간 뒤 파기한다고 정했습니다.

둘을 같이 지키면 이렇게 됩니다.

| 시점 | 사용자가 하려는 것 | 실제로 |
| --- | --- | --- |
| 1일차 | 사건 등록, 지급정지 요청 | 정상 |
| **3영업일** | 피해구제 신청서 작성 (`F-08`) | 브라우저 세션 만료 → 계좌번호가 `[계좌-1]`로만 보임 → **서류를 못 씀** |
| 2개월 | 채권소멸공고 확인 | 사건 자체가 파기됨 |

`spec/backend/08-14-channel-matrix.md`가 지목한 **"가장 많이 놓치는 두 지점"** 중 첫째가 "전화로 지급정지를 걸어놓고 3영업일 신청을 안 해서 효력이 날아가는 것"입니다. **바로 그 시점에 서비스가 무력해집니다.**

### 원인은 포지셔닝 전환의 미반영입니다

기획서 v1.2는 구 명칭(골든30) 시점 문서라 **"30분 긴급 대응"** 을 전제했습니다. 한 세션에서 모든 일이 끝난다면 이전 규칙이 옳습니다.

[ADR-002](002-project-name.md)에서 포지셔닝이 **사건 관리**로 바뀌었는데 PII 규칙만 그대로 남았습니다. `spec/README.md`의 「개정해야 할 것」에 포지셔닝 전환이 **미반영**으로 이미 올라 있었고, 그 목록이 `06-screens.md`만 지목했는데 **실제로는 `04-pii-boundary.md`에도 걸려 있었습니다.**

## 결과

**얻는 것**

- 재방문이 가능해집니다. 3영업일 시점에 서류를 만들 수 있습니다.
- 서버는 여전히 원문을 못 읽습니다. 암호문만 있고 키가 없습니다.
- 세션키를 지우면 남은 암호문이 영구히 복호 불능이 됩니다.

**잃는 것**

- **주장이 한 단계 약해집니다.** "서버가 아예 모른다"에서 "서버가 암호문은 갖고 있지만 키가 없다"로 바뀝니다. 발표에서 설명이 한 겹 더 필요합니다.
- 다른 기기에서는 여전히 못 봅니다. 세션키가 그 브라우저에만 있습니다.
- 사용자가 브라우저 데이터를 지우면 매핑이 죽습니다. 이전 규칙에서는 "탭을 닫을 때"였던 것이 "브라우저를 초기화할 때"로 미뤄질 뿐입니다.

**주장 문장이 이렇게 바뀝니다.**

> 서버는 암호문만 보관하고 복호화 키를 갖지 않습니다. 키는 사용자 브라우저에만 있습니다.

## 탈락한 후보

| 후보 | 사유 |
| --- | --- |
| **현행 유지 (클라이언트 세션만)** | 개인정보 측면에서 가장 강하지만 **서비스가 3영업일 시점에 동작하지 않습니다.** 보호가 아무리 강해도 서비스가 안 되면 의미가 없습니다. 유지하려면 "몇 달 관리" 문구를 서비스 설명에서 빼야 합니다 |
| **서버 볼트 + 사용자에게 복구 키 발급** | 다른 기기에서도 볼 수 있어 가족 대응 시나리오가 해결됩니다. 버린 이유는 **패닉 상태 사용자에게 복구 코드를 맡기는 것이 현실적이지 않기** 때문입니다 — `spec/common/08-14-glossary.md`의 "사용자는 패닉 상태이고 정보를 못 주는 것이 정상"이라는 전제와 어긋납니다. 복구 코드가 유출되면 서버 볼트와 합쳐져 원문이 드러나는 새 공격면도 생깁니다. 일정도 4~5일로 부담입니다 |

## 남은 것

- **세션키 보관처.** `localStorage`인지 다른 방법인지. `sessionStorage`는 탭을 닫으면 사라져 이전 규칙과 같아지므로 안 됩니다.
- **세션키를 잃었을 때의 화면.** 매핑 없이도 기한·진행 상태는 토큰 상태로 보여줄 수 있습니다. 무엇을 보여주고 어떻게 안내할지 정해야 합니다 → `spec/frontend/08-14-screens.md`
