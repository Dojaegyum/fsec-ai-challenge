# ADR-007. 시스템 구조를 최상위 ARCHITECTURE.md에 둔다

- 상태: **채택**
- 날짜: 2026-08-16
- 결정: @Dojaegyum
- 관련: [RFC-001](../rfc/001-repo-structure.md) (규약 본문) · [ADR-003](003-spec-layout.md) (spec 폴더 구분)

## 맥락

백엔드 정의(@kth)를 앞두고 **"무엇이 어디서 어떻게 도는가"를 적을 자리가 없다**는 것이 드러났습니다.
기술 스택은 세 곳에 흩어져 있고([용어와 전제](../spec/common/08-14-glossary.md) §기술 스택,
[design-system README](../spec/frontend/design-system/README.md), `src/package.json`),
**백엔드 런타임과 DB는 어디에도 없습니다.**

기존 네 폴더 중 어디도 맞지 않았습니다.

- `spec/`은 **제품이 무엇을 만족해야 하는가**(계약)입니다. DB 선택·배포 대상은 계약이 아닙니다.
- `docs/plans/`는 **무엇을 어떤 순서로 만드는가**(일정)라 구조의 자리가 아닙니다.
- `rfc/`는 저장소 작업 규약이고, `decisions/`는 이력이라 현행 구조를 담지 않습니다.

## 결정

**최상위에 `ARCHITECTURE.md`를 둡니다.** 기술 선택·모듈 배치·저장소·데이터 흐름·외부 의존·환경·배포·관측이
여기 모입니다. 백엔드 담당이 각 절의 `TODO(kth)`를 채워 완성합니다.

**경계** — `spec/`이 *무엇을 만족해야 하는가*, `ARCHITECTURE.md`가 *무엇으로 어떻게 구현하는가*입니다.
**둘이 어긋나면 `spec/`이 이깁니다.**

## 근거

- **계약과 구현 선택은 수명이 다릅니다.** PII 경계는 바뀌면 안 되는 것이고, DB 선택은 바뀔 수 있는 것입니다.
  같은 폴더에 섞으면 "이건 바꿔도 되나"를 매번 판단해야 합니다.
- **최상위인 이유는 진입점이기 때문입니다.** 새로 합류하는 사람이 구조를 찾는 곳은 관행적으로 최상위
  `ARCHITECTURE.md`입니다. `CLAUDE.md`(에이전트 규약)·`README.md`(소개)와 같은 층에 두는 것이 맞습니다.
- **한 사람이 한 문서를 채우는 편이 낫습니다.** 구조를 spec 여러 문서에 흩어 놓으면
  백엔드 정의가 `common/`·`backend/` 양쪽을 건드리게 되고, 리뷰 지점이 흩어집니다.

### 검토한 대안

| 대안 | 사유 |
| --- | --- |
| `spec/backend/`에 아키텍처 문서 | 프론트·배포·환경까지 담게 되어 폴더 이름과 어긋납니다. spec은 "누가 지키는 계약인가"로 가르는데 구조는 그 축에 안 걸립니다 |
| `docs/`에 Markdown으로 | 구조는 **현행 정본**이라 계획·배경과 성격이 다릅니다. `docs/`에 두면 최상위에서 안 보입니다 |
| RFC로 작성 | RFC는 저장소 작업 규약입니다. 어기면 저장소가 어질러지는 것과, 어기면 제품이 안 도는 것은 다릅니다 |
| 안 만들고 spec에 흡수 | 지금 겪은 문제(백엔드 스택이 어디에도 없음)가 그대로 남습니다 |

## 결과

**얻는 것**

- 백엔드 담당이 채울 자리가 하나로 정해져, DDL·모듈 정의가 흩어지지 않습니다.
- 기술 스택이 한 곳에서 보입니다(값의 정본은 여전히 `src/package.json`).

**잃는 것 · 감수하는 것**

- **최상위 Markdown이 셋이 됩니다**(`CLAUDE.md`·`README.md`·`ARCHITECTURE.md`).
- **spec과 내용이 겹칠 위험**이 생겼습니다. 그래서 문서 머리에 "spec에 있는 것을 다시 적지 않는다"와
  우선순위를 명시했습니다. 겹치기 시작하면 재검토합니다.

## 재검토 트리거

- `ARCHITECTURE.md`가 spec 계약을 되풀이하기 시작하면 경계를 다시 봅니다.
- 문서가 길어져 절별로 갈라야 하면, 최상위 파일 대신 폴더로 승격할지 판단합니다.
