# 0006. 절차 지식을 4개 소스에서 하루 1회 수집해 조문 단위로 저장한다

- 상태: **채택**
- 날짜: 2026-08-16
- 결정: @kth9245
- 관련: [ADR-012](012-kb-collection.md) · `spec/backend/08-14-kb-operations.md` · `spec/backend/08-16-data-model.md` §12

## 결정

**소스를 넷으로 두고 하루 1회 자동 수집합니다.**

| 층 | 소스 | 방식 | 무엇을 잡나 |
| --- | --- | --- | --- |
| 1 | 국가법령정보 API | `api` | **공포된** 법령·시행령 |
| 2 | 법제처 입법예고 API | `api` | **공포 전 예고 중인** 개정 |
| 3 | 금융위 게시판 | `board` | 정책 발표·해설 |
| 4 | 기관 실무 정보 | `human` | 콜센터·창구 (자동 감시 불가) |

**법령은 조문 단위로 저장합니다.** 원문은 관계형 DB에 두고, 테이블 셋을 씁니다.

```
source_snapshot    가져온 원문 (조문 단위) + 내용 해시
source_change      변경이 감지되면 쌓이는 검수 큐
source_registry    감시 소스 목록 + 생존 확인
```

스키마는 `spec/backend/08-16-data-model.md` §12에 있습니다.

## 왜 소스가 넷인가

**법령 API만 보면 예정된 개정을 전부 놓칩니다.**

실측에서 통신사기피해환급법 이력 22건을 전부 조회했는데, **가상자산 2026년 10월 1일 개정이 그 안에 없었습니다.** 공포 전에는 법령정보센터에 안 뜨기 때문입니다.

우리가 10월 개정을 아는 이유는 **금융위 보도자료를 봤기 때문**입니다. 그런데 이 서비스에서 가장 중요한 정보가 "곧 바뀐다"입니다.

그래서 **입법예고를 별도 층으로** 추가했습니다.

## 왜 조문 단위인가

시행령 본문이 **223KB**입니다. 조문 하나가 바뀌었는데 전체를 다시 저장하면 그만큼 늘어납니다.

| 저장 단위 | 개정 1회당 | 연 4회면 |
| --- | --- | --- |
| 법령 전체 | 223KB | 약 892KB |
| **조문 단위** | **약 8KB** | **약 32KB** |

약 28배 절약됩니다. **다만 저장 절약보다 더 큰 이득이 있습니다.**

| 저장 단위 | 변경 감지 결과 |
| --- | --- |
| 법령 전체 | "시행령이 바뀌었다" — 검수자가 27개 조문을 다시 뒤져야 함 |
| **조문 단위** | **"제3조가 바뀌었다"** — 그 조문만 보면 됨 |

그리고 `kb_entry.legal_basis`가 조문을 가리키므로 **영향받는 항목을 바로 고를 수 있습니다.**

## 왜 하루 1회이고, 게시판만 다르게 다루나

**법령은 주기가 문제되지 않습니다.** 실측에서 2011년 제정부터 22건이 한 번에 다 나왔습니다. 언제 호출해도 전체를 주므로 놓칠 수 없습니다.

**게시판은 다릅니다.** 실측 결과입니다.

| 측정 | 결과 |
| --- | --- |
| 보도자료 RSS 항목 수 | 최근 **10건만** |
| 그 10건이 담는 기간 | **4일치** (하루 평균 2.5건) |
| 수집이 며칠 멈추면 | 그 사이 게시물이 RSS 에서 밀려나 **영구히 사라짐** |
| 게시글 번호로 구멍 감지 | **불가.** 번호가 게시판별 연속이 아니라 전체 공유 |

**그래서 RSS는 감지에만 쓰고 실제 수집은 목록 페이지에서 합니다.**

```
last_seen_date = 지난번 수집에서 가장 최신 게시물 날짜
page = 1
반복:
    목록 페이지(page) 읽고 새 항목 저장
    if 가장 오래된 날짜 <= last_seen_date: 중단   ← 겹쳤다
    page += 1
```

**고정 쪽수가 아니라 겹칠 때까지 읽습니다.** 수집이 한 달 멈췄다 재개돼도 그 구간이 자동 복구됩니다. 목록 페이지는 쪽당 10건이고 2쪽이면 약 2주치입니다.

## 결과

**얻는 것**

- 변경 감지가 데이터베이스 제약으로 동작합니다. `(source_key, content_hash)` 유일 제약이 걸려 있어 **같은 내용을 다시 가져오면 삽입이 실패하고, 성공하면 그게 곧 변경**입니다.
- `source_change.review_status`가 사람 승인을 강제합니다. `approved` 없이 KB에 안 들어갑니다 — `spec/backend/08-14-kb-operations.md`의 "절차 지식은 자동 반영 금지"가 칼럼으로 구현됩니다.
- 수집이 조용히 멈춘 것을 감지합니다.

**잃는 것 / 감수하는 것**

- **1순위(기관 전용) 층은 자동 감시가 불가능합니다.** 법령은 "금융회사에 요청한다"까지만 정하고, 어느 번호로 어떤 메뉴에서 하는지는 은행 재량이라 어떤 소스에도 없습니다. **「전부 감시한다」고 말할 수 없습니다.**
- 저장소가 하나 더 커집니다.

### 이 결정의 실제 성과

원문을 읽자마자 **우리 자료의 오류 하나와 미확인 항목 하나의 답**이 나왔습니다.

| | 이전 | 원문 확인 후 |
| --- | --- | --- |
| 3영업일 기산점 | 지급정지 요청 시각 | **피해구제를 신청한 날** |
| 30영업일의 정체 | 미확인 | **수사기관의 피해자·피해금 통지 기한** (2023-11-07 신설) |

**미확인 목록에 없던 항목도 틀려 있었습니다.** 「확인」 등급 표시가 1차 출처 대조를 대신하지 못한다는 사례입니다.

## 탈락한 후보

| 후보 | 사유 |
| --- | --- |
| **커버리지 요구사항 테이블** | 「있어야 할 항목」을 선언하고 빈칸을 시스템이 찾게 하는 방안. 8유형 × 필수 단계면 수십 행이라 **손으로 관리해도 되는 크기**이고, `research/05-미확인-목록.md`가 이미 그 역할을 합니다. 나중에 필요하면 기존 구조를 안 건드리고 추가할 수 있습니다 |
| **원문을 파일 + 형상 관리로** | 변경 이력이 형상 관리에 남아 사람이 보기 좋습니다. 버린 이유는 서버리스에서 저장소에 커밋하는 경로를 만들어야 하고, **검수 상태(`pending`/`approved`)를 파일로 관리하기 어렵기** 때문입니다 |
| **원문을 객체 저장소로** | 큰 본문을 DB 밖에 둡니다. 변경 빈도가 낮아(연 몇 회) 얻는 게 없고 조회만 두 번이 됩니다 |
| **은행 홈페이지 크롤링** | 기관 정보 자동화를 위해 검토. 24개 기관의 구조가 전부 달라 **3주 반에 못 만들고, 만들어도 개편되면 깨집니다.** 깨진 것을 감지하려면 또 다른 감시가 필요합니다 |

## 남은 것

- **법령 API 이용 조건.** 안내 페이지에 상업적 이용 제한 취지의 문구가 있으나 정확한 내용 미확인. 신청 시 확인 (승인 1~2일, 문의 02-2109-6446)
- **입법예고 API 실호출.** 존재는 확인했으나 인증키 신청 후 응답 형식을 봐야 합니다
- **보도자료 키워드 필터 vs LLM 판정.** 놓치는 것과 비용의 절충
- **기관 정보의 사람 확인 주기.** 자동 감시되는 층은 90일이 무의미하고, **안 되는 기관 정보만 짧아야 합니다**
- **콜센터 번호를 안내할지.** 주면 틀릴 위험, 안 주면 골든타임에 사용자가 검색해야 합니다
- **스냅샷 보관 기간.** 감사 목적이면 길어야 합니다
