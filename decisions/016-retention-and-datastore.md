# ADR-016. 사건 보관을 마지막 활동일 기준 180일로 하고, 저장소를 Supabase(서울)로 옮긴다

- 상태: **채택**
- 날짜: 2026-08-16
- 결정: @Dojaegyum
- 관련: [ADR-010](010-case-store.md) **부분 대체** · [ADR-009](009-restore-mapping-location.md) ·
  근거 자료 [docs/research/06-경로별-실측조사.md](../docs/research/06-경로별-실측조사.md)

## 맥락

[ADR-010](010-case-store.md)은 저장소를 셋으로 나누고 보관 기간을 90일로 정하면서,
그 값에 대해 **스스로 이렇게 적어 두었습니다.**

> **근거가 약한 값입니다.** … 환급이 6개월 걸리는 경우는 덮지 못합니다.
> ⬜ 실사용 데이터가 없어 확정이 아닙니다. 바꾸려면 새 ADR을 씁니다.

2026-08-16, 자금 유출 경로 10종의 절차·기한을 실측했습니다
([docs/research/06](../docs/research/06-경로별-실측조사.md)). 두 가지가 드러났습니다.

**하나. 90일은 6개월 케이스가 아니라 표준 케이스도 못 덮습니다.**

```
지급정지 D0 → 피해구제 서류 3영업일(+14일 유예)  ≈ D+20
   → 금융회사의 공고 요청 '지체 없이'(실무 수일)   ≈ D+25
   → 채권소멸절차 개시 공고 2개월                  ≈ D+86
   → 채권 소멸 → 환급금 결정 14일                  ≈ D+100
```

공고 2개월(법 제9조제1항) 하나만으로 D+86이고, 환급금 결정 14일이 그 뒤에 붙습니다.
**90일이면 환급금이 결정되기 직전에 사건이 파기됩니다.** 여기에 명의인이 이의를 제기하면
피해자가 통보받은 날부터 2개월이 통째로 얹혀(법 제8조제2항제2호) **≈D+160**이 됩니다.

**둘. `Vercel Postgres`는 더 이상 존재하지 않는 제품입니다.**

2024년 12월 폐지됐고 기존 DB는 Neon으로 자동 이관됐습니다(Vercel 공식 문서).
지금 그 이름을 고르면 실제로 쓰는 것은 **Neon**인데, **Neon에는 서울 리전이 없습니다** —
AWS 8개 리전뿐이고 도쿄도 없어 가장 가까운 곳이 싱가포르입니다.

## 결정

### 하나 — 보관 기간은 **마지막 활동일 기준 180일**입니다

`CASE_PURGE_DAYS` 기본값을 **180**으로 올리고, `case.purge_after`를 **사건 생성 시 한 번 박는 값이 아니라
활동이 있을 때마다 미는 값**으로 바꿉니다.

| | 이전 (ADR-010) | 이 결정 |
| --- | --- | --- |
| 기간 | 90일 | **180일** |
| 기산 | 사건 생성일 | **마지막 활동일** (롤링) |

### 둘 — 관계형 DB와 객체 저장소를 **Supabase**로 옮깁니다

| 저장소 | 담는 것 | 이전 | 이 결정 |
| --- | --- | --- | --- |
| 관계형 DB | 사건 상태 | Vercel Postgres | **Supabase Postgres** (`ap-northeast-2` 서울) |
| 객체 저장소 | 업로드 원본 | Vercel Blob | **Supabase Storage** |
| 볼트 | 복원 매핑 암호문 | Vercel KV | **미결** — 아래 「남은 것」 |

**요금제는 Pro($25/월)입니다.** Free는 1주 미사용 시 프로젝트가 정지되고 파일 상한이 50MB입니다 —
심사위원이 며칠 뒤 접속하는 시점에 정지돼 있으면 그대로 실격 사유이고, 피해자 녹음은 50MB를 쉽게 넘습니다.

### ADR-010에서 그대로 살아 있는 것

- **저장소를 셋으로 나누는 구조** — 사건 상태 / 볼트 / 원본을 분리한다는 판단.
- **볼트를 관계형 DB와 다른 인스턴스에 둔다** — 한 번의 유출로 암호문과 사건 구조가 함께 나가지 않게.
- **세 층이 같은 날 함께 파기된다** — 층마다 수명을 다르게 두면 어느 한 층만 남은 상태를 추적할 수 없습니다.
- 관계형 DB를 쓰는 이유 셋(완수 검증·감사 로그·기한 재현).

## 근거

### 왜 180일인가

**"기능이 안정적으로 구동될 수 있는 최소 기간"을 경로별 최장 기간에서 역산한 값입니다.**

| 경로 | 최장(일) |
| --- | ---: |
| 은행 계좌이체 · 가상자산 | **180** |
| 간편송금 · 휴대폰 소액결제 | 150 |
| 인터넷은행 · 증권 | 120 |
| 대면편취 · 상품권 | **상한 없음** (검거·형사절차 대기) |

카드·명의도용의 1,095일(비대면 금융사고 책임분담 신청 3년)은 **사건이 굴러가는 기간이 아니라
나중에 신청할 수 있는 창**입니다. 3년간 관리할 마감이 매일 있는 것이 아니므로 사건을 3년 살려두는 방식이 아니라
**"3년 안에 신청할 수 있다"는 사실과 서류 목록을 리포트로 내려주는 방식**으로 해결합니다
([PII 경계](../spec/common/08-14-pii-boundary.md) 불변규칙 4가 이미 허용한 경로).
같은 논리로 상한이 없는 두 경로도 사건 보존으로 감당하지 않습니다.

### 왜 마지막 활동일 기준인가

**숫자보다 이쪽이 중요합니다.**

1. **진입 시점이 사건 발생일이 아닙니다.** 법 제6조제1항은 공고 후에 피해를 알게 된 사람도
   공고일부터 2개월 안에 신청할 수 있게 합니다 — 이 사람은 **들어올 때 이미 두 달이 지나 있습니다.**
   생성일 고정이면 며칠 만에 사건이 만료되는 사고가 납니다.
2. **상한이 사라지는 상태 전이가 모든 경로에 있습니다** (명의인 이의제기, 소송 이행).
   롤링이면 사용자가 살아 있는 한 사건도 살아 있습니다.
3. **아무도 돌아오지 않는 사건은 180일 뒤 조용히 사라집니다** — 보관 최소화가 자동으로 달성됩니다.

### 왜 Supabase인가

**리전이 결정적이었습니다.** 금융보안원 주최 대회 출품작이 피해자 진술을 싱가포르에 두고
심사에서 설명하는 그림은 스스로 약점을 만듭니다. Supabase는 `ap-northeast-2`를 명시 제공합니다.

그다음은 **조각 수**입니다. 우리가 필요한 것은 Postgres + 파일 저장 + 시간 기반 자동 파기 +
벡터 검색 + 행 단위 접근 제어인데, Supabase는 이것을 한 벌로 줍니다(Storage · pg_cron · pgvector · RLS).
특히 **파일 저장과 접근 제어를 같은 정책 언어로 거는 곳은 Supabase뿐**입니다.

`spec/common/08-14-glossary.md` §9가 배포를 Vercel로 정한 것은 그대로입니다 — **앱은 Vercel, 데이터는 Supabase**입니다.
ADR-010이 "같은 곳으로 맞추면 별도 설정이 필요 없다"고 한 이유는 유효하지만, 그 대가가 리전이라면 너무 큽니다.

### 탈락한 후보

| 후보 | 사유 |
| --- | --- |
| **Neon** (Vercel Postgres의 실질적 후신) | **서울·도쿄 리전 없음.** 파일 저장 없음. pg_cron이 "컴퓨트 활성 시에만 실행"이라 자동 파기를 얹으면 비용 이점이 사라짐 |
| **AWS RDS/Aurora** | 서울 리전과 컴플라이언스 표면은 최상이지만 VPC·접속·백업을 직접 운영해야 함. 소수 인원·짧은 일정에 몇 주를 씀. 파일·인증·접근제어 계층이 통째로 우리 몫 |
| **PlanetScale** | 서울이 GCP 쪽에만 있고, 파일 저장·pgvector·RLS를 한 제품으로 못 받음 |
| **Firebase** | 서울 리전과 벡터 검색은 있으나 **문서 DB라 관계형 도메인 모델과 기한 계산을 다시 설계**해야 함. `spec/backend/08-16-data-model.md`를 버리게 됨 |

## 결과

**얻는 것**

- 표준 트랙(D+100)과 이의제기 케이스(D+160)를 **둘 다 덮습니다.**
- 늦게 진입한 피해자의 사건이 며칠 만에 만료되지 않습니다.
- 데이터가 **서울에** 있고, 심사에서 그렇게 설명할 수 있습니다.

**잃는 것 · 감수하는 것**

- **개인정보를 두 배 오래 들고 있습니다.** 보관 최소화 원칙과 맞바꾼 것이 기능 성립입니다.
  롤링이므로 활동이 없으면 만료된다는 점이 완화 장치입니다.
- **Supabase Storage에 네이티브 만료가 없습니다.** 파일 파기는 `pg_cron` 잡이 Storage API를 호출하도록
  **직접 구현하고 실제로 지워지는지 검증**해야 합니다. 플랫폼이 해준다고 전제하면 안 됩니다.
- **서울 리전 ≠ 국내 사업자입니다.** 해외 법인이 AWS 서울을 쓰는 구조라 국외이전 논점이 완전히 사라지지 않습니다.
  발표에서 **"리전은 서울, 사업자는 해외"**라고 정확히 말해야 하고, "국내 저장이라 문제없다"고 말하면 안 됩니다.
- **RLS 설계 실수가 최대 위험입니다.** 세션이 없으면 `auth.uid()`가 null이 되어 정책이 조용히 통과/실패합니다.
  잘못 걸면 **다른 피해자의 사건이 노출됩니다** — 스키마 확정 전에 RLS 정책 테스트를 먼저 씁니다.
- 컴플라이언스 문서(SOC 2·ISO) **실물 열람은 Team 플랜 이상**입니다. Pro에서는 보유 사실까지만 인용할 수 있습니다.
- Postgres 자체는 이식 가능하지만 **RLS·Storage 정책·Auth는 Supabase 형태**라 락인이 그 위층에 걸립니다.
