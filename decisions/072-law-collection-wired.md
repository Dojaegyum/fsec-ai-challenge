# ADR-072. 법령 수집을 국가법령정보 API 조문 단위로 매일 돌리고, 검수는 명령줄로 한다

## 맥락

절차 지식을 KB 로 뺀 것([불변 규칙 1](../CLAUDE.md))의 나머지 절반은 **그 KB 가 낡는 것을 누가 알아채는가**입니다.
[ADR-012](012-kb-collection.md)가 답을 그려 두었고 — 원문을 보존하고 바뀐 것을 검수 큐에 쌓는다 —
`kb-collector`·`kb-reviewer` 두 모듈이 2026-08 에 만들어졌습니다. 그런데 **넷이 없었습니다.**

| 없던 것 | 그래서 |
| --- | --- |
| 표 셋의 마이그레이션 (`source_snapshot`·`source_change`·`source_registry`) | 모듈이 붙을 자리가 없었습니다 |
| 수집원 | `kb-collector/types.ts` 가 *"국가법령정보 API 는 OC 키 승인 대기 중"* 이라고 적어 둔 채였습니다 |
| 부르는 크론 | `KB_FETCH_CRON` 환경변수 이름만 있었습니다 |
| 검수 자리 | 관리자 화면을 만들지 않기로 했고([ADR-068](068-no-admin-screen.md)), 대신할 것이 없었습니다 |

2026-09-06 에 사용자가 업스테이지 해커톤 때 승인받은 국가법령정보 Open API 사용자 ID 를 냈고, `lawSearch`·`lawService`
둘 다 200 을 돌려주는 것을 확인했습니다 — 통신사기피해환급법 본문 103KB 가 조문 31개로 왔습니다. 막고 있던 것이 풀렸습니다.

## 결정

### ① 수집원은 국가법령정보 API 하나, 조문 단위

`lib/law-fetcher.ts` 가 `law:{법령ID}` 소스를 `lawService.do?target=law&ID=…&type=JSON` 으로 받아 **조문마다 하나씩**
냅니다 — `source_key` 는 §12.1 그대로 `law:법령ID:조문번호[:가지번호]`, 원문은 조문 → 항 → 호 → 목 순서로 펼친 글
그대로, `meta` 에 법령명·조문제목·시행일·공포번호. 법령 전체를 한 행에 넣으면 「시행령이 바뀌었다」까지만 알고,
조문 단위면 「제10조가 바뀌었다」를 압니다 — `kb_entry.legal_basis` 가 조문을 가리킵니다.

**JSON 이 아니면 던집니다.** 승인 안 된 ID 에는 API 가 안내 HTML 을 주는데, 그것을 조문으로 저장하면 검수 큐가
쓰레기로 찹니다. 던지면 `kb-collector` 가 그 소스의 `last_error` 에 남기고 다음 소스로 갑니다. 앱은 영향이 없습니다.

감시 소스는 둘 — KB 32 항목이 인용하는 **법(011359)과 시행령(011448)**. 마이그레이션 0010 이 `source_registry` 에
심습니다. 금융위 게시판·입법예고(§12.4 의 나머지)는 이 결정에 없습니다 — 수집원이 하나 더 생기면 같은 인터페이스에 붙입니다.

### ② 사용자 ID 는 환경변수 `LAW_API_OC`

비밀값은 아니지만(공개 API 의 식별자) 사람마다 다른 값이라 코드에 두지 않습니다. 없으면 수집 크론이 소스마다
「없다」로 남기고 지나갑니다 — 조용히 빈 결과를 내지 않습니다. 배포 값은 `vercel-env` 워크플로의 `law_api_oc` 로 넣습니다.

### ③ 크론은 하루 1회 `GET /api/cron/kb-collect`

`vercel.json` 에 UTC 19:00(KST 04:00) — 알림(09:00)·파기(03:00)와 겹치지 않는 시각입니다(§6.4). 응답은 소스별
건수뿐입니다. 손으로는 `npm run kb:collect`.

### ④ 검수는 명령줄 — `npm run kb:review`

관리자 화면을 만들지 않기로 했으므로 검수의 자리는 명령입니다. 큐를 원문 앞부분과 함께 보여주고,
`--approve|--reject|--defer <change_id> --by <이름>` 으로 판단을 적고, 릴리스 뒤 `--released <change_id> --version …` 으로
어느 버전에 실렸는지 남깁니다. **승인이 곧 반영이 아닙니다** — 반영은 사람이 `src/kb/*.json` 을 고쳐 `kb:load` 로
릴리스하는 별도 단계입니다(RFC-002 네 구간). 포트 목록에 `kb_entry` 를 건드리는 자리가 없는 것은 그대로입니다.

### ⑤ 최초 수집은 전부 「최초 수집」으로 큐에 오른다

첫 회차는 모든 조문이 새 원문이라 `snapshot_before = NULL` 인 변경으로 쌓입니다(§12.2). 그것을 자동으로 승인하지
않습니다 — 기준선을 사람이 한 번 보는 것이 검수의 시작입니다. 큐가 그 상태라는 것을 명령이 「최초 수집」이라고 표시합니다.

## 근거

**바뀌는 것을 알아채는 장치가 없으면 KB 는 낡습니다.** 이 서비스의 근거는 시행일이 붙은 조문이고, 가상자산 환급처럼
시행을 앞둔 개정이 있습니다. 어제 받은 본문만 봐도 2026-08-04 시행 개정으로 「사기관련의심계좌」 정의(제2조제8호)와
제13조의4 가 새로 들어와 있었습니다 — 사람이 매일 법령 사이트를 열어 보는 것은 지속되지 않습니다.

**모듈은 이미 옳게 그려져 있었습니다.** 변경 감지에 비교 로직을 두지 않고 유일성 제약 하나로 판정하는 것, 승인이
반영이 아닌 것 — 새로 정한 것이 아니라 붙이기만 했습니다. 이 ADR 이 정한 것은 수집원·환경변수·크론 시각·검수 자리 넷입니다.

### 검토한 대안

| 대안 | 왜 아닌가 |
| --- | --- |
| **법령 전체를 한 행으로** | 「어느 조가 바뀌었나」를 잃습니다. §12.1 이 이미 조문 단위로 정했고, 저장도 28배 적습니다 |
| **바뀐 조문을 LLM 이 KB 에 자동 반영** | 원칙 4 위반. 절차 지식을 모델이 쓰게 되고, 틀리면 피해자의 금전 손실입니다 |
| **검수 화면을 만든다** | ADR-068 로 관리자 화면을 안 만들기로 했습니다. 큐를 보는 사람은 팀이고, 명령줄로 충분합니다 |
| **최초 수집분을 자동 승인** | 기준선을 아무도 안 본 채 「검수됨」이 됩니다 |
