# ADR-051. 읽기 접수는 멱등하고, 재시도는 막지 않는다

- 상태: **채택**
- 날짜: 2026-08-24
- 결정: @Dojaegyum
- 관련 문서: [API 계약](../spec/common/08-14-api.md) §3.2 3단계 · §3.3 (폴링) · §1.3 (속도 제한) ·
  [에러 계약](../spec/backend/08-16-errors.md) §2 (`retryable`) ·
  [ADR-028](028-runtime-and-module-shape.md) (모델은 앱 밖) ·
  [ADR-043](043-gpu-hosting.md) (그 모델을 돌리는 값)

## 맥락

`POST /api/cases/{case_token}/evidence/{evidence_id}/complete` 는 **다시 불릴 수
있는 자리**입니다. 네트워크가 흔들리면 브라우저가 다시 보내고, 사용자가 다시
누를 수도 있으며, §1.3 표에 이 자리가 없어 창 상한도 걸려 있지 않습니다.

그 라우트는 이미 「두 번 와도 됩니다」라고 적어 두고 있었는데, **절반만
참이었습니다.**

| | 두 번 불렀을 때 | |
| --- | --- | --- |
| 사건 행 | `markUploaded` 가 `pending` 일 때만 옮깁니다 | 멱등 ✅ |
| 모델 실행 | 부를 때마다 다시 돕니다 | **멱등 아님** ❌ |

전사 서비스의 작업 저장소는 원래 멱등하게 설계돼 있었습니다 — 「같은 번호로
다시 열면 앞의 작업을 그대로 돌려준다」. 실제로 그렇게 돌려줍니다.
**그런데 그 결과를 부르는 쪽이 안 봤습니다.**

```python
job = jobs.create(req.kind, req.job_id)   # 기존 작업을 돌려받아도
tasks.add_task(_run, job.job_id, req)     # 「돌리기」는 무조건 걸립니다
```

돌리는 자리에도 「이미 돌고 있으면 그만두기」가 없어, **N 번 부르면 같은 파일을
N 번 내려받아 모델을 N 번 돌립니다.** 진행률이 서로 덮어써 화면의 폴링이 뒤로
가고, [실측](../docs/research/09-로컬모델-PII인식-실측.md)이 한 사건 48분인
작업이라 비용이 그대로 배수로 붙습니다.

## 결정

**접수는 멱등하고, 재시도는 막지 않습니다.** 둘은 다른 물음입니다.

| 물음 | 답하는 곳 |
| --- | --- |
| **다시 할 것인가** | 앱 — `retry-checker` 가 [에러 계약](../spec/backend/08-16-errors.md) §2 의 `retryable` 을 보고 정합니다 |
| **중복으로 돌 것인가** | 전사 서비스 — 접수 자리가 막습니다 |

### 판정은 잠금 안에서 합니다

작업을 여는 자리가 **「이번에 실제로 열렸는가」를 함께 돌려주고**, 열렸을 때만
돌립니다.

**밖에서 먼저 조회해 보는 방식으로는 못 막습니다** — 두 요청이 나란히 「없다」를
보고 둘 다 돌립니다. 여는 것과 판정이 같은 잠금 안에 있어야 합니다.

### 상태별로 이렇게 갈립니다

| 지금 상태 | 다시 접수하면 |
| --- | --- |
| 돌고 있음 | **안 돌립니다.** 진행률을 그대로 두고 폴링이 이어집니다 |
| 끝났음 | **안 돌립니다.** 결과가 이미 있습니다 |
| **실패했음** | **다시 돌립니다.** 상태를 되돌리고 새로 시작합니다 |

**실패한 것을 다시 여는 것이 이 결정의 핵심 절반입니다.** 사용자가 「끝까지
완수하기로 한 일」은 실패했다고 거기서 끝나면 안 됩니다. 안 열어 주면 실패한
증거는 작업 기록이 청소될 때까지 영영 다시 읽을 수 없고, 사용자는 같은 파일을
다시 올려야 합니다 — 그 자체가 §3.2 의 상한(사건당 30개·300MB)을 태웁니다.

### 그래서 이 경로에 창 상한을 걸지 않습니다

**상한은 중복 실행을 막지 못합니다** — 분당 10회를 걸어도 창 안에서 10번 돕니다.
반대로 상한은 **재시도를 막습니다.** 급한 사용자가 다시 눌렀을 때 429 를 주면,
막히는 것은 공격이 아니라 피해자입니다.

중복은 멱등으로 막았으므로 이 자리는 `rate: 'none'` 으로 **일부러 안 겁니다.**
빠뜨린 것과 구분되게 표기는 남깁니다.

## 검토한 대안

| 안 | 왜 안 골랐나 |
| --- | --- |
| 창 상한으로 막는다 | 중복을 못 막고 재시도만 막습니다. 위 |
| 앱이 먼저 상태를 보고 안 부른다 | 앱과 서비스 사이에 경합이 그대로 남습니다. 앱 인스턴스가 둘이면 둘 다 「아직 안 돌고 있다」를 봅니다 |
| 돌리는 자리에서 파일 잠금으로 막는다 | 그때는 이미 파일을 내려받은 뒤입니다. 아낄 것을 이미 씁니다 |
| 실패한 것도 다시 안 연다 | 사용자가 파일을 다시 올려야 하고, 그게 증거 상한을 태웁니다 |

## 결과

**좋아지는 것**

- 다시 불러도 안전합니다 — 「두 번 와도 됩니다」가 끝까지 참이 됩니다
- 재시도가 막히지 않습니다. 실패한 증거를 사용자가 다시 시도할 수 있습니다
- 이 경로에 상한을 안 걸어도 됩니다

**감수하는 것**

- **작업 기록이 메모리에만 있습니다.** 서비스가 다시 뜨면 사라지고, 그때는
  같은 번호로 와도 새로 돌립니다. 사건 상태가 정본이라 다시 접수시키면 되는
  구조라 지금은 감수합니다 — 오래 걸리는 작업이 잦아지면 다시 봅니다.
- 여는 자리가 `(작업, 열렸는가)` 를 돌려주게 되어 **부르는 쪽이 두 번째 값을
  반드시 봐야 합니다.** 안 보면 조용히 예전 모양으로 돌아갑니다. 그래서 시험이
  이것을 지킵니다(동시 요청 여덟에 하나만 열리는지).

## 남은 것

- **작업 기록의 영속화** — 위 감수 항목. 서비스 재기동이 잦아지면 필요합니다
- **`retry-checker` 와의 대조** — 앱이 어떤 오류에서 다시 부르는지와 여기서
  다시 여는 조건이 어긋나지 않는지. 지금은 「실패면 연다」로 넓게 잡아 두었습니다
