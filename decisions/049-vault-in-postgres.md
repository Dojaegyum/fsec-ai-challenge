# ADR-049. 볼트를 같은 Postgres 안 별도 스키마에 둔다

- 상태: **채택**
- 날짜: 2026-08-24
- 결정: @Dojaegyum
- 대체하는 것:
  [ADR-010](010-case-store.md) 「볼트를 관계형 DB와 다른 인스턴스에 둡니다」·「Vercel KV」 ·
  [ADR-016](016-retention-and-datastore.md) 「남은 것」의 **볼트 제품 미결**
- 관련 문서: [API 계약](../spec/common/08-14-api.md) §3.11 (이 결정으로 개정됨) ·
  [데이터 모델](../spec/backend/08-16-data-model.md) §3 ·
  [ADR-009](009-restore-mapping-location.md) (매핑은 암호문으로 서버에) ·
  [ADR-027](027-session-key-storage.md) (키는 브라우저 IndexedDB 에 `extractable: false`)

## 맥락

[ADR-016](016-retention-and-datastore.md)이 **볼트 제품을 미결로 남기며** 이렇게 적었습니다.

> Vercel KV를 계속 쓸지 Supabase 별도 프로젝트로 갈지는 **리전 확인 후** 정합니다.
> TODO(근거 필요): Vercel KV(Upstash)의 서울 리전 제공 여부.

그 확인을 했고, 확인하는 김에 **원칙 자체를 다시 봤습니다.** 셋이 나왔습니다.

### ① Upstash 에 서울 리전이 없습니다

공식 문서의 리전 목록에 `ap-northeast-2` 가 없습니다. 아시아 최근접은 도쿄(`ap-northeast-1`)입니다.

### ② 분리 원칙이 막으려던 사고가 이 구조에서는 일어나지 않습니다

[ADR-010](010-case-store.md)의 근거는 이것이었습니다.

> 볼트를 관계형 DB와 다른 인스턴스에 둡니다. 같은 곳에 두면
> **한 번의 유출로 암호문과 사건 구조가 함께 나갑니다.**

그런데 **함께 나가도 열리지 않습니다.** 이후에 정해진 둘 때문입니다.

| | |
| --- | --- |
| [ADR-009](009-restore-mapping-location.md) | 볼트에 들어가는 것은 **AES-GCM 암호문**뿐 |
| [ADR-027](027-session-key-storage.md) | 복호화 키는 **브라우저 IndexedDB 에 `extractable: false`** 로 |

[데이터 모델](../spec/backend/08-16-data-model.md) §3 이 이미 같은 말을 다른 각도로 적어 뒀습니다 —
`case.session_key_id` 는 **키 식별자만** 저장하고, 그 이유가
*"세션키가 DB에 있으면 DB 유출 시 볼트가 함께 뚫려 저장소를 분리한 의미가 없어집니다"* 입니다.

**뒤집어 읽으면 결론이 나옵니다.** 키가 DB 에 없으므로, 볼트가 같은 DB 에 있어도
**DB 유출로는 안 뚫립니다.** 분리로 얻는 것이 ADR-010 을 쓸 때 예상한 것보다 작습니다.

### ③ `VAULT_MASTER_KEY` 를 쓰는 코드가 없습니다

`lib/env.ts`·`lib/config-report.ts`·`lib/container.ts` 의 **배관에만** 있고
실제 봉하기는 전부 `key-handler` 가 브라우저에서 합니다.
그래서 `.env.example` 의 이 문장은 **사실이 아니었습니다** —

> `VAULT_MASTER_KEY` 가 노출되면 볼트 암호문이 전부 풀립니다.

**서버 키로는 아무것도 못 엽니다.** 서버가 암호화하던 옛 설계의 잔재입니다.

## 결정

**볼트를 사건 DB 와 같은 Postgres 인스턴스의 `case_vault` 스키마에 둡니다.**

```
서울 Supabase Postgres
 ├ public 스키마   사건 · 증거 · 감사 · 플랜 · 기한
 └ case_vault      복원 매핑 (AES-GCM 암호문)
서울 Supabase Storage   업로드 원본
```

- 키는 `(case_id, token)` 이고 **덮어씁니다** — 같은 값에는 같은 토큰이 붙으므로
  덮어쓰기로 충분합니다 ([API](../spec/common/08-14-api.md) §3.11).
- `token` 은 평문입니다. `[계좌-1]` 자체는 개인정보가 아니고 조회 키로 써야 합니다.
- **새 인프라도 새 비밀값도 없습니다.** `postgres` 드라이버와 기존 접속 정보를 그대로 씁니다.

### 함께 정하는 것

| 무엇 | 어떻게 |
| --- | --- |
| `KV_URL` · `VAULT_MASTER_KEY` | **지웁니다.** 쓰는 코드가 없고, 남겨 두면 「채워야 하는 값」으로 오해됩니다 |
| 세션키 | **여전히 DB 에 넣지 않습니다.** `case.session_key_id` 는 식별자만 — 이 결정이 그 규칙을 **더 중요하게** 만듭니다 |
| 스키마 분리 | 표를 `public` 에 섞지 않고 **`case_vault`** 에 둡니다. **`vault` 는 못 씁니다** — Supabase 가 `supabase_vault` 확장을 그 이름으로 이미 깔아 두고 관리합니다(붙여서 실측 확인) |

## 잃는 것 — 정직하게

**만료(TTL)를 기본으로 못 받습니다.** [ADR-010](010-case-store.md)이 Vercel KV 를 고른 이유가
바로 그것이었고, 그때 이렇게 경고했습니다.

> 관계형 DB에서 만료를 흉내내려면 배치가 필요하고,
> **그 배치가 멈춘 것을 아무도 모르는 상태**가 생깁니다.

**이 위험은 실재하고, 이 결정으로 사라지지 않습니다.** 다만 둘로 완화됩니다.

1. **어차피 배치가 필요했습니다.** [ADR-016](016-retention-and-datastore.md)이
   *"Supabase Storage에 네이티브 만료가 없습니다 … 직접 구현하고 실제로 지워지는지
   검증해야 합니다"* 라고 이미 감수했습니다. 볼트에 TTL 이 있어도 **파기 배치는 남습니다.**
2. **같은 DB 라 파기가 한 트랜잭션에 들어갑니다.** 나뉘어 있으면 「사건은 지웠는데 볼트가
   남는」 상태가 생기고, 그걸 `case-purger` 의 `remains()` 가 사후에 잡아야 합니다.
   같은 곳이면 그 상태가 **애초에 안 생깁니다.**

**그래도 배치가 멈춘 것을 알아채는 장치는 따로 필요합니다** — 아래 「남은 것」.

## 왜 다른 길을 안 갔나

| 안 | 왜 아닌가 |
| --- | --- |
| **Upstash Redis (도쿄)** | 얻는 것이 TTL 하나인데, 잃는 것이 「데이터는 서울에 있습니다」라는 발표 문장입니다. 새 벤더·새 비밀값·새 클라이언트도 따라옵니다 |
| **Supabase 별도 프로젝트 (서울)** | 원칙에는 가장 충실합니다. 버린 이유는 **얻는 격리가 위 ②대로 실효가 없는데** 무료 활성 프로젝트 한도 2개를 꽉 채우고(1주일 무호출 시 일시정지), 접속 정보와 파기 경로가 둘로 늘기 때문입니다 |
| **`public` 스키마에 표 하나 더** | 가장 싸지만 **「무엇이 볼트인가」가 이름에서 사라집니다.** 스키마를 가르는 비용은 거의 0 입니다 |

## 결과

- [API 계약](../spec/common/08-14-api.md) §3.11 의 **「저장 위치는 볼트입니다 — 관계형 DB 가
  아닙니다 … DDL 이 바뀌지 않습니다」가 이 결정으로 대체됩니다.** DDL 이 바뀝니다.
- [데이터 모델](../spec/backend/08-16-data-model.md)의 저장소 표에서 볼트 칸이
  「Vercel KV」에서 「같은 Postgres · `case_vault` 스키마」로 바뀝니다.
- 환경변수 둘이 사라집니다.
- `case-purger` 의 `VaultStore`(`delete`·`remains`)는 **그대로**입니다 — 인터페이스는
  안 바뀌고 구현만 붙습니다. **거기에 쓰기(`put`)를 더하지 마세요**: 매핑을 맡는 포트는
  쓰는 쪽이 자기 것으로 선언합니다 (`case-purger/types.ts` 의 경고 그대로).

## 남은 것

- **파기 배치가 멈춘 것을 알아채는 장치.** 지금은 없습니다. 마지막 파기 실행 시각을
  설정 현황(`lib/config-report.ts`)이나 감사 기록으로 드러내는 것이 가장 싼 길로 보이지만,
  **이 ADR 에서 정하지 않습니다** — 파기 실행 방식 자체가 아직
  [ADR-016](016-retention-and-datastore.md) 「남은 것」입니다.
- **RLS 정책.** ADR-016 이 *"RLS 설계 실수가 최대 위험"*이라고 적었습니다.
  `case_vault` 스키마도 같은 검토를 받아야 하고, **서비스 역할 키로만 닿게** 두는 것이 기본입니다.

## 재검토 트리거

- **세션키를 서버가 알게 되는 변경이 생기면 이 결정이 무너집니다.** 그때는 분리가
  다시 실효를 갖습니다 — ②의 논거가 통째로 사라지기 때문입니다.
- 볼트 크기가 커져 사건 DB 의 성능에 영향을 주면 다시 봅니다.
- 국내 사업자 요건이 확정돼 저장소를 통째로 옮겨야 하면 함께 판단합니다.
