# ADR-024. 절차 단계에 「무슨 행동인가」를 담고, 주소를 본문에 쓰지 않는다

- 상태: **채택**
- 날짜: 2026-08-18
- 결정: @Dojaegyum (서브 BE)
- 관련: [ADR-012](012-kb-collection.md) · [ADR-023](023-frontend-module-names.md) ·
  [데이터 모델](../spec/backend/08-16-data-model.md) §11.4.6 §11.4.7 ·
  [API 계약](../spec/common/08-14-api.md) §3.6 ·
  [워크스페이스 패널](../spec/frontend/08-17-workspace-panels.md)

## 맥락

[워크스페이스 패널](../spec/frontend/08-17-workspace-panels.md)이 단계마다 **다른 모양**을 그립니다 —
전화를 걸거나, 밖에 나갔다 오거나, 받아적거나, 파일을 올리거나, 서류를 내려받거나, 그냥 기다립니다.
**한 모양으로 렌더하면 전부 「읽고 체크하는 목록」이 되고**,
[완수 검증](../spec/backend/08-14-completion-hook.md)이 막으려던 *"체크는 됐는데 행위는 안 된 상태"*로 돌아갑니다.

그런데 **화면이 어느 모양을 그릴지 알 방법이 계약에 없었습니다.**

초안은 프론트가 `actor`·`body.channel`·`required_artifact` **세 필드를 조합해 추론**하는 것이었습니다.
일곱 중 다섯은 실제로 갈렸지만 둘이 안 갈렸고, 무엇보다 **근거가 세 곳에 흩어져 있어**
절차가 늘면 새 유형이 조용히 `read`로 떨어집니다.

두 번째 문제는 **밖으로 내보낼 주소**입니다. 2026년 7월부터 피해구제 신청이 **은행 앱 비대면**이라
사용자를 내보내야 하는데, `steps[]`에 주소를 담을 자리가 없었습니다.

## 결정

### 하나 — `kb_entry.body.steps[]`에 `action`을 둡니다

**값 일곱.** `call` · `visit` · `write` · `upload` · `download` · `wait` · `read`
→ [데이터 모델](../spec/backend/08-16-data-model.md) §11.4.6.

**KB 항목마다 사람이 적고, 비면 릴리스가 거부됩니다.** 유형도 절차의 일부이므로
`CLAUDE.md` 불변 규칙 1(LLM은 절차를 창작하지 않는다)이 그대로 적용됩니다 — **모델이 정하지 않습니다.**

**`action`과 `channel`은 다른 축입니다.**

| | 뜻 | 개수 |
| --- | --- | --- |
| `action` | **무슨 행동인가** | 하나 |
| `channel` | **어느 창구로** (`app`·`phone`·`visit`·`web`) | 복수 가능 |

`["phone", "app"]`은 전화로도 앱으로도 된다는 뜻이고, 그때도 행동은 하나입니다.
**`action`이 `call`·`visit`이 아니면 `channel`은 빈 배열입니다** — 적재 검증이 봅니다.

### 둘 — 주소를 본문에 직접 쓰지 않습니다

§11.4.1이 **전화번호**에 건 규칙을 **주소**에 그대로 적용합니다 → §11.4.7.

| 주소의 성격 | 어디에 |
| --- | --- |
| **기관별** (국민은행 앱 신청 경로) | `contact_ref` → `org.contact` |
| **기관 무관** (정부24 · 어카운트인포 · 엠세이퍼) | `steps[].url` · `url_label` |

**`steps[].text`에 `http`로 시작하는 문자열이 있으면 적재를 거부합니다.**

### 셋 — 클라이언트는 추론하지 않습니다

`GET /plan`이 `body.action`을 그대로 내려주고, `work-handler`는 그 값으로 패널을 고릅니다
→ [API 계약](../spec/common/08-14-api.md) §3.6.

## 근거

### 왜 새 컬럼이 아니라 JSONB 키인가

`kb_entry.body`와 `plan_step.body`가 **이미 JSONB입니다.** 마이그레이션 없이 키만 늘면 됩니다.
그리고 `action`은 **조회 조건이 아니라 표시용**이라 인덱스가 필요 없습니다 —
조회 축은 `track`·`channel_id`·`org_id`·시행일 넷이고 그건 칼럼으로 이미 있습니다.

### 왜 `channel` 값을 늘려서 대신하지 않았나

가장 싼 안이었고, **`web`이 이미 값에 있어** 절반은 되는 것처럼 보였습니다.
**`visit`이 걸렸습니다** — 지금 「영업점 방문」 뜻으로 쓰이고 있는데,
워크스페이스의 `WS-visit`은 「외부 사이트·앱으로 나갔다 오기」입니다.

한 값이 두 뜻이 되는 것을 [ADR-014](014-module-names.md)가 `orchestrator`에서 이미 거부했고,
[ADR-023](023-frontend-module-names.md)이 `key`에서 다시 거부했습니다. **세 번째로 같은 판단을 합니다.**

그리고 축이 실제로 둘입니다 — 창구는 복수일 수 있고 행동은 하나입니다.
한 필드에 섞으면 `["phone", "app"]`을 어떻게 읽어야 할지가 사라집니다.

### 왜 프론트 파생을 버렸나

**되돌리는 비용이 시간에 비례해 커지기 때문입니다.** 지금은 KB가 비어 있어 `action`을
채우는 비용이 0에 가깝지만, 100건을 쓴 뒤에 바꾸면 **전부 다시 훑어야 합니다.**

파생 안의 실질 문제는 정확도가 아니라 **침묵**입니다. 새 절차 유형이 들어오면
세 필드 조합이 아무것에도 안 맞아 기본값 `read`로 떨어지는데, **아무도 그걸 모릅니다.**
`action`이 필수면 적재 시점에 걸립니다.

### 왜 genlab 매뉴얼 구조로 갈아타지 않았나

`action` 자체가 genlab CS 매뉴얼의 `action.pattern`(정보제공·정보확인·행위요청·담당자연결·함수호출)에서
온 발상입니다. 그래서 **구조를 통째로 도입하는 안**을 검토했습니다.

**우리 `kb_entry.body`가 이 도메인에 이미 더 맞습니다.** genlab에 없는 것이 셋입니다.

| | genlab | 우리 |
| --- | --- | --- |
| **시행일** | 없음 | `effective_from`·`effective_until` — `CH-crypto` 10월 시행이 이것으로 갈림 |
| **법정 기한** | 없음 | `deadline.owner`·`grace` — 3영업일과 14일 유예 |
| **부산물** | 없음 | `required_artifact` — 완료 판정의 근거 |

그리고 genlab의 채널 축(chat·board·주말)은 **상담 창구**이고 우리 것은 **돈이 지나간 금융 서비스**라
같은 자리에 놓이지 않습니다.

**대신 두 가지를 빌렸습니다** — `action` 축, 그리고 **참조로 가리키고 본문에 값을 박지 않는 방식**
(`references[].identifier` ↔ 우리 `contact_ref`·`citations`). 뒤쪽은 우리가 이미 하던 것이라 **확인에 가깝습니다.**

### 탈락한 후보

| 후보 | 사유 |
| --- | --- |
| `channel` 값 확장 | `visit`이 「영업점 방문」과 「외부 이동」 두 뜻이 됨. 축이 둘인데 하나로 섞임 |
| 프론트 파생 | 근거가 세 필드에 흩어짐. **새 유형이 조용히 `read`로 떨어짐** |
| `plan_step`에 별도 칼럼 | JSONB로 족하고 조회 조건이 아님. 마이그레이션만 늘어남 |
| genlab 구조 전면 도입 | 시행일·법정 기한·부산물을 다시 얹어야 함. 채널 축의 뜻이 다름 |

## 결과

**얻는 것**

- **화면이 추론하지 않습니다.** 서버가 준 값을 그리기만 합니다.
- 새 절차 유형이 들어오면 **적재 시점에 걸립니다.** 조용히 잘못 그려지지 않습니다.
- **마이그레이션이 없습니다** — 둘 다 JSONB입니다.
- 주소가 절차 본문에서 빠져, 은행이 앱 경로를 바꿔도 **KB 릴리스가 필요 없습니다.**

**잃는 것 · 감수하는 것**

- **KB 항목마다 사람이 하나 더 적어야 합니다.** 추산 100~120건 × 항목 안의 `steps[]` 개수만큼입니다.
- **`action`을 잘못 적으면 화면이 틀린 패널을 그립니다.** 적재 검증은 값이 일곱 안인지만 보고,
  **그 단계에 맞는 값인지는 못 봅니다** — 사람 검수(`kb-reviewer`)에 걸립니다.
- `org.contact`의 키 구조가 아직 없어 **`contact_ref` 경로를 확정하지 못했습니다** → 「남은 것」.

## 남은 것

- **`org.contact`의 키 구조.** `call_center`·`app_path` 같은 이름이 정의되지 않았습니다.
  [기관정보 조사](../docs/research/04-기관정보.md)가 **연락처를 전부 비워 둔 상태**라 값과 함께 정합니다 → TODO(근거 필요).
- **`WS-download`가 가리킬 초안.** `doc-builder`(F-08)가 P1이라 계약이 없습니다.
  **`action: "download"`인 단계를 KB에 아직 넣지 않습니다.**
- **한 단계에 행동이 둘일 때** (통화 → 받아적기). 지금은 `steps[]` 배열로 나눠 담지만,
  화면에서 한 패널의 두 단계로 볼지 두 패널로 볼지 정하지 않았습니다 → TODO(미정).

## 재검토 트리거

- **일곱으로 안 담기는 절차가 나오면.** 값을 늘리기 전에 **기존 일곱으로 못 담는 것이 맞는지** 먼저 봅니다.
- `org.contact` 구조가 정해지면 `contact_ref` 경로 표기를 확정합니다.
- KB를 실제로 쓰기 시작해 `action`을 적는 부담이 예상보다 크면 다시 봅니다.
