## 맥락

### 팟 한 대가 곧 서비스입니다

2026-09-06 13:36 KST 에 띄운 RunPod 팟(SECURE RTX 4090 · 시간당 $0.748)에 STT·OCR·이름 2차 탐지가 함께 올라 있고,
배포본의 `TRANSCRIBER_URL`·`NER_URL` 이 그 팟의 프록시 주소를 가리킵니다. 이 팟이 응답하지 않으면 —

심사위원은 2026-09-11(금) 23:59 KST 까지 아무 때나 들어옵니다.

전부이고, 죽으면 사람이 ssh 로 들어가기 전까지 그대로입니다.

### 사용자가 물리친 것

- **GitHub Actions 스케줄** — *"깃헙 말고"*. 5~20분 늦는 스케줄과 공개 실행 로그.
- **앱이 감시자를 깨우는 신호** — *"앱이 감시자를 깨울 이유가 없고"*. 감시자 주기가 이미 짧아 이득이 없고 결합만 늡니다.
- **「연속 N회 실패」 조건** — *"감시자 자체가 왜 연속 실패조건이있냐"*. 아래 「세지 않는다」.

## 결정

세 겹입니다. **돈은 RunPod 의 기능으로, 프로세스는 팟 안에서, 팟은 밖에서.**

### A. 돈 — RunPod auto-pay 와 잔액 알림은 사용자가 켠다

자동화가 못 막는 유일한 꺼짐이라 먼저입니다. 콘솔 Billing 에서 카드 등록 · auto-pay(기준 잔액 · 충전액) · Notification 의
잔액 알림을 켭니다. 감시자는 잔액 ÷ 시간당 요금이 **12시간 아래**로 내려가면 메일을 보냅니다(6시간에 한 번).

### B. 팟 안 — 자가 재시작 루프 `watchdog.sh`

`deploy/runpod-provision.sh` 가 설치하고 띄우며, 지금 팟에는 ssh 로 같은 것을 넣습니다(서비스 중단 없음).

- 20초마다 팟 안에서 `localhost:8917/health` 를 부릅니다.
- `ready` 가 아니고 **마지막 재시작이 180초보다 오래됐으면** `restart.sh` 를 돌리고 시각을 적습니다. Ollama 가 안 잡히면
  그것도 다시 띄웁니다.
- `setsid nohup … < /dev/null` 로 띄워 ssh 가 끊겨도 죽지 않습니다(`runpod-bench.md` 의 같은 이유).

### C. 밖 — 상시 서버의 감시자 `finally-runpod-watch`

상시 서버(OCI · 141.148.13.6)에 **systemd 서비스**로 둡니다(cron 이 아닙니다 — 30초 주기와 상태를 한 프로세스가 듭니다).
본체는 `deploy/runpod-watch.py`(이 결정으로 만듭니다) 이고 `runpod-pod.py` 의 `up` · `provision` · `health` · `down` 을
그대로 부릅니다. 2026-09-07 에 그 서버에서 확인한 것 — Python 3.12 · git · curl · ssh 있음 · 팟의 ssh 포트와 RunPod API 에
닿음.

**매 회(30초) 하는 일 — 순서가 곧 정책입니다.**

1. RunPod API 로 이름이 `finally-demo` 인 팟을 봅니다. **RUNNING 인 팟이 없으면 그 자리에서 새 팟(D)** 을 만듭니다.
   API 가 사실을 말해 주는 것이라 흔들릴 여지가 없습니다.
2. 있으면 `/health` 를 한 번(10초) 부릅니다. `ready` 면 상태를 정리하고 끝입니다.
3. 아니면, **방금 한 조치가 있는지** 봅니다.
   - 재시작을 건 지 180초 안이면 기다립니다 — 모델이 올라오는 중입니다.
   - 새 팟을 만드는 중이면 그것이 끝나기를 기다립니다.
   - 아무 조치도 진행 중이 아니면 **그 자리에서 ssh 로 `restart.sh`** 를 돌리고 시각을 적습니다.
4. 재시작을 건 지 180초가 지났는데도 `ready` 가 아니면 그 팟을 terminate 하고 **새 팟(D)** 을 만듭니다.

**세지 않습니다.** 「연속 N회 실패」 조건이 없습니다. 그 조건이 막으려던 것은 둘이었는데 둘 다 다른 방법으로 막힙니다 —
재시작 직후 모델을 올리는 20~40초 동안 `/health` 가 정상적으로 안 잡히는 것은 **「조치 뒤 유예 180초」** 로, 잠깐의 흔들림에
비싼 조치를 하는 것은 **「싼 조치부터, 비싼 조치는 확인된 사실 뒤에만」** 으로. 한 번의 `/health` 실패에 바로 재시작하는
대가는 1~2분의 워밍업뿐입니다. 새 팟은 「API 가 없다고 한다」 또는 「재시작이 효과가 없었다」 뒤에만 옵니다.

### D. 새 팟 — 손 절차 그대로, 사람 없이

| 순서 | 무엇 | 비고 |
| --- | --- | --- |
| ① | `up` — SECURE 4090 · CUDA ≥ 12.8 · 22/tcp 두 함정 판정 | 함정에 걸리면 `down` 뒤 다시 `up`(최대 3회) — `runpod-bench.md` 「띄운 직후」 |
| ② | `provision` — ssh 로 꾸러미를 올리고 팟 안에서 `provision.sh` | 꾸러미는 그 서버의 저장소 체크아웃에서. `watchdog.sh` 도 여기서 |
| ③ | `health` — `ready: true` 까지 | 10~12분 |
| ④ | GitHub `vercel-env` 워크플로 dispatch — `transcriber_url` · `ner_url` = 새 주소 · `set_ner_token` · `redeploy` | 그 뒤 `deploy` 실행이 끝날 때까지 기다림(2~3분) |
| ⑤ | 앱 `POST /api/cron/evidence-resubmit` | 닫힌 창의 「재시도중」 자료를 미리 맡김 — [ADR-091](091-evidence-retrying-not-failed.md) §5 |
| ⑥ | 죽은 옛 팟이 남아 있으면 terminate · 메일 | 과금을 두 대로 안 늘림 |

**왜 `vercel-env` 워크플로인가.** 이미 있고 검증된 길이고, Vercel 토큰이 **저장소 시크릿에만** 있습니다(로컬에도 OCI 에도
없음). 감시자에게 필요한 것은 그 워크플로를 부를 권한(Actions write) 뿐인 fine-grained PAT 하나입니다. 재배포 2~3분은
팟을 채우는 10~12분 뒤에 붙는 것이라 결정적이지 않습니다.

### E. 감시자가 갖는 것 — 전부 저장소 밖

`/etc/finally/watch.env`(root 만 읽음): `RUNPOD_API_KEY` · 팟 ssh 개인키 경로 · GitHub PAT(이 저장소 · Actions write 만) ·
`CRON_SECRET` · `MAILER_API_KEY` · `MAILER_FROM` · 알림 받을 주소. 저장소 체크아웃은 `/home/ubuntu/fsec-ai-challenge`
(공개 저장소 · 꾸러미와 스크립트 원본). 상태는 `/var/lib/finally/watch.json`(마지막 조치 · 시각 · 만드는 중인 팟 id).
감시자가 죽으면 systemd 가 다시 띄웁니다(`Restart=always`).

### F. 알림 — Brevo 메일

앱이 쓰는 메일 계정으로 보냅니다. 재시작함 · 새 팟 만듦(새 주소) · 새 팟 못 만듦(GPU 없음 · 잔액 부족) · 잔액 12시간 아래.
같은 종류는 6시간에 한 번만. `new_pod` 메일만은 6시간 규칙에서 뺀다 — 매번 새 주소를 담고 있어 사람이 봐야 한다.

## 검토한 대안

| 대안 | 왜 아닌가 |
| --- | --- |
| GitHub Actions 5분 스케줄 | 사용자가 물리침. 스케줄이 5~20분 늦고, 공개 저장소라 실행 로그가 공개됩니다. 시크릿이 이미 거기 있는 장점은 있었습니다 |
| Vercel 크론 | Hobby 는 하루 한 번([ADR-078](078-shell-polls-all-processing-evidence.md) 이 문서로 확인). 함수는 ssh 를 못 하고 몇 분을 못 삽니다 |
| Vercel 라우트 + 외부 1분 호출(Supabase pg_cron · cron-job.org) | 됩니다 — 단 팟이 스스로 채우도록 바꿔야 하고(ssh 없음) 상태 표가 필요합니다. 더 큰 개발이라 이번엔 상시 서버로 |
| UptimeRobot · Better Stack · cron-job.org 단독 | 알림과 웹훅뿐, 살리지 못합니다 |
| 앱의 실패가 감시자를 깨움 | 사용자가 물리침. 감시자 주기가 30초라 이득이 없고, 앱이 인프라를 아는 결합이 생깁니다 |
| 감시자의 「연속 N회 실패」 | 사용자가 물리침. 조치 뒤 유예와 싼 조치 우선으로 같은 것을 막습니다 |
| 멈춘 팟 `start` 로 다시 켜기 | 디스크가 비어 채우는 시간은 같고, GPU 가 남아 있지 않을 수 있습니다(RunPod FAQ). 새 팟이 확실합니다 |
| RunPod Serverless | 20GB 이미지 빌드·업로드와 다른 배포 방식. 남은 기간에 맞지 않습니다 |
| 상시 서버 Caddy 를 앞단으로(주소 고정 · 자동 전환) | 그 서버가 죽으면 살아 있는 팟까지 못 씁니다 — 단일 장애점을 옮길 뿐 |
| 내 컴퓨터(WSL)의 타이머 | 컴퓨터가 꺼지면 끝 |

| 프로세스만 죽음 | 팟 안 루프 20초 + 워밍업 → **2~3분** |
| 팟은 있는데 재시작해도 안 됨 | 30초 + 재시작 3분 + 새 팟 12분 + 주소 교체 3분 → **20분 안팎** |
| 팟 소실 | 30초 + 새 팟 12분 + 주소 교체 3분 → **15분 안팎** |
| 잔액 0 | 자동화 밖 — auto-pay 가 막고, 12시간 전에 메일 |

그 사이 자료는 [ADR-091](091-evidence-retrying-not-failed.md) 로 「재시도중」에서 기다리고, 팟이 돌아오면 늦어도 5초 안에
이어집니다. 진술·채팅은 그 사이 503 과 「다시 시도」 단추입니다 — 예비 이름 탐지 서버는 별도 결정입니다.

**어려워지는 것** — 감시자와 예비 전사 서버가 같은 기계(OCI)라, 그 서버가 죽으면 감시와 예비가 함께 사라집니다(팟은 그동안
자가 재시작으로 버팁니다 · 다른 회사 · 다른 나라라 함께 죽을 이유가 없음). 비밀값 한 벌이 OCI 에 더 생깁니다. 공개 저장소의
`vercel-env` 실행 요약에 새 팟 주소가 남습니다 — 이미 배포본이 부르는 값이라 새로 새는 것은 없습니다.

**되돌리기** — systemd 서비스를 끄고(`systemctl disable --now finally-runpod-watch`), 팟 안 `watchdog.sh` 프로세스를 죽이면
2026-09-06 상태입니다. 앱 코드는 [ADR-091](091-evidence-retrying-not-failed.md) 의 것뿐이라 이 결정에는 마이그레이션이 없습니다.

**재검토 트리거** — 팟 소실을 실제로 겪으면 네트워크 볼륨과 자가 채우기(G). 진술·채팅의 503 이 문제가 되면 예비 이름 탐지
ADR. 대회가 끝난 운영은 [ADR-043](043-gpu-hosting.md) 대로 국내 GPU 이고 이 감시자는 그 배치에 맞춰 다시 정합니다.
