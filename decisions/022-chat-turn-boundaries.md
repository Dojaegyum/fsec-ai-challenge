# ADR-022. 챗 한 턴의 진입과 송출에 이름을 붙이고, 근거 화면은 보류한다

- 상태: **채택**
- 날짜: 2026-08-17
- 결정: @Dojaegyum
- 관련: [ADR-014](014-module-names.md) 보완 · [ADR-015](015-citation-and-reask.md) ·

  [spec/common/08-14-api.md](../spec/common/08-14-api.md) §3.9 §5.4 ·

## 맥락

층 2(사용자가 말할 때마다)는 다섯 모듈이 정해져 있습니다.

```
pii-tokenizer → kb-finder → prompt-builder → [ 모델 1회 ] → citation-checker → pii-restorer
```

**양 끝에 이름이 없습니다.**

**하나. 이 순서를 누가 부르는지에 이름이 없습니다.** [모듈 명칭](../spec/common/08-16-module-names.md)이 API Gateway를 「진입 경로라서 이 목록에 넣지 않았다」로 뒀기 때문입니다. 그래서 "조회는 됐는데 조립에서 막혔다"는 말할 수 있어도, 그 순서를 부르는 자리는 지목할 말이 없습니다.

**둘 — 이쪽이 더 급합니다. 나가는 것을 마지막으로 만지는 자리에 주인이 없습니다.** [모듈 경계](../spec/common/08-16-module-boundaries.md)가 **송출 전 검사 셋**을 명시합니다.

| 검사 | 주인 |
| --- | --- |
| 인용 검증 | `citation-checker` |
| **판단 근거 분리** | **없음** |
| **잔여 PII** | **없음** |

[챗 컨텍스트](../spec/backend/08-16-chat-context.md) §9의 `EGRESS_BLOCKED` 422도 누가 던지는지 정해져 있지 않습니다. **규칙은 있는데 지킬 모듈이 없는 상태**입니다.

여기에 더해, 답변의 근거를 사용자에게 보여주는 화면을 만들지 검토했습니다. 신뢰를 얻는 가장 직접적인 방법으로 보였습니다.

## 결정

### 하나 — `chat-receiver`: 층 2의 순서를 부르는 자리

발화를 받아 `pii-tokenizer` · `kb-finder` · `prompt-builder`를 순서대로 부르고 모델을 1회 호출합니다.

**절대 하지 않는 것 — 이 조항이 이 결정의 핵심입니다.**

- **갈래를 판정하지 않습니다.** 답변인지 1332 안내인지 슬롯 질문인지는 `citation-checker`가 가릅니다
- **조회·조립·토큰화를 직접 하지 않습니다.** 부르기만 합니다
- **응답 형태를 만들지 않습니다.** `chat-publisher`의 일입니다

**이 조항이 없으면 반드시 비대해집니다.** 재시도 판단·감사 로그·캐싱 경계·예외 전달이 전부 이 자리로 몰릴 자연스러운 힘이 있고, 그렇게 되면 「순서를 부르는 얇은 자리」라는 정의가 거짓말이 됩니다. 그때는 이미 못 쪼갭니다.

### 둘 — `chat-publisher`: 나가는 것을 마지막으로 만지는 자리

**책임 셋입니다.**

1. **세 갈래를 한 형태로 씌웁니다.** 답변·1332 안내·슬롯 질문이 같은 껍데기로 나가, 화면이 갈래를 분기하지 않습니다
2. **판단 근거를 분리합니다** → [API 계약](../spec/common/08-14-api.md) §5.4
3. **잔여 PII를 검사합니다.** 걸리면 `EGRESS_BLOCKED` 422 → [챗 컨텍스트](../spec/backend/08-16-chat-context.md) §9

**`citation-checker`와의 경계** — 어느 갈래인지 **판정**하는 것은 `citation-checker`, 그 갈래를 **형태로 옮기는** 것은 `chat-publisher`입니다. 판정이 이쪽으로 새면 갈래가 두 곳에서 결정됩니다.

**이름이 전송 방식을 뜻하지 않습니다.** `receiver`와 대칭을 이루려고 고른 말이고, 실제로 하는 일은 HTTP 응답 본문을 만드는 것입니다. 구독·푸시·발행과 무관합니다.

### 셋 — 근거 화면은 **보류**합니다

**`citations`를 응답에 실어 보내는 것은 [API 계약](../spec/common/08-14-api.md) §3.9 현행대로 유지합니다.** 보류하는 것은 **그것으로 화면을 만드는 일**입니다.

**보류지 폐기가 아닙니다.** `message.citations`와 `kb_context_refs`는 검증·감사에 필요해 매 턴 저장되고, `kb_entry`의 기본키가 `(kb_entry_id, kb_version)`이라 **그때 그 버전을 그대로 되살릴 수 있습니다.** 나중에 켜면 그동안 쌓인 대화도 전부 근거를 볼 수 있습니다.

**재개 조건 — 셋 다 충족해야 합니다.**

1. **검증받지 않은 문장이 화면에 나가지 않는 것을 구조로 보장할 것.** 사람이 조심하는 것으로는 부족합니다
2. **내부 용어 없이 피해자의 말로 쓸 것.** `kb-2`·`kb_entry_id`는 피해자에게 뜻이 없습니다
3. **이름을 정할 것.** `metadata`가 후보입니다. **`artifact`는 쓸 수 없습니다** — 이 프로젝트에서 부산물(접수번호·접수증)로 이미 예약돼 있고 `completion-checker`가 그것으로 완료를 판정합니다

### 넷 — 전송은 요청·응답입니다 (이미 정해진 것의 재확인)

**웹소켓과 스트리밍을 쓰지 않습니다.** 새로 정하는 것이 아니라 [모듈 경계](../spec/common/08-16-module-boundaries.md)가 이미 폴링으로 확정하고 「챗에도 스트리밍을 쓰지 않습니다」를 명시한 것을, **결정 둘의 근거와 같은 것임을 확인**하는 것입니다.

## 근거

### 왜 이번에는 「순서를 부르는 자리」에 이름을 두는가

[ADR-014](014-module-names.md)가 `orchestrator`를 명시적으로 버렸습니다. 그것을 뒤집는 것처럼 보이므로 답해야 합니다.

**그때 버린 것은 「분석 오케스트레이터」였고, 셋으로 갈려 사라질 이름이었습니다.** 남기면 없어진 것을 가리키게 되고, 같은 말이 두 뜻으로 쓰이던 상태였습니다.

**층 2는 사정이 다릅니다.** 갈래가 셋이고 실패가 여섯 종류인데(§9), 그것을 부르는 자리에 이름이 없으면 **"어디서 막혔나"에 답할 수 없습니다.** 이름 체계를 층으로 나눈 이유 자체가 그 질문에 한마디로 답하기 위해서였습니다.

**그래도 오케스트레이터를 다시 들이는 것은 맞습니다.** 그 위험을 이름이 아니라 **금지 조항**으로 막습니다 — 결정 하나의 「절대 하지 않는 것」.

### 이름이 하는 일을 다 담지 못합니다 — 알고 골랐습니다

`chat-receiver`는 받고·조회하고·조립하고·모델을 부릅니다. 「받는다」는 그중 첫 동작일 뿐이라 [ADR-014](014-module-names.md) 명명 원칙 2(하는 일이 이름에 드러난다)에 어긋납니다.

**`receiver`/`publisher` 대칭이 주는 기억하기 쉬움과 맞바꿨습니다.** 층 2를 설명할 때 "받는 쪽과 내보내는 쪽, 사이에 인용 검증"이라고 한 문장으로 말할 수 있습니다. 이 손해는 감춰두면 나중에 지적으로 돌아오므로 여기 적어둡니다.

### 왜 근거 화면을 보류하는가 — 신뢰 장치가 신뢰를 깎습니다

**화면에 띄우려면 `why`를 써야 하는데, `why`는 인용 검증을 받지 않은 모델의 자유 텍스트입니다.** 검증의 *재료*라서 그 자신은 검증 대상이 아닙니다.

이것은 [API 계약](../spec/common/08-14-api.md) §5.4가 판단 근거를 사용자 응답에서 막은 것과 **같은 구조의 문제**입니다. 그 조항이 든 이유가 그대로 적용됩니다.

> 최종 응답에서는 `CLAUDE.md` 불변 규칙 1이 지켜지는데 판단 근거에서 새는 상태가 됩니다.
> 사용자는 둘을 구분해 읽지 않습니다.

**사고 흐름(CoT)을 그대로 보여주는 안은 §5.4가 이미 금지합니다.** 별도 LLM으로 정제하는 안도 답이 아닙니다 — **정제하는 모델도 창작합니다.** 검증받지 않은 문장이 한 겹 더 생길 뿐입니다.

**「AI가 절차를 창작하지 않는다」를 보여주려고 만든 화면이 창작으로 채워지면 역효과입니다.** 아무것도 안 보여주는 것보다 나쁩니다.

### 왜 스트리밍이 아닌가

[모듈 경계](../spec/common/08-16-module-boundaries.md)가 이미 답을 적어뒀고, 그 이유가 결정 둘과 같은 것입니다.

**송출 전 검사 셋은 응답을 다 받은 뒤에야 가능합니다.** 인용이 붙었는지는 답변이 끝나야 알고, 잔여 PII도 전체를 봐야 압니다. **스트리밍이면 근거 없는 절차 문장이 화면에 먼저 뜬 뒤 지워집니다** — 피해자가 이미 읽은 다음입니다.

세 가지가 같은 방향을 가리킵니다.

| | |
| --- | --- |
| 검사 순서 | 다 받아야 검사할 수 있습니다 (위) |
| 대화 구조 | 모델 호출이 한 번뿐이라 서버가 먼저 말 걸 일이 없습니다 → [챗 컨텍스트](../spec/backend/08-16-chat-context.md) §1 |
| 배포 | Vercel 서버리스는 웹소켓 서버를 띄우지 못합니다 → [ADR-016](016-retention-and-datastore.md) |

**진짜 푸시가 필요한 자리는 챗이 아닙니다** — 기한 리마인더입니다. 그때 사용자의 브라우저는 닫혀 있으므로 웹소켓으로는 애초에 해결되지 않습니다.

### 탈락한 후보

| 후보 | 사유 |
| --- | --- |
| `chat-receiver`가 하위 모듈을 **품는** 계층 구조 | `pii-tokenizer`가 **층 1에서도 돕니다.** 하위로 넣으면 층 1이 챗 모듈 안을 들여다봐야 합니다. 게다가 이 모듈은 **격리 경계 그 자체**라 다른 모듈 안에 감추면 「이것만이 경계」라는 규칙이 눈에서 사라집니다. `src/modules/` 검사도 바로 아래 한 겹만 보므로 폴더를 겹치면 이름과 코드의 1:1이 깨집니다 → [ADR-019](019-module-code-sync.md) |
| `reply-builder` · `answer-publisher` | `chat-` 접두가 층 2 전체를 한 눈에 묶어줍니다. `receiver`와 짝이 맞는 쪽을 택했습니다 |
| `trace-builder` — 근거를 짓는 모듈 | 위 「왜 보류하는가」. **모듈이 나쁜 것이 아니라 지금 채울 내용이 검증되지 않습니다** |
| 근거를 **누를 때** 짓기 | 보류로 함께 미뤄졌습니다. 참고로 `kb_version`이 저장돼 있어 나중에 지어도 그때 버전이 나옵니다 — 재개 시 유효한 선택지입니다 |

## 결과

**얻는 것**

- **주인 없던 규칙 둘에 주인이 생깁니다** — 판단 근거 분리와 잔여 PII 검사. 규칙만 있고 지킬 모듈이 없던 상태가 해소됩니다
- **화면이 갈래를 분기하지 않습니다.** 세 갈래가 한 형태로 나갑니다
- 층 2를 한 문장으로 설명할 수 있습니다 — 받는 쪽, 인용 검증, 내보내는 쪽
- **근거를 안 보여주기로 했지만 데이터는 쌓입니다.** 재개 시점이 언제든 과거 대화까지 소급됩니다

**잃는 것 · 감수하는 것**

- **오케스트레이터를 층 2에 다시 들였습니다.** 금지 조항으로 막고 있을 뿐, **강제하는 검사기는 없습니다.** 코드 리뷰에서 지켜야 합니다
- `chat-receiver`라는 이름이 하는 일의 첫 동작만 가리킵니다
- **신뢰를 보여줄 가장 직접적인 화면을 포기했습니다.** 발표에서 "근거를 화면으로 보여준다"고 말할 수 없습니다. 대신 **인용이 없으면 답하지 않는다는 구조 자체**를 설명해야 합니다

## 재검토 트리거

- **근거 화면 재개** — 위 재개 조건 셋이 충족될 때. MVP 범위가 확정되고 여유가 생기면 가장 먼저 볼 항목입니다
- **`chat-receiver`가 커질 때** — 조회·판정·분기가 들어오기 시작하면 쪼갤 시점입니다
- **전송 방식** — 리마인더 발송 주체가 정해지면 실시간 경로 전체를 다시 봅니다. 다만 그때도 **챗의 스트리밍은 별개**입니다
