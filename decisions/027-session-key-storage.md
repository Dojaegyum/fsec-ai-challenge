# ADR-027. 세션키를 꺼낼 수 없는 형태로 만들어 브라우저에 가둔다

- 상태: **채택**
- 날짜: 2026-08-18
- 관련 문서: [ADR-009](009-restore-mapping-location.md) · [ADR-021](021-reentry-and-identity.md) ·
  [PII 격리 경계](../spec/common/08-14-pii-boundary.md) · `src/modules/key-handler/`

## 맥락

[ADR-009](009-restore-mapping-location.md)가 **매핑은 암호문으로 서버 볼트에, 복호화 키는 클라이언트에**를
정했습니다. 그런데 **키를 클라이언트의 어디에 어떤 형태로 두는지**는 정하지 않았습니다.

`key-handler`를 구현하려니 그 자리에서 갈렸습니다. 웹 크립토의 키는 만들 때
`extractable`을 정해야 하고, 이 한 값이 **되돌리기 어려운 성질**을 결정합니다.

[ARCHITECTURE.md](../ARCHITECTURE.md) §10이 「브라우저를 바꾸면 키가 없어 서류를 못 만듭니다」를
이미 미결로 올려 두고 있었습니다.

## 결정

**세션키를 `extractable: false`인 `CryptoKey`로 만들고, IndexedDB에 그대로 보관합니다.**

| | |
| --- | --- |
| 알고리즘 | AES-GCM 256. IV는 **암호화마다 새로** |
| 보관 | **IndexedDB** — `CryptoKey`가 구조화 복제로 저장됩니다 |
| 식별자 | 난수 ULID. **키에서 파생하지 않습니다** |
| 사건당 | **키 하나.** 먼저 찾고 없을 때만 만듭니다 |

**그래서 기기를 바꾸거나 저장소를 지우면 서류를 못 만듭니다.** 이것을 감수하기로 했습니다.

**절차 안내는 그대로 돕니다.** 링크만 있으면 사건·플랜·기한은 전부 보입니다 —
못 하게 되는 것은 **가려진 값을 되살리는 일**, 즉 서류 자동 작성뿐입니다.

## 근거

**「키는 이 브라우저에만 있다」를 부탁이 아니라 구조로 만들려는 것입니다.**

이 서비스의 신뢰 근거는 서버가 통째로 유출돼도 원문을 못 읽는다는 것인데,
그 약속은 **클라이언트가 뚫렸을 때** 시험받습니다. XSS가 들어왔을 때
`extractable: true`면 키가 통째로 실려 나가고, 그 키 하나로 볼트 전체가 풀립니다.
`false`면 공격자는 **그 탭이 열려 있는 동안 복호화를 시킬 수는 있어도 키를 가져갈 수 없습니다.**

**`localStorage`를 안 쓰는 이유가 여기서 나옵니다.** 문자열만 담기므로 키를 저장하려면
먼저 꺼내야 하고, **꺼낼 수 있으면 XSS도 꺼낼 수 있습니다.** IndexedDB는 `CryptoKey` 객체를
그대로 담아, 저장을 위해 평문으로 만들 필요가 없습니다.

**감수하는 쪽의 무게도 재 봤습니다.** [ADR-021](021-reentry-and-identity.md)이 이미
**링크를 잃으면 사용자 귀책**으로 정했고, `ARCHITECTURE.md`가 브라우저 변경 시의 제약을
알고 있었습니다. 새로 잃는 것이 아니라 **이미 있던 제약을 명시로 바꾼 것**입니다.

### 탈락한 대안

| 대안 | 왜 안 골랐나 |
| --- | --- |
| **`extractable: true` + 「키 옮기기」 기능** | 기기 이전이 되는 것은 실질적 이득입니다. 다만 그 기능은 **아직 없고**, 없는 기능을 위해 있는 보호를 내주는 셈입니다. 필요해지면 새 ADR로 뒤집습니다 — 대회 기간엔 사용자가 없어 마이그레이션 비용이 사실상 0입니다 |
| **`localStorage`에 키 원문** | 저장하려면 꺼내야 하고, 꺼낼 수 있으면 XSS도 꺼냅니다 |
| **비밀번호에서 키 유도(PBKDF2)** | 기기 이전이 되고 서버는 여전히 못 읽습니다. 그런데 **비밀번호를 만들게 하는 순간 계정이 생깁니다** — [ADR-021](021-reentry-and-identity.md)의 「`User` 테이블 없음」과 정면으로 부딪히고, 충격 상태의 사용자에게 관문을 하나 더 세웁니다 |
| **서버가 키를 보관** | ADR-009 자체를 뒤집는 것이라 검토 대상이 아닙니다 |

## 결과

**쉬워지는 것**

- 「키가 안 샌다」를 발표에서 **구조로 설명**할 수 있습니다 — `exportKey`가 던지는 것이 증거입니다.
- 키 유출 경로가 좁아져 감사 항목이 줄어듭니다.

**어려워지는 것**

- **기기 이전이 안 됩니다.** 사용자가 폰에서 시작해 PC에서 서류를 만들 수 없습니다.
- **저장소를 지우면 끝입니다.** 시크릿 창·브라우저 데이터 삭제·일부 iOS 저장소 정리 정책에 걸립니다.
- 화면이 이 사실을 **미리 알려야 합니다.** 서류를 못 만들게 된 다음에 알리면 늦습니다.

**재검토 트리거**

- 사용자 조사나 심사에서 **기기 이전 요구가 실제로 나오면** — 새 ADR로 뒤집고
  「키 옮기기」를 설계합니다. 그때 옮기는 것은 키이지 사건이 아니라는 점에 유의해야 합니다.
- iOS Safari의 저장소 정리로 **키가 예고 없이 사라지는 사례**가 확인되면.
