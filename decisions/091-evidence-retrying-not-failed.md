## 맥락

배포본의 전사(STT)·판독(OCR)·이름 2차 탐지(NER)는 **RunPod 팟 한 대**를 봅니다. 2026-09-07 01:00 KST 에 그 팟의
요청 기록을 읽으니 앱이 보낸 전사 작업 64건과 이름 탐지 1,737건이 찍혀 있었고, 상시 서버(OCI)에는 지난 24시간 전사
요청이 0건이었습니다. 팟이 응답하지 않으면 자료 경로는 세 자리에서 죽습니다.

| 자리 | 지금 동작 | 사용자가 보는 것 |
| --- | --- | --- |
| 맡기기 — `startReading` 이 `POST /jobs` 에 못 닿음 | 그 자리에서 `ingest_status = failed`(`submit_failed`) | 「이 파일은 읽어내지 못했습니다」 → 다시 올려야 함 |
| 묻기 — `collect` 가 `GET /jobs/{id}` 에 못 닿음 | `IngestError`(`poll_failed`) 422 | 「다시 확인」 단추 — 사람이 눌러야 다음 폴링 |
| 토큰화 — 원문은 받았는데 이름 탐지 서비스가 안 됨 | `PiiTokenizerUnavailableError` 503 | 같은 단추 |

첫째 줄은 2026-09-06 에 일부러 그렇게 만든 것입니다 — 그 전에는 맡기기 예외가 202 뒤로 사라져 화면이 「읽는 중」을
그렸습니다. 그때의 전제는 **팟은 살아 있다**였습니다. 맡기기가 실패하는 이유가 「팟이 요청을 거절했다」라면 실패로
적는 것이 맞지만, **「팟에 닿지 못했다」는 일시적**입니다 — [ADR-092](092-pod-self-heal-and-watcher.md) 가 팟을
2~20분 안에 되살립니다.

반면 **팟이 살아 있는데 작업을 잊은 경우**(끝난 결과를 30분 뒤 버림 · 다시 뜸 → 404)는
[ADR-078](078-shell-polls-all-processing-evidence.md) 이 이미 같은 번호로 다시 맡깁니다. 즉 지금은 「팟이 기억을 잃음」은
스스로 낫고 「팟에 못 닿음」은 죽습니다. 이 둘의 차이는 사용자에게 아무 뜻이 없습니다 — 파일은 우리 저장소에 그대로 있고,
작업 번호는 증거 번호라([ADR-051](051-idempotent-ingest.md)) 언제든 다시 맡길 수 있습니다.

「몇 번 연속 실패하면」 같은 조건을 앱에 두지 않습니다. 앱의 요청이 실패한 것 자체가 확실한 신호이고, 다시 맡기는
비용은 팟이 살아 있을 때 HTTP 한 번, 죽어 있을 때 타임아웃 한 번뿐입니다.

## 결정

**「서버에 못 닿았다」와 「서버가 파일을 읽어 보고 실패했다」를 가릅니다. 앞의 것은 `failed` 로 적지 않고
`processing` 인 채 「재시도중」으로 답하며, 브라우저의 기존 폴링이 물을 때마다 서버가 다시 맡깁니다.**

### 1. 일시적인가 최종적인가 — 판정은 어댑터, 갈래는 흐름

| 일시적(transient) — 재시도중으로 | 최종적(terminal) — 지금처럼 |
| --- | --- |
| 연결 실패 · 타임아웃 (`AbortSignal.timeout`) | 팟이 작업을 돌려 보고 `status: failed` 라고 답한 것 |
| 5xx — RunPod 프록시가 팟이 없을 때 내는 502·503·504 포함 | 맡기기의 4xx(413 · 415 · 422 …) — 요청 자체가 거절된 것 |
| 이름 탐지 서비스에 못 닿음 · 타임아웃 · 5xx · 저장소 서명 주소 요청에 못 닿음 · 5xx (`read_url_failed` 도 같은 규칙 — 2026-09-07 구현 검토에서 보탬) | 저장소의 4xx(`read_url_failed`) · 글 파일을 못 읽음(`text_read_failed`) |
| | 묻기의 404 는 그대로 **`missing`** — ADR-078 의 다시 맡기기 |

상태 코드를 들고 있는 자리는 어댑터(`lib/inference.ts` · `lib/ner.ts`)뿐이므로 **「일시적인가」는 어댑터가 표시**하고,
`transcriber` 모듈이 `IngestError` 의 `detail.transient` 로 올리며, 흐름(`flows/read-evidence.ts`)이 그 표시로 갈래를
정합니다. 흐름이 상태 코드를 직접 보지 않습니다 — 그러면 서비스를 갈아 끼울 때 흐름이 바뀝니다.

### 2. 응답 — `ingest_status` 는 그대로, `progress.retrying` 을 더한다

```jsonc
// §3.3 응답 200 — 재시도중
{
  "evidence_id": "01J8XKR6...",
  "ingest_status": "processing",
  "progress": { "phase": "stt", "percent": 0, "retrying": true },
  "poll_after_ms": 5000
}
```

- `ingest_status` 칸은 **바뀌지 않습니다.** 스키마 변경이 없고, 목록(`GET …/evidence`)은 지금처럼 `processing` 을 봅니다.
- `poll_after_ms` 는 **5,000** — 평소 1,500 보다 길게. 죽은 서버를 1.5초마다 두드릴 이유가 없고, 팟이 돌아온 뒤
  늦어도 5초 안에 다음 시도가 갑니다.
- `retrying` 이 없으면(옛 응답) 화면은 지금처럼 「처리중」을 그립니다 — 호환됩니다.

### 3. 세 자리의 동작

| 자리 | 바뀌는 동작 |
| --- | --- |
| **맡기기** (`startReading`) | 일시적 실패면 [에러 §2](../spec/backend/08-16-errors.md) 그대로 **2초 뒤 한 번 더**. 그래도 안 되면 `failed` 로 적지 않고 `{ ok: false, transient: true }` 를 돌려주며, 완료 통지 라우트는 `processing` + `retrying` 으로 202. 최종적 실패는 지금처럼 그 자리에서 `failed` |
| **묻기** (`collectReading`) | 전송 실패가 일시적이면 던지지 않고 **다시 맡기기를 시도**한 뒤(팟이 없으면 이것도 실패) 「재시도중」으로 답합니다. `missing`(404) 갈래는 그대로 — 다시 맡기기가 일시적으로 실패하면 `failed` 가 아니라 「재시도중」 |
| **토큰화** (`maskLines` 안의 `piiTokenizer`) | 원문을 받은 뒤 이름 탐지 서비스가 일시적으로 안 되면 **원문을 버리고** 「재시도중」으로 답합니다. 원문은 그 함수의 메모리에만 있었고 저장·응답 어디에도 실리지 않습니다 — 토큰화는 순수 계산이라 절반쯤 하다 멈춰도 흔적이 없습니다. 다음 폴링이 팟에서 **같은 결과를 다시 받아**(팟은 끝난 결과를 30분 보관 · `services/transcriber/jobs.py` 의 `KEEP_DONE_SECONDS`) 다시 토큰화합니다. 30분을 넘기면 404 → ADR-078 의 다시 맡기기 → STT·OCR 이 한 번 더 돕니다 |

토큰화 재시도가 성공하는 응답에 대응표(`pii_mappings`)가 실립니다 — [ADR-062](062-transcript-mapping-handover.md) 그대로,
앞서 실패한 시도 때문에 잃는 것은 없습니다.

### 4. 상한을 두지 않는다

「N시간 뒤 `failed`」 같은 타이머를 두지 않습니다. 이 결정의 목적이 **팟이 돌아올 때까지 사용자가 아무것도 안 해도 되게**
하는 것이라, 상한을 두면 팟 복구가 그보다 늦을 때 지금 문제로 돌아갑니다. 오래된 사건은 파기 크론이 정리합니다(§6.3).

### 5. 다시 맡기기는 서버 혼자 할 수 있다 — `POST /api/cron/evidence-resubmit`

재시도의 주인은 그대로 **브라우저 셸**입니다([ADR-078](078-shell-polls-all-processing-evidence.md) — 결과를 받아 토큰화하는
단계는 대응표를 받을 브라우저가 있어야 합니다). 다만 **팟에 다시 맡기는 단계만은 원문을 다루지 않으므로** 서버 혼자
할 수 있습니다. 그래서 기계가 부르는 주소를 하나 둡니다.

| | |
| --- | --- |
| 무엇 | `processing` 이고 **48시간 안에** 만들어진 녹음·이미지 자료 중, 팟이 모르는 것(404 또는 못 닿음)을 같은 번호로 다시 맡깁니다. **토큰화는 하지 않습니다** |
| 누가 | [ADR-092](092-pod-self-heal-and-watcher.md) 의 감시자가 팟을 되살린 직후 한 번. 사람이 손으로도 부를 수 있습니다 |
| 왜 | 사용자가 창을 닫아 둔 자료도 팟에서 미리 처리돼 있다가, 돌아왔을 때 첫 폴링에서 바로 결과가 뜹니다 |
| 문지기 | `/api/cron/` 아래라 `Authorization: Bearer <CRON_SECRET>` 로 이미 지킵니다(§6.1). 다른 문을 열지 않습니다 |
| 상한 | 한 번에 20건. 팟이 막 돌아온 순간 수십 건이 몰리지 않게 |

48시간인 이유는 사건 화면을 닫고 이틀 넘게 안 돌아온 자료까지 GPU 를 태울 이유가 없어서입니다 — 그런 자료는 사용자가
돌아왔을 때 셸의 폴링이 어차피 다시 맡깁니다.

### 6. 화면

`progress.retrying` 이면 자료함의 「처리중」 자리에 이렇게 적습니다.

> 전사 서버에 다시 연결하는 중입니다. 파일은 안전하게 보관돼 있고, **다른 화면에 가셔도 됩니다** — 연결되면 이어서
> 처리합니다.

진행률은 적지 않습니다(0% 를 보여 주면 멈춘 것으로 보입니다). 「다시 확인」 단추는 지금처럼 **조회가 끊긴 경우에만**
— 재시도중은 끊긴 것이 아니라 도는 중입니다.

### 7. 바뀌지 않는 것

- [에러 §3.1](../spec/backend/08-16-errors.md) 「오류 응답은 스스로 다시 부르지 않는다」는 그대로입니다. 이 결정은 오류를
  내지 않고 **처리중으로 답하기** 때문에 기존 폴링이 그대로 재시도가 됩니다.
- **진술·채팅의 이름 탐지 실패는 이 결정의 범위 밖**입니다. 그쪽은 기다릴 파일이 없어 「재시도중」으로 둘 수 없고, 예비
  이름 탐지 서버로의 즉시 전환이 답입니다 — 별도 ADR 로.
- 팟이 파일을 읽어 보고 실패한 것(`failed`)은 지금처럼 즉시 「읽어내지 못했습니다」입니다 — 불변 규칙 5.

## 검토한 대안

| 대안 | 왜 아닌가 |
| --- | --- |
| 지금대로 `failed` + 재업로드 안내 | 팟이 죽어 있는 10~20분 동안 심사위원은 오류를 보고 떠납니다. 파일은 멀쩡한데 다시 올리라고 하는 것이고, 다시 올려도 같은 팟이라 또 실패합니다 |
| N시간 뒤 `failed` 로 전환 | 팟 복구가 그보다 늦으면 같은 문제. 타이머와 상태가 하나 더 생깁니다. 오래된 사건은 파기 크론이 처리합니다 |
| 일시적 실패도 오류 응답으로 내고 **브라우저가** 자동 재시도 | 에러 §3.1 을 뒤집어야 하고, 「오류인데 다시 부르는 것」과 「오류라 안 부르는 것」 두 길이 생깁니다. 처리중으로 답하면 기존 폴링 하나로 끝납니다 |
| 서버가 스스로 폴링·토큰화해 저장 | [ADR-078](078-shell-polls-all-processing-evidence.md) 이 막은 이유 그대로 — 대응표를 받을 브라우저가 없고([ADR-062](062-transcript-mapping-handover.md)), Hobby 크론은 하루 한 번 |
| 원문을 서버에 잠시 보관해 두고 재토큰화 | 스키마 「원문 금지」 · 불변 규칙 3 위반. 팟이 30분 보관하므로 필요도 없습니다 |
| 이름 탐지를 CPU 예비 서버로 넘겨 자료도 처리 | 자료는 **줄마다** 이름 탐지를 한 번씩 부릅니다. CPU 는 한 줄에 10.7~12.3초([09 §7.3](../docs/research/09-로컬모델-PII인식-실측.md))라 30줄이면 330초 — 증거 조회 함수의 상한 120초를 넘겨 영영 못 끝냅니다. 여러 줄을 한 번에 보내도록 `/ner` 을 고친 뒤에나 가능합니다(재검토 트리거) |
| 「연속 N회 실패」 뒤에만 재시도중으로 | 앱의 요청 실패 자체가 확실한 신호이고, 다시 맡기는 비용이 HTTP 한 번이라 셀 이유가 없습니다(사용자 결정) |

## 결과

**쉬워지는 것** — 팟이 죽어 있는 동안 올린 녹음·화면이 「재시도중」으로 기다렸다가, 팟이 돌아오면 늦어도 5초 안에 처리가
시작됩니다. 사용자는 아무 단추도 누르지 않고 파일을 다시 올리지도 않습니다. 이름 탐지만 죽었을 때는 전사를 다시 돌리지
않고(30분 안) 토큰화만 다시 합니다. 감시자가 팟을 되살리면 닫힌 창의 자료도 미리 처리됩니다.

**어려워지는 것** — 팟이 「맡기기는 받는데 바로 잊는」 상태면 5초마다 다시 맡기기가 반복될 수 있습니다(팟 로그의
`POST /jobs` 로 드러납니다 — ADR-078 이 이미 받아들인 것). 팟이 돌아온 순간 재시도중 자료가 많으면 전사가 한꺼번에
몰립니다 — 셸은 한 바퀴 넷, 서버 다시 맡기기는 한 번에 20건으로 누릅니다. 진술·채팅은 이 결정으로 낫지 않습니다.

**되돌리기** — 흐름의 `transient` 갈래를 빼면 옛 동작(즉시 `failed` · 422 · 503)으로 돌아갑니다. `/api/cron/evidence-resubmit`
는 독립이라 남겨도 됩니다. 스키마 변경이 없어 마이그레이션이 없습니다.

**재검토 트리거** — `/ner` 이 여러 줄 묶음 호출을 받게 되면 자료 토큰화도 예비 서버로 넘길 수 있습니다. 서버 자율 수신
(대응표 설계 변경)이 생기면 셸 폴링 없이도 끝까지 갈 수 있습니다. 「재시도중」이 몇 시간씩 이어지는 사례가 보이면 그것은 이
결정이 아니라 [ADR-092](092-pod-self-heal-and-watcher.md) 의 복구가 안 된 것입니다 — 거기서 봅니다.
