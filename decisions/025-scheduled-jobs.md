# ADR-025. 주기 실행을 Vercel Cron으로 하고 앱 안에서 돌린다

- 상태: **채택**
- 날짜: 2026-08-18
- 결정: @Dojaegyum (서브 BE)
- 관련: [ADR-016](016-retention-and-datastore.md) **보완** · [ADR-021](021-reentry-and-identity.md) ·
  [모듈 명칭](../spec/common/08-16-module-names.md) 층 4 ·
  [모듈 경계](../spec/common/08-16-module-boundaries.md) 미결 해소 · `ARCHITECTURE.md` §4

## 맥락

`reminder-sender`와 `case-purger`는 **사용자 요청이 없어도 돌아야 합니다.**
기한은 사용자가 접속하지 않아도 다가오고, `purge_after`는 아무도 안 와도 지나갑니다.

[모듈 경계](../spec/common/08-16-module-boundaries.md)가 이 자리를 미결로 두면서 이렇게 적었습니다.

> TODO(미정): 리마인더 발송 주체 — 서버 스케줄러인가 외부 서비스인가.
> **파기 실행(`case.purge_after` 도달)과 같은 문제입니다** — Vercel 서버리스에 상시 배치가 없습니다.

**2026-08-18 시점에 이 자리를 두 번 잘못 좁혔습니다.**

**하나.** [ADR-016](016-retention-and-datastore.md)이 Supabase를 고르며 `pg_cron`을 언급했고,
그것을 그대로 실행 트리거로 적어 커밋했습니다(`2b1d8ec`). **대안을 따져보지 않았습니다.**

**둘.** ADR-016의 *"Vercel 서버리스에 상시 배치가 없습니다"*를 **"크론도 없다"로 읽었습니다.**
그 문장의 맥락은 [ADR-022](022-chat-turn-boundaries.md)가 웹소켓을 버린 이유 —
**상주 프로세스**가 없다는 것이고, **주기 트리거는 별개**입니다.

## 결정

### 하나 — Vercel Cron이 앱의 API 라우트를 깨웁니다

두 모듈 모두 **Next.js 앱 안의 코드**로 돌고, 트리거만 밖에서 옵니다.
`pg_cron`을 실행 트리거로 쓰지 않습니다.

### 둘 — `2b1d8ec`의 「실행 트리거는 pg_cron」을 철회합니다

같은 날 커밋이라 되돌리는 비용이 문서 수정뿐입니다.

## 근거

### 결정적인 것 — `case-purger`가 세 저장소를 건드립니다

[ADR-016](016-retention-and-datastore.md)이 **세 층을 같은 날 함께 지우기로** 했습니다.

| 층 | 어디 |
| --- | --- |
| 토큰화된 사건 상태 | Supabase Postgres |
| 업로드 원본 | **Supabase Storage** |
| 복원 매핑 암호문 | **볼트** (제품 미결) |

**`pg_cron`은 SQL만 돕니다.** Postgres 밖을 건드리려면 `pg_net`으로 HTTP를 쏘거나
Edge Function을 하나 더 두어야 하고, **그러면 실행 자리가 셋이 됩니다** — 크론·SQL·함수.

ADR-016이 남긴 숙제가 *"Storage 파일까지 실제로 지워지는지 **검증**해야 한다"*인데,
**검증은 지운 뒤 다시 조회해 보는 일**입니다. 세 저장소를 오가는 절차를 SQL로 짜는 것보다
**앱에서 SDK로 하는 편이 짧고, 실패했을 때 무엇이 남았는지 말할 수 있습니다.**

### 리마인더도 같은 방향입니다

`pg_cron`은 메일을 보낼 수 없습니다. 어차피 앱이나 함수가 필요하고,
그렇다면 **깨우는 것도 같은 곳이 낫습니다.**

그리고 리마인더는 **보낼지 말지를 판단해야 합니다** — 이메일이 있는가, 기한이 확정인가
(부산물이 없으면 추정일 뿐이라 보내면 안 됩니다), 이미 보낸 건 아닌가.
**이건 규칙이지 쿼리가 아닙니다.**

### 왜 이게 ADR인가

[ADR-020](020-adr-threshold.md)의 문턱 셋 중 둘에 걸립니다 —
**같은 날 문서에 적어 푸시한 것을 뒤집고**, **탈락한 대안(`pg_cron`)의 이유가 나중에 필요합니다.**
데이터 가까이에서 도는 쪽이 자연스러워 보이는 논의라 **다시 나올 것입니다.**

### 탈락한 후보

| 후보 | 사유 |
| --- | --- |
| **Supabase `pg_cron`** | 데이터에 가깝지만 **SQL만 돕니다.** Storage 삭제·삭제 검증·메일 발송에 `pg_net`·Edge Function이 또 필요해 실행 자리가 셋이 됩니다 |
| **둘로 나누기** (파기는 `pg_cron`, 리마인더는 Vercel) | 각자 자연스러운 자리지만 **운영할 곳이 둘로 늘어납니다.** 2인 팀에 실패 지점을 늘릴 이유가 없습니다 |
| 외부 스케줄러 (GitHub Actions 등) | 배포와 분리돼 **환경변수·시크릿을 한 벌 더** 관리하게 됩니다 |

## 결과

**얻는 것**

- **`case-purger`가 세 저장소를 한 코드에서 다룹니다.** 삭제와 검증이 같은 자리에 있습니다.
- 실행 자리가 하나입니다 — 배포·시크릿·로그가 앱과 같은 곳입니다.
- 리마인더의 「보낼지 말지」 판단을 규칙 코드로 씁니다.

**잃는 것 · 감수하는 것**

- ⬜ **Vercel Cron의 플랜별 실행 빈도·타임아웃을 확인하지 않았습니다.**
  하루 1회면 충분할 것으로 보지만 **근거를 확인하지 않은 상태입니다** → 「남은 것」.
- **사건이 늘면 한 번의 실행이 길어집니다.** 서버리스는 실행 시간 상한이 있어
  **배치를 쪼개는 설계가 필요할 수 있습니다.**
- 데이터에서 한 겹 멀어져 **DB만 남고 앱이 죽으면 파기가 멈춥니다.**
  `purge_after`가 지난 채 남아 있는 사건을 **관측할 방법**이 필요합니다.

## 재검토 트리거

- **Vercel Cron 제약을 확인한 결과 하루 1회가 안 되면** 즉시 다시 봅니다.
- 사건 수가 늘어 한 번의 실행이 타임아웃에 닿으면 배치 분할 또는 큐로 옮깁니다.
- 볼트 제품이 정해지면([ADR-016](016-retention-and-datastore.md) 미결) 파기 경로를 다시 확인합니다.
