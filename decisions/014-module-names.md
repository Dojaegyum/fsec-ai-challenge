# ADR-014. 모듈 이름을 영어 한 층으로 정하고 동작을 네 층으로 나눈다

- 상태: **채택**
- 날짜: 2026-08-16
- 결정: @kth9245
- 관련 문서: [spec/common/08-16-module-names.md](../spec/common/08-16-module-names.md) · [spec/common/08-14-api.md](../spec/common/08-14-api.md) · [spec/backend/08-16-chat-context.md](../spec/backend/08-16-chat-context.md) · [spec/common/08-14-glossary.md](../spec/common/08-14-glossary.md)

## 맥락

사람과 사람, 사람과 에이전트가 같은 것을 다른 말로 부르고 있었습니다.

- [spec/common/08-14-api.md](../spec/common/08-14-api.md) 「서버 구성 요소」 표가 7개 항목을 **영어·한국어 혼합**으로 적어두고(`API Gateway` · `Ingest 서비스` · `2차 PII 스크러버` · `분석 오케스트레이터` · `슬롯 체커` · `Case Store` · `감사 로그`) 각각의 책임 범위를 정의하지 않았습니다.
- 한 저장소를 **세 개의 세션이 동시에** 작업하는 상황이라, 같은 대상을 가리키는 말이 문서마다 달랐습니다.
- `src/`에는 create-next-app 스캐폴딩만 있고 **도메인 코드가 하나도 없습니다.** 이름을 정하기에 가장 비용이 싼 시점입니다.

## 결정

### 1. 영어 한 층만 쓴다

한국어 별칭 표를 따로 두지 않습니다. 발표에서도 같은 이름을 쓰고 뜻은 말로 풉니다.

이름은 **하는 일이 드러나되 어려운 단어를 피하고**, 모듈은 `-er`·`-checker` 꼴로 두어 도메인 명사(`Case`·`Slot`·`Plan`)와 형태로 구분합니다. 소리 내어 말했을 때 "플래너가 플랜을 만든다"처럼 구분되는 것이 조건입니다.

### 2. 용어집 수준으로 둔다

코드 폴더 구조나 새 ID 접두에 묶지 않습니다. `F`·`S`·`CH` 외의 ID 체계를 만들지 않습니다.

### 3. 동작을 네 층으로 나눈다

| 층 | 언제 도나 |
| --- | --- |
| 1 | 증거가 들어올 때만 (한 번) |
| 2 | 사용자가 말할 때마다 (매 턴) |
| 3 | 사건 상태가 바뀔 때 |
| 4 | 하루 1회 |

**어느 기능에도 묶이지 않는 둘은 층 밖에 「항상」으로 둡니다** — `audit-logger`(모든 LLM 호출 기록)와 `retry-checker`(예외의 `retryable` 값을 보고 재시도·중단 판단). 둘 다 어떤 모듈이 부르든 같은 일을 합니다.

전체 목록은 [spec/common/08-16-module-names.md](../spec/common/08-16-module-names.md).

### 4. 도메인 용어는 하나도 바꾸지 않는다

`Case` · `Evidence` · `Slot` · `Channel` · `Plan` · `Artifact` · `PII Token` · `KB` 전부 현행 유지입니다.

논의 중 `Channel`(경유 서비스)을 `payment-service`로 바꾸는 안이 나왔으나 **철회**했습니다(아래 근거). 대신 [spec/common/08-14-glossary.md](../spec/common/08-14-glossary.md)의 정의문을 고쳐 오해 소지를 없앴습니다.

## 근거

### 영어 한 층 — 두 층 안을 버린 이유

내부용 영어 식별자와 대외용 한국어 별칭을 1:1로 묶는 안을 먼저 검토했습니다. 대응표를 유지하는 비용이 들고, 실제로 부를 때마다 어느 층의 말인지 고르는 부담이 생깁니다. **한 이름으로 통일하고 뜻을 말로 푸는 편이 싸다**고 판단했습니다.

### `-er` 꼴 — 동사 한 단어 안을 버린 이유

`plan` · `chat` · `verify` 처럼 동사 하나로 짓는 안이 가장 짧았지만, **도메인 명사와 소리로 구분되지 않습니다.** "플랜이 안 나온다"가 절차 문서를 가리키는지 그것을 만드는 모듈을 가리키는지 문장만으로는 알 수 없습니다.

### 네 층 — 파이프라인 한 줄 그림이 실제와 달랐다

이름을 붙이는 과정에서 드러난 것입니다. [spec/common/08-14-glossary.md](../spec/common/08-14-glossary.md)의 파이프라인 도식과 [spec/backend/08-14-slot-tiering.md](../spec/backend/08-14-slot-tiering.md)의 흐름도는 **한 번 흘러서 끝나는 그림**인데, [spec/backend/08-16-chat-context.md](../spec/backend/08-16-chat-context.md)가 정의한 챗은 **사용자가 말할 때마다** 조회·조립·검증·복원을 전부 다시 돕니다.

**언제 도는지가 다르면 다른 층입니다.** 층을 이름 체계에 넣어두면 "인용 검증에서 막혔다"처럼 어디서 문제가 났는지 한마디로 지목할 수 있습니다.

### `Channel` 개명을 검토했다가 철회한 이유

먼저 개명 쪽 논거는 이렇습니다. 영어 `channel`은 통신 경로나 알림 채널로 읽힙니다. 이 프로젝트에서 가리키는 것은 **돈이 빠져나간 경로**이고, 이것이 [spec/backend/08-14-channel-matrix.md](../spec/backend/08-14-channel-matrix.md)가 정한 **절차 분기의 유일한 축**입니다. 핵심 차별점을 가리키는 말이 이름에서 안 보이는 것은 손해입니다. **이 지적 자체는 사실입니다.**

그럼에도 철회한 이유가 셋입니다.

**첫째, `payment-service`가 8유형을 다 담지 못합니다.** `CH-facetoface`(대면편취)는 **어떤 서비스도 거치지 않고 현금을 직접 건넨** 유형이고, `CH-giftcard`(상품권 핀번호 전달)도 결제 서비스로 부르기 어렵습니다. 빠뜨려도 되는 유형이 아닙니다 — `CH-facetoface`는 2023년 11월부터 환급 대상이 됐고, 계좌이체가 막히자 사기범들이 옮겨간 수법이라 비중이 큽니다. **이름을 바꾸면 분기축의 정의가 좁아집니다.**

**둘째, 반만 바꾸면 안 바꾸느니만 못합니다.** ID 접두 `CH-`를 남긴 채 용어만 바꾸면 `payment_service_id = "CH-bank"` 같은 상태가 되어, "왜 payment_service인데 값이 CH로 시작하나"라는 질문이 새로 생깁니다. 헷갈리는 지점을 없애는 대신 하나 더 만드는 셈입니다.

**셋째, 식별자까지 바꾸면 KB 릴리스가 걸립니다.** `channel`은 DDL 칼럼명·테이블명·인덱스명이자 **T1 슬롯의 키 이름**입니다. `kb_entry.body`의 `requires_slots`가 이 키를 참조하며 **적재 검증이 슬롯 이름 목록과 대조해 없으면 릴리스를 거부합니다** → [spec/backend/08-16-data-model.md](../spec/backend/08-16-data-model.md) §11. 지식베이스 데이터와 코드가 동시에 움직여야 하고, 어긋나는 순간 릴리스가 막힙니다. 대회까지 남은 기간을 감안하면 감당할 이유가 없습니다.

### 이름 대신 정의를 고쳤다

개명 논의의 실제 소득은 **기존 정의문이 부정확했다는 발견**이었습니다. [spec/common/08-14-glossary.md](../spec/common/08-14-glossary.md)가 「돈이 지나간 **금융 서비스** 유형」이라고 적고 있었는데, 이 표현이 대면편취를 담지 못합니다.

정의문을 이렇게 고쳤습니다.

- 「금융 서비스 유형」 → **「돈이 빠져나간 경로의 유형」**
- **통신 경로(전화·문자·앱)를 뜻하지 않는다**는 문장 추가 — 사기범이 어떻게 연락했는지가 아니라 돈이 어디로 갔는지입니다
- `CH-facetoface`처럼 **금융 서비스를 거치지 않은 유형도 포함**하므로 「결제 서비스」로 좁혀 읽지 말라는 문장 추가

**이름이 오해를 부른다고 해서 이름을 바꾸는 것만이 답은 아닙니다.** 이 경우에는 정의를 정확히 쓰는 쪽이 비용도 낮고 얻는 것도 많았습니다.

### 탈락한 이름들

| 대상 | 탈락 후보 | 사유 |
| --- | --- | --- |
| 경유 서비스 | `payment-service` | `CH-facetoface`(현금 직접 전달)·`CH-giftcard`가 결제 서비스가 아니라 **8유형을 다 못 담음.** 위 「개명을 검토했다가 철회한 이유」 참조 |
| 부산물 | `proof` · `receipt` | 뜻은 더 정확하지만 `artifact` 테이블([09](../spec/backend/08-16-data-model.md) §7)과 여러 문서에 이미 박혀 있어 교체 비용이 이득보다 큼. `artifact`가 빌드 산출물과 겹친다는 문제는 남으므로, **설명할 때 "절차를 마치면 남는 것 — 접수번호·접수증"이라고 푼다**는 규칙으로 대신함 |
| 수법 판별 | `scam-classifier` | 통장묶기 트랙은 사기 피해자가 아니라 **억울하게 계좌가 묶인 사람**이라 `scam`이 들어간 이름이 맞지 않음 → [03](../spec/backend/08-14-channel-matrix.md) |
| 수법 판별 | `incident-profiler` | `profiler`가 성능 분석 도구 이름으로 널리 쓰여 다른 것을 떠올리게 함 |
| PII 경계 | `pii-scrubber` (현행) | `scrub`은 문질러 없앤다는 뜻인데, 이 모듈은 지우지 않고 **토큰으로 바꾸어 되돌릴 수 있게 남깁니다.** 동작과 이름이 어긋남 |
| KB 조회 | `kb-retriever` | 검색해 가져온 자료를 모델에 넣는 방식(RAG)의 표준어라 개발자에게는 명확하지만, `retrieve`가 일상어가 아니라 `kb-finder`로 |
| 재시도 판단 | `orchestrator` (현행) | 어려운 단어인 데다, [spec/common/08-14-api.md](../spec/common/08-14-api.md)의 「분석 오케스트레이터」와 **같은 말이 두 뜻으로 쓰이고 있었음.** 그쪽은 셋으로 갈려 사라지므로 이 말을 남기면 없어진 것을 가리키게 됨 |
| 재시도 판단 | `error-handler` · `retry-policy` | 앞은 "에러를 처리한다"가 너무 넓어 무엇을 판단하는지 안 보이고, 뒤는 모듈이 아니라 규칙 문서를 가리키는 말로 읽힘 → `retry-checker` |

## 결과

**쉬워지는 것**

- 문제가 난 자리를 한마디로 지목할 수 있습니다 — "인용 검증에서 막혔다", "슬롯 추출이 실패했다".
- 세션·사람이 나뉘어 작업해도 같은 말을 씁니다.
- LLM을 쓰는 자리와 규칙이 도는 자리가 이름에서 갈립니다 — `slot-extractor`(LLM)와 `slot-checker`(규칙), `planner`(LLM)와 `date-checker`(규칙).

**어려워지는 것**

- 기존 문서들은 당분간 「Ingest 서비스」·「2차 PII 스크러버」 같은 옛 표기를 그대로 씁니다. **문서 사이에 모듈 이름이 어긋난 기간이 생깁니다.** 세 세션이 같은 파일을 동시에 고치면 충돌하므로 일괄 반영을 미뤘습니다 → [spec/common/08-16-module-names.md](../spec/common/08-16-module-names.md) 「기존 문서 반영은 별도 작업입니다」.
- `Channel`이라는 이름은 여전히 통신 경로로 오해될 수 있습니다. **이름이 아니라 정의문으로 막고 있으므로**, 정의를 안 읽은 사람에게는 그대로 노출됩니다.

**재검토 트리거**

- 구현에 착수해 폴더 구조를 잡을 때. 이름과 폴더가 어긋나면 그때 어느 쪽을 맞출지 정합니다.
- 화면·프론트 구성의 명칭을 정할 때. 이번 범위에서 제외했습니다.

## 아직 안 정한 것

- **상태·등급의 호칭** — `plan_step.state` 다섯 가지, 완료 판정 `L1`·`L2`·`L3`, 슬롯 티어 `T0`·`T1`·`T2`. 값은 정의돼 있으므로 부르는 말만 정하면 됩니다.
- **화면·프론트 구성의 명칭** → [spec/frontend/08-14-screens.md](../spec/frontend/08-14-screens.md).
