# ADR-035. 화면 상태는 두 축이다 — 「국면」은 여정에만 쓴다

- 상태: **채택**
- 날짜: 2026-08-20
- 결정: @Dojaegyum
- 관련 문서: [화면 설계](../spec/frontend/08-14-screens.md) (이 결정으로 개정됨) ·
  [서비스 골자](../spec/common/08-17-service-concept.md) 「여정 — 여섯 국면」 (이 결정으로 신설) ·
  [워크스페이스 패널](../spec/frontend/08-17-workspace-panels.md) ·
  [ADR-033](033-ws-panel-placement.md) (패널이 오른쪽 열로 들어간 결정)

## 맥락

**`국면`이라는 낱말이 세 가지를 가리키고 있었습니다.**

| 어디서 | 무슨 뜻이었나 |
| --- | --- |
| 「국면 0·1 — 발견」, 「국면 1~4」 | 사건의 **일생** — 몇 달짜리 타임라인 |
| 「S-06 챗 국면」, 「S-07 보드 국면」 | **본문이 무엇을 보여주나** |
| 「오른쪽 열의 두 국면」 | **오른쪽 350px에 무엇이 있나** |

게다가 **`국면 0~5`는 spec 어디에도 정의가 없이 숫자만 쓰이고 있었습니다.**
정의는 [여정과 화면](../assets/artifacts/plans/08-17-journey-and-screens.html) §02에만 있고,
읽는 사람은 숫자를 보고 어디를 찾아가야 할지 알 수 없었습니다.

핸드오프 번들이 화면 상태를 이렇게 정의해 왔습니다.

```ts
phase: 'chat' | 'chat_panel' | 'board' | 'evidence'
```

**한 축에 두 가지가 섞여 있습니다.** `chat_panel`은 「챗 다음 단계」가 아니라
**「본문은 챗인데 옆칸이 다른 것」**입니다. 그런데 한 줄로 늘어놓으니 순차처럼 읽히고,
실제로는 순차가 아닙니다 — 사용자는 며칠 뒤 링크를 열면 곧장 플랜부터 봅니다.

## 결정

### ① 화면 상태는 독립된 두 축입니다

```ts
focus: 'chat' | 'plan' | 'evidence'   // 본문이 무엇을 보여주나
side:  'casefile' | 'work'             // 오른쪽 열이 무엇을 보여주나
```

기존 네 값이 이렇게 대응됩니다.

| 이전 | 지금 |
| --- | --- |
| `chat` | `{ focus: 'chat', side: 'casefile' }` |
| `chat_panel` | `{ focus: 'chat', side: 'work' }` |
| `board` | `{ focus: 'plan', side: 'work' }` |
| `evidence` | `{ focus: 'evidence', side: 'work' }` |

**두 축은 독립이므로 「다음」이 없습니다.** 타입이 그걸 말해 줍니다.

**모션도 이 축을 따릅니다.** 핸드오프의 전환 네 개가 축과 정확히 맞물립니다 —
①은 `side`만, ②·④는 `focus`만 바뀝니다. **바뀐 축이 곧 재생할 전환**입니다.

### ② `board`를 `plan`으로 바꿉니다

모듈이 `plan-viewer`이고 API가 `GET …/plan`인데 화면만 `board`였습니다.
**「보드」는 일반명사라 아무 데나 붙습니다** — 그 자리를 비워 둡니다.

### ③ 「국면」은 **여정**에만 씁니다

| 낱말 | 무엇 | 값 |
| --- | --- | --- |
| **국면** | 사건의 일생 | 0~5 (아래 ④) |
| **본문** | `focus` | 챗 · 플랜 · 증거함 |
| **오른쪽 열** | `side` | 사건 파일 · 워크스페이스 |

「챗 국면」·「보드 국면」이라는 표현을 쓰지 않습니다. `S-06`·`S-07`·`S-08`은
**본문이 무엇이냐**로 갈리는 같은 주소의 상태입니다.

### ④ `국면 0~5`의 정의를 spec에 옮깁니다

[서비스 골자](../spec/common/08-17-service-concept.md)에 「여정 — 여섯 국면」을 신설하고,
[여정과 화면](../assets/artifacts/plans/08-17-journey-and-screens.html) §02의 값을 그대로 옮깁니다.
**새로 만드는 것이 아니라 옮기는 것입니다** — 숫자를 쓰는 곳이 참조할 데를 갖게 하려는 것입니다.

## 근거

**순차가 아닌 것을 순차로 적으면 구현이 따라갑니다.** 한 축짜리 `phase`는
「다음 단계로 넘긴다」는 코드를 부르고, 그러면 며칠 뒤 재진입한 사용자가
챗부터 다시 보게 됩니다. **재진입 시 첫 줄은 「지금 뭘 해야 하나」여야 합니다.**

**같은 낱말이 세 층위를 가리키면 문서를 읽는 사람이 매번 문맥으로 추론해야 합니다.**
`국면 2~5`와 `보드 국면`이 한 표 안에 같이 있는 상태였습니다.

**정의 없는 숫자는 인용할 수 없습니다.** `국면 3`이 무엇인지 spec만 읽고는 알 수 없었습니다.

### 검토한 대안

| 대안 | 왜 아닌가 |
| --- | --- |
| 네 값 유지, 이름만 손보기 | 섞인 축이 그대로라 `chat_panel` 류가 다시 생깁니다 |
| 축은 나누되 `board` 유지 | 모듈·API와 낱말이 어긋난 채로 남습니다 |
| `국면`을 화면 상태에 주고, 여정에 새 낱말 | 여정 쪽이 원본(기획서)의 표현이라 그쪽을 옮기면 출처와 어긋납니다 |

## 결과

**아티팩트는 고치지 않습니다.** [여정과 화면](../assets/artifacts/plans/08-17-journey-and-screens.html)은
사람이 쓴 원본이고 「챗 국면」이라고 적혀 있습니다. 이 결정은 **spec의 어휘만** 정리합니다 —
아티팩트를 읽을 때 낱말이 다를 수 있다는 것을 알고 보세요.

**핸드오프 번들의 State Management 절과 어휘가 달라집니다.** 번들은 받은 그대로 두는
스냅샷이므로([RFC-003](../rfc/003-design-handoff.md)) 고치지 않고, 대응표를 위 ①에 남깁니다.

**앵커가 바뀝니다.** `#s-06--사건--챗-국면--ctoken` → `#s-06--사건--챗--ctoken`.
바깥에서 이 앵커를 인용하던 곳은 없었습니다(전부 같은 문서 안).

**재검토 트리거** — 본문이나 오른쪽 열에 **세 번째 축**이 필요해지면(예: 상시 열리는 서랍)
축을 늘리는 게 맞는지, 아니면 그게 다른 화면인지부터 다시 봅니다.
값을 늘려서 축을 흐리지 않습니다.
