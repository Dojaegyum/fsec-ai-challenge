## 맥락

**챗의 매뉴얼 조회는 발화를 보지 않습니다.** `kb-finder` 의 조회 조건은 매뉴얼 버전 · 트랙 · 경유 유형 · 기관 넷이고
(`src/modules/kb-finder/types.ts` `KbQuery`), 사용자가 무슨 말을 했는지는 조건에 없습니다. 그래서 이 사건에 **적용되는** 절차는
빠짐없이 들어가지만, 발화가 요구하는 다른 자료는 프롬프트에 없습니다.

| 발화 | 프롬프트에 없던 것 | 어디에 있었나 |
| --- | --- | --- |
| 「3영업일이 정확히 무슨 뜻이에요?」(2026-09-06 02:56 배포본) | 영업일의 뜻 | 어디에도 없었음 → [PR #80](https://github.com/Dojaegyum/fsec-ai-challenge/pull/80) 이 `summary` 에 씀 |
| 「서류는 뭘 내야 하나요? 수수료도 있어요?」(같은 날) | 같은 행의 `steps` | 행에는 있었음 → [ADR-080](080-kb-entry-fields-to-prompt.md) |
| 「카드로 보냈으면 뭐가 달라요?」 | 다른 경유 유형 절차의 상세 | `reference` 묶음에 요약 한 줄만 |
| 「은행에 전화했는데 안 받아요」 | 그 기관의 신고 전화·운영 시간 | `org.contact` — 챗에 배선 없음([09](../spec/backend/08-16-data-model.md) §11.4.4 「막혔을 때만」) |
| 「법에 그렇게 적혀 있어요?」 | 조문 원문 | `source_snapshot` 58조문 — 챗에 배선 없음 |

이 자료들은 **전부 DB 에 있습니다.** 없는 것은 「이번 발화에 어느 것이 필요한가」를 고르는 자리뿐입니다. 벡터 검색은
[ADR-012](012-kb-collection.md) 가 버렸고(시행일·기관 우선순위를 유사도가 보장하지 못함), 자료를 전부 넣는 것은 한 턴 입력이
6,785 토큰([ADR-080](080-kb-entry-fields-to-prompt.md) 실측)에서 서너 배로 늘어 안 됩니다.

사내 `global_information` 검색기(`~/genlab_module/global_information/global_info/information_search.py`)가 같은 문제를
**「답은 쓰지 않고 쓸 항목의 id 만 고르는 LLM」** 으로 풉니다 — 항목을 3,000토큰 묶음으로 나눠 병렬로 후보를 건지고(1단계),
후보를 다시 묶어 이유를 적게 하며 줄입니다(2단계). 이 구조와 프롬프트를 옮깁니다.

## 결정

### ① 층 2에 `kb-selector` 를 둔다

`chat-receiver` 가 `pii-tokenizer` → `kb-finder` → **`kb-selector`** → `prompt-builder` 순으로 부릅니다. `kb-selector` 는
**토큰화된** 대화 이력(최근 6턴 + 이번 발화)과 `kb-finder` 가 이미 고른 항목의 id 를 받아, 그 밖의 자료 중 이번 답변에 쓸
항목 id 를 최대 `top_k`(기본 5)개 돌려줍니다. **답은 쓰지 않고, 절차를 만들지 않고, 고르기만 합니다.**

### ② 후보 풀 — DB 에 있는 것 셋

| 후보 | 어디서 | 한 줄 모양 `[id] 태그: 앞 200자` |
| --- | --- | --- |
| 절차 항목 | 현재 릴리스(`KB_VERSION`)의 `kb_entry` **전부** — 트랙·유형 무관 | `[12] 카드 지급정지 신청: 카드사에 …` |
| 기관 연락처 | `org` 중 `contact` 가 있는 곳 (51곳). `org_public` 은 연락처 칸이 없어 풀에 없다 | `[63] KB국민은행 연락처: 1588-9999 · 24시간 · 영업점 서면 …` |
| 법령 조문 | `source_snapshot` 의 `source_type='law'` **최신본** | `[91] 통신사기피해환급법 제3조: 피해자는 …` |

`kb-finder` 가 이미 넣은 항목은 제외합니다(사내 검색기의 `exclude_tags` 와 같은 자리). 트랙 밖의 절차(통장묶기 사건에서
피해자 절차)도 풀에 있습니다 — 고르면 §2.3 의 조건 라벨 규칙대로 「…라면」을 붙여 답합니다.

### ③ 2단계 선별 — 구조와 프롬프트를 옮긴다

```
1단계  풀을 3,000토큰 묶음으로 나눠 병렬 호출 · id 만 · 추론 없음 · 인사말이면 {"selected": []}
2단계  후보를 다시 3,000토큰 묶음으로 · 항목마다 고르는/안 고르는 이유 한 줄 + 마지막 줄 JSON
       top_k 이하가 될 때까지 반복(최대 6라운드) · 줄지 않으면 한 프롬프트에 모아 마지막 한 번
출력   {"selected": [숫자, 숫자]}
```

선별 프롬프트에 규칙 셋을 더합니다 — **연락처 항목은 사용자가 진행이 막혔다고 말할 때만 고른다**([09](../spec/backend/08-16-data-model.md) §11.4.4 를
프롬프트로 옮긴 것), **조문은 사용자가 근거·법 조항을 물을 때 고른다**, **후보 이름 뒤의 「(이 사건의 기관)」·「(이 사건의 유형)」 표시를
우선한다**. 마지막 것은 첫 실측에서 「은행에 전화했는데 안 받아요」에 은행 셋을 고른 것을 보고 더했습니다 — 선별기는 사건 속성을
모르므로 후보 목록에서 알아보게 합니다(`src/lib/adapters.ts` `markForCase`).

### ④ 선별 전용 모델 · 시간 예산

- 모델은 답변 모델과 따로 둡니다 — `LLM_SELECT_MODEL`. id 만 고르는 일이라 인용 계약이 필요 없어, 2026-08-28 실측에서 2~6초였던
  빠른 모델(`grok-4.20-0309-non-reasoning` 급)을 씁니다. **비어 있으면 선별기가 꺼지고 지금과 같습니다.**
- 선별 전체 상한은 `LLM_SELECT_TIMEOUT_MS`(기본 10,000). 넘기거나 실패하면 **빈 선택으로 답변을 진행**합니다 — 선별이 답변을
  막지 않습니다. 답변 호출의 상한은 90초(`lib/llm.ts` · 2026-09-06 에 55초에서 올림)에서 선별에 쓴 시간을 뺀 값입니다. 챗 라우트의 100초는 그대로입니다.

### ⑤ 프롬프트 블록 · 참조 번호

고른 항목은 사건 상태 다음, 대화 이력 앞의 새 블록 `<kb_selected trusted="true">` 에 **전문**으로 들어갑니다. 절차는 적용 절차와
같은 다섯 줄([ADR-080](080-kb-entry-fields-to-prompt.md) ①), 기관은 신고 전화 · 운영 시간 · 제출 경로 · 주의 넷, 조문은 원문
(1,500자 상한). 참조 번호는 절차 `kb-`(기존 번호에 이어서), 기관 `org-`, 조문 `law-` 입니다. `citation-checker` 의 「이번 턴에
발급한 번호인가」 검사는 이 셋을 다 압니다.

### ⑥ 법령 조문 원문은 검수 없이 후보에 넣는다 — 원칙 4 의 예외

「사람 검수는 생략 불가」는 **우리가 쓴 절차 요약**에 대한 것입니다. `source_snapshot` 의 조문은 국가법령정보 Open API 에서
**글자 그대로** 가져온 원문이라 우리의 해석이 들어 있지 않고, 출처가 법제처입니다. 사람이 다시 읽어 확인할 것이 없습니다.
그래서 `source_change` 의 승인 여부와 무관하게 `source_type='law'` 의 **최신 스냅샷**을 후보 풀에 넣습니다.

범위와 조건:

- **조문 원문만.** 입법예고·보도자료(`pre_notice`·`press`)는 해당 없습니다 — 그쪽은 시행 전이거나 해석이 섞입니다.
- 인용 라벨에 법령명 · 조문 번호 · `fetched_at` 을 넣어 **어느 날의 어느 조문**인지 답변에 남깁니다. 릴리스 고정([ADR-045](045-kb-release-pin.md))은
  매뉴얼 항목의 것이고, 조문은 현행 법령의 최신본이 곧 정본입니다.
- 답변 지시문에 한 줄 — **조문은 그대로 인용하고, 절차의 해석은 적용 절차 요약을 우선한다.** 법조문을 모델이 풀어 말하는 것은
  사람이 쓴 요약보다 잘못 읽을 위험이 큽니다.
- 매뉴얼 항목(`kb_entry`)의 검수·릴리스 절차는 그대로입니다. 이 예외는 조문을 **답변의 인용 후보**로 쓰는 것이지 매뉴얼에 넣는 것이 아닙니다.

### ⑦ 감사 · 계측

- 선별 호출마다 `llm.called` 를 `purpose: "select"` 로 남깁니다(토큰 수 포함). 실패는 `llm.failed`. 답변 호출은 `purpose: "answer"`.
- 한 턴의 선별 결과는 `chat.selected` 한 건 — 풀 크기 · 묶음 수 · 라운드 · 고른 id · 소요 ms.
- `chat.context_built` 의 detail 에 `selected: n` 을 더합니다.

### ⑧ [ADR-022](022-chat-turn-boundaries.md) 와의 관계 — 부분 대체

ADR-022 「모델을 1회 호출」은 **답변 모델 1회**로 좁힙니다. 선별 호출은 답변이 아니라 자료 고르기이고, 따로 세고 따로 예산을
갖습니다. `chat-receiver` 의 세 금지(갈래 판정 안 함 · 조회·조립·토큰화 직접 안 함 · 응답 형태 안 만듦)는 그대로이고, `kb-selector` 도
그 「부르기만 하는」 목록에 하나 더 들어갈 뿐입니다.

## 근거

- **발화 기준의 고르기와 사건 기준의 조회를 나눕니다.** 적용 절차는 지금처럼 결정적으로 조회해 재현성과 인용 검증을 지키고, 발화가
  요구하는 추가 자료만 모델이 고릅니다. 모델이 고른 것도 **DB 에 있는 것 중에서** 고른 것이라 불변 규칙 1(절차 창작 금지)을 넘지 않습니다.
- **id 만 고르는 호출은 값싸고 빠릅니다.** 사내 검색기가 1단계 출력을 수십 토큰으로 눌러 병렬 호출 지연을 잡았습니다. 인용 계약이
  필요 없으니 빠른 모델을 써도 됩니다.
- **실패해도 답변은 나갑니다.** 선별은 있으면 좋은 것이고, 없어도 지금 수준입니다. 그래서 시간 초과를 에러가 아니라 빈 선택으로 둡니다.
- **조문을 검수 큐에 묶어 두면 이 결정이 무의미해집니다.** 58조문이 「최초 수집」으로 대기 중이고, 매뉴얼 전체가 그 법 위에 서 있습니다.
  원문 인용은 요약보다 근거로서 강합니다.

### 검토한 대안

| 대안 | 왜 아닌가 |
| --- | --- |
| 벡터 유사도 검색 | [ADR-012](012-kb-collection.md) 그대로 — 시행일·기관 우선순위를 유사도가 보장하지 못하고, 후보가 150줄이라 임베딩이 필요할 만큼 크지 않습니다 |
| 자료를 전부 프롬프트에 | 6,785 → 2만 토큰대. 캐시가 깨지고 답변 지연이 늘어 60초 예산을 위협합니다 |
| 답변이 `insufficient` 일 때만 자료를 넓혀 한 번 더 | 느린 답변 모델을 두 번 부릅니다. 첫 답이 정직하게 `insufficient` 를 내야 작동하고, 인사말·잡담을 가르지 못합니다 |
| 발화의 낱말로 조건 조회에 태그 매칭 | 「전화가 안 돼요」에서 「연락처」를 못 잡습니다. 표현이 다르면 실패합니다 |
| 조문도 사람 승인 뒤에만 | 원문에 사람이 확인할 해석이 없습니다. 승인을 기다리면 58조문이 쓰이지 못합니다 |

## 결과

**쉬워지는 것**

- 다른 유형 절차의 상세 · 기관 연락처 · 조문 원문을 발화에 맞춰 답합니다. 「막혔을 때만 연락처」 계약이 선별 규칙으로 실제 배선됩니다.
- 선별 결과가 감사에 남아 「왜 이 자료를 넣었나」를 추적할 수 있습니다.

**어려워지는 것**

- 선별이 켜진 턴은 3~10초 느립니다. 병렬 호출이 늘어 모델 호출 수가 턴당 5~8회가 됩니다(토큰은 호출당 수십~수백).
- 선별이 틀리면 엉뚱한 자료가 들어갑니다. 답변 모델은 그것을 인용할 수도 있습니다 — 근거 검증은 「넣어 준 것 안에 있는가」만 봅니다.

**재검토 트리거**

- 선별 정확도·시간 실측 뒤 `top_k` · 최근 턴 수 · 상한을 조정할 때
- 매뉴얼 항목이 수백 개로 늘어 1단계 묶음이 10개를 넘을 때 — 그때는 트랙으로 풀을 먼저 자릅니다

## 정하지 않은 것

- 선별 모델의 최종 이름 — `LLM_SELECT_MODEL` 값. 후보는 `grok-4.20-0309-non-reasoning`. `npm run probe:select` 로 실제 풀과 모델로 재서 정합니다.
- 용어·제도 설명 항목 — 어디에도 저장돼 있지 않은 지식은 이 결정 밖입니다. 필요하면 매뉴얼 항목으로 씁니다([RFC-002](../rfc/002-kb-authoring.md)).
- 조문 인용을 화면에 어떻게 보일지 — [ADR-022](022-chat-turn-boundaries.md) 셋(근거 화면 보류) 그대로입니다.

## 어떻게 지키나

- 모듈 이름은 [모듈 명칭](../spec/common/08-16-module-names.md) 층 2 표에 있고 CI `module-sync` 가 폴더 이름을 대조합니다.
- 계약은 [챗 문맥](../spec/backend/08-16-chat-context.md) §2.6 · §3.1 · §3.4, 감사는 [데이터 모델](../spec/backend/08-16-data-model.md) §10.2,
  환경변수는 [API 계약](../spec/common/08-14-api.md) §1.2. 코드는 같은 날 들어갔습니다 — `src/modules/kb-selector/`(선별) ·
  `src/lib/db-selector.ts`(풀) · `src/lib/adapters.ts`(본문 옮기기 · `asSelectorSource`) · `src/lib/llm.ts`(`createSelectLlmClient`) ·
  `src/modules/prompt-builder`(블록 6 · `org-`·`law-`) · `src/modules/chat-receiver`(순서 · 예산) · `src/flows/chat-turn.ts`(감사) ·
  `npm run probe:select`(탐침).
- 선별기의 입력은 토큰화 뒤의 글뿐입니다 — `chat-receiver` 가 `pii-tokenizer` 다음에 부르는 순서로 지킵니다(불변 규칙 2).
