# ADR-047. 절차 단계의 응답 모양을 하나로 한다

- 상태: **채택**
- 날짜: 2026-08-21
- 결정: @kth9245
- 관련 문서: [API 계약](../spec/common/08-14-api.md) §3.1 (이 결정으로 개정됨) · §3.6 ·
  [데이터 모델](../spec/backend/08-16-data-model.md) §6 §7 §11.4 ·
  [ADR-024](024-step-action-and-url.md) `body.action` 이 작업 패널을 정한다 ·
  [워크스페이스 패널](../spec/frontend/08-17-workspace-panels.md)

## 맥락

정본이 **같은 절차 단계를 두 곳에서 다르게** 그렸습니다.

| 담는 것 | §3.1 사건 생성 | §3.6 플랜 조회 |
| --- | --- | --- |
| `step_id`·`seq`·`title`·`state`·`actor`·`conditional` | 있음 | 있음 |
| `citation` | 네 칸 | **`legal_basis` 도** |
| `body`·`artifacts`·`required_artifact` | **없음** | 있음 |

**얇은 쪽이면 화면이 사건을 만든 직후에 작업 패널을 못 그립니다.** [ADR-024](024-step-action-and-url.md)가
*"클라이언트가 `actor`·`channel`·`required_artifact` 로 유형을 추론하지 않습니다 — 서버가 준
`action` 을 그대로 씁니다"*라고 정했는데, 그 `action` 이 `body` 안에 있습니다. 화면은 곧바로
플랜 조회를 한 번 더 불러야 합니다.

**모양이 둘이면 옮기는 코드도 둘입니다.** 한쪽만 고치면 조용히 갈라집니다 — JSON 이라
컴파일이 안 막습니다.

## 결정

**§3.1을 §3.6과 같은 모양으로 맞춥니다.** 두꺼운 쪽입니다.

사건 생성 응답의 `plan.steps[]` 가 `body`·`artifacts`·`required_artifact` 를 담고,
`citation` 에 `legal_basis` 가 들어갑니다.

**옮기는 자리는 하나입니다** — `flows/api-plan.ts` 의 `toApiStep` 을 두 경로가 함께 씁니다.

## 왜 이렇게

**화면이 한 번만 부르면 됩니다.** 사건을 만든 직후가 가장 급한 순간인데(112 신고·지급정지),
거기서 왕복을 한 번 더 하면 그만큼 늦습니다.

**응답 모양을 한 벌만 만들면 됩니다.** 프론트가 같은 타입을 두 경로에 씁니다.

**막힌 것이 없었습니다.** 처음에는 두 가지가 미정이라 얇은 쪽을 따랐는데, 확인해 보니 둘 다
이미 정본에 있었습니다.

| 걱정했던 것 | 실제 |
| --- | --- |
| `contact_ref` 푸는 규칙 | §11.4 「안내까지의 세 단계」가 **2026-08-16 확정** |
| `legal_basis` 를 어디서 | **`kb_entry` 의 칼럼**(§11.3). 절차를 고를 때 이미 손에 들어옵니다 |

**얇은 쪽으로 통일하는 것을 안 고른 이유**는 §3.6이 이미 그 모양으로 확정돼 있고, 줄이면
화면이 단계마다 본문을 따로 불러야 하기 때문입니다.

## 결과

- §3.1의 응답 예시가 §3.6과 같아집니다.
- `plan_step` 에 `legal_basis` 칼럼이 없으므로, 플랜을 읽을 때 **`kb_entry` 를
  `(kb_entry_id, kb_version)` 으로 함께 읽어야 합니다.**
- 저장소가 단계마다 `artifact` 를 함께 돌려줘야 합니다 → §7 `idx_artifact_step`.

## 남은 것

**`required_artifact` 가 `body` 의 어느 키인지 정본이 예시로만 보여 줍니다**(§11.4 `{ "kind": …, "label": … }`).
키 이름과 필수 여부는 KB 적재 검증(§11.4.5)을 만들 때 함께 못 박습니다.
