# ADR-090. 없는 증거는 404 로 끊고, 오래 멈춘 `pending` 은 조회가 다시 깨운다

## 맥락

2026-09-06 밤 배포본 최종 점검(아티팩트 「FinAlly 제출 전 최종 점검」)에서 자료 처리 경로의 결함 둘을 재현·확인했다.

**결함 1 — 없는 증거로 완료 통지하면 500.** `POST …/evidence/{evidence_id}/complete` 에 형식은 맞지만 존재하지
않는 증거 번호를 보내면 404 가 아니라 500(`INTERNAL`)이 났고, 그 응답에는 감사 로그 식별자도 붙지 않았다. 완료 처리
(`case-intake` `completeUpload` → `db.markUploaded`)가 대상 행이 없을 때 **일반 `Error('증거를 찾지 못했습니다')`**
를 던졌고, 그것은 404 로 매핑되는 예외가 아니라 껍데기가 500 으로 감쌌다. 같은 자원을 읽는 `GET …/evidence/{id}`
는 이미 `CaseNotFoundError`(404)를 던지고 있어(§3.3), 두 자리의 처리가 어긋나 있었다.

**결함 2 — 올린 자료 한 건이 `pending` 에서 영영 멈춤.** 시연 자료 여섯 중 이미지 한 건이 `ingest_status=pending`
인 채 처리로 넘어가지 못했고, 새로고침 뒤에도 자료함에 「대기 중」으로 남았다. 원인은 완료 통지(`…/complete`)의 누락이다.
업로드 흐름은 자리 요청(행이 `pending` 으로 생김) → 저장소로 직접 PUT → 완료 통지(`pending`→`processing` + 판독 시작)
순인데, 그 통지가 화면 이동이나 네트워크로 빠지면 행이 `pending` 에 남는다. 조회 폴링은 `pending` 을 보면 그대로 돌려줄
뿐 깨우지 않았고, 전사기가 결과를 버린 뒤의 재맡기기(`collectReading` 의 `missing`)는 `processing` 만 되살릴 뿐
시작조차 못 한 `pending` 은 대상이 아니었다.

## 결정

**결함 1 — 완료 통지도 없는 증거는 404 로 끊는다.** `POST …/complete` 가 완료 처리 전에 증거를 먼저 조회해,
없으면 `GET …/evidence/{id}` 와 똑같이 `CaseNotFoundError`(404)를 던진다. `db.markUploaded` 의 일반 `Error` 는 이제
정상 흐름에서 도달하지 않지만, 방어로 그대로 둔다. 조회는 `case_id` 를 함께 봐 남의 사건 증거를 자기 주소로 열 수 없다
(ADR-039).

**결함 2 — 오래 멈춘 `pending` 은 조회가 완료 처리를 다시 태운다.** `GET …/evidence/{id}` 가 `pending` 을 만나면
행의 생성 시각을 보고, **90초(`STALE_PENDING_MS`)** 를 넘겼으면 `completeUpload`(`pending`→`processing`)와 판독 맡기기를
다시 실행하고 `processing` 을 낸다. 둘 다 멱등이라 다시 불러도 안전하다 — `markUploaded` 의 UPDATE 는 `pending` 일 때만
한 번 옮기고, `startReading` 은 전사기 잠금으로 두 번 돌지 않는다. 파일이 저장소에 없으면 판독이 `failed` 로 떨어져
「대기 중」 무한 대기를 벗어난다(ADR-026 · 불변 규칙 5 — 막지 않고 갈림길로).

이를 위해 `EvidenceReader.read` 의 반환에 `createdAt`(ISO)을 더했다.

### 왜 90초인가 · 왜 서버인가

- **90초는 넉넉하게 잡았다.** 정상 업로드+완료 통지는 몇 초면 끝난다(우리 자료는 이미지·짧은 녹음). 임계값을 짧게
  잡으면, 큰 파일을 올리는 중인 정상 `pending` 을 다른 뷰어의 폴링이 성급히 깨워 저장 전 판독이 실패할 수 있다. 영영
  멈추는 것보다 나쁘지 않지만, 오검을 줄이려 넉넉히 뒀다. 파일이 저장소에 실제로 있는지 확인(HEAD)하는 신호가 더
  정확하지만, 저장소 결합을 늘려 이 결함 하나에는 과하다.
- **서버가 낫는다.** 원래 올린 브라우저는 이미 떠났을 수 있고, 링크 재진입이 유일한 복귀 수단이라(ADR-021) 며칠 뒤
  다른 기기로 돌아온 사람도 낫는 것이 맞다. 조회를 폴링하는 것 자체가 복구를 일으키므로 별도 크론이 필요 없다.

## 낳는 것

- 완료 통지의 없는 증거 응답이 500 → 404(`CASE_NOT_FOUND`)로 바뀐다. 계약 모양은 그대로다 — 조회 경로가 이미 그랬다.
- `GET …/evidence/{id}` 가 오래된 `pending` 을 만나면 **쓰기(상태 전이 + 판독 시작)를 일으킨다.** 조회에 부수효과가 붙지만,
  이 경로는 원래 `collectReading` 으로 전사·토큰화를 돌리는 자리라 새로운 성격은 아니다. 동시 폴링 둘이 겹쳐도 멱등이라
  안전하다.
- 되돌리려면 이 두 곳을 되돌리면 된다 — 마이그레이션은 없다. `createdAt` 컬럼은 원래 있던 것이고 읽기만 더했다.
