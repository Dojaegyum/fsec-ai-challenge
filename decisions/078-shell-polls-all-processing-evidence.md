# ADR-078. 처리중인 자료는 브라우저 셸이 전부 묻는다 — 서버가 스스로 받아 오지 않고, 팟이 버린 작업은 다시 맡긴다

  `src/app/c/[token]/load.ts` 의 `useEvidenceReads` · `src/flows/read-evidence.ts` 의 `missing` 갈래

## 맥락

접수 마감 전날 배포본에서 **통지문을 올리고 자료함을 떠났다가 돌아오니 25분째 「개인정보 보호
처리중」**이었습니다. 팟(추론 서버)에서는 판독이 이미 끝나 있었습니다. 자료함을 열어 두고 90초를
봐도 그대로였고, 그 줄을 클릭하자 조회 한 번이 나가 60초 뒤 「전사 완료」로 바뀌었습니다.

코드를 끝까지 짚은 원인 사슬은 이렇습니다.

| 자리 | 하는 일 |
| --- | --- |
| `POST …/evidence/{id}/complete` | 팟에 맡기고 202. **그 뒤 서버가 스스로 하는 일은 없습니다** |
| `GET …/evidence/{id}` → `collectReading` | 팟 결과를 서버로 옮기는 **유일한 길.** 끝났으면 토큰화·기관명 보정·슬롯 추출까지 하고 저장합니다 |
| `useEvidence`(자료함 화면 안) | 그 길을 부르는 **유일한 곳.** 선택된 파일 하나만, 자료함 화면이 떠 있는 동안만 |
| `GET …/evidence`(목록) | DB 만 읽습니다. 아무도 DB 를 앞으로 옮기지 않으면 계속 `processing` 입니다 |
| 팟 `jobs.py` | 끝난 작업을 **30분 뒤 지웁니다**(`KEEP_DONE_SECONDS`). 그 뒤 404 → 어댑터가 `poll_failed`(422) 로 던짐 → 화면은 「다시 확인」을 **아무리 눌러도 같은 답** |

그래서 파일을 올리고 다른 화면으로 간 사람 — 심사위원이 늘 그렇습니다 — 은 영원히 「처리중」을 봤고,
25분 사례는 결과를 영영 잃기 5분 전이었습니다. 통화 녹음이 92초에 끝난 것처럼 보인 이유는 그 줄을
선택한 채 자료함에 머물러 폴링이 살아 있었기 때문입니다.

### 왜 서버가 스스로 받아 오면 안 되나

가장 먼저 떠오르는 고침은 「서버가 주기적으로 팟에 물어 결과를 저장한다」입니다. 두 벽이 있습니다.

- **[ADR-062](062-transcript-mapping-handover.md) 와 부딪힙니다.** 토큰화가 일어나는 순간 생기는
  `token ↔ 원문` 대응표는 서버가 보관하지 않고(스키마 「원문 금지」 · 불변 규칙 3) **그 응답에 실어
  브라우저에 건넵니다.** 크론이 대신 토큰화하면 받을 브라우저가 없어 대응표가 버려지고, 올린 본인의
  기기에서도 전사문에 `[계좌-3]` 만 남습니다 — 9월 2일에 고친 바로 그 결함으로 돌아갑니다.
- **Vercel Hobby 플랜은 크론을 하루 한 번까지만 허용합니다.** 1분 간격 표현식은 배포가 실패하고,
  실행 시각도 ±59분입니다(Vercel 문서 「Usage & Pricing for Cron Jobs」 · 2026-07-15 갱신본 확인).
  [ADR-025](025-scheduled-jobs.md) 가 「근거를 확인하지 않은 상태」로 남겨 둔 것이 이것입니다.

## 결정

**폴링의 주인을 자료함 화면에서 사건 페이지 셸로 올리고, 대상을 「선택된 파일」에서 「처리중인
파일 전부」로 넓힙니다. 팟이 작업을 버린 뒤에는 서버가 같은 번호로 다시 맡깁니다.**

1. **셸이 묻습니다** — `page.tsx` 의 `useEvidenceReads`. 처리중·대기중인 자료 전부와 지금 자료함이
   그릴 파일 하나를, **어느 화면에 있든** 서버가 준 `poll_after_ms` 로 끝까지 묻습니다. 한 바퀴에
   넷까지만 — §1.3 「세션당 분당 300회」 안에서(1.5초 간격 × 넷 = 분당 160회). 다섯째부터는 다음
   바퀴에 앞으로 옵니다. 끝나면 레일 줄을 서버 값으로 맞추고 **플랜을 한 번 다시 읽습니다** —
   판독이 끝나며 서버가 단계·기한을 옮겼을 수 있습니다. 자료함 화면은 받은 상태를 그리고
   「다시 확인」을 셸에 알리기만 합니다.
2. **팟이 모르면 다시 맡깁니다** — 어댑터가 404 를 `missing` 으로 옮기고(`inference.ts`), 흐름이
   같은 번호로 `startReading` 을 다시 부른 뒤 `processing`·`percent: 0` 으로 답합니다. 파일은
   저장소에 그대로 있고 작업 번호는 증거 번호라 가능합니다([ADR-051](051-idempotent-ingest.md)).
   다시 맡기는 것도 안 되면 그때 `failed` 로 적힙니다. 브라우저를 닫고 며칠 뒤 돌아와도
   「다시 확인」 무한 반복이 아니라 다시 처리중으로 돕니다.
3. **문구** — 「처리중」에 *「다른 화면에 가셔도 됩니다 — 이 창을 열어 두면 끝났을 때 자료함에
   「전사 완료」로 표시됩니다」* 와 진행률을 적습니다. 1번 때문에 이 문장이 참입니다. **예상 시간은
   적지 않습니다** — 실측이 없고, 틀린 숫자는 기다리는 사람을 더 불안하게 합니다. 자료함 탭에는
   판독 중일 때 맥동하는 점이 켜집니다.

에러 §3.1 은 그대로입니다 — 조회가 **끊긴** 번호는 스스로 다시 묻지 않고, 누르는 것은 사용자입니다.
서버가 `poll_after_ms` 로 시킨 되풀이만 셸이 이어 갑니다.

### 검토한 대안

| 대안 | 왜 아닌가 |
| --- | --- |
| 목록 API(`GET …/evidence`)를 폴링한다 | 목록은 DB 만 읽습니다. 팟 결과를 옮기는 것은 파일별 §3.3 뿐이라, 목록을 1초마다 불러도 `processing` 이 안 움직입니다 |
| 서버 크론이 팟 결과를 받아 온다 | 위 「왜 서버가 스스로 받아 오면 안 되나」 — 대응표를 받을 브라우저가 없고(ADR-062), Hobby 크론은 하루 한 번 |
| 팟이 끝나면 서버를 부른다(webhook) | 크론 간격 제약은 피하지만 토큰화를 받을 브라우저가 없는 것은 같습니다. 팟이 「끝났다」고 표시만 해 두는 용도라면 가능하나, 화면에 보이는 차이가 없어 안 했습니다 |
| 팟의 30분 보존을 늘린다 | 원문 전사가 팟 메모리에 머무는 시간을 늘리는 일입니다. 다시 맡기기가 같은 결과를 원문 노출 없이 냅니다 — 대신 STT·OCR 이 한 번 더 돕니다 |
| 서버가 브라우저 공개키로 대응표를 봉한다 | 키 설계가 하나 더 생깁니다(불변 규칙 3 의 경계 재설계). 대회 기간에 할 크기가 아닙니다 — 서버 자율 수신이 꼭 필요해지면 그때 새 ADR 로 |
| 파일별 폴링을 각각 독립 타이머로 | 처리중 파일 수만큼 요청이 곱해져 §1.3 상한을 넘을 수 있습니다. 한 바퀴 넷으로 묶었습니다 |

## 결과

**쉬워지는 것** — 파일을 올리고 대화·기재 안내 탭으로 가도 끝나면 자료함에 「전사 완료」가 뜹니다.
새로고침이나 링크 재진입 뒤 목록에서 `processing` 으로 돌아온 파일도 끝까지 갑니다. 팟이 결과를
버린 뒤 돌아와도 스스로 복구됩니다.

**어려워지는 것** — 팟이 버린 뒤 돌아오면 STT·OCR 이 다시 돕니다(GPU 팟 기준 통화 한 건 수십 초).
처리중 파일이 넷을 넘으면 파일마다 묻는 간격이 바퀴 수만큼 늘어납니다. 팟이 「맡기기는 되는데
바로 잊는」 상태면 다시 맡기기가 폴링마다 반복될 수 있습니다 — 맡기기 자체가 실패하면 `failed` 로
멈추므로 팟이 아예 죽은 경우는 여기 들지 않습니다.

**되돌리기** — `page.tsx` 의 `useEvidenceReads` 배선을 빼고 `evidence.tsx` 가 다시 자기 파일을 묻게
하면 화면 쪽은 돌아갑니다. 서버의 `missing` 갈래는 독립이라 남겨도 됩니다.

**재검토 트리거** — Pro 플랜으로 올라가거나 대응표 건네기 설계가 바뀌어 서버 자율 수신이 가능해질
때. §1.3 상한(429)이 폴링에서 관측될 때는 `READS_PER_ROUND` 나 서버의 `poll_after_ms` 를 먼저 봅니다.
증거 조회 라우트가 토큰화(NER · LLM 둘)를 그 요청 안에서 하는데 `maxDuration` 이 없습니다 —
배포본에서 60초를 넘는 사례가 보이면 그때 `messages` 라우트처럼 못박습니다.
