# 모듈 구현 순서 — 무엇이 막혀 있고 무엇부터 만드나

> **일시 문서입니다.** 모듈이 다 서고 병목이 풀리면 지웁니다.
> 정본이 아니라 **지금 시점의 지도**입니다 — 모듈 이름·책임의 정본은
> [모듈 명칭](../../spec/common/08-16-module-names.md)과 [모듈 경계](../../spec/common/08-16-module-boundaries.md)입니다.

**작성 이유** — 모듈 21개 중 6개를 만든 시점에 남은 15개의 의존과 걸림돌을 한 번도
정리하지 않았습니다. **2026-08-18 기준 9개가 섰습니다.** 만들기 쉬운 것부터 집어 오다 보면 **조립이 안 되는 부품만 쌓입니다.**

언어모델도 지식베이스도 필요 없는 것들이라 먼저 설 수 있었습니다.

## 진짜 병목은 셋입니다

남은 12개 중 **거의 전부가 아래 셋 중 하나 이상에 걸립니다.** 모듈을 더 만들어도 이것이
풀리지 않으면 조립이 안 됩니다.

### ① 언어모델을 부르는 수단이 없습니다

`XAI_API_KEY` 도 없고 Grok 클라이언트도 없습니다. **모델명과 단가도 미정**입니다
→ [ARCHITECTURE.md](../../ARCHITECTURE.md) §10.

막히는 것: `case-reader` · `slot-extractor` · `planner` · 챗 한 턴 전체

### ② 저장소가 없습니다

Supabase 프로젝트도 접속 정보도 없고, 테이블 14개가 정의만 되어 있습니다.
**마이그레이션 방식도 미정**입니다.

막히는 것: `case-intake` · `kb-finder` · `planner`

> `audit-logger` 와 `completion-checker` 는 **저장을 인터페이스로 비워** 완성했습니다.
> 판단 로직은 다 있고, 실제로 쌓으려면 그 인터페이스를 구현할 저장소가 필요합니다.

### ③ 지식베이스에 항목이 하나도 없습니다

이게 가장 무겁습니다. **사건을 만드는 즉시 T0 공통 안전 절차가 붙어야 하는데, 그 T0 도
`kb_entry` 항목**이라 인용 없이는 내보낼 수 없습니다 →
[10-errors.md](../../spec/backend/08-16-errors.md) §4.1.

즉 **KB 가 비어 있으면 사건 생성 API 조차 규칙을 지키며 만들 수 없습니다.**

막히는 것: `case-intake` · `kb-finder` · `planner`
