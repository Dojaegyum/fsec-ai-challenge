## ① 보존 기간 — 24시간 파기와 몇 달 관리가 충돌합니다

기획서는 사건을 **세션 격리 · TTL 24시간**으로 잡았는데, 지금 포지셔닝은 **기한과 서류를 몇 달 관리**하는 것입니다.
24시간 뒤 사건이 사라지면 3영업일 리마인더도, 2개월 공고 추적도 성립하지 않습니다.
오늘 만든 진입 플로우의 동의 문구도 "24시간 후 자동 파기"라, 지금 셋이 어긋나 있습니다.

**무엇을 24시간에 버리고, 무엇을 몇 달 남깁니까?**

- [ ] **A. 원본만 파기** — 업로드 파일·전사 원문은 24시간, 사건·플랜·단계·기한·부산물(토큰화된 것)은 장기 보존
- [ ] **B. 전부 24시간** — 사용자가 내려받은 사본만 남음. 리마인더·장기 추적 기능은 포기
- [ ] **C. 사용자 선택** — 기본은 전부 파기, 동의하면 사건 메타만 보존
- [x] **D. 전부 같은 수명** — 원본도 함께 장기 보존. 아래 답 참조

| | 파일 스토어 | 사건 DB | 동의·만료 컬럼 |
| --- | --- | --- | --- |
| A | 24h 수명 | 장기 | 불필요 |
| B | 24h | 없음 | 불필요 |
| C | 24h | 동의 시에만 | **필요** |

딸린 질문 — **어느 것을 고르든** 복원 매핑과 원문 PII는 서버에 남지 않습니다(불변).

- 장기 보존한다면 얼마나? (사건 종결까지 / 고정 기간 / 사용자가 지울 때까지)
- 부산물(접수번호 등)은 PII에 가깝습니다. 서버에 두나요, 토큰만 두나요?

**답: D — 전부 `case.purge_after`, 마지막 활동일부터 180일** (`CASE_PURGE_DAYS`)
→ [ADR-010](../../decisions/010-case-store.md)에서 한 층으로 통일, [ADR-016](../../decisions/016-retention-and-datastore.md)에서 기간·기산 조정

**A를 안 고른 이유는 층마다 수명이 다르면 어느 한 층만 남은 상태가 생기기 때문입니다.** 파기가 한 층에서 조용히 실패하면 그게 무엇인지 추적할 방법이 없습니다.

**원본을 남기는 이유**는 즉시 파기하면 전사·판독 오류를 되돌릴 수 없기 때문입니다. 충격 상태의 사용자에게 재업로드를 요구하게 됩니다. **대신 객체 저장소를 저장 시 암호화하고 사건별 키를 씁니다.**

**딸린 질문 답**

- **얼마나?** ~~90일~~ → **마지막 활동일부터 180일** ([ADR-016](../../decisions/016-retention-and-datastore.md), 2026-08-16 조정).
  경로 10종을 실측하니 **표준 트랙만 D+100**이고(공고 2개월 D+86 + 환급금 결정 14일), 명의인이 이의를 제기하면 D+160입니다.
  90일은 6개월 케이스가 아니라 **정상 케이스도 못 덮었습니다** → [research/06](../research/06-경로별-실측조사.md) §5.
  기산을 생성일이 아니라 **마지막 활동일**로 바꾼 이유는, 공고 후에 피해를 알고 들어온 사람(법 제6조제1항)이
  **진입 시점에 이미 두 달이 지나 있기** 때문입니다.
- **부산물은?** **토큰화해서 서버에 둡니다.** 접수번호는 다음 단계의 입력이고 완료 판정의 근거라 서버가 가져야 합니다 → [데이터 모델](../../spec/backend/08-16-data-model.md) §7.
- **복원 매핑은?** 질문의 전제가 바뀌었습니다. [ADR-009](../../decisions/009-restore-mapping-location.md) 로 **암호문은 서버 볼트에, 복호화 키만 클라이언트**입니다. 3영업일 뒤 재방문해 서류를 만들려면 필요합니다.

## ② 재진입 — 사용자가 어떻게 돌아옵니까

몇 달을 관리하려면 사용자가 다시 들어와야 하는데, 기획서에 계정 개념이 없습니다.
**`User` 테이블의 존재 여부 자체가 여기서 갈립니다.**

- [ ] **A. 익명 링크 토큰** — 사건 URL을 아는 사람이 접근. 계정 없음
- [ ] **B. 이메일 확인** — 리마인더를 보내려면 어차피 연락처가 필요
- [ ] **C. 정식 계정** — 로그인·비밀번호
- [ ] **D. 재진입 없음** — 한 세션 안에서 끝 (①-B와 짝)

딸린 질문

- 리마인더를 **어디로** 보냅니까? (웹 알림 / 이메일 / 문자) — 채널이 정해져야 연락처 컬럼이 정해집니다
- 연락처는 PII입니다. 어디에 어떻게 둡니까?
- 보호자 공유(가족이 진행 현황 열람)를 MVP에 넣습니까? 넣으면 권한 모델이 여기 딸립니다

**답: 아직 못 정했습니다. 이것만 남았습니다.**

**다만 관련된 것 셋은 정해졌습니다.**

- **사건은 90일 남습니다**(①). 돌아올 대상이 있습니다.
- **복원 매핑 암호문이 서버 볼트에 있고 복호화 키는 클라이언트에 있습니다**([ADR-009](../../decisions/009-restore-mapping-location.md)).
  **재진입 방식이 이 키를 어떻게 다시 얻느냐와 직결됩니다** — 브라우저를 바꾸면 키가 없어 서류를 못 만듭니다.
- **관리자 계정은 하나**로 확정했습니다(환경변수 `ADMIN_USERNAME`·`ADMIN_PASSWORD_HASH`). **사용자 계정 체계는 여기 없습니다** → [API 계약](../../spec/common/08-14-api.md) §5.
- 지금 API 계약은 `X-Session-Id` 헤더만 정의하고 **발급·검증 절차가 비어 있습니다.** 이 답이 그것을 결정합니다.

**리마인더 발송 주체는 파기 실행과 같은 문제입니다** — Vercel 서버리스에 상시 배치가 없어 예약 실행·접근 시점 검사 중 하나를 골라야 합니다.

## ③ 절차 KB를 DB에 넣습니까, 파일로 둡니까

KB는 **출처·시행일 메타를 갖는 버전드 데이터**이고, 운영 파이프라인(사람 검수)으로만 갱신됩니다.
사건 데이터와 성격이 완전히 다릅니다.

- [ ] **A. 저장소의 파일** — JSON을 git으로 버전 관리. 릴리스 = 커밋·배포
- [x] **B. DB 테이블** — 사건 DB와 같은 곳. 검수 UI를 붙이기 쉬움
- [ ] **C. 파일이 정본 + 런타임엔 적재** — git이 정본, 기동 시 읽어 인덱싱

딸린 질문

- MVP의 KB는 **수동 구축**입니다(F-11 파이프라인은 P2). 그래도 버전 개념은 지금 넣습니까?
- RAG 인덱스를 쓴다면 그 저장소도 여기서 같이 정해야 합니다

**답: B — 관계형 DB 테이블** → [ADR-012](../../decisions/012-kb-collection.md)

**조회 조건이 세 축(기관·유형·시행일)의 조합**이라 파일에서는 매번 전부 읽어 걸러야 합니다. 시행일 분기(`effective_from`·`effective_until`)를 조건으로 거는 것도 DB 쪽이 자연스럽습니다.

**사건 DB와 같은 곳에 두되 트랜잭션 경계는 다릅니다.** KB는 사람 검수를 거친 릴리스로만 갱신되고 사건 처리와 함께 커밋되지 않습니다.

**딸린 질문 답**

- **버전 개념을 지금 넣나?** **넣습니다.** `kb_version` 이 인용에 함께 저장되지 않으면 **나중에 "왜 그렇게 안내했는지"를 재현할 수 없습니다.** 제도가 바뀐 뒤에는 같은 조회가 다른 답을 냅니다.
- **RAG 인덱스?** **안 씁니다.** 벡터 유사도 검색이 아니라 **조건 조회**입니다 → [챗 컨텍스트](../../spec/backend/08-16-chat-context.md). 시행일과 기관 우선순위는 유사도로 보장되지 않습니다.
- **수집 파이프라인은 P2가 아닙니다.** 하루 1회 자동 수집 + 사람 검수 큐로 설계했습니다 → [데이터 모델](../../spec/backend/08-16-data-model.md) §12.

1. ①②는 결정 근거가 커서 **ADR로 남깁니다**(다음 번호는 `decisions/`에서 확인).
2. ①은 [PII 격리 경계](../../spec/common/08-14-pii-boundary.md) 규칙 3과
   [진입 플로우 목업](../../assets/artifacts/plans/08-16-entry-flow-mockup.html)의 동의 문구를 **같이** 고쳐야 합니다 — 셋이 어긋난 채로 두지 않습니다.
3. ②③④는 [도메인 모델](../../spec/common/08-16-domain-model.md)의 「미결」 절을 지우고 본문에 반영합니다.
4. 반영이 끝나면 **이 파일을 지웁니다.**
