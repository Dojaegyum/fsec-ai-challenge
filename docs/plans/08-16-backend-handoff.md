## ① 보존 기간 — 24시간 파기와 몇 달 관리가 충돌합니다

기획서는 사건을 **세션 격리 · TTL 24시간**으로 잡았는데, 지금 포지셔닝은 **기한과 서류를 몇 달 관리**하는 것입니다.
24시간 뒤 사건이 사라지면 3영업일 리마인더도, 2개월 공고 추적도 성립하지 않습니다.
오늘 만든 진입 플로우의 동의 문구도 "24시간 후 자동 파기"라, 지금 셋이 어긋나 있습니다.

**무엇을 24시간에 버리고, 무엇을 몇 달 남깁니까?**

- [ ] **A. 원본만 파기** — 업로드 파일·전사 원문은 24시간, 사건·플랜·단계·기한·부산물(토큰화된 것)은 장기 보존
- [ ] **B. 전부 24시간** — 사용자가 내려받은 사본만 남음. 리마인더·장기 추적 기능은 포기
- [ ] **C. 사용자 선택** — 기본은 전부 파기, 동의하면 사건 메타만 보존

| | 파일 스토어 | 사건 DB | 동의·만료 컬럼 |
| --- | --- | --- | --- |
| A | 24h 수명 | 장기 | 불필요 |
| B | 24h | 없음 | 불필요 |
| C | 24h | 동의 시에만 | **필요** |

딸린 질문 — **어느 것을 고르든** 복원 매핑과 원문 PII는 서버에 남지 않습니다(불변).

- 장기 보존한다면 얼마나? (사건 종결까지 / 고정 기간 / 사용자가 지울 때까지)
- 부산물(접수번호 등)은 PII에 가깝습니다. 서버에 두나요, 토큰만 두나요?

## ② 재진입 — 사용자가 어떻게 돌아옵니까

몇 달을 관리하려면 사용자가 다시 들어와야 하는데, 기획서에 계정 개념이 없습니다.
**`User` 테이블의 존재 여부 자체가 여기서 갈립니다.**

- [ ] **A. 익명 링크 토큰** — 사건 URL을 아는 사람이 접근. 계정 없음
- [ ] **B. 이메일 확인** — 리마인더를 보내려면 어차피 연락처가 필요
- [ ] **C. 정식 계정** — 로그인·비밀번호
- [ ] **D. 재진입 없음** — 한 세션 안에서 끝 (①-B와 짝)

딸린 질문

## ③ 절차 KB를 DB에 넣습니까, 파일로 둡니까

KB는 **출처·시행일 메타를 갖는 버전드 데이터**이고, 운영 파이프라인(사람 검수)으로만 갱신됩니다.
사건 데이터와 성격이 완전히 다릅니다.

- [ ] **A. 저장소의 파일** — JSON을 git으로 버전 관리. 릴리스 = 커밋·배포
- [ ] **B. DB 테이블** — 사건 DB와 같은 곳. 검수 UI를 붙이기 쉬움
- [ ] **C. 파일이 정본 + 런타임엔 적재** — git이 정본, 기동 시 읽어 인덱싱
