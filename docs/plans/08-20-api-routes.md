### 미설정을 어느 코드로 내나

**새 `code` 를 지어내지 않았습니다.** 정본의 코드 표에 미설정용이 없어
`INTERNAL`·500·재시도 없음 그대로입니다.

**503 을 쓰지 않은 이유**는 `Retry-After: 10` 이 붙어 사용자가 10초마다
헛되이 다시 누르고, `retry-checker` 가 20초 예산을 태우기 때문입니다.
「있는데 지금 안 된다」와 「아직 없다」는 다른 사건입니다.

### 타입이 실제로 안 맞던 자리 셋

`tsc` 로 직접 확인했습니다 (2026-08-20). 무보정 주입이면 셋 다 깨집니다.

| 자리 | 왜 |
| --- | --- |
| `audit-logger` → `case-purger` | 한쪽은 기록을 돌려주고 받는 쪽은 안 받습니다 |
| `retry-checker` → `chat-receiver` | `error`·`lane` 의 넓이가 **서로 반대**입니다 |
| `kb-finder` → `chat-receiver` | 표는 `title`·JSONB, 프롬프트는 `label`·문자열 |

전부 [`lib/adapters.ts`](../../src/lib/adapters.ts) 에 **손으로 쓴** 어댑터를 뒀습니다.
자동 변환을 안 쓰는 이유는 **내보내면 안 되는 필드가 같이 실려 나가기** 때문입니다
(저장소 내부 경로 · 원문 개인정보 · 평문 이메일).

모든 요청이 지나는 길목이라 터지게 두면 서비스 전체가 500 이 됩니다. §1.3 의
*"제한이 정상 사용을 막으면 안 됩니다"* 의 가장 심한 형태입니다. 문진 문구와 같은
예외로 두고, **못 하는 일은 설정 현황에 드러냅니다.**

### 4단계 검토에서 실제로 고친 것

네 갈래로 대조하고 지적마다 반증해 **27건 중 8건**이 남았습니다. 라우트를 쓸 때
같은 실수를 반복하지 않도록 남깁니다.

| 무엇이 틀렸었나 | 왜 위험했나 |
| --- | --- |
| `EGRESS_BLOCKED` 응답이 `X-Pii-Egress-Residual: 0` | 잔여 때문에 막은 응답이 「잔여 0건」이라고 증언했습니다. §6 (1) 이 `1` 을 못 박은 자리입니다. 던지는 쪽은 건수를 `detail.counts` 에만 싣습니다 |
| 창 없는 429 에 `Retry-After: 1` | 정본에 없는 값입니다. 증거 상한은 기다려도 안 풀리는데 1초마다 다시 누르게 됩니다 |
| 메모리 카운터가 **삽입 순서로** 축출 | 창이 가장 긴 사건 생성 카운터(1시간)가 먼저 밀려나 §1.3 의 「IP당 시간당 20건」이 0으로 돌아갑니다. **먼저 끝나는 창부터** 버리게 고쳤습니다 |
| 세션 키와 IP 대체 키가 같은 이름 공간 | `X-Session-Id: ip:1.2.3.4` 를 보내면 그 주소 뒤 사람들의 통을 대신 태울 수 있었습니다. 접두사(`s:`·`ip:`)로 갈랐습니다 |

`ADMIN_PASSWORD_HASH` 가 어떤 해시인지(알고리즘·솔트·표기)가 정본에 없습니다.

**관리자가 영영 못 들어옵니다.** 해시 형식이 정해진 뒤에 붙입니다.

### 5단계 검토에서 실제로 고친 것

세 갈래(우회 가능성·정본 대조·Next 정확성)로 대조하고 지적마다 반증해
**16건 중 11건**이 남았습니다. 겹치는 것을 묶으면 일곱입니다. **둘은 실제 서버에서
재현됐습니다** — 라우트를 쓰기 전에 잡아서 다행인 것들입니다.

| 무엇이 틀렸었나 | 왜 위험했나 |
| --- | --- |
| **뒤 슬래시 한 칸** — 문지기가 `/api/admin/` 로 시작하는지만 봤습니다 | Next 의 경로 패턴 `/api/admin/:path*` 는 **뒤 슬래시가 없는 `/api/admin` 도 덮습니다.** 그래서 `app/api/admin/route.ts` 를 만들면 그 한 경로만 인증 없이 열립니다. 두 관문이 같은 자리에서 함께 비껴갔습니다. 실제 서버에서 200 으로 통과하는 것을 확인했습니다 |
| **계측 헤더가 전송 중에 사라짐** | 빈 문자열로 「없음」을 표기했는데, Next 가 문지기 응답의 헤더를 옮길 때 `if (value)` 로 걸러 **셋이 통째로 버려졌습니다**. §1.1 이 문지기가 낸 401 에서만 안 지켜지고 있었습니다 |
| **서명 비교가 던짐** | `timingSafeEqual` 은 **바이트** 길이가 다르면 예외를 던지는데 글자 수로 쟀습니다. `é` 한 글자가 2바이트라 「글자 수는 같은데 바이트 수는 다른」 쿠키 한 줄로 401 대신 500 이 났습니다 |
| **쿠키 디코딩이 던짐** | `decodeURIComponent('%')` 가 예외를 던집니다. 인증 없는 요청 한 줄로 §5.1(401)·§1.1(계측 헤더)·§1.4(에러 봉투)를 한꺼번에 어길 수 있었습니다 |
| **같은 이름 쿠키 밀어내기** | 앞의 것 하나만 봐서, 가짜를 앞에 끼우면 진짜 관리자가 로그인해도 계속 401 을 받았습니다. 권한은 안 올라가지만 조사가 막힙니다 |
| 설정 현황의 크론 설명이 **정반대** | 5단계가 동작을 뒤집었는데(밖에서 부를 수 있음 → 전부 막힘) 설명이 그대로였습니다. 운영자가 파기가 멈춘 원인을 못 찾습니다 |
| 401 문구를 두 곳이 다른 자리에서 얻음 | 코드 표에 `UNAUTHORIZED` 행이 생기면 같은 코드의 응답 둘이 서로 다른 문장을 말합니다 |

**막은 방법:** 경로 판단을 [`lib/gated-paths.ts`](../../src/lib/gated-paths.ts) 한 곳으로
모아 문지기·요청 껍데기·Next 의 경로 패턴 셋이 같은 집합을 가리키게 했고,
서명은 양쪽을 한 번 더 해시해 길이를 맞춰 비교하며, 문지기 본문 전체를 감싸
**어떤 예외든 401 로 떨어지게** 했습니다.

### 6단계에서 드러난 것 — 500 의 이유가 아무 데도 안 남았습니다

실제 서버에 붙여 보고 찾았습니다. 안 붙은 자원을 부르면 `not-configured.ts` 가
「무엇이 · 어느 환경변수 때문에」를 담아 던지는데, **그 말을 아무도 못 들었습니다.**
껍데기가 잡아 응답으로 바꾸고 끝냈고, `detail` 이 가는 감사 로그도 아직 안 붙어
있기 때문입니다.

요청 껍데기가 **5xx 만** 서버 로그에 남깁니다. 400·401·429 는 정상적으로 오가는
요청이라 남기면 로그가 그것으로 덮이고, 밖에서 일부러 틀린 요청을 반복해 로그를
채울 수 있습니다.

```
[POST /api/cases] INTERNAL: CaseStore 이(가) 아직 설정되지 않았습니다: createCase
  { port: 'CaseStore', member: 'createCase', missingEnv: [ 'DATABASE_URL' ] }
```

### 6단계 검토에서 실제로 고친 것

세 갈래(계약 대조·흐름과 모듈 계약·실제로 도는가)로 대조하고 지적마다 반증해
**17건 중 7건**이 남았습니다. 겹치는 것을 묶으면 여섯입니다.

| 무엇이 틀렸었나 | 왜 위험했나 |
| --- | --- |
| **본문이 `null` 이면 500** | `null` 은 JSON 으로 유효해 파싱을 통과하는데, 그걸 객체로 알고 칸을 읽으면 터집니다. 잘못된 요청인데 서버 잘못으로 보이고, **그 500 이 운영자 로그에 쌓여 밖에서 본문 한 글자로 로그를 채울 수 있었습니다.** `readJsonObject` 를 만들어 열두 라우트가 같은 자리를 쓰게 했습니다 |
| **가짜 저장소가 포트 계약을 어김** | 시험의 대역이 `upsert` 만 돌려줘, DB 구현자가 그걸 본뜨면 **재생성할 때마다 완료·미확인 단계가 플랜에서 통째로 사라집니다** — §6.1 이 막으려던 바로 그 파손인데 시험은 초록이었습니다. 대역이 계약을 지키게 하고, 사라지면 걸리는 시험을 더했습니다 |
| **응답 칸 시험이 겉만 봄** | 최상위 다섯 칸만 못 박아 `steps[]` 의 칸이 §3.1 과 달라져도 통과했습니다. 단계와 근거의 칸 집합을 못 박았습니다 |
| 주석 둘이 사실과 다름 | 감사 식별자가 계측 헤더에 실린다고 적었는데 안 실립니다(먼저 남은 것이 헤더를 차지). `date-checker` 를 안 쓰는 이유도 틀렸습니다 — 그 모듈엔 오늘을 내주는 메서드가 애초에 없습니다 |

### ⬜ 안 고치고 밝혀 둔 것 — 사건은 저장됐는데 플랜이 실패하면

`caseIntake.open()` 이 돌아온 시점에 **사건 행은 이미 커밋돼 있습니다.** 그 뒤
플랜 만들기가 실패하면 에러 응답이 나가는데, **에러 봉투에 `case_id` 를 담을 칸이
없어**(§3) 사용자가 방금 만들어진 자기 사건으로 돌아갈 수 없습니다.

지금은 저장소가 하나도 안 붙어 있어 `open()` 이 먼저 멈추므로 안 일어납니다.
**DB 만 붙고 KB 릴리스가 미결인 다음 단계에서 드러납니다** — 진입할 때마다 빈
사건이 쌓이고 사건 생성 상한(IP당 시간당 20건)까지 소진됩니다.

**되돌리는 코드를 지어내지 않았습니다.** 정본이 부분 실패를 정하지 않았고
`CaseStore` 에 사건을 지우는 자리도 없습니다. 답이 셋인데 셋 다 사용자에게 하는
약속이 달라 사람이 정해야 합니다.

| 답 | 무엇이 달라지나 |
| --- | --- |
| ① 순서를 바꿔 플랜을 먼저 만든다 | 식별자를 미리 발급해야 하고, `case-intake` 가 저장까지 하는 지금 모양이 바뀝니다 |
| ② 실패하면 사건을 지운다 | `CaseStore` 에 삭제가 생깁니다. 감사 기록(`case.opened`)과 어긋납니다 |
| ③ 플랜 없이 201 을 내고 화면이 다시 부른다 | §3.1 의 「사건을 만드는 즉시 T0 가 붙습니다」를 못 지킵니다 |

### ~~② 개인정보 쓰기 경로가 경계를 우회합니다~~ — ✅ **2026-08-21 계약 확정**

`PATCH /slots` 와 `POST /artifacts` 가 「클라이언트가 이미 토큰화했다」를 믿고

> **→ [ADR-040](../../decisions/040-write-path-boundary.md) 으로 정했습니다. 다만 한 가지가 다릅니다.**

> **「토큰화에 통과」가 아니라 「검사하고 거부」입니다.** 서버가 대신 토큰화하면 매핑을

> **브라우저가 모르는 토큰이라 복원이 안 돼 그 슬롯이 영영 빈칸**이 됩니다.

>

> 순수 함수라(브라우저 API 0개) **서버에서 그대로 돕니다.** `pii-tokenizer` 가 그것을
> import 해서 1차 게이트를 먼저 세우고, NER 이 붙으면 같은 자리에 2차를 더합니다.
> **패턴을 복사하지 마세요** — 두 곳에 두면 어긋난 쪽이 조용히 새는 쪽이 됩니다.

- `unlocked_steps` · `referenced_steps` · `referenced_deadlines` 세 배열이 계약 예시에
  있는데 「주인이 없다」로 빠졌습니다
- 모든 슬롯을 「모름」으로 답한 사용자가 근거 부족 턴을 만나면 **갈래가 없습니다** —
  `citation-checker` 는 물을 슬롯이 있는지 안 보는데 `chat-publisher` 는 질문을 필수로 받습니다
