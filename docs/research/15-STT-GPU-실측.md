# STT GPU 실측 — 22배, 그리고 배치는 GPU 에서만 산다

> 2026-08-25 측정. 측정 원본은 [assets/datasets/08-25-stt-gpu/](../../assets/datasets/08-25-stt-gpu/),
> 하네스는 [services/transcriber/bench_stt.py](../../services/transcriber/bench_stt.py) 입니다.
>
> [14](14-STT-전처리-실측.md) 가 답하지 못하고 남긴 물음 — 「GPU 에서 얼마나 빨라지나」 —
> 를 잰 것입니다. 평가셋도 하네스도 그대로라 **14 의 표와 바로 이어 읽힙니다.**
>
> **사람이 보는 요약**은 [assets/artifacts/research/08-25-stt-benchmark.html](../../assets/artifacts/research/08-25-stt-benchmark.html)
> 입니다(사본). **고른 것과 탈락시킨 이유**는 [ADR-052](../../decisions/052-stt-configuration.md).

## 결론 — 넷

**① 장치만 바꿔도 22배입니다.** 같은 모델·같은 설정으로 719.2초 → 33.3초.
품질 지표는 **한 자리도 안 움직였습니다**(PII 손상 11/33 동일).

**② 모델은 `large-v3` 입니다.** GPU 에서는 `medium` 을 쓸 이유가 없습니다 —
같은 시간에 **절반 이하로 잃습니다**(PII 11 → 5, keep 21 → 11).

**③ 배치는 6배를 법니다 — 단 긴 녹음에서만, 그리고 VAD 가 필수입니다.**
14 §3 이 「CPU 에서 이득 없음」이라 한 것을 GPU 가 뒤집습니다. 다만 조건이 둘 붙습니다.

**④ 모델을 좋게 하면 「자리표기 변형」이 두 배가 되는데, 경계는 그걸 이미 막고
있었습니다 — 한 곳만 빼고.** `medium` 2건 → `large-v3` 4건입니다. 값이 사라지는
것보다 나쁜 상태인데, `pii-tokenizer` 의 숫자 규칙이 **늘어난 몫까지 잡습니다.**
새던 한 곳은 이음 거리(`gapJoin`)가 `마이너스` 를 못 건너서였고, 5 → 8 로 넓혀
**누출 0 · 과차단 0** 이 됐습니다 → §6 · [ADR-052](../../decisions/052-stt-configuration.md).

권고 한 줄로는 이렇습니다.

```
large-v3 · float16 · batch_size=16 · vad_filter=True · word_timestamps=True
  + DEFAULT_DIGIT_RULE.gapJoin 5 -> 8
  -> 6.8분 통화를 7.6초에 (실시간 0.019배) · 숫자류 누출 0건 · 과차단 0건
```

## 1. 잰 것

```
RunPod 커뮤니티 · RTX 4090 24GB · 드라이버 570.133.20 · $0.34/시간
faster-whisper 1.2.1 · CTranslate2 4.8.1 · compute_type=float16
평가셋은 09·10 의 것 그대로 — 40발화 · pii 33건 · keep 80건 · 합계 6.8분
```

**`float16` 을 씁니다.** `int8` 은 CPU 에서 메모리를 아끼려던 선택이라, 연산이
남아도는 GPU 에서 굳이 정확도를 깎을 이유가 없습니다.

## 2. GPU 로 옮긴 몫 — 조건 `E` 가 다리입니다

발화 40개를 **하나씩** 옮긴 것입니다(14 §1 과 같은 방식).

| | 장치 | 모델 | 벽시계 | 실시간 | PII 손상 | keep 손상 |
| --- | --- | --- | --- | --- | --- | --- |
| `A` | cpu · int8 | medium | 719.2초 | 1.77배 | 11/33 | 20/80 |
| `E` | cuda · fp16 | medium | **33.3초** | 0.082배 | **11/33** | 21/80 |
| `F` | cuda · fp16 | medium | 26.6초 | 0.066배 | 10/33 | 21/80 |
| `G` | cuda · fp16 | large-v3-turbo | 16.6초 | 0.041배 | 7/33 | 15/80 |
| `H` | cuda · fp16 | large-v3 | 32.2초 | 0.079배 | **5/33** | **11/80** |

`A` 는 14 에서 옮겨 온 CPU 기준선입니다. `E` 는 **모델·빔·무음이 `A` 와 같고
장치만 다릅니다** — 그래서 719.2 → 33.3초는 온전히 GPU 의 몫입니다.

**PII 손상이 11/33 로 정확히 같습니다.** 장치를 바꿔도 품질이 안 움직인다는 뜻이고,
동시에 이 측정이 14 와 같은 것을 재고 있다는 확인입니다.

### 걱정이 빗나갔습니다

`large-v3-turbo` 는 디코더를 32층에서 4층으로 줄인 모델이라 계좌번호 같은 긴
숫자열에서 문맥 유지가 약할까 봐 하네스에 경고를 달아 뒀었습니다. **반대였습니다** —
`medium` 보다 낫습니다(11 → 7).

그리고 `large-v3` 는 **`E` 와 같은 시간에**(32.2 vs 33.3초) 절반 이하로 잃습니다.
GPU 에서 `medium` 을 쓸 이유가 없어졌습니다.

> ⚠️ **`E` → `F` 의 25% 를 「배치 덕」으로 읽지 마세요.** 저 `batch=16` 은 실제로
> 배치가 아니었습니다 — 이유는 다음 절입니다. `F` 가 번 몫은 낱말 시각을 끈 것입니다.

## 3. 배치가 짧은 클립에서 아무 일도 안 한 이유

`faster_whisper/transcribe.py` 를 열어 확인했습니다.

```python
chunk_length = chunk_length or self.model.feature_extractor.chunk_length   # 30초
if not clip_timestamps:
    if vad_filter:
        clip_timestamps = get_speech_timestamps(audio, vad_parameters)
    # run the audio if it is less than 30 sec even without clip_timestamps
    elif duration < chunk_length:
        clip_timestamps = [{"start": 0, "end": audio.shape[0]}]
    else:
        raise RuntimeError(
            "No clip timestamps found. Set 'vad_filter' to True or provide 'clip_timestamps'.")
```

여기서 둘이 나옵니다.

**① 30초 미만이면 덩어리 하나로 처리하고 끝냅니다.** 우리 평가셋은 발화당 10초라
whisper 창(30초) 하나도 못 채웁니다. `batch_size=16` 을 줘도 **묶을 게 없습니다.**

**② 배치에는 VAD 가 필수입니다.** 무엇을 묶을지 정하는 것이 VAD 라, 30초를 넘는
파일에 `vad_filter=False` 를 주면 위 `RuntimeError` 로 **거절합니다.**
「배치는 켜고 VAD 는 끈다」는 선택지가 **아예 없습니다.**

그래서 14 §4 의 「VAD 는 속도로는 켤 이유가 없다」가 바뀝니다 — **배치의 전제
조건이므로 켭니다.** 0.4% 때문이 아니라 6배 때문입니다.

## 4. 그래서 긴 녹음 하나로 다시 쟀습니다

40개를 이어붙여 **6.8분짜리 하나**를 만들었습니다. 실제 통화 녹음의 모양입니다.
기준(`L1`)은 지금 서비스가 하는 그대로 — 배치 없음·VAD 없음·낱말 시각 켬 — 로 잡고,
하나씩 벗겨 무엇이 값을 버는지 갈랐습니다.

| | `large-v3` | | | `large-v3-turbo` | | |
| --- | --- | --- | --- | --- | --- | --- |
| | 벽시계 | PII | keep | 벽시계 | PII | keep |
| `L1` 기준(배치✗ VAD✗ 낱말✓) | 30.7초 | 7/33 | 29/80 | 10.3초 | 9/33 | 13/80 |
| `L2` 낱말 시각만 끔 | 42.4초 | 8/33 | 25/80 | 10.1초 | 9/33 | 12/80 |
| `L3` VAD 켬 | 45.1초 | 8/33 | 25/80 | 12.0초 | 9/33 | 12/80 |
| `L4` 배치 8 | 9.6초 | 8/33 | 13/80 | 5.7초 | 12/33 | 13/80 |
| `L5` 배치 16 | **7.6초** | 8/33 | **13/80** | 6.2초 | **12/33** | 13/80 |
| `L6` 배치 32 | 7.6초 | 8/33 | 13/80 | 5.9초 | 12/33 | 13/80 |

**`large-v3` 는 배치로 4배를 법니다**(30.7 → 7.6초). VAD 를 고정하고 보면
`L3` → `L5` 가 **5.9배**입니다 — 이쪽이 배치만의 몫입니다.

**`L6` 이 `L5` 와 같습니다.** 32 로 올려도 더 안 벌립니다. 16 에서 이미 GPU 가 찹니다.

### turbo 는 배치에서 무너집니다

배치 없이는 `turbo` 가 좋아 보였는데(`L1` 10.3초 · PII 9), 배치를 켜면 **PII 손상이
9 → 12 로 늘어납니다.** 전사문 글자 수도 2,274 → 1,973 으로 13% 줄었습니다 —
**줄어든 몫이 우리가 지켜야 할 값이었습니다.**

`large-v3` 도 글자가 줄지만(2,412 → 2,230) 그쪽은 잃은 게 아니라 **환각이 준
것**으로 보입니다. `keep` 손상이 29 → 13 으로 **오히려 좋아졌습니다.**

**이것이 벤치마크 숫자가 아니라 이 채점으로 골라야 하는 이유입니다.** 평균 WER 로는
`turbo` 가 이겼을 자리입니다.

## 5. 낱말 시각을 켰더니 더 빨랐습니다

반직관이라 **세 번씩 다시 쟀습니다**(`large-v3` · 긴 녹음).

| | 세 번 | 평균 | 폭 |
| --- | --- | --- | --- |
| `L1` 낱말 시각 켬 | 29.1 · 29.0 · 31.7초 | 29.9초 | 2.7초 |
| `L2` 낱말 시각 끔 | 39.9 · 37.4 · 50.9초 | **42.7초** | **13.5초** |
| `L5` 배치 16 | 8.3 · 7.9 · 7.9초 | 8.0초 | 0.4초 |

재현됩니다. 끄면 **느리고 들쭉날쭉합니다**(폭 13.5초). 정렬이 붙는 비용보다,
껐을 때 whisper 가 반복에 빠져 오래 도는 쪽이 컸던 것으로 보입니다 — 폭이 큰 것이
그 흔적입니다.

**배치에서는 공짜입니다.** 실제로 붙일 조합을 따로 쟀습니다.

| | 세 번 | 평균 | PII | keep |
| --- | --- | --- | --- | --- |
| 배치 16 · 낱말 시각 끔 | 9.1 · 7.6 · 7.4초 | 8.0초 | 8/33 | 13/80 |
| 배치 16 · 낱말 시각 **켬** | 7.4 · 7.7 · 7.8초 | **7.6초** | 8/33 | 13/80 |

**켜도 안 느려지고 품질도 같습니다.** 모듈 계약의 `pieces` 가 낱말 시각을
요구하므로 이건 그냥 켜면 됩니다.

## 6. 모델을 좋게 하면 위험이 옮겨 갑니다 — 「자리표기 변형」

여기까지의 「PII 손상」은 **값이 살아남았나**만 셌습니다. 그런데 못 살아남은 것들을
열어 보니 **성격이 둘로 갈립니다.**

```
소실        전사문에 없다.        화면에서 빈칸으로 보이니 사용자가 고칩니다 (ADR-038)
자리표기 변형  값이 있는데 모양이 다르다.  아무도 이상함을 못 느낍니다
```

whisper 가 하이픈 낀 숫자를 **날짜로 정규화**합니다.

```
3333-01-2345678  ->  "3333년 1월 23일 45678"
7777-01-9988776  ->  "7777년 1월 마이너스 9988776"
3333-05-1122334  ->  "3333년 5월 11일 이만 2334"
880312-2345678   ->  "88만 312-2345678"
```

**이게 왜 소실보다 나쁜가.** 소실은 사용자가 confirm 화면에서 채웁니다. 변형은
**그럴듯한 텍스트로 남아 있어** 확인 화면에서도 안 걸립니다. 그런데 그 값은
계좌번호이고, `pii-tokenizer` 의 정규식·LLM 이 날짜로 읽고 지나치면 **원문 계좌번호가
그대로 외부 LLM 으로 나갑니다** — [불변 규칙 2](../../CLAUDE.md) 위반입니다.

[09 §5.4](09-로컬모델-PII인식-실측.md) 가 「전사문에서는 정규식이 6\~10건밖에 못
잡는다」고 한 것이 바로 이 자리입니다.

### 세어 보면 이렇습니다

`pii` 33건을 셋으로 갈랐습니다.

| | 모델 | 보존 | **자리표기 변형** | 소실 | 되돌린 뒤 |
| --- | --- | ---: | ---: | ---: | ---: |
| `A`·`E` | medium | 22 | **2** | 9 | 24/33 (72.7%) |
| `G` | large-v3-turbo | 26 | **4** | 3 | 30/33 (90.9%) |
| `H` | large-v3 | 28 | **4** | 1 | **32/33 (97.0%)** |

**모델을 좋게 하니 변형이 2 → 4 로 늘었습니다.** `medium` 이 아예 못 듣던 계좌번호를
`large-v3` 는 듣고 **날짜로 적습니다.** 소실이 변형으로 옮겨 간 것이고, 위험한 쪽으로
옮겨 간 것입니다.

**그래서 모델만 보고 판단하면 안 됩니다.** 놓치는 값은 줄지만 위험한 형태가 늘어나니,
경계 쪽이 그걸 감당하는지 함께 봐야 합니다 — 아래에서 실제로 쟀습니다.

### 그래서 실제로 새나 — 재 봤습니다

**형태만 보고 「위험하다」고 말할 뻔했습니다.** `pii-tokenizer/transcript-digits.ts`
가 이미 이 문제를 다루고 있었습니다. 그것도 더 나은 방식으로 — 되돌려서 알아보는 게
아니라 **기본값을 가리는 쪽으로 뒤집어**, 안전한 형태로 확인된 것만 통과시킵니다
([ADR-011](../../decisions/011-pii-boundary-hardening.md)). 그 파일 주석은
`"3333년 5월 11일 임한 2334로"` 를 **예로 이미 적어 두고** 있었습니다.

그래서 물음이 바뀝니다 — **「무엇을 새로 만들까」가 아니라 「있는 것이 늘어난 몫까지
버티나」.** 저장된 전사문 40발화를 그대로 넣고, **가리고 남은 글에 정체불명 숫자가
있는지**로 셌습니다.

| 전사 | `gapJoin` 5 (기존) | **`gapJoin` 8** | 과차단 |
| --- | ---: | ---: | ---: |
| `A` medium · CPU | 2건 | 1건 | 0건 |
| `E` medium · GPU | 2건 | **0건** | 0건 |
| `G` large-v3-turbo | 1건 | **0건** | 0건 |
| `H` large-v3 | 1건 | **0건** | 0건 |

**버팁니다 — 한 곳만 빼고.**

```
7777-01-9988776  ->  "7777년 1월 마이너스 9988776"
                             └── "월 마이너스 " = 7자 > 5
```

규칙에는 「단위가 붙었어도 바로 뒤에 정체불명 숫자가 이어지면 안전을 거두는」 장치가
있는데, **보는 거리가 5자**였습니다. 전사가 하이픈을 `마이너스` 로 읽으면 못 건넙니다.
안전이 안 거둬지니 `9988776` 이 홀로 남고, 7자리는 최소 자릿수(9) 미만이라 안
가려집니다 — **계좌번호 뒷자리 7개가 그대로 나갔습니다.**

**8 로 넓히면 잡히고 과차단은 그대로 0 입니다.** 10·12 도 같아 8 이 하한입니다.

`A` 에 남는 1건은 성격이 다릅니다 — `5501234567` 이 `"501-34567"` 로 읽혀 **8자리만
남은** 것이라 최소 자릿수 아래로 떨어집니다. 값이 샌 게 아니라 전사가 깨진 것이고,
`large-v3` 에서는 사라집니다. **전사를 좋게 하는 것이 숫자 규칙의 누출도 줄입니다** —
[09 §5.4](09-로컬모델-PII인식-실측.md) 의 「전사 개선은 누출 대책이 아니다」에
**숫자 규칙 쪽에서는 조금 다르다**는 단서가 붙습니다.

> ⚠️ **판정 기준이 함정입니다.** 「가려진 숫자가 원래 값과 같은가」로 세면 안 됩니다 —
> 자리표기가 깨졌으니 애초에 다릅니다. 그렇게 세면 **가려진 것을 누출로 오인합니다**
> (처음에 실제로 그렇게 셌고, 남은 글을 눈으로 보고서야 알았습니다).
> 그리고 **남아 있어야 맞는 숫자**를 빼야 합니다 — 대표번호·금액·일시·사원번호는
> 제외 목록입니다.

회귀는 `src/modules/pii-tokenizer/transcript-digits.leak.test.ts` 가 지킵니다.

### 그래서 「되돌리기」는 안 씁니다

`notation.py` 는 위 표(보존·변형·소실)를 만든 **분석 도구로만** 남깁니다.
토큰화 앞에 붙이지 않습니다 — 되돌리기는 「알아본 것만 가린다」로 되돌아가는 셈이라
[ADR-011](../../decisions/011-pii-boundary-hardening.md) 과 어긋납니다.

| GPU 로 이전 | ✅ **22배.** 품질은 그대로. [ADR-043](../../decisions/043-gpu-hosting.md) 의 판단이 숫자로 확인됐습니다 |
| `large-v3` | ✅ `medium` 과 **같은 시간에** 절반 이하로 잃습니다 |
| `large-v3-turbo` | ✗ 배치 없이는 좋지만 **배치에서 PII 9 → 12 로 무너집니다.** 우리 채점으로 탈락 |
| `batch_size=16` | ✅ 긴 녹음에서 **4배**(VAD 고정 시 5.9배). 32 는 더 안 벌립니다 |
| `vad_filter=True` | ✅ **이제 켤 이유가 생겼습니다** — 배치의 전제 조건입니다 |
| `word_timestamps=True` | ✅ 켜 두세요. 배치에서 공짜이고, 배치 없이는 **끄는 쪽이 더 느립니다** |
| `beam_size` 5 → 1 | ✗ 14 §4 그대로 — 개인정보를 더 잃습니다 |
| **`gapJoin` 5 → 8** | ✅ **경계의 값입니다.** 전사가 하이픈을 `마이너스` 로 읽으면 계좌 뒷자리 7개가 샜습니다. 넓히면 **누출 0 · 과차단 0** → §6 |
| 기관명 어휘 힌트 | △ **[17](17-기관명-사전-실측.md) 이 이어서 쟀습니다** — 사전이 있으면 회수되는데 8유형 중 2유형만 있습니다. `keep` 손상 중 기관명이 19% 인데 모델을 바꿔도 28% → 19% 뿐입니다. 엔진이 `vocabulary → initial_prompt` 를 이미 받고 있어 붙일 자리는 있습니다 |

**6.8분 통화가 7.6초입니다.** 14 §4 가 「사용자가 지금 막혀 있지는 않다」고 한
전제는 그대로지만, 이제 **폴링을 기다릴 일이 사실상 없습니다.**

그런데 **속도가 이 실측의 결론은 아닙니다.** 22배는 켜기만 하면 되는 것이고,
정작 손이 간 것은 §6 의 이음 거리 한 줄입니다 — 그쪽이 경계를 지킵니다.

## 8. 이 실측이 답하지 못한 것

- **이름은 재다 말았습니다.** §6 의 측정은 숫자류만입니다 — 숫자 규칙이 이름을
  안 잡기 때문입니다(형태가 없어 `NerModel` 몫). 그래서 `gemma3:4b` 로 따로
  돌려 봤고([ner_probe.py](../../assets/datasets/08-25-stt-gpu/ner_probe.py)),
  **누출은 두 조건 다 0% 였습니다.**

  | | 이름 생존 | 누출 |
  | --- | ---: | ---: |
  | `E` medium | 11/13 | **0 (0.0%)** |
  | `H` large-v3 | **13/13** | **0 (0.0%)** |

  `large-v3` 는 이름을 하나도 안 깨뜨렸고, 그 13개를 탐지기가 전부 잡았습니다 —
  **지켜야 할 이름이 더 많이 살아남은 채로 다 잡혔습니다.**

  ⚠️ **과차단은 못 정했습니다.** 같은 프롬프트·같은 입력을 **다른 실행**에서 넣으면
  답이 달라집니다(`temperature=0 · seed=7` 인데도). 한 프로세스 안에서 연달아
  부르면 3회 모두 같으니 흔들림은 프로세스 간에 있습니다. 그래서 과차단 건수를
  조건끼리 비교할 수 없습니다 — **반복 측정 전에는 그 숫자를 인용하지 마세요.**
  누출 0 은 두 실행 모두 0 이라 그나마 견고합니다.

  이 흔들림을 더 파지 않은 이유는 **과차단이 회수 가능한 사고**이기 때문입니다 —
  가려진 것은 경계 안쪽에서 사용자에게 보여주고 되돌릴 수 있지만, 누출은 이미
  넘어간 것이라 닿지 않습니다 ([ADR-038](../../decisions/038-transcript-confirm.md)).
- **`gapJoin` 8 이 옳은 값이라는 근거는 없습니다.** 이 평가셋에서 10·12 와 결과가
  같아 하한으로 고른 것입니다. 실제 통화에는 `마이너스` 보다 긴 삽입이 있을 수
  있습니다.
- **긴 녹음의 채점은 발화별 채점과 절대값을 견줄 수 없습니다.** §4 는 이어붙인
  전사문 **전체**에 값이 남아 있는지로 셉니다 — 다른 발화 자리에서 우연히 맞아도
  삽니다. **§4 안에서 조건끼리는 비교되지만, §2 의 표와 나란히 놓지 마세요.**
- **이어붙인 음성은 실제 통화가 아닙니다.** 서로 무관한 40발화를 붙인 것이라
  whisper 가 앞 창의 결과를 다음 창의 문맥으로 쓰는 대목에서 실제 통화와 다르게
  움직일 수 있습니다. 그래서 `L1` 의 `keep` 손상(29/80)이 §2 보다 큽니다.
- **여전히 합성음입니다.** 실제 통화의 말겹침·끊김은 재현하지 못했습니다
  ([ADR-043](../../decisions/043-gpu-hosting.md) — 합성 데이터만 올립니다).
- **RTX 4090 한 장에서만 쟀습니다.** 실제로 어느 GPU 를 빌릴지는
  [13](13-GPU-클라우드-단가.md) 의 단가와 함께 봐야 합니다.
- **배치가 `keep` 을 왜 좋게 만들었나** — 29 → 13 은 큰 차이인데, 환각이 준
  것이라는 해석은 글자 수 감소에서 미뤄 짚은 것이지 직접 확인한 것이 아닙니다.
