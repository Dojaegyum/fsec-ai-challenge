# 11 · 로컬 OCR PII 인식 실측

2026-08-21, **증거 화면(이체내역·문자 캡처)에서 로컬 OCR 이 무엇을 흘리는지**를 처음 쟀습니다.
[09](09-로컬모델-PII인식-실측.md)가 STT 를 잰 것의 짝입니다 — 같은 채점 규칙에 **지표 둘을 더** 붙였습니다.

## 먼저 결론 넷

1. **OCR 은 숫자를 거의 안 흘립니다.** 리터럴 생존률 96.6\~100% — STT 의 5\~65%와 정반대입니다.
   **계좌번호는 화면에서 읽는 게 압도적으로 낫습니다** → §3.1
2. **대신 한글이 깨집니다.** Tesseract 는 한글을 낱자로 쪼개고(`국민은행` → `국 민 은 행`),
   EasyOCR 은 라벨을 오독합니다(`받는 분` → `본는 분`) → §4
3. **깨지는 방식이 달라 고치는 법도 다릅니다.** 후처리 한 줄씩이 결정적입니다 —
   Tesseract 는 **공백 복원**으로 누출 32.4%→14.7%, EasyOCR 은 **좌표로 행 복원**으로 짝유지가 살아납니다 → §5
4. **최적 구성의 누출률은 5.7%** (EasyOCR+좌표복원 + 정규식 + gemma3:4b + 허용목록).
   STT 최적(9.1%)보다 낫습니다 → §3

⚠️ **합성 화면 기준입니다.** 실제 은행 앱은 글꼴·자간·배경이 달라 결과가 달라집니다 → §2.4

---

> **속도는 [16](16-OCR-GPU-실측.md) 이 GPU 에서 다시 쟀습니다** — 장치만 바꿔 37배이고,
> 이 문서의 결론 ①·②(숫자는 살고 한글이 깨진다)가 그대로 재현됐습니다.

## 1. 왜 쟀나

[09](09-로컬모델-PII인식-실측.md)는 STT 만 재고 **OCR 을 범위 밖으로 뒀습니다**(그 문서 §7 P-06).
그런데 OCR 은 빼놓을 자리가 아닙니다.

- **이체내역 캡처가 `slot-extractor` 의 주 입력**입니다 → [슬롯 티어링](../../spec/backend/08-14-slot-tiering.md)
  *"T2는 증거 자동 추출이 우선"* — 그 증거가 대개 화면 캡처입니다.
- **OCR 도 `pii-tokenizer` 이전 단계**입니다 → [ARCHITECTURE](../../ARCHITECTURE.md) §6 의 ⚠️ 와 같은 자리.
- **깨지는 방식이 STT 와 다릅니다.** 09 의 결론을 그대로 옮겨 쓸 수 없습니다.

## 2. 어떻게 쟀나

### 2.1 평가셋 — 증거 화면 20장

합성 화면 20장. [경유 서비스 8유형](../../spec/backend/08-14-channel-matrix.md)에서 실제로 나오는
증거 종류를 덮습니다 — 이체 완료 화면 · 통장 거래내역 · 간편송금 내역 · 증권 출금 ·
가상자산 출금 · 상품권 핀 문자 · 소액결제 문자 · 기관 사칭 문자.

| 라벨 | 건수 | 뜻 |
| --- | ---: | --- |
| `fields` | 81 | **라벨-값 쌍** (`받는 분 = 김도현`). 문자 화면 12건을 뺀 **69건**이 짝짓기 채점 대상 |
| `pii` | 36 | 반드시 토큰화돼야 하는 값 — 이름 16 · 계좌 14 · 전화 5 · 주민번호 1 |
| `keep` | 70 | 절대 토큰화하면 안 되는 값 — 기관 26 · 금액 19 · 일시 15 · 대표번호 6 · 상품권사 2 · 통신사 2 |

> ⚠️ **계좌·주민번호·전화·이름·핀번호는 전부 실존하지 않는 임의값입니다.**
> 화면 디자인도 실제 앱을 모사하지 않은 일반형입니다.

### 2.2 지표 — STT 것에 둘을 더했습니다

전사문은 한 줄이라 「값이 살아남았나」만 보면 됐습니다. **화면은 2차원입니다.**

| 지표 | 무엇 | 09 과 |
| --- | --- | --- |
| 누출 · 과차단 · 손상 | PII 36건과 분기입력 70건의 행방 | **같은 채점기** |
| **필드 짝짓기** | `받는 분 = 김도현` 이 **한 줄에** 붙어 있나 | **신설** |
| **자형 혼동** | `0↔O` `1↔l` `5↔S` `8↔B` 로 잘못 읽힌 숫자 | **신설** |

**값을 다 읽어도 어느 항목의 값인지 모르면 `slot-extractor` 가 죽습니다.** 그게 짝짓기 지표의 이유입니다.

### 2.3 열화 3단

| 조건 | 무엇 |
| --- | --- |
| `clean` | 화면 캡처 그대로 (PNG) |
| `lowres` | 긴 변 720px · JPEG q80 — 메신저를 한 번 거친 캡처 |
| `photo` | 2.4도 기울기 · 대각선 조명 · 블러 · JPEG q62 — **다른 폰으로 화면을 찍은 것** |

### 2.4 ⚠️ 한계 — 먼저 읽으세요

- **합성 화면입니다.** Pillow 로 맑은고딕을 써서 그렸습니다. 실제 은행 앱은 자체 글꼴·좁은 자간·
  컬러 배경을 쓰므로 **여기 숫자를 그대로 옮기면 안 됩니다.** 특히 Tesseract 의 한글 낱자 분리는
  글꼴에 민감합니다.
- **표본이 작습니다** — 화면 20장, PII 36건.
- **비전 모델은 부분 표본**(3장)입니다 — 장당 176\~240초라 전수를 못 돌렸습니다 → §6.
- **EasyOCR 의 열화 조건은 `clean` 만** 쟀습니다 — 장당 80\~95초.

*사전복구시* — 라벨이 **한 글자만** 틀린 경우를 사전으로 되돌린다고 가정한 짝유지율.
화면 라벨은 종류가 정해져 있어 실제로 되돌릴 수 있습니다 → §5.2.

### 3.1 숫자는 화면에서 읽는 게 압도적으로 낫습니다

| | 리터럴 생존률 |
| --- | ---: |
| STT · whisper base | 5\~10% |
| STT · whisper small | 30\~35% |
| STT · whisper medium | 60\~65% |
| **OCR · 전 엔진·전 조건** | **96.6\~100%** |

**계좌번호를 말로 듣는 것과 화면에서 읽는 것은 난이도가 다릅니다.**
`110-234-567890` 을 STT 는 "일일공에 234마이너스 56만 7,890" 으로 흘렸지만,
OCR 은 전 조건에서 그대로 읽었습니다.

**정규식 1차가 전사문에서는 무너졌지만(6\~10건) 화면에서는 살아납니다** — 계좌 12/14 · 전화 5/5.
[09 §5.4](09-로컬모델-PII인식-실측.md)의 「역할 역전」은 **STT 경로에 한정된 이야기**입니다.

### 3.2 그래서 남은 구멍도 STT 와 같습니다 — 이름

정규식만 썼을 때 누출 17건의 구성입니다.

| 종류 | 전체 | 차단 | 누출 | 손상 |
| --- | ---: | ---: | ---: | ---: |
| **이름** | 16 | **0** | **16** | 0 |
| 계좌 | 14 | 12 | 0 | 2 |
| 전화 | 5 | 5 | 0 | 0 |
| 주민번호 | 1 | 0 | 1 | 0 |

이름 16건이 통째로 누출입니다 — [09 §3.1](09-로컬모델-PII인식-실측.md)과 같은 그림이고,
같은 이유(정규식은 이름을 안 봅니다)입니다. 주민번호 1건은 OCR 이 줄을 바꿔 쪼갠 것입니다
(`880312-2345` / `678`).

## 4. 발견 ① — 한글이 깨지는 방식이 엔진마다 다릅니다

| 엔진 | 원문 `국민은행 · 받는 분 김도현` 을 이렇게 읽습니다 |
| --- | --- |
| **Tesseract** | `민 은 행` · `ge 분 김 도현` — **낱자로 쪼개고 공백을 넣습니다** |
| **EasyOCR** | `국민은행` · `본는 분` — 한글은 붙어 있고 **라벨을 오독**합니다 |
| **gemma3 비전** | `국민은행` · `분는 분` — 한글은 좋고 **라벨·값이 줄로 갈립니다** |

**이 차이가 실무 판단을 가릅니다.**

- Tesseract 의 낱자 분리는 **기관명 대조를 통째로 무너뜨립니다** — `국민은행` 이 `국 민 은 행` 이면
  8유형 분기의 입력이 사라집니다. 심하면 LLM 이 문장 자체를 못 알아봅니다
  (사칭 문자 한 건에서 gemma3:4b 가 `[]` 를 냈습니다).
- EasyOCR 의 라벨 오독은 **한 글자짜리**라 되돌릴 수 있습니다.

---

## 5. 발견 ② — 후처리 한 줄씩이 결정적입니다

STT 실측에서 「허용 목록을 코드로 걸어야 한다」가 나왔던 것과 같은 모양입니다.

### 5.1 Tesseract — 한글 낱자 공백 복원

낱자가 둘 이상 잇달을 때만 붙입니다(`받는 분` 처럼 원래 띄어 쓴 자리는 안 건드림).

| | 누출 | 과차단 |
| --- | ---: | ---: |
| 공백 복원 전 | 11 (32.4%) | 2 |
| **공백 복원 후** | **5 (14.7%)** | **0** |

### 5.2 EasyOCR — 좌표로 행 복원 + 라벨 사전

**EasyOCR 은 좌표를 이미 주는데, 흔히 쓰는 `detail=0` 호출이 그걸 버립니다.**
y 좌표로 묶고 x 순서로 이으면 원래 행이 돌아옵니다.

```
detail=0 (좌표 버림)          detail=1 + 행 복원
  김도현                        본는 분 김도현
  본는 분                       본는 계좌 신한은행 110-234-567890
  신한은행 110-234-567890       보랜 금액 8,500,000원
```

그러고도 짝유지가 63.8%인 이유는 **레이아웃이 아니라 라벨 오독**입니다 —
`받는 분`→`본는 분`, `보낸 금액`→`보랜 금액`. **한 글자만 틀립니다.**

**화면 라벨은 유한 집합입니다.** 사전으로 되돌린다고 가정하면 **63.8% → 94.2%** 입니다.

---

## 6. 발견 ③ — 예상했던 자형 혼동은 나오지 않았습니다

`0↔O` · `1↔l` · `5↔S` · `8↔B` 를 따로 집계했는데 **전 조건에서 0건**이었습니다.

**화면 캡처에서는 이 실패가 안 나옵니다.** 화면 글자는 인쇄물·스캔과 달리 픽셀이 또렷하고,
숫자가 놓인 자리도 문맥이 분명합니다. 종이 서류를 스캔·촬영하는 경로를 열면 다시 봐야 하지만,
**증거가 화면 캡처인 한 이건 걱정거리가 아닙니다.**

솔직한 부정 결과로 남깁니다 — 예측이 빗나갔고, 그래서 대비할 필요가 줄었습니다.

---

## 7. 발견 ④ — 열화가 거의 영향을 안 줍니다

| 조건 | 리터럴 | 짝유지 | 누출률 |
| --- | ---: | ---: | ---: |
| clean | 96.6% | 85.5% | 50.0% |
| lowres | 100.0% | 91.3% | 45.7% |
| photo | 98.3% | 91.3% | 51.4% |

**STT 는 모델 크기가 결정적이었지만(리터럴 5%→65%), OCR 은 화질이 거의 안 걸립니다.**
`lowres`·`photo` 가 `clean` 보다 나은 것은 **확대가 Tesseract 에 유리했기** 때문으로 보입니다 —
900px 원본이 이 엔진의 적정 크기보다 작았던 것입니다.

**피해자가 캡처를 카톡으로 돌려 보내거나 다른 폰으로 찍어 보내도 괜찮다**는 뜻입니다.
STT 쪽 걱정을 여기 옮겨 붙일 필요가 없습니다.

---

## 8. 속도 — 비전 모델은 지금 하드웨어에서 논외입니다

| 엔진 | 장당 소요 (CPU) | 배수 |
| --- | ---: | ---: |
| **Tesseract** | **약 3초** | 1× |
| EasyOCR | 80\~95초 | 약 30× |
| gemma3:4b 비전 | **176\~240초** | 약 70× |

비전 모델은 OCR 과 PII 인식을 한 번에 할 수 있어 구조상 매력적이지만,
**장당 3\~4분이면 증거 다섯 장에 20분**입니다. GPU 없이는 못 씁니다.

품질은 나쁘지 않았습니다 — 폼 화면에서 **짝짓기가 완벽**했고(`계좌번호 5501234567`),
숫자도 정확했습니다. 다만 `컬쳐랜드` 를 `결격랜드` 로 읽는 등 **기관명을 뭉개는** 문제가 있었습니다.
