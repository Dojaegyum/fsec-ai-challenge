# STT 전처리 실측 — 지연은 전처리로 안 줄어든다

> 2026-08-25 측정. 측정 원본은 [assets/datasets/08-25-stt-preprocess/](../../assets/datasets/08-25-stt-preprocess/),
> 하네스는 [services/transcriber/bench_stt.py](../../services/transcriber/bench_stt.py) 입니다.
>
> 평가셋은 [09](09-로컬모델-PII인식-실측.md)·[10](10-PII인식-실측-방법론.md) 의 것을 그대로 썼습니다 —
> 40발화 · `pii` 33건 · `keep` 80건. 같은 평가셋이라 그때 숫자와 바로 비교됩니다.

## 왜 쟀나

전사가 오래 걸립니다. **전처리를 먼저 해서 지연을 줄일 수 있는지** 봤습니다.
특히 「음성을 청크로 쪼개 배치로 돌리고 결과를 합산하는」 방식이 후보로 나왔습니다.

## 결론 — 셋

**① 전처리로는 안 줄어듭니다.** 무음 건너뛰기(VAD)는 **0.4%**, 빔 폭 축소는 14% 를
버는데 그 14% 는 **개인정보 2건을 더 잃고** 사는 것입니다.

**② 청크·배치는 CPU 에서 이득이 없습니다.** 매트릭스에 넣지도 않았습니다 — 아래 §3.

**③ 남은 길은 하드웨어입니다.** [ADR-043](../../decisions/043-gpu-hosting.md) 이
「CPU 로는 서비스가 안 된다」고 한 판단을 이 실측이 한 번 더 뒷받침합니다.

---

## 1. 잰 것

```
오라클 애슈번 · VM.Standard.A1.Flex (ARM Ampere) · 2 OCPU · 12GB
faster-whisper medium · device=cpu · compute_type=int8
모델은 조건마다 다시 올리지 않고 한 번만 적재
```

`vad_filter` 와 `beam_size` 는 호출 인자라 모델을 다시 만들 필요가 없습니다.
다시 만들면 적재 시간이 조건마다 섞여 들어갑니다.

| | 무음 없는 음성 (6.8분) | 무음 37% 넣은 음성 (10.8분) |
| --- | --- | --- |
| A `vad=off beam=5` | **719.2초** · 실시간 1.77배 · PII 11/33 · keep 20/80 | **722.5초** · 실시간 1.12배 · PII 12/33 · keep 24/80 |
| B `vad=on  beam=5` | **716.1초** · 실시간 1.77배 · PII 11/33 · keep 22/80 | **716.3초** · 실시간 1.11배 · PII 11/33 · keep 19/80 |
| C `vad=off beam=1` | **615.9초** · 실시간 1.52배 · PII 13/33 · keep 20/80 | — |
| D `vad=on  beam=1` | **616.4초** · 실시간 1.52배 · PII 13/33 · keep 21/80 | — |

**조건 A 의 PII 손상 11/33 은 [09](09-로컬모델-PII인식-실측.md) 의
`medium / +잡음` 값과 같습니다.** 하드웨어가 다른데 품질 지표가 일치했다는 것은,
이 하네스가 그때 조건을 제대로 되살렸다는 뜻입니다 — **GPU 를 재도 그때 값과 바로
비교됩니다.**

> ⚠️ **「실시간 배수」를 조건 간에 그대로 비교하지 마세요.** 분모가 오디오 길이라,
> 무음을 넣으면 같은 말을 같은 시간에 옮겨도 배수가 떨어집니다. 무음 있는 것과
> 없는 것을 견줄 때는 **벽시계 절대 시간**을 보세요. 이 함정이 아래 §2 의 발견을
> 만들었습니다.

## 2. VAD 가 아무것도 안 한 이유 — 침묵이 이미 공짜였다

처음 측정(무음 없는 음성)에서 VAD 는 0.4% 를 벌었습니다. 측정 오차입니다.
**합성 낭독음엔 건너뛸 무음이 없어서**라고 보고, 발화 앞뒤에 3초씩 침묵을 넣어
**침묵 비율 37%** 짜리를 새로 만들어 다시 쟀습니다.

침묵에는 회선 잡음이 깔리게 했습니다 — 순서를 반대로 하면 침묵이 완전한 무음이
되어 VAD 가 너무 쉽게 가릅니다. 실제 통화에서 VAD 가 푸는 문제는 「무음 찾기」가
아니라 **「잡음 속에서 말 찾기」** 입니다.

결과는 이렇습니다.

```
오디오        6.8분  ->  10.8분   (+4.0분, 침묵 37%)
벽시계 (A)   719.2초 -> 722.5초   (+3.3초)
```

**오디오가 4분 늘었는데 처리 시간은 3초 늘었습니다.** 침묵 4분의 값이 3초입니다.

즉 **VAD 가 없어도 침묵은 이미 거의 공짜**입니다. whisper 는 말이 없는 창에서
디코딩을 일찍 접습니다. VAD 는 그 위에 얹혀서 **이미 싼 것을 조금 더 싸게** 만들
뿐이고, 그 몫이 0.4% 였던 것입니다.

**이건 「우리 평가셋이 이상해서」가 아니라 구조입니다.** 침묵 비율을 37% 까지
올려도 안 나왔으니, 실제 통화에서도 VAD 로 얻을 것은 크지 않습니다.

> 다만 VAD 는 **품질 쪽에서 이득이 있었습니다.** 무음 조건에서 `keep` 손상이
> 24 → 19 로 줄었습니다. 침묵 구간에서 whisper 가 없는 말을 지어내는 것(환각)을
> VAD 가 막은 것으로 보입니다. **속도가 아니라 이 이유로 켤 만합니다.**

## 3. 청크·배치를 매트릭스에 안 넣은 이유

세 가지가 각각 다른 이유로 막습니다.

| | |
| --- | --- |
| **whisper 는 이미 30초 창으로 쪼갭니다** | 밖에서 또 쪼개는 것은 겹치는 일이고, 경계만 늘어납니다 |
| **코어가 2개입니다** | CPU 바운드 작업을 프로세스로 나눠도 같은 2코어를 나눠 쓸 뿐입니다. 배치가 이득인 곳은 유휴 연산 유닛이 남는 GPU 입니다 |
| **경계에서 셋이 깨집니다** | 앞 창의 결과를 다음 창의 프롬프트로 쓰는 **문맥**, 계좌번호를 읽는 도중 잘리는 **단어**, 전체를 봐야 정해지는 **화자** |

그리고 이번 측정이 근본 이유를 하나 더 보탭니다 — **병목이 인코더**입니다.
whisper 는 30초 창을 통째로 인코딩하고, 그 비용은 **오디오 길이에만 비례**합니다.
빔 폭·무음과 무관합니다. 쪼개면 창 수가 늘어 오히려 총 인코딩량이 커집니다.

`beam=5 -> 1` 이 14% 밖에 못 준 것도 같은 이유입니다. 빔은 디코더 탐색 폭이라
전체를 못 흔듭니다.

## 4. 그래서 무엇을 할 것인가

| 수단 | 판정 |
| --- | --- |
| 청크 → 배치 → 합산 | ✗ CPU 에서 이득 없음. GPU 로 옮긴 뒤 다시 볼 것 |
| `beam_size` 5 → 1 | ✗ **14% 를 벌고 개인정보 2건을 더 잃습니다.** 이 서비스에서 그 값이 틀리면 곧 피해자의 금전 손실입니다 ([불변 규칙 8](../../CLAUDE.md)) |
| `FINALLY_VAD=1` | △ **속도로는 켤 이유가 없습니다**(0.4%). 다만 침묵 구간의 환각을 줄여 `keep` 손상이 24 → 19 로 나아졌습니다 — 품질을 이유로 켜는 것은 검토할 만합니다 |
| GPU | **여기가 남은 길입니다** |

**사용자가 지금 막혀 있지는 않습니다.** `complete` 가 202 로 접수만 하고 화면이
폴링하는 구조라(§3.3 · [ADR-051](../../decisions/051-idempotent-ingest.md)),
전사가 몇 분 걸려도 사용자는 다른 것을 합니다. 줄여서 좋은 것은 **비용**과
**결과가 늦게 나오는 답답함**이지 요청이 막히는 문제가 아닙니다.

## 5. 이 실측이 답하지 못한 것

- **GPU 에서 얼마나 빨라지나** — 오라클로는 못 쟀습니다. 이 계정의 GPU 형상 한도가
  전부 0 이라, 자리 문제가 아니라 권한 문제입니다(종량제 전환 + 한도 증액 심사가
  필요). [ADR-043](../../decisions/043-gpu-hosting.md) 이 개발용으로 RunPod 을 고른
  이유가 이것입니다. **하네스는 그대로 돌아갑니다** — 조건 목록만 바꾸면 됩니다.
- **실제 통화 녹음에서도 같은가** — 합성음으로만 쟀습니다. 침묵 비율을 37% 까지
  올려 구조는 확인했지만, 실제 통화의 말겹침·끊김은 재현하지 못했습니다.
- **`keep` 손상이 왜 이렇게 큰가** — 조건 A 에서 80건 중 20건이 전사에서 사라집니다.
  기관명이 사라지면 8유형 분기가 무너지는데, 이 실측의 물음이 아니라 따로 봐야
  합니다.
