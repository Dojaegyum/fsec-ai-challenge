로컬 모델은 진술과 화면에서
개인정보를 잡아낼 수 있는가

STT·OCR에 브라우저 모델을 쓰지 않기로 한 뒤, 남은 선택지는 로컬 모델이었습니다. 그 모델의 성능이 전사된 진술에서 무엇이 개인정보인지 가려내는 정확도를 좌우할 것 같아 처음으로 재봤습니다. 합성 평가셋 40발화, 전화 음질로 합성한 음성, Whisper 세 크기와 로컬 LLM 두 종입니다. 증거 화면 20장으로 OCR 엔진 넷도 이어서 쟀습니다.

깨끗한 텍스트 누출률0.0% 전사문 누출률9.1% 화면(OCR) 누출률5.7% 분기 입력 훼손0건

결론부터 — 로컬 4B 모델로 충분합니다. 다만 그건 텍스트가 깨끗할 때 이야기이고, 전사문에서는 정규식과 LLM의 역할이 통째로 뒤집힙니다. 그런데 화면에서는 안 뒤집힙니다 — 같은 계좌번호도 듣는 것과 보는 것은 난이도가 다릅니다.

평가셋의 첫 발화입니다. 음성을 전화망 음질(8kHz·μ-law)로 떨어뜨린 뒤 Whisper 크기를 올려가며 받아썼습니다. 계좌번호가 어떻게 되는지만 보세요.

OCR 발견 1

한글이 깨지는 방식이 엔진마다 다릅니다

원문 국민은행 · 받는 분 김도현
Tesseract 민 은 행 · ge 분 김 도현 ← 낱자로 쪼개고 공백을 넣음
EasyOCR 국민은행 · 본는 분 김도현 ← 한글은 붙어 있고 라벨을 한 글자 오독
비전 모델 국민은행 · 분는 분 / 김도현 ← 라벨과 값이 줄로 갈림

고치는 법도 달라집니다. Tesseract는 낱자 공백을 다시 붙이면 누출이 32.4%에서 14.7%로 떨어집니다. EasyOCR의 오독은 한 글자뿐이라, 화면 라벨이 유한 집합인 걸 이용해 사전으로 되돌리면 짝유지가 63.8%에서 94.2%가 됩니다.

OCR 발견 2

엔진이 주는 좌표를 버리고 있었습니다

EasyOCR은 글자 덩어리를 찾은 순서대로 뱉습니다. 흔히 쓰는 detail=0 호출은 좌표를 버려서, 화면에서 한 줄이던 받는 분 | 김도현이 두 줄로 갈리고 순서까지 뒤집힙니다.

좌표는 엔진이 이미 주고 있습니다. 안 쓰면 버리는 것입니다.

OCR 발견 3

예상했던 자형 혼동은 나오지 않았습니다

0↔O · 1↔l · 5↔S를 따로 집계했는데 전 조건에서 0건이었습니다. 화면 글자는 인쇄물·스캔과 달리 픽셀이 또렷합니다. 예측이 빗나갔고, 그래서 대비할 필요가 줄었습니다 — 다만 종이 서류를 받는 경로를 열면 다시 봐야 합니다.

OCR 발견 4

화질은 거의 안 걸립니다

저해상도(긴 변 720px)도, 다른 폰으로 찍은 것도 원본과 비슷하거나 오히려 나았습니다 — 확대가 Tesseract에 유리했던 것으로 보입니다. 피해자가 캡처를 메신저로 돌려 보내거나 다른 폰으로 찍어 보내도 괜찮습니다. STT는 모델 크기가 결정적이었지만(5%→65%), 여기서는 그 걱정을 옮겨 붙일 필요가 없습니다.

⚠️ 합성 화면 기준입니다. 실제 은행 앱은 자체 글꼴·좁은 자간·컬러 배경을 써서 결과가 달라집니다 — 특히 Tesseract의 한글 낱자 분리는 글꼴에 민감합니다. 비전 모델(gemma3:4b)은 장당 176~240초라 지금 하드웨어에서는 논외이고, 3장짜리 부분 표본입니다.

발견 · 진술(STT)

네 가지

발견 1

지금 정규식의 구멍은 정확히 「이름」 하나입니다

계좌 8/8 · 전화 8/8 · 주민번호 3/3 · 카드 1/1 을 전부 잡고, 가리면 안 되는 값 80건은 한 건도 안 건드립니다. 대표번호 1588·112·114를 안 가리는 것까지 설계대로였습니다. 누출 13건은 전부 이름이었습니다 — 오탐이 폭발한다는 이유로 일부러 비워 둔 자리이고, 아직 비어 있는 것입니다.

발견 2

프롬프트로 부탁하는 것만으로는 경계가 안 지켜집니다

「금액은 뽑지 마라」를 목록으로 명시했는데도 qwen3:4b는 금액을 뽑았습니다. 그것도 스스로 금액이라고 이름 붙여서요. 알면서 낸 겁니다. 프롬프트를 더 세게 쓸 문제가 아닙니다.

"300만원" → { kind: "금액", ... } ← 금지 목록에 있는 말을 종류 이름으로
"1588-5000" → { kind: "전화", ... } ← 대표번호. 어느 기관에 전화했는지가 분기 입력
"케이뱅크 7777-01-9988776" → { kind: "계좌" } ← 기관명까지 한 덩어리로. 가리면 분기가 무너짐

해법은 이미 저장소에 적혀 있었습니다 — 「허용 목록을 NER 결과보다 우선 적용한다」. 그 문장을 코드로 실제 걸었더니 분기 입력 훼손이 14건에서 0건이 되고, 누출은 하나도 늘지 않았습니다. 장식이 아니라 필수 부품이었습니다.

발견 3

전사문에서는 정규식과 LLM의 역할이 뒤집힙니다

깨끗한 텍스트에서 숫자 20건을 전부 잡던 정규식이, 전사문에서는 10건입니다. 반대로 LLM은 19건을 잡습니다. "공이 9876543"을 전화번호로 읽는 건 정규식이 할 수 없는 일이니까요.

110-234-567890 → "일일공에 234마이너스 56만 7,890"
02-987-6543 → "공이 9876543으로"
5501234567 → "5501이 참사 567이에요"
010-4821-9930 → "1010-4821-930으로" ← 자릿수가 밀림
880312-2345678 → "88만 312-2345678" ← 0 하나가 사라짐

1차 정규식은 「사용자가 타이핑한 텍스트」를 위한 도구입니다. 전사문은 성질이 다른 입력이고, 같은 도구를 그대로 대면 못 잡습니다.

발견 4

가장 위험한 오독은 「신뢰도가 낮을 때만 확인」으로는 못 잡습니다

계좌번호가 날짜로 바뀐 경우가 있었습니다. 값이 사라진 게 아니라 다른 슬롯의 그럴듯한 값이 된 것이라, 모델이 확신을 갖고 틀립니다 — 자연스러운 날짜 표현이니 신뢰도가 낮게 나올 이유가 없습니다.

3333-01-2345678 → "3333년 1월 23일 35678로"

기한 계산의 기산점이 여기서 틀어지는데 아무도 이상하다고 느끼지 않습니다. 기계가 읽은 값을 사람이 확인하는 화면은 유지해야 하고, 여는 조건을 넓히는 쪽을 검토해야 합니다.

권고 일곱

R-1

2차 NER은 로컬 4B급으로 간다. gemma3:4b 기준 깨끗한 텍스트에서 누출 0%·훼손 0%. 미뤄 두던 모델 선택을 닫을 근거가 생겼습니다.

R-2

허용 목록을 코드로 건다. 프롬프트만으로는 훼손 17.5%.

R-3

허용 목록에 기관명 사전을 넣는다. 형태 규칙만으로는 KT를 사람 이름으로 본 것을 못 막습니다.

R-4

전사문 경로에서 정규식 1차를 신뢰하지 않는다. 타이핑 텍스트용 도구와 전사문 경로를 갈라야 합니다.

R-5

STT는 medium 이상을 쓴다. base는 숫자가 5~10%만 살아남아 파이프라인이 무너집니다.

R-6

기계가 읽은 값을 확인하는 화면을 없애지 않는다. medium에서도 33건 중 9~11건이 전사에서 깨집니다.

R-7

전사 품질 개선은 누출 대책이 아니라 슬롯 대책으로 잡는다. small에서 medium으로 올려도 누출률은 10.5%→9.1%밖에 안 내려갔습니다.

단서

이 숫자를 얼마나 믿을 수 있나

여기 오독률은 낙관적 하한값입니다. 음성을 TTS로 합성했는데, 실제 통화보다 발음이 또렷합니다. 실제 피해자의 진술에는 울먹임·말 끊김·사투리가 섞이므로 실제 오독률은 이보다 나쁩니다.

상한을 보려면 실제 통화 음성이 필요한데, 금융감독원 「그놈 목소리」는 공공누리 유형과 내려받기 가능 여부가 아직 미확인이라 이번엔 쓰지 않았습니다.

표본이 작습니다 — 40발화, 개인정보 33건. 백분율의 한 칸이 대략 1건입니다. 속도는 순위 판단에만 쓰고 절대값으로 인용하지 마세요. OCR은 이번 범위 밖입니다.
