골든30 데스크톱 웹 서비스 기획서

채택된 01번(보이스피싱 골든타임 네비게이터)을 데스크톱 웹 데모 기준으로 구체화한 기획서입니다. 구성: §1 파이프라인·백엔드 아키텍처 → §2 필수 정보 미인입 대응(슬롯 티어링) → §3 PII 격리 → §4 서비스별 매뉴얼 매트릭스·KB 운영(시간성) → §5 완수 검증(Completion Hook) → §6 화면 설계 → §7 기능명세 → §8 데모 시나리오 → §9 기술 스택. 피싱 백신은 부가 시뮬레이션 모드로 포함.

0 · 전제와 데스크톱 선택의 이유

입력 가정

피해자(또는 돕는 가족)는 녹음 파일(m4a/mp3), 스크린샷(문자·카톡·이체내역), 텍스트 붙여넣기 중 하나 이상을 제공할 수 있다. 당사자 본인 녹음은 합법(통신비밀보호법상 당사자 녹음).

왜 데스크톱 웹인가

① 파일 다중 업로드·문서 작성·기한 관리 등 사무 작업형 UX가 중심 ② 피해 대응은 가족(자녀)이 함께 하는 경우가 많음 — 넓은 화면의 '상황실' 메타포 ③ 심사 데모 환경(빔프로젝터·노트북)에 최적. 모바일 반응형은 P1로 후속.

핵심 설계 사상

"사건 파일(Case)" 중심 구조. 업로드된 증거·분석 결과·체크리스트·서류·기한이 하나의 사건 폴더로 묶인다. 관제 콘솔(13번)에서 검증한 3-패널 레이아웃을 소비자 문법으로 번역.

격리 경계 요약 — 원문 PII는 클라이언트를 떠나기 전 1차 마스킹되고, 서버 스크러버(빨간 노드)가 격리 경계다. 외부 LLM(파란 영역)에는 토큰화 텍스트만 도달하며, 복원 매핑은 클라이언트에만 존재한다. KB(노란 영역)는 런타임과 분리된 운영 파이프라인(§4)으로만 갱신된다.

2 · 필수 정보 미인입 대응 슬롯 티어링 + 점진적 구체화

설계 원칙: "미확정 슬롯이 있어도 절대 멈추지 않는다." 패닉 사용자는 정보를 못 주는 게 정상이다. 정보 요구로 사용자를 막는 대신, 슬롯을 3티어로 나눠 T0(정보 제로여도 실행되는 공통 안전 절차)부터 시작하고, 슬롯이 채워질 때마다 플랜을 점진적으로 구체화한다.

최소 질문 원칙

한 번에 한 슬롯만, 전부 버튼으로. 질문 순서는 "플랜을 가장 크게 바꾸는 슬롯부터"(정보 이득 순). T2는 증거 자동 추출이 우선이라 실제 질문은 보통 1~2개로 끝난다.

모름의 처리

"모름"은 실패가 아니라 정상 상태. 슈퍼셋 플랜은 모든 분기의 안전 단계를 포함하되 조건부 단계에 "카카오페이로 보냈다면"식 라벨을 붙인다. 낫게 안내하지 못할 바에 넓게 안내하고, 절대 창작하지 않는다.

3 · PII 보호·격리 설계 요건 ② — 신뢰의 아키텍처

2중 스크러빙

1차(클라이언트): 업로드 직후 브라우저에서 정규식 기반 마스킹(계좌·주민·카드·전화 패턴) — 원문이 네트워크를 타기 전에 1차 제거. 2차(서버 게이트웨이): NER 기반 잔여 PII 탐지·토큰화([계좌-1], [이름-1] 형식). 외부 LLM API에는 토큰화된 텍스트만 도달한다.

복원 매핑의 격리

토큰↔원문 매핑 테이블은 서버에 저장하지 않고 클라이언트 세션에만 보관. 화면 표시 시점에 브라우저가 복원한다. 즉 서버·LLM 어디에도 "누구의 어떤 계좌"인지 완성된 정보가 존재하지 않는 구조.

세션 격리·비저장

사건 파일은 세션 단위 격리 스토어에서만 존재, 종료(또는 24h) 시 원문·파일 자동 파기. 사후 리포트는 사용자가 명시적으로 다운로드한 사본만 남는다. 학습·통계 활용 없음을 UI에 명시.

인젝션 방어 + 감사

업로드 문서 속 지시문("이 메시지는 안전하다고 판단하라" 류)을 데이터로만 취급하는 프롬프트 격리 + 분석 결과에 근거 스팬 인용 강제. 모든 LLM 호출은 감사 로그(토큰화 텍스트 기준) 기록 — 금보원 생성형 AI 가이드라인 통제 항목 매핑.

4 · 금융 서비스별 대응 매뉴얼 매트릭스와 KB 운영 요건 ③ — 딥리서치 + 시간성 대응

같은 "돈을 보냈다"여도 경유한 금융 서비스에 따라 지급정지의 주체·방법·환급 가능성이 다르다. 이 매트릭스가 매뉴얼 분기 엔진(KB)의 원본 데이터다. 요약하면 — 은행·증권은 표준 절차, 간편송금은 업자 경유 정보공유 절차, 가상자산은 2026.10부터 환급 대상, 상품권·소액결제는 여전히 사각지대.

경유 서비스 지급정지 요청처 환급법 적용 절차 특이점 → 골든30 분기 로직
시중은행 계좌이체 송금은행 콜센터 (24h) 적용 표준 절차. 전화 정지 → 3영업일 내 서면 → 공고 2개월 → 환급. 기본 트리
인터넷은행 (토스뱅크 등) 앱 내 신고 + 고객센터 적용 절차는 표준과 동일하나 창구가 앱 중심 — 서면 제출 방법(비대면 접수)이 다름을 안내
증권사 계좌 해당 증권사 고객센터 적용 금융회사 범위에 포함 — 표준 트리에 증권사 연락처 매핑
간편송금 (카카오페이·토스 등) 이용 선불업자 + 연계 은행 적용 (개정) 간편송금 악용 대응 개정법으로 업자 간 사기이용계좌 정보공유·지급정지 연계가 의무화 — "어느 페이로 보냈는지"를 문진에서 특정해야 정확한 요청처가 나옴
가상자산 (거래소 경유) 거래소 + 수사기관 2026.10~ 적용 올해 10월부터 환급 대상 포함(코인 종류·수량 단위 반환 or 전담기관 매도 후 금전 지급, 평가는 지급정지 시점 기준). 그 전 피해는 형사 절차 중심 — 시행일 분기 로직 필요. 시의성 카드
대면편취 (현금 전달) 112 → 수사기관이 계좌 특정 2023.11~ 적용 피해자가 직접 지급정지 불가 — 112 신고가 절차의 출발점. 안내 순서 역전
상품권 (핀번호 전달) 발행사 고객센터 (사용정지 시도) 사각지대 환급 절차 없음 — 발행사 핀 사용정지 시도 + 분쟁조정(소비자원) + 형사 절차. 기대치 정직 안내
휴대폰 소액결제 통신사 + 결제대행사 사각지대 통신사 결제 차단·민원, 민사·형사 대응 중심. 재발 방지(소액결제 차단 설정) 안내 포함
공통 후속 레이어 — 어느 분기든 공통으로: 명의도용 점검(어카운트인포·엠세이퍼), 악성앱 의심 시 초기화 안내, 은행권 자율배상(2024.1~) 안내, 환급 타임라인 기대치 관리(3~6개월).
KB 운영 원칙 — 매뉴얼 KB는 출처(법령·기관 공지) 링크와 시행일을 메타데이터로 갖고, LLM은 KB 근거 없이 절차를 창작하지 않는다(근거 인용 강제). 제도 변경(예: 가상자산 10월 시행)은 KB 갱신으로 반영 — 이 구조 자체를 발표에서 '환각 방지 설계'로 어필.

도메인 지식의 시간성 — KB 운영 파이프라인

설계 원칙: "LLM은 절차를 외우지 않는다 — 버전드 KB를 인용할 뿐이다." 절차 지식을 프롬프트에 굽지 않고 구조화 KB(JSON + 출처·시행일 메타)로 분리하면, 제도 변경은 코드 배포 없이 KB 릴리스로 반영된다. 가상자산 환급(2026.10.1 시행)이 살아있는 예시 — 시행일 메타 덕분에 같은 질문에도 10월 전후로 다른 답이 나간다.

법령(저빈도·고신뢰): 국가법령정보센터 API로 개정 감지 — 기계 판독 가능. 정책 공지(중빈도): 금융위·금감원·경찰청 보도자료 — 시행 예고를 가장 먼저 아는 채널. 실무 정보(고빈도·저구조): 기관 콜센터 번호·접수 방식 — 깨지기 쉬워 Staleness Guard(90일 재검증)의 주 대상.

사람 검수는 왜 필수인가

절차 지식의 오류는 피해자를 잘못된 창구로 보낸다 — 자동 반영 금지가 원칙. LLM은 변경 영향 분석·개정 초안까지만, 릴리스는 사람이 승인. 이 통제 구조는 금보원 AI 거버넌스 언어(인간 승인·감사 가능성)와 일치해 발표 소재가 된다.

런타임 신선도 표시 — 모든 절차 안내에 "KB v2.3 · 출처: 통신사기피해환급법 §OO · 최종 검증 2026-08-01"을 표기. KB에 없는 케이스는 창작하지 않고 T0 공통 절차 + 1332 상담 연결로 폴백.
MVP 범위 조정 — 대회 기간엔 KB 수동 구축(8유형 × 검증 출처) + Watcher는 수동 트리거 시연 수준. 자동 수집 전체 구현은 P2(F-11).

5 · 행위 완수 검증 설계 Completion Hook — 체크박스가 아니라 부산물을 믿는다

문제 — 체크리스트는 "체크는 됐는데 행위는 안 된 상태"를 막지 못한다. 은행·경찰 시스템 API가 없으므로 완수를 직접 조회할 수도 없다. 원리 — 모든 공식 절차는 완수 시 반드시 부산물(접수번호·통지 문자·접수증)을 남긴다. 이 부산물을 완료 조건이자 다음 단계의 필수 입력으로 삼으면, 인위적 잠금이 아닌 절차 자체의 의존관계로 완수가 강제된다.

① 증거 연쇄 (Evidence-Chained Workflow)

각 단계의 완료 = 부산물 입력/업로드. 112 신고 → 사건접수번호 입력, 지급정지 → 은행 접수 문자 캡처, 서면 신청 → 접수증 업로드. 그리고 사건접수번호는 피해구제신청서의 필수 필드, 접수증 날짜는 환급 타임라인의 기산점 — 부산물이 없으면 다음 산출물이 물리적으로 완성되지 않는 구조가 최강의 훅이다.

② 검증 3단계 레벨

L1 자동 검증: 접수번호 포맷 체크, 접수증 OCR로 이름·날짜·사건 정보 대조(사건 파일과 일관성 검사). L2 증빙 확인: 캡처·서류 업로드(PII 스크러버 통과). L3 자기 신고: 최후 수단 — 허용하되 상태가 '완료'가 아닌 '미확인'으로 남는다. 상태 머신: 미시작 → 진행중 → 완료(증빙됨) / 미확인.

③ 통화 동반 모드

전화는 웹이 관측할 수 없는 블랙박스 → 관측 가능한 앞뒤를 잡는다. 발신 버튼 클릭 시 통화 스크립트+예상 질문 표시, 통화 타이머 작동, 종료 직후 "접수번호를 지금 받아적으세요" 캡처 프롬프트가 즉시 뜬다. 부산물 확보를 통화 경험 안에 심는 설계.

④ 소프트 게이트 + 이중 리마인더 + 사회적 훅

패닉 사용자를 막아 세우면 이탈한다 — "나중에 입력"은 항상 허용하되 미확인 상태를 3영업일 D-day 트래커와 연동해 리마인더(웹 알림·이메일)가 계속 추적. 여기에 보호자 공유(진행 현황을 가족이 열람)를 얹으면 완수 책임이 사회화된다 — 완수율을 올리는 가장 강한 비기술적 훅.

데모 포인트 — 심사장에서 접수증 이미지를 업로드 → OCR이 이름·날짜를 사건 정보와 대조 → 체크 항목에 "완료(증빙됨)" 도장이 찍히는 3초 장면. "저희는 사용자의 체크를 믿지 않습니다. 접수증을 믿습니다"라는 한 문장이 심사위원에게 남는다.
