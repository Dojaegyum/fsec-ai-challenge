# reminder-sender

다가온 기한과 `미확인` 단계를 찾아 **보낼지 말지를 판단합니다.** 메일 문구를 짓거나
실제로 보내지는 않습니다 — 발송은 밖에 위임합니다.

## 알맹이는 판정입니다

[ADR-025](../../../decisions/025-scheduled-jobs.md)가 이 모듈을 데이터베이스 안이 아니라
앱 안에 둔 이유입니다.

> 리마인더는 **보낼지 말지를 판단해야 합니다** — 이메일이 있는가, 기한이 확정인가
> (부산물이 없으면 추정일 뿐이라 보내면 안 됩니다), 이미 보낸 건 아닌가.
> **이건 규칙이지 쿼리가 아닙니다.**

## 보낼 수 없는 사건이 있습니다 — 실패가 아닙니다

| 건너뛰는 이유 | 왜 |
| --- | --- |
| `no_email` | **이메일은 선택입니다.** 안 준 사건도 정상 사건입니다 → [ADR-021](../../../decisions/021-reentry-and-identity.md) |
| `not_confirmed` | 기산점이 부산물로 확인 안 됐습니다. **추정 기한입니다** |
| `already_sent` | 같은 것을 이미 보냈습니다 |
| `nothing_due` | 창에 든 것이 없습니다 |

**연락처를 새로 요구하는 흐름을 만들지 마세요.** 이메일이 없으면 그냥 안 보냅니다.

**확정되지 않은 기한으로 알리지 마세요.** 부산물이 아직 없으면 기한은 추정일 뿐이라
[기한 계산 규칙](../../../spec/common/08-16-deadline-rules.md)이 「미확인 배지와 함께 추정만」으로
정했습니다. **추정 날짜를 메일로 보내면 사용자는 그것을 확정으로 읽습니다.**

같은 사건에 확정 기한과 추정 기한이 섞여 있으면 **확정된 것만 담아 보냅니다.**

## 지난 기한도 알립니다

**유예가 남아 있을 수 있습니다.** 기한이 지났다고 화면에서 지우지 않는 것과 같은 이유입니다.
지난 기한이 섞여 있으면 **그쪽을 보내는 이유로 삼습니다** — 더 급하기 때문입니다.

| 이유 | 언제 |
| --- | --- |
| `deadline_passed` | 지난 기한이 하나라도 있음 |
| `deadline_near` | 창에 든 기한이 있음 |
| `step_unconfirmed` | 기한은 없고 `미확인` 단계만 있음 |

## 같은 것을 두 번 보내지 않습니다

무엇을 알리는지로 **열쇠**를 만들어 대조합니다. **알릴 것이 늘면 열쇠가 바뀌어 새 메일이
나가고, 그대로면 안 나갑니다.** 조회 순서가 흔들려도 같은 열쇠가 나오도록 정렬합니다.

**보낸 뒤에 표시합니다.** 먼저 표시하고 발송이 실패하면 그 메일은 영영 안 갑니다.

## 쓰는 법

```ts
import { createReminderSender } from '@/modules/reminder-sender'

const reminder = createReminderSender({ source, sentLog, mailer, clock, dates })

const run = await reminder.run({ daysBefore: 3 })
// { sent: [...], skipped: [{ caseId, reason: 'no_email' }], failed: [] }
```

**문구를 여기서 짓지 않습니다.** `reason` 과 알릴 거리만 넘기고 문장은 발송 쪽이 만듭니다.

## 밖에서 넣어야 하는 것

| 무엇 | 어디서 | 비고 |
| --- | --- | --- |
| `ReminderSource` | 관계형 DB | ⬜ 어댑터 미구현 |
| `SentLog` | ⬜ **정할 곳이 없습니다** | 아래 참고 |
| `Mailer` | ⬜ **발송 수단 미정** → [ADR-021](../../../decisions/021-reentry-and-identity.md) 「남은 것」 |
| `Clock` | 서버 시계 | — |
| `DateGap` | `date-checker` 의 `daysLeft` | 있음 |

## 정본에 없는 것 둘 — 확인이 필요합니다

- ⬜ **이메일을 저장할 자리가 스키마에 없습니다.**
  [ADR-021](../../../decisions/021-reentry-and-identity.md)이 「알림용 이메일 하나만 선택 입력」으로
  정했는데, [09-data-model.md](../../../spec/backend/08-16-data-model.md)의 `case` 표에 그 칼럼이
  없고 [08-api.md](../../../spec/common/08-14-api.md)에도 받는 자리가 없습니다.
  `spec/` 전체에 `email` 이라는 낱말이 한 번도 안 나옵니다.

- ⬜ **발송 이력을 남길 자리도 없습니다.** 「이미 보낸 건 아닌가」를 판단해야 하는데
  `deadline`·`plan_step` 어디에도 그 칼럼이 없습니다. 지금은 `SentLog` 인터페이스로 두었습니다.

- ⬜ **주기와 문구가 안 정해졌습니다.** 며칠 전에 몇 번인지 → [12-module-names.md](../../../spec/common/08-16-module-names.md) 층 4 TODO.
  값을 밖에서 받을 수 있게 둔 이유입니다. 기본값은 하루 전입니다.

## 판단이 필요했던 자리

| 무엇 | 어떻게 | 왜 |
| --- | --- | --- |
| **확정·추정이 섞였을 때** | **확정된 것만 담아 보낸다** | 사건 전체를 건너뛰면 확정 기한까지 안 알리게 됩니다 |
| **지난 기한** | **알린다** | 유예가 남아 있을 수 있습니다. 기한이 지났다고 화면에서 지우지 않는 것과 같습니다 |
| **여러 건일 때 이유** | **지난 것이 있으면 그쪽** | 더 급합니다 |
| **표시 시점** | **보낸 뒤** | 먼저 표시하고 발송이 실패하면 영영 안 갑니다 |
| **열쇠에 무엇을 넣나** | **무엇을 알리는지 전부** | 알릴 것이 늘면 새 메일이 나가야 하고, 그대로면 안 나가야 합니다 |
| **문구를 여기서 지을지** | **안 짓는다** | 주기와 문구가 정본에 없습니다. 지어내면 나중에 정해질 때 두 곳이 됩니다 |
| **예외를 던질지** | **안 던진다** | 한 사건이 실패해도 나머지를 계속하고, 무엇을 왜 건너뛰었는지 말할 수 있어야 합니다 |
