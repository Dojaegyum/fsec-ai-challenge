# case-purger

`purge_after` 가 지난 사건의 **세 층을 함께 지우고, 실제로 지워졌는지 확인합니다.**

| | |
| --- | --- |
| 계약의 정본 | [09-data-model.md](../../../spec/backend/08-16-data-model.md) §14 §2 |
| 이름의 정본 | [12-module-names.md](../../../spec/common/08-16-module-names.md) 「층 4」 |
| 책임의 정본 | [모듈 경계](../../../spec/common/08-16-module-boundaries.md) |
| 근거 | [ADR-016](../../../decisions/016-retention-and-datastore.md) · [ADR-025](../../../decisions/025-scheduled-jobs.md) · [ADR-028](../../../decisions/028-runtime-and-module-shape.md) |

## 세 층이 같은 날 함께 사라집니다

| 층 | 어디 |
| --- | --- |
| 토큰화된 사건 상태 | 관계형 DB |
| 업로드 원본 | 객체 저장소 |
| 복원 매핑 암호문 | 볼트 |

[ADR-016](../../../decisions/016-retention-and-datastore.md)이 층마다 수명을 다르게 두지 않기로 한
이유가 **「파기가 한 층에서 조용히 실패하면 어느 한 층만 남고, 그게 무엇인지 추적할 방법이
없다」**입니다. **그래서 이 모듈은 지우는 것만으로 끝나지 않고 확인까지 합니다.**

## 순서가 규칙입니다

```
1. 볼트 항목 삭제        (만료로 이미 없을 수 있음)
2. 객체 저장소 파일 삭제
3. 관계형 DB 사건 행 삭제 (외래키 연쇄)
4. audit_log 에 case.purged 기록  ← 감사 로그는 남긴다
```

**관계형 DB 가 마지막인 것은 그 행이 「무엇을 지워야 하는가」의 유일한 단서이기 때문입니다.**
먼저 지우고 뒤에서 실패하면 어디에 뭐가 남았는지 알 방법이 없습니다. 남겨 두면 다음 회차가
같은 사건을 다시 집습니다.

**층마다 지우고 바로 확인하며, 확인이 안 되면 다음 층으로 넘어가지 않습니다.**

**감사 로그는 함께 지우지 않습니다.** `audit_log.case_id` 에 외래키가 없는 이유가 그것입니다 —
연쇄 삭제가 걸려 있으면 파기가 곧 감사 기록의 소멸이 됩니다
→ [09-data-model.md](../../../spec/backend/08-16-data-model.md) §1.

## 절대 하지 않는 것

- **한 층만 지우고 성공으로 처리하지 않습니다.** 남은 층을 목록으로 돌려줍니다.
- **확인 없이 끝내지 않습니다.** 객체 저장소에는 네이티브 만료가 없어 반드시 다시 조회합니다.
- **실패했는데 `case.purged` 를 기록하지 않습니다.** 지우지 않은 것을 지웠다고 남기면
  나중에 무엇이 남았는지 알 수 없습니다.
- **예외를 던지지 않습니다.** 던지면 어느 사건에서 멈췄는지, 그 앞의 것들은 지워졌는지
  알 수 없습니다.

## 쓰는 법

```ts
import { createCasePurger } from '@/modules/case-purger'

const purger = createCasePurger({ cases, objects, vault, audit, clock })

const run = await purger.run({ limit: 100 })
// { scanned: 12, purged: ['01J...'], failed: [{ caseId, remaining: ['objects','database'] }] }
```

**`failed` 가 비지 않았으면 그대로 두면 안 됩니다.** 다음 회차가 다시 집기는 하지만,
계속 실패하면 파기가 밀린 채 쌓입니다 → 아래 「아직 아닌 것」.

## 밖에서 넣어야 하는 것

| 무엇 | 어디서 | 비고 |
| --- | --- | --- |
| `CaseStore` | 관계형 DB | ⬜ 어댑터 미구현 |
| `ObjectStore` | 객체 저장소 | ⬜ 제품 미정 |
| `VaultStore` | 볼트 | ⬜ 제품 미정 → [ADR-016](../../../decisions/016-retention-and-datastore.md) |
| `AuditSink` | `audit-logger` | 있음 |
| `Clock` | 서버 시계 | — |

## 언제 도나

**Vercel Cron 이 앱의 API 라우트를 깨웁니다** → [ADR-025](../../../decisions/025-scheduled-jobs.md).
데이터베이스 안에서 도는 방식(`pg_cron`)을 쓰지 않는 이유는 **세 저장소를 건드려야 하기**
때문입니다 — SQL 만으로는 객체 저장소도 볼트도 못 지웁니다.

## 아직 아닌 것

- ⬜ **한 번에 몇 건까지 처리할 수 있는지 모릅니다.** 서버리스는 실행 시간 상한이 있어
  배치를 쪼개야 할 수 있습니다. 상한을 확인하기 전까지 기본값을 100 으로 두었습니다
  → [ADR-025](../../../decisions/025-scheduled-jobs.md) 「남은 것」.
- ⬜ **파기가 밀린 것을 관측할 자리가 없습니다.** `purge_after` 가 지났는데 남아 있는
  사건 수를 세는 곳이 필요합니다. 이 모듈은 결과를 돌려줄 뿐입니다.
- ⬜ **크론 엔드포인트 보호 방식이 안 정해졌습니다.** 외부에서 호출되면 안 됩니다.

## 판단이 필요했던 자리

| 무엇 | 어떻게 | 왜 |
| --- | --- | --- |
| **한 층이 실패했을 때** | **다음 층으로 안 넘어간다** | 앞 층이 남은 채 DB 행을 지우면 남은 것을 가리킬 단서가 사라집니다 |
| **멈춘 뒤 남은 층 표기** | **멈춘 지점부터 뒤를 전부 남은 것으로** | 다음 층은 손도 안 댔으므로 확실히 남아 있습니다. 지우지 않은 것을 지웠다고 하지 않습니다 |
| **확인 자체가 실패하면** | **지워졌다고 보지 않는다** | 조회를 못 했으면 있는지 없는지도 모릅니다. `kb-finder` 의 0건·실패 구분과 같은 논리입니다 |
| **한 사건이 실패하면** | **나머지를 계속한다** | 하나 때문에 전부 밀리면 파기가 무한정 늦어집니다 |
| **예외를 던질지** | **안 던진다** | 어디서 멈췄는지, 그 앞은 지워졌는지를 결과로 말할 수 있어야 합니다 |
| **실패 시 감사 기록** | **남기지 않는다** | 감사 사건 종류에 실패용이 없고, 지어내면 정본과 어긋납니다. 결과로 돌려줍니다 |
| **감사 기록의 `actorType`** | **`system` 을 실어 보낸다** | 사용자 요청 없이 도는 모듈입니다. 연쇄 시험([case-lifecycle.test.ts](../../lib/case-lifecycle.test.ts))이 이 칸이 빠진 것을 잡았습니다 |
