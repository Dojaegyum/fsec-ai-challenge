# kb-selector

토큰화된 대화를 보고 **두 묶음 밖의 자료를 고릅니다.** 답은 쓰지 않고 번호만 냅니다.
고른 항목의 본문을 DB 에서 읽어 프롬프트에 넣는 것은 부르는 쪽(`src/lib/adapters.ts`)입니다.

## 무엇을 고르나

`kb-finder` 는 사건 속성(트랙 · 경유 유형 · 기관)으로 절차를 조회하고 발화는 보지 않습니다.
그래서 발화가 요구하는 다음 셋이 프롬프트에 빠집니다.

| 후보 | 어디서 | 언제 고르나 |
| --- | --- | --- |
| 절차 | 현재 릴리스의 `kb_entry` 전부 (두 묶음에 이미 든 것은 제외) | 사용자가 그 방법·기관·상황을 직접 말할 때 |
| 연락처 | `org.contact` | 전화가 안 된다거나 진행이 막혔다고 말할 때 (§11.4.4) |
| 조문 | `source_snapshot` 의 법령 원문 최신본 | 법·근거·규정을 물을 때 |

## 두 단계

```
1단계  후보 전체를 6,000자 묶음으로 → 묶음마다 병렬 호출 → 번호만 {"selected": [...]}
2단계  건진 후보가 topK(5) 를 넘으면 다시 묶어 이유를 적게 하며 줄인다 (최대 6라운드)
       줄지 않으면 한 프롬프트에 모아 마지막 한 번
```

1단계는 추론을 없애 호출당 수십 토큰입니다. 묶음 수만큼 동시에 부르므로 호출당 지연이
전체 시간을 정합니다. 2단계가 이유를 적게 하는 것은 정확도를 위해서이고, 규칙 문단은
두 단계가 같습니다 — 다르면 1단계가 건진 것을 2단계가 다른 이유로 떨어뜨립니다.

## 판단이 필요했던 자리

| 자리 | 그렇게 한 이유 |
| --- | --- |
| **던지지 않습니다** | 선별은 있으면 좋은 것입니다. 호출 하나가 죽으면 그 묶음만 빈 답이고, 시간이 다 되면 그때까지 건진 것 중 앞 `topK` 로 끝냅니다. 부르는 쪽은 결과가 비어도 답변으로 갑니다 |
| **토크나이저를 안 들입니다** | 원형은 tiktoken 으로 3,000토큰씩 묶습니다. 여기서는 글자 6,000자로 어림합니다 — 묶음 크기가 조금 어긋나도 정확도에는 영향이 없습니다 |
| **번호는 풀 안의 위치입니다** | 한 턴 안에서만 뜻이 있습니다. 모델이 없는 번호를 내면 버립니다. 2단계에서는 그 라운드의 후보 밖 번호도 버립니다 |
| **대화는 최근 6턴만** | 발화가 요구하는 자료는 최근 말에 있습니다. 20턴을 다 넣으면 1단계 묶음마다 그만큼이 붙어 지연이 늘어납니다 |
| **선별 전용 모델** | 번호만 고르는 일이라 인용 계약이 필요 없습니다. 답변 모델(grok-4.5 · 5~18초)로 묶음 여섯을 부르면 예산이 안 남습니다 → `LLM_SELECT_MODEL` |
| **원문을 검사하지 않습니다** | 대화 내역은 `pii-tokenizer` 를 지난 것이어야 합니다. 여기서 다시 검사하면 경계가 둘이 됩니다. 순서는 `chat-receiver` 가 지킵니다 |

## 하지 않는 것

- 답변·요약·해석을 만들지 않습니다. 후보의 글도 고치지 않습니다.
- DB 를 부르지 않습니다. 후보는 `src/lib/db-selector.ts` 가 만들어 넘깁니다.
- 되묻기·1332 를 판정하지 않습니다. 그건 `citation-checker` 입니다.
