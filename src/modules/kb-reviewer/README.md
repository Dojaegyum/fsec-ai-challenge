# kb-reviewer

**사람이 볼 것을 묶어서 내놓고, 사람의 판단을 기록합니다. 승인하지 않습니다.**

## 승인이 곧 반영이 아닙니다

RFC-002 가 파이프라인을 네 구간으로 갈랐습니다.

```
1. 수집    source_snapshot   자동 · 하루 1회      ← kb-collector
2. 검수    source_change     사람 — 무엇이 바뀌었나  ← 이 모듈
3. 반영    src/kb/*.json     사람 — 파일을 고친다
   릴리스  kb_entry          적재기 — kb_version 을 찍는다
```

**이 모듈은 2번까지입니다.** RFC-002:

> *"파이프라인이 `kb_entry` 를 직접 쓰지 않습니다. 승인이 곧 반영이 되면 무엇이
> 어떻게 바뀌었는지가 어디에도 남지 않고, 「사람 검수 생략 불가」가 승인 버튼
> 한 번으로 축소됩니다. **검수의 산출물은 diff 입니다.**"*

승인은 「사람이 봤고 반영해도 된다」는 표시일 뿐입니다. 릴리스가 실제로 끝나면
그 버전을 이 모듈이 **기록**합니다 — 하는 것이 아니라 적는 것입니다.
[12-module-names.md](../../../spec/common/08-16-module-names.md) 층 4 도 같은 말로
적혀 있습니다.

## 확신도가 낮다고 버리지 않습니다

§12.2 가 못 박았습니다:

> *"확신도가 낮은 판정을 자동으로 버리지 않습니다. `impact.confidence` 가 낮으면
> `pending` 으로 사람에게 갑니다."*

**낮은 확신도는 덜 중요하다는 뜻이 아니라 기계가 판단을 못 했다는 뜻**이고,
그럴수록 사람이 봐야 합니다.

그래서 이 모듈은 확신도로 거르지도, **줄 세우지도** 않습니다. 확신도순으로
정렬하면 낮은 것이 아래로 밀려 결국 안 보게 됩니다. **큐는 먼저 감지된 것이
앞**이고, 확신도는 묶음마다 값으로 함께 나갈 뿐입니다.

LLM 이 낸 영향 분석은 **판정이 아니라 참고**입니다 — 릴리스 판단은 사람의 몫입니다.

## 같은 발표는 한 묶음

금융위는 게시판을 넷 운영해서 **같은 발표가 보도자료·보도설명자료·공지사항에
함께 올라옵니다.** 본문이 달라 해시로는 안 걸리고, 그대로 두면 사람이 같은 것을
네 번 봅니다 → §12.2.

`dedupe_key` 가 같은 것을 한 묶음으로 냅니다. **원문 스냅샷은 전부 남습니다** —
근거가 여럿인 편이 낫습니다.

> ⬜ **지금은 이 값을 넣는 자리가 없어 늘 `NULL` 입니다.** 수집기는 원문만 보므로
> 계산할 수 없고(본문이 다릅니다), 정본도 누가 채우는지 정하지 않았습니다.
> 그래서 **묶음 기능은 코드에만 있고 운영에서는 안 돕니다** — 모든 변경이 각자
> 한 묶음으로 나갑니다. `impact` 와 같은 자리입니다.

**묶는 키가 없는 것은 각자 한 묶음입니다.** 억지로 합치면 서로 다른 제도 변경이
한 줄로 보여, 하나를 승인하면서 다른 하나까지 승인하게 됩니다.

묶음의 확신도는 **그 안에서 가장 높은 것**입니다. 낮은 쪽으로 잡으면 근거가
여럿인 묶음이 오히려 덜 확실해 보입니다.

## 덮어쓰지 않습니다

이미 판단이 끝난 것을 다시 판단하면 던집니다. **검수 이력이 사라지면 「사람 검수
생략 불가」를 지켰는지 확인할 방법이 없어집니다.**

`reviewed_by` 가 비어도 던집니다 — 누가 봤는지가 안 남으면 「사람이 봤다」를
증명할 수 없습니다.

> ⬜ **그래서 `deferred` 로 미룬 것이 되돌아올 길이 없습니다.** 큐는 `pending` 만
> 내놓는 것이 정본(§12.2)이고, 다시 판단하는 것은 이력을 덮어쓰는 일입니다.
> 정본에 `deferred` 는 `CHECK` 제약의 허용값으로만 있고 **무슨 뜻인지·어떻게
> 푸는지가 적혀 있지 않습니다.** 지어내지 않고 사람에게 남깁니다 — 지금 상태로는
> 미룬 변경이 화면에서 사라지고 승인 기록도 못 받습니다.

## 승인 없이 반영된 것으로 표시할 수 없습니다

`markReleased` 는 `approved` 가 아닌 것을 거절합니다. 이 검사가 없으면 **거절된
변경도 반영된 것으로 표시**할 수 있고, 그러면 승인 없이 매뉴얼에 들어가는 경로가
생깁니다 → 원칙 4.

반영된 KB 버전이 비어도 거절합니다. 어느 버전에 들어갔는지가 안 남으면 나중에
「왜 이렇게 바뀌었나」를 되짚을 수 없습니다.

## 쓰는 법

```ts
import { createKbReviewer } from '@/modules/kb-reviewer'

const reviewer = createKbReviewer({ store, clock })

const queue = await reviewer.queue()                    // 사람이 볼 묶음들
await reviewer.review({ changeId, status: 'approved', reviewedBy: '…' })
await reviewer.markReleased(changeId, 'kb-2026-08-21')  // 릴리스가 끝난 뒤
```

## 판단이 필요했던 자리

| 무엇 | 어떻게 | 왜 |
| --- | --- | --- |
| **릴리스** | **안 한다 · 기록만** | RFC-002 가 구간을 갈랐습니다. 승인이 곧 반영이면 diff 가 안 남습니다 |
| **낮은 확신도** | **안 버린다 · 안 내린다** | 기계가 판단을 못 했다는 뜻입니다 → §12.2 |
| **큐 순서** | **감지된 때** | 확신도순이면 낮은 것이 아래로 밀려 안 보게 됩니다 |
| **키 없는 변경** | **각자 한 묶음** | 합치면 하나를 승인하며 다른 것까지 승인합니다 |
| **묶음 확신도** | **가장 높은 것** | 낮은 쪽으로 잡으면 근거가 여럿인 묶음이 덜 확실해 보입니다 |
| **재판단** | **던진다** | 이력이 사라지면 검수했음을 증명할 수 없습니다 |
| **큐 정렬 비교** | **시각으로 센다** | 문자열 대조는 밀리초 표기가 섞이면 순서를 뒤집습니다 |

## 아직 아닌 것

⬜ **영향 분석과 `dedupe_key` 를 누가 넣는지 정해지지 않았습니다.** 둘 다 LLM 이
채울 자리인데, 그 호출이 어느 모듈인지 정본에 없습니다. 이 모듈은 **읽기만** 합니다.

⬜ **`deferred` 를 어떻게 푸는지 정해지지 않았습니다** — 위 참고.

⬜ **검수 화면이 없습니다.** `S-` 번호가 아직 안 붙었고, 관리자 경로 계약도
비어 있습니다. 이 모듈은 묶음을 돌려주기만 합니다.

⬜ **diff 를 만들지 않습니다.** RFC-002 가 *"검수의 산출물은 diff"* 라고 적었지만,
지금은 스냅샷 ID 만 넘깁니다 — 앞 스냅샷을 못 가리키는 것이 `kb-collector` 쪽
남은 자리와 같은 문제입니다.
