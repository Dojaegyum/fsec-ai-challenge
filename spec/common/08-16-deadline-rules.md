# 기한 계산 규칙 — 날짜를 세는 것은 코드의 일

> **출처** — [경유 서비스 매트릭스](../backend/08-14-channel-matrix.md)(기한 값의 정본) ·
> [완수 검증](../backend/08-14-completion-hook.md)(부산물이 기산점) ·
> [사후처리 리서치](../../assets/artifacts/context/08-13-aftermath-research.html).

> **절차를 고르는 것은 LLM, 날짜를 세는 것은 규칙입니다.**
> 법정 기한을 모델이 틀리게 말하면 사용자가 권리를 잃습니다. 규칙으로 처리했다는 사실 자체가 발표에서 근거가 됩니다.

**기한의 값(3영업일·14일·2개월·5영업일)은 [매트릭스](../backend/08-14-channel-matrix.md)가 정본입니다.**
여기 다시 적지 않습니다 — 두 곳에 적으면 반드시 어긋납니다. 이 문서는 **그 값을 어떻게 세는가**만 정합니다.

## 계산의 전제

| 항목 | 규칙 |
| --- | --- |
| 타임존 | **`Asia/Seoul` 고정.** 서버·클라이언트 어디서 계산해도 같은 날짜가 나와야 합니다 |
| 단위 | **날짜 단위**로 셉니다. 시각으로 세지 않습니다 (법정 기한이 날짜 기준) |
| 기준 시계 | **서버 시계.** 클라이언트 시계를 신뢰하지 않습니다 — 사용자 기기의 날짜가 틀리면 기한을 놓칩니다 |
| 계산 주체 | **코드.** LLM 응답에서 날짜를 파싱해 쓰지 않습니다 |

## 기산점은 부산물입니다

기한은 "사용자가 했다고 말한 시점"이 아니라 **절차가 실제로 남긴 부산물의 시점**부터 셉니다.
이래야 [완수 검증](../backend/08-14-completion-hook.md)과 기한 추적이 같은 사실 위에 섭니다.

| 기한 | 기산 이벤트 | 부산물 |
| --- | --- | --- |
| 피해구제 신청 마감 | 지급정지 완료 | 은행 접수 문자 |
| 환급 타임라인 | 피해구제 신청 접수 | 접수증 |
| 채권소멸 공고 · 환급 결정 | 위 접수를 기점으로 이어짐 | — |

- 부산물이 아직 없으면(`미확인`) **기한을 확정하지 말고 "미확인" 배지와 함께 추정만** 보여줍니다.
  추정 날짜를 확정 기한처럼 보여주면, 사용자는 틀린 날짜를 믿고 권리를 잃습니다.
- TODO(근거 필요): 각 기한의 법정 기산점(요청일 기준인지 정지일 기준인지)의 조문 확인.
  현재 근거는 "지급정지 후 3영업일"까지이고, 하루 차이가 나는 지점입니다.

- **영업일 = 금융회사가 영업하는 날.** 주말과 공휴일은 세지 않습니다.

## 표시 규칙

- 상단에 **대응 경과 타이머**, 플랜 단계부터 **D-day**가 함께 붙습니다 → [화면 설계](../frontend/08-14-screens.md).
- **놓치면 되돌릴 수 없는 기한**(피해구제 신청)은 다른 기한과 시각적으로 구분합니다 →
  [디자인 시스템](../frontend/design-system/).
- 환급 타임라인은 **기대치 관리가 목적**입니다. 통상 3~6개월이라는 사실을 D-day가 아니라
  **진행 단계 설명**으로 보여줍니다 — 카운트다운으로 만들면 매일 실망을 줍니다.
- 기한이 지났다고 화면에서 지우지 않습니다. **유예(14일)가 남아 있을 수 있습니다.**

## 하지 않는 것

- **LLM에 날짜를 계산시키지 않습니다.** "3영업일 뒤가 며칠인가"를 모델에 묻지 마세요.
- **기한 값을 코드에 흩뿌리지 않습니다.** 제도가 바뀝니다 — 값은 KB, 계산은 규칙입니다 →
  [KB 운영](../backend/08-14-kb-operations.md).
- **채널마다 기한이 다릅니다.** 표준 트리(`CH-bank`)의 기한을 전 채널에 그대로 적용하지 마세요.
  `CH-facetoface`는 순서 자체가 다르고, `CH-giftcard`·`CH-carrier`에는 환급 기한이 없습니다.
- **클라이언트에서 계산한 날짜를 서버가 그대로 신뢰하지 않습니다.**
