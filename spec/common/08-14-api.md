# 08 · API 계약

기획서 v1.2에는 엔드포인트 수준의 계약이 없어 추출할 것이 없었습니다.
**아래는 구현 결정입니다** — [ADR-010](../../decisions/010-case-store.md)의 스키마 위에서 설계했습니다.
바꿀 때는 spec을 직접 고치지 말고 RFC → ADR 절차를 거칩니다.

## 기획서에서 이미 정해진 제약

API를 설계할 때 지켜야 하는 것들입니다. 이건 정해져 있습니다.

- **PII 경계** — 외부 LLM으로 나가는 페이로드는 토큰화된 텍스트만. `pii-tokenizer` 를 우회하는 경로를 만들 수 없습니다 → [04](08-14-pii-boundary.md)
- **복원 매핑의 복호화 키는 서버에 없음** — 매핑은 **암호문 상태로** 서버 볼트에 있고, 서버 API가 다루는 것은 토큰과 암호문뿐입니다 → [ADR-009](../../decisions/009-restore-mapping-location.md)
- **사건 수명 `CASE_PURGE_DAYS` (기본 180일 · 마지막 활동일 기준)** — `case.purge_after` → [09](../backend/08-16-data-model.md) §2 · [ADR-016](../../decisions/016-retention-and-datastore.md)
- **감사 로그** — 모든 LLM 호출 기록 (토큰화 텍스트 기준)
- **KB 인용 강제** — 플랜 생성 응답은 근거·시행일을 함께 반환해야 합니다 → [07](../backend/08-14-kb-operations.md)

> 2026-08-16 [ADR-009](../../decisions/009-restore-mapping-location.md) 채택으로 둘째·셋째가 바뀌었습니다.
> **이전 문구는 "복원 매핑은 서버에 저장하지 않음 / 세션 격리 · TTL 24h"였습니다.** 구 명칭(골든30) 시점의 30분 대응 전제에서 나온 것이라, **3영업일 뒤 재방문해 서류를 만드는 것이 불가능했습니다.**
>
> `04-pii-boundary.md` 불변 규칙 3도 같은 날 24시간에서 이 값으로 통일됐습니다.

## 1. 공통 규약

| 항목 | 값 |
| --- | --- |
| 기본 경로 | `/api` |
| 형식 | JSON. `Content-Type: application/json` |
| 인코딩 | UTF-8 |
| 시각 | ISO 8601, **시간대 포함** (`2026-08-16T14:30:00+09:00`) |
| 사건 식별 | 경로 파라미터 `{case_id}` (ULID) |
| 세션 식별 | `X-Session-Id` 헤더 |

**모든 시각에 시간대를 포함합니다.** 기한 계산이 날짜 경계에 걸리면 시간대 하나로 하루가 어긋납니다.

### 1.1 계측 헤더

모든 응답에 붙습니다. **PII 보호가 작동한다는 것을 응답 자체가 증명합니다** → [04](08-14-pii-boundary.md) "작동할 뿐 아니라 보여야 합니다".

| 헤더 | 예 | 뜻 |
| --- | --- | --- |
| `X-Pii-Token-Count` | `account=1;name=2` | 유형별 토큰화 건수 |
| `X-Pii-Egress-Residual` | `0` | 송출 직전 잔여 건수. 정상은 `0` |
| `X-Kb-Version` | `2026.08.1` | 이 응답이 인용한 KB 버전 |
| `X-Audit-Id` | `01J8XKR2...` | 감사 로그 식별자 |

**건수만 담습니다. 값을 담지 않습니다.**

**해당 없는 헤더에는 `none` 을 넣습니다.**

> 2026-08-21 확정.

빈 문자열을 쓰지 않습니다 — **관리자 문지기(`proxy.ts`)를 거친 응답에서 그 헤더가 통째로
사라지는 것을 실측으로 확인했습니다.** Next.js 가 프록시 응답 헤더를 옮길 때 값이 거짓으로
평가되면 건너뜁니다(`resolve-routes.js`). 헤더가 없는 것과 「해당 없음」은 다른 뜻이라,
**증명이 목적인 헤더가 조용히 사라지면 안 됩니다.**

### 1.2 환경변수

**비밀 값을 코드나 설정 파일에 넣지 않습니다.** 전부 환경변수로 받습니다.

| 변수 | 무엇 | 필수 | 정의된 곳 |
| --- | --- | :---: | --- |
| `DATABASE_URL` | 관계형 DB 접속 | Y | [09](../backend/08-16-data-model.md) |
| `KV_URL` | 볼트 저장소 접속 | Y | [09](../backend/08-16-data-model.md) §11 |
| `SUPABASE_URL` · `SUPABASE_SERVICE_ROLE_KEY` | Supabase 접속 (DB·Storage) | Y | [ADR-016](../../decisions/016-retention-and-datastore.md) |
| `VAULT_MASTER_KEY` | 볼트 마스터 키 | Y | [04](08-14-pii-boundary.md) |
| `BLOB_TOKEN` | 객체 저장소 접근 | Y | [09](../backend/08-16-data-model.md) §3 |

> **전사·판독은 앱 밖에서 돕니다.** 모델을 서버리스 함수에 못 띄우기 때문입니다
> ([ADR-028](../../decisions/028-runtime-and-module-shape.md)). `TRANSCRIBER_URL` 이 비면
> 녹음·캡처를 올려도 글로 안 옮겨지고, **사건 진행은 그대로 돕니다** — 파일과 무관한 절차는
> 즉시 나갑니다(§3.1).
>
> ⚠️ **밖에 열린 서비스에는 `TRANSCRIBER_TOKEN` 이 반드시 있어야 합니다.** 그 서비스는
> 넘겨받은 주소를 내려받으므로, 비워 두면 남의 심부름을 하게 됩니다.

### 1.3 속도 제한

> 2026-08-16 확정.

**보호가 목적이지 절약이 목적이 아닙니다.** 이 서비스의 사용자는 피해 직후라 급합니다. **제한이 정상 사용을 막으면 안 됩니다** — 아래 값은 전부 사람이 손으로 낼 수 있는 속도보다 훨씬 위입니다.

| 대상 | 제한 | 근거 |
| --- | --- | --- |
| 챗 (`POST …/messages`) | **사건당 분당 20턴** | 사람이 읽고 답하는 속도의 몇 배입니다. LLM 호출이라 가장 비쌉니다 |
| 증거 업로드 | **사건당 파일 30개 · 합계 300MB** | 녹음 여러 개 + 캡처 수십 장을 상정한 값 |
| 슬롯 응답 (`PATCH …/slots/…`) | **사건당 분당 60회** | 버튼 연타를 흡수합니다 |
| 매핑 맡기기 (`POST …/vault`) | **사건당 분당 60회** | 값을 쓰기 직전마다 도니 슬롯과 같은 급입니다 |
| 사건 생성 (`POST /api/cases`) | **IP당 시간당 20건** | 남용 방지. 가족이 같은 망에서 여러 건 만드는 경우까지 덮습니다 |
| 그 외 조회 | **세션당 분당 300회** | 폴링(§3.3)이 여기 포함됩니다 |
| **사건 조회 실패**(404) | **IP당 분당 10회** | **열거 방어.** 아래 |

**초과하면 `429`(`RATE_LIMITED`)입니다.** `Retry-After` 에 남은 창 시간이 들어갑니다 → [10-errors.md](../backend/08-16-errors.md) §3.1.
**증거 업로드 상한은 창이 없어 이 헤더를 안 붙입니다** — 같은 절을 보세요.

**세는 단위가 사건(`case_id`)입니다.** 사용자 계정 체계가 없어(§5) 사람을 셀 방법이 없고, 사건은 진입 시점에 하나씩 생기므로 이게 가장 가까운 단위입니다. **사건 생성만 IP로 셉니다** — 사건이 아직 없는 시점이라 다른 기준이 없습니다.

**404 만 IP 로 셉니다.** 나머지 카운터는 사건당인데, **없는 사건을 찌르는 공격에는
무의미합니다** — 매번 다른 사건을 부르니까요. 정상 사용자는 404 를 거의 만들지 않습니다
→ [ADR-039](../../decisions/039-link-token.md) ④.

**관리자 경로(§5)는 제한하지 않습니다.** 계정이 하나뿐이고 조사 중에 걸리면 곤란합니다.

**`X-Session-Id` 가 없으면 IP 로 셉니다.**

> 2026-08-21 확정.

헤더 하나가 없다고 조회를 거절하면 위의 *"제한이 정상 사용을 막으면 안 됩니다"* 를 정면으로
어깁니다. IP 는 사건 생성에서 이미 쓰는 기준이라 새로 만든 것이 아닙니다.
**세는 키의 이름 공간을 가릅니다** — 세션 값과 IP 값이 우연히 같아도 서로를 밀어내지 않게
접두사를 붙입니다.

**세는 곳은 공유 저장소이고, 없으면 프로세스 메모리입니다.**

> 2026-08-21 확정.

`KV_URL` 이 설정돼 있으면 거기서 셉니다 — 서버가 여럿이어도 상한이 정확합니다.
없으면 프로세스 메모리에 셉니다.

**「부르면 터지는 미설정 자원」으로 두지 않습니다.** 속도 제한은 모든 요청이 지나는 길목이라,
터지게 두면 사건 생성도 조회도 전부 500 이 됩니다 — 「제한이 정상 사용을 막으면 안 된다」의
가장 심한 형태입니다. 대신 **어느 쪽으로 세고 있는지를 설정 점검에 드러냅니다.**

**증가와 조회는 한 번에 일어나야 합니다.** 읽고 나서 쓰면 동시에 들어온 요청이 같은 값을 읽어
상한을 넘깁니다.

## 2. 엔드포인트

> ⛔ **경로의 `{case_token}` 은 `case_id` 가 아닙니다** → [ADR-039](../../decisions/039-link-token.md).
> `case_id` 는 ULID 라 **앞자리가 생성 시각**이고, URL 에 쓰면 이웃 사건을 좁혀서
> 찔러볼 수 있습니다. 계정이 없어 **주소를 아는 사람이 곧 주인**이므로
> ([ADR-021](../../decisions/021-reentry-and-identity.md)) 이 값이 사실상 비밀번호입니다.
>
> **`case_id` 는 응답 본문에 그대로 나갑니다** — 숨기려는 것이 아니라 **URL 에 쓰지
> 않으려는 것**입니다. 값의 규격은 [09](../backend/08-16-data-model.md) §2 `link_token`.

## 3. 계약

### 3.1 `POST /api/cases`

```jsonc
// 요청
{ "track": "victim" }          // victim | frozen_account

// 응답 201
{
  "case_id": "01J8XKQZ3M7N2P4R6T8V0W2Y4A",
  "track": "victim",
  "status": "intake",
  "opened_at": "2026-08-16T14:30:00+09:00",
  "plan": {                     // T0 공통 안전 절차가 즉시 붙는다
    "is_superset": true,
    "steps": [                  // 단계 모양은 §3.6 과 같다 → ADR-047
      { "step_id": "01J...", "seq": 1, "title": "112에 신고하기",
        "state": "not_started", "actor": "victim", "conditional": null,
        "body": { "text": "...", "action": "call", "channel": ["phone"],
                  "contact": "112", "url": null, "url_label": null },
        "citation": { "kb_entry_id": "report-112", "kb_version": "2026.08.1",
                      "legal_basis": "통신사기피해환급법 제3조",
                      "source_url": "https://...", "effective_from": "2020-01-01" },
        "artifacts": [],
        "required_artifact": null }
    ]
  }
}
```

**사건을 만드는 즉시 T0 공통 안전 절차가 붙습니다.** 슬롯이 하나도 없어도 그렇습니다 → [02](../backend/08-14-slot-tiering.md) "진입 자체로 충분".

**단계 모양은 §3.6 과 같습니다** → [ADR-047](../../decisions/047-one-step-shape.md).

> 2026-08-21 개정. 전에는 `body`·`artifacts`·`required_artifact` 가 없고 `citation` 도 네 칸이었습니다.
> 얇은 쪽이면 **화면이 사건을 만든 직후에 작업 패널을 못 그립니다** — `body.action` 이 그 패널을
> 정하기 때문입니다([ADR-024](../../decisions/024-step-action-and-url.md)). 화면이 곧바로 플랜 조회를
> 한 번 더 불러야 했습니다.

**둘 다 실패하면 사건도 안 만들어집니다** → [ADR-046](../../decisions/046-case-and-plan-together.md).
사건을 먼저 저장하면 플랜 실패 시 **되돌아갈 수 없는 빈 사건**이 남습니다 — 에러 봉투에
`case_id` 를 담을 칸이 없기 때문입니다([10-errors.md](../backend/08-16-errors.md) §3).

### 3.2 `POST /api/cases/{case_token}/evidence`

업로드는 **presigned URL 방식**입니다. 파일이 API 서버를 거치지 않고 객체 저장소로 직접 갑니다.

```jsonc
// 1단계 — 업로드 자리 요청
{ "kind": "audio", "mime_type": "audio/m4a", "byte_size": 4210553 }

// 응답 201
{
  "evidence_id": "01J8XKR6...",
  "upload_url": "https://...",     // 유효기간 있는 직접 업로드 URL
  "upload_method": "PUT",
  "expires_at": "2026-08-16T14:35:00+09:00"
}

// 2단계 — 클라이언트가 upload_url 로 직접 PUT

// 3단계 — 업로드 완료 통지
// POST /api/cases/{case_token}/evidence/{evidence_id}/complete
// 응답 202 — Ingest 시작됨
{ "evidence_id": "01J8XKR6...", "ingest_status": "processing" }
```

**presigned 방식을 쓰는 이유:** Vercel 서버리스 함수는 요청 본문 크기와 실행 시간에 제한이 있습니다. 녹음 파일이 수십 MB일 수 있어 API 서버를 통과시키면 한계에 걸립니다.

### 3.3 `GET /api/cases/{case_token}/evidence/{evidence_id}`

전사·분석 진행 상태입니다. **폴링 방식**입니다.

```jsonc
// 응답 200 — 처리 중
{
  "evidence_id": "01J8XKR6...",
  "ingest_status": "processing",
  "progress": { "phase": "stt", "percent": 62 },
  "poll_after_ms": 1500
}

// 응답 200 — 완료
{
  "evidence_id": "01J8XKR6...",
  "ingest_status": "done",
  "transcript": [
    { "speaker": "A", "text": "[이름-1] 고객님 되시죠", "start_ms": 0 },
    { "speaker": "B", "text": "네 맞는데요", "start_ms": 2100 }
  ],
  "pii_tokens": [
    { "token": "[이름-1]", "kind": "name" },
    { "token": "[계좌-1]", "kind": "account" }
  ],
  "extracted_slots": [
    { "slot_key": "org_name", "value": "국민은행", "confidence": 0.91 }
  ]
}
```

**`transcript`는 토큰화된 상태로 내려갑니다.** 브라우저가 자기 매핑으로 복원해 화면에 표시합니다.

**`pii_tokens`는 어떤 토큰이 있는지 알려줄 뿐 원문을 담지 않습니다.** 브라우저가 파란 토큰으로 표시할 때 씁니다 → [04](08-14-pii-boundary.md) UI 절.

> 폴링을 택한 이유: Vercel 서버리스는 장시간 연결을 유지하는 스트리밍에 제약이 있습니다.
> `poll_after_ms`로 서버가 다음 호출 시점을 지시해 부하를 조절합니다.
>
> **2026-08-16 — 챗에도 스트리밍을 쓰지 않기로 확정했습니다.** 이유는 §3.9.

### 3.4 `GET /api/cases/{case_token}/slots`

```jsonc
// 응답 200
{
  "slots": [
    { "slot_key": "transferred", "tier": "T1", "state": "confirmed", "value": true },
    { "slot_key": "channel",     "tier": "T1", "state": "confirmed", "value": "CH-bank" },
    { "slot_key": "org_name",    "tier": "T2", "state": "extracted",
      "value": "국민은행", "confidence": 0.91, "source_ref": "01J8XKR6..." },
    { "slot_key": "amount",      "tier": "T2", "state": "empty", "value": null }
  ],
  "tier_status": { "T1": "satisfied", "T2": "partial" },
  "next_question": {
    "slot_key": "amount",
    "text": "얼마를 보내셨나요?",
    "input": "buttons",
    "options": ["100만원 미만","100~500만원","500~1000만원","1000만원 이상","모름·기억 안 남"]
  }
}
```

#### `next_question` — 정의는 여기 하나입니다

**이 구조는 다른 엔드포인트에서도 나갑니다** (§3.9 되묻기, [10-errors.md](../backend/08-16-errors.md) §4). **정의는 이 절에만 두고 나머지는 참조합니다** — 모양이 갈라지면 프론트가 같은 것을 두 번 구현하게 됩니다.

| 칸 | 타입 | 필수 | 뜻 |
| --- | --- | :---: | --- |
| `slot_key` | string | Y | 채우려는 슬롯. [09](../backend/08-16-data-model.md) §5.1 목록에 있는 이름만 |
| `text` | string | Y | 사용자에게 보일 질문 |
| `input` | enum | Y | `buttons` \| `text` \| `date` \| `amount` |
| `options` | string[] | `input="buttons"` 일 때 | 선택지 |

**만드는 주체는 언제나 슬롯 체커 하나입니다.** 슬롯이 비어서 묻든 모델이 근거를 못 찾아서 묻든, **사용자에게는 같은 질문이고 실제로 같은 코드가 만듭니다.**

**`next_question`은 한 번에 하나입니다.** 질문 순서는 플랜을 가장 크게 바꾸는 슬롯부터입니다 → [02](../backend/08-14-slot-tiering.md) 최소 질문 원칙.

**`options`에 「모름·기억 안 남」이 항상 들어갑니다.** 없으면 스펙 위반입니다.

**`next_question`이 `null`이어도 실행 보드는 열립니다.** 슬롯 미충족으로 진입을 막지 않습니다.

### 3.5 `PATCH /api/cases/{case_token}/slots/{slot_key}`

```jsonc
// 요청 — 값 입력
{ "action": "answer", "value": "3000000" }

// 요청 — 모름
{ "action": "unknown" }

// 응답 200
{
  "slot": { "slot_key": "amount", "state": "confirmed", "value": "3000000" },
  "plan_regenerated": true,
  "next_question": null,
  "changed_deadlines": [
    { "deadline_id": "01J...", "kind": "primary",
      "due_at": "2026-08-21T23:59:59+09:00",
      "changed_from": "2026-08-20T23:59:59+09:00" }
  ]
}
```

#### 값은 경계를 지나서 저장됩니다

> 2026-08-21 신설 → [ADR-040](../../decisions/040-write-path-boundary.md).
> 같은 날 [ADR-041](../../decisions/041-pii-confirm-with-user.md)로 **거부 대신 되묻기**가 됐습니다.

**`value` 를 그대로 저장하지 않습니다.** `pii-tokenizer` 가 검사하고, 개인정보 후보가
있으면 **저장을 미루고 사용자에게 되묻습니다.**

```jsonc
// 응답 200 — 개인정보 후보가 있어 확인이 필요합니다
{
  "slot": { "slot_key": "counterpart_account", "state": "pii_pending", "value": null },
  "pii_confirm": {
    "found": [ { "kind": "계좌번호", "text": "352-0912-3456-73" } ],
    "text": "여기에 계좌번호가 들어 있는 것 같습니다.",
    "note": "가리면 이 값은 이 기기 밖으로 나가지 않습니다.",
    "options": [
      { "id": "mask", "label": "맞아요 — 가릴게요" },
      { "id": "keep", "label": "아니에요 — 계좌번호가 아닙니다" }
    ]
  },
  "plan_regenerated": false,
  "next_question": null
}
```

**「아니에요」는 「개인정보지만 괜찮다」가 아닙니다.** 분류를 고치는 것입니다 —
`keep` 을 고르면 그 값은 **애초에 개인정보가 아니었던 것**으로 처리됩니다
([허용 목록](08-14-pii-boundary.md)과 같은 취급). **불변 규칙 2 는 사용자가 원해도
깨지지 않습니다** → [ADR-041](../../decisions/041-pii-confirm-with-user.md) ④.

**문구는 `S-11` 의 어휘를 씁니다** — 「가려진 것」·「나간 것」.
**토큰·마스킹·API 같은 말을 화면에 쓰지 않습니다.**

**확인이 플랜을 막지 않습니다.** 그 슬롯이 `pii_pending` 으로 남을 뿐이고,
**T0 와 유형 기본은 그대로 나갑니다.**

> `EGRESS_BLOCKED`(422) 는 **되묻을 수 없는 자리**에만 남습니다 — 챗 발화의 잔여 검사와
> `chat-publisher` 의 나가기 직전 검사입니다.

**서버가 몰래 토큰화하지도 않습니다.** 그러려면 서버가 매핑을 만들어야 하는데,
매핑은 브라우저가 만들어 암호화해 맡기는 것이고([ADR-009](../../decisions/009-restore-mapping-location.md)),
**서버가 만든 토큰은 브라우저가 복원하지 못해 그 슬롯이 영영 빈칸이 됩니다.**
**가리는 것은 사용자가 「맞아요」를 누른 뒤 브라우저가 합니다.**

**금액·기관명·시각은 원문 그대로가 정상입니다** → [토큰화 제외 목록](08-14-pii-boundary.md).
`counterpart_account` 처럼 토큰으로 오는 슬롯은 [09](../backend/08-16-data-model.md) §5.1이 표시합니다.

**슬롯이 채워지면 플랜을 자동 재생성합니다** → [02](../backend/08-14-slot-tiering.md).

**재생성 시 이미 완료된 단계와 부산물은 보존됩니다** → [09](../backend/08-16-data-model.md) §6.1.

**기한이 바뀌면 `changed_from`을 함께 보냅니다.** 안내한 날짜가 조용히 바뀌면 사용자가 이전 날짜를 계속 믿습니다.

```jsonc
  "kb_version": "2026.08.1",
  "channels": [

      "org_id": "kb-bank",        // 서버가 해석한 기관. null 이면 미특정

                "step_key": "bank-freeze-request",// KB 항목 식별자 — 사슬을 잇는 열쇠
                "after": [] },                    // 선행 사슬. 없으면 빈 배열
      "citation": {
        "kb_entry_id": "bank-freeze-request",
        "kb_version": "2026.08.1",
        "legal_basis": "통신사기피해환급법 제4조",

```

**모든 `steps[]` 에 `citation`이 있습니다. 없으면 응답을 만들지 않습니다** → `CLAUDE.md` 불변 규칙 1.

**`body.action`이 화면의 작업 패널을 정합니다** — 일곱 값과 뜻은
[09](../backend/08-16-data-model.md) §11.4.6, 패널은 [워크스페이스 패널](../frontend/08-17-workspace-panels.md).
**클라이언트가 `actor`·`channel`·`required_artifact`로 유형을 추론하지 않습니다** —
서버가 준 `action`을 그대로 씁니다 → [ADR-024](../../decisions/024-step-action-and-url.md).

**`contact`는 서버가 `contact_ref`를 푼 값입니다.** 기관을 특정 못 했거나 번호가 미확인이면 `null`이고,
**그때도 절차는 나갑니다** → [09](../backend/08-16-data-model.md) §11.4.3.

**`org_id`가 `null`이면 기관을 특정하지 못한 것입니다.** 클라이언트는 이때 "어느 은행인지 확인해 주세요"를 띄울 수 있습니다. `org_name`만으로는 서버가 표기를 어떻게 해석했는지 알 수 없어 이 판단이 불가능합니다 → [09](../backend/08-16-data-model.md) §4.1.

**슈퍼셋 플랜이면 `is_superset: true`이고 조건부 단계에 `conditional` 라벨이 붙습니다.**

```jsonc
{ "title": "간편송금 사업자에 지급정지 요청",
  "conditional": "카카오페이로 보냈다면" }
```

> ✅ **확정 — `body` 에 `step_key`·`after` 를 싣습니다** (2026-08-23)
>
> [화면 설계](../frontend/08-14-screens.md) §S-07 은 **「번호는 `body.after` 사슬에 있는
> 단계에만」** 붙입니다. **우리 단계는 절반이 순서가 없습니다** — 112 신고와 지급정지는
> 동시에 하는 것이라, 전부 번호를 매기면 **없는 순서를 지어내는 것**이 됩니다.
>
> | 칸 | 무엇 |
> | --- | --- |
> | `step_key` | KB 항목 식별자. 남의 `after` 가 이 값을 가리킵니다 |
> | `after` | 선행 사슬. **없으면 빈 배열**(칸을 빼지 마세요 — 「모른다」와 「없다」가 갈립니다) |
>
> KB 가 이미 가진 값이고 `plan_step.body` 는 JSONB 라 담는 데 스키마 변경이 없습니다.
> 안 실으면 화면은 **전부 점**으로 그립니다 — 진짜 순서가 있는 곳(신청 → 서류 → 접수증)이
> 안 보이고, 「번호가 붙은 것만 순서대로」 안내 줄도 뜨지 않습니다.
>
> 화면 쪽(`plan-viewer` 의 `numberSteps`)은 **이 모양을 기다리며 이미 서 있습니다.**
>
> → [층 C · 보여주는 셋 구현 계획](../../docs/plans/08-22-layer-c-viewers.md) Task 3

> 화면이 `due_at` 에서 세면 **사용자 기기의 날짜가 틀릴 때 기한을 놓칩니다.**
>
> | | |
> | --- | --- |
> | 칸 | `days_left: number` |
> | 언제 | **아직 안 지난 기한에만.** 오늘이면 `0` |
> | 지난 기한은 | **칸을 뺍니다.** `status: "missed"` 하나로 말합니다 |
> | 음수 | **보내지 않습니다** |
>
> 지난 기한의 표시는 **「본 기한 8월 20일 · 지남」 배지**가 맡습니다 (시안 「deadline-badges」).
> 「D+3」 같은 표시는 시안에 없으므로, 음수가 와도 화면은 **그리지 않고 날짜만 보입니다.**
>
> ⚠️ **대가 하나:** 서버가 `missed` 를 늦게 붙이면 그 사이 지난 기한이
> **아직 안 지난 것처럼** 보입니다. `days_left` 계산과 `status` 전이를 **같은 자리에서**
> 하세요 — 둘이 갈라지면 화면이 알아챌 신호가 없습니다.
>
> → [층 C · 보여주는 셋 구현 계획](../../docs/plans/08-22-layer-c-viewers.md) Task 5·6

> ✅ **확정 — 대기 국면은 `starts_at`·`elapsed` 를 함께 싣습니다** (2026-08-23)
>
> [화면 설계](../frontend/08-14-screens.md) §S-07 공고 대기 카드는 **달력 앵커**를 그립니다 —
> 「8월 30일 공고 시작 · **지금** · 10월 30일 만료 예정」. 그런데 응답에는 만료 시점밖에 없어
> **시작 시점도, 지금이 어디쯤인지도** 알 수 없었습니다.
>
> **화면이 만들 수 없습니다.** 만들려면 기기 시계를 읽어야 하고, 그건
> [기한 규칙](08-16-deadline-rules.md) 「기준 시계는 서버」와 `CLAUDE.md` 불변 규칙 7 을 어깁니다.
>
> | 칸 | 무엇 | 없으면 |
> | --- | --- | --- |
> | `starts_at` | 그 기간이 시작된 시점 (`due_at` 과 짝) | 앵커 왼쪽 끝을 못 그립니다 |
> | `elapsed` | 시작~만료 사이에서 지금이 어디인가. `0`~`1` | **마커를 못 놓습니다** — 카드가 「언제 끝나는지」만 말하게 됩니다 |
>
> **`kind: "info"` 에만 필요합니다.** 사용자 기한(`primary`·`grace`)은 D-day 로 충분합니다.
> **이름은 제안입니다** — 서버가 다른 이름을 쓰면 화면이 맞춥니다.
> 화면 쪽(`deadline-viewer` 의 `WaitCard`)은 이 두 값을 **밖에서 받는 모양으로 이미 서 있고**,
> 지금은 `src/app/c/[token]/fixtures.ts` 의 견본을 먹고 있습니다.

### 3.8 `POST /api/cases/{case_token}/steps/{step_id}/artifacts`

```jsonc
// 요청 — 접수번호 직접 입력
{ "kind": "receipt_no", "value": "2026-1234567" }

// 요청 — 캡처 업로드 (evidence 와 같은 presigned 흐름)
{ "kind": "sms_capture", "evidence_id": "01J8XKRB..." }

// 요청 — 자기 신고
{ "kind": "other", "self_reported": true }

// 응답 200 — L1 통과
{
  "artifact_id": "01J8XKRC...",
  "verify_level": "L1",
  "verify_result": "passed",
  "step_state": "done_verified",
  "unlocked_steps": [
    { "step_id": "01J8XKRD...", "title": "피해구제 신청서 작성",

  ]
}

// 응답 200 — L1 실패 (에러 아님)
{
  "artifact_id": "01J8XKRC...",
  "verify_level": "L1",
  "verify_result": "failed",
  "verify_detail": { "reason": "format_mismatch" },
  "step_state": "in_progress",
  "next_options": [
    { "level": "L2", "label": "접수 문자 캡처를 올려주세요" },
    { "level": "L3", "label": "번호 없이 접수했다고 표시" }
  ]
}

// 응답 200 — L3 자기 신고
{
  "artifact_id": "01J8XKRC...",
  "verify_level": "L3",
  "verify_result": "not_applicable",
  "step_state": "unconfirmed",
  "note": "완료로 기록되지 않습니다. 접수번호를 확인하시면 알려주세요"

```

**`value` 도 경계를 지납니다** — §3.5와 같습니다. 접수번호는 개인정보가 아니지만
사용자가 다른 것을 붙여 넣을 수 있고, **`artifact.value_masked` 는 이름 그대로 원문을
금지합니다** → [ADR-040](../../decisions/040-write-path-boundary.md).

**`unlocked_steps`는 증거 연쇄를 보여줍니다.** 부산물이 다음 단계의 입력이 되는 구조를 사용자가 이해하게 만듭니다.

### 3.9 `POST /api/cases/{case_token}/messages` — 대응 비서 챗 (`F-07`)

```jsonc
// 요청
{ "content": "지급정지는 걸었는데 이제 뭘 해야 하나요" }

// 응답 200
{
  "message_id": "01J8XKRE...",

  "reply": "지급정지를 거셨으면 다음은 피해구제 신청서 제출입니다. 8월 20일까지 하셔야 하고, 이 날짜를 넘기면 은행이 9월 3일까지 추가 기간을 줍니다. 접수 문자가 오면 올려주세요.",

  "citations": [
    { "ref": "kb-2",
      "label": "피해구제 신청서 제출",
      "why": "지급정지를 이미 걸었으므로, 다음 단계가 신청서 제출이라고 안내하는 데 썼습니다",
      "kb_entry_id": "relief-application",
      "kb_version": "2026.08.1",
      "legal_basis": "통신사기피해환급법 시행령 제3조 제2항·제3항",
      "source_url": "https://www.law.go.kr/...",
      "effective_from": "2026-07-01" },
    { "ref": "case-3",
      "label": "피해구제 신청 기한",
      "why": "8월 20일이라는 날짜를 문장에 그대로 옮기는 데 썼습니다" }
  ],

  "referenced_steps": ["01J8XKRD..."],
  "referenced_deadlines": ["01J8XKR8...", "01J8XKR9..."]
}
```

**`citations`가 이 답변이 무엇을 보고 쓰였는지 밝힙니다.** `ref`는 서버가 이번 턴 프롬프트에 발급한 번호입니다 → [11](../backend/08-16-chat-context.md) §3.4 · §5.

| `ref` 접두 | 무엇을 가리키나 | `kb_entry_id` |
| --- | --- | :---: |
| `kb-` | 절차 항목 (적용·참고 둘 다) | **있음** |
| `case-` | 사건 정보 — 슬롯·단계·기한·부산물 | 없음 |
| `t-` | 전사 한 줄 | 없음 |
| `null` | 정보를 담지 않는 문장 (서비스 사용법·인사) | — |

**`citations`에 두 종류가 섞이므로 `kb_entry_id`·`kb_version`·`legal_basis`·`source_url`·`effective_from`은 선택 항목입니다.** `kb-` 항목에만 붙습니다. **화면에서 법령 근거로 표시하는 것도 `kb-`뿐입니다** — 사건 정보와 전사는 지식베이스 항목이 아닙니다.

**`why`는 「어떻게 썼는지」를 적습니다.** 답변의 어느 대목에 쓰였는지가 드러나야 합니다. 「왜 관련 있는지」만 적으면 안 쓴 항목에도 그럴듯하게 붙습니다.

> **답변을 문장 단위로 쪼개지 않습니다.** 2026-08-16 검토했다가 접었습니다 — **분할 기준을 정할 수 없었습니다.** 한국어에서 `"~하고,"`로 이어지는 문장을 끊으면 어색해지고, 모델 출력이 복잡해져 형식 오류 재시도가 늘어납니다. **대신 인용이 실제로 답변에 쓰였는지를 기계로 확인할 수 없게 됐습니다** → §3.9 검증 3번.

#### 근거가 없으면 되묻습니다

**모델이 답할 근거를 못 찾으면 `insufficient: true`를 냅니다.** 그러면 에러가 아니라 질문이 나갑니다.

```jsonc
// 응답 200
{
  "message_id": "01J8XKRF...",
  "reply": "정확한 안내를 위해 하나만 확인하겠습니다.",
  "citations": [],
  "next_question": { "slot_key": "channel", "…": "…" }   // 구조는 §3.4
}
```

**`next_question` 은 §3.4 와 같은 구조입니다.** 만드는 것도 같은 슬롯 체커입니다.

**이 경로에서는 재시도하지 않습니다.** 형식 오류가 아니라 근거가 없다는 선언이라 **같은 프롬프트로 다시 부르면 같은 답이 옵니다.** 재시도는 `ref` 검증을 어겼을 때만 합니다 → [10-errors.md](../backend/08-16-errors.md) §2.

**채울 슬롯이 더 없으면 그때 1332를 안내합니다** → [10-errors.md](../backend/08-16-errors.md) §4.1.

#### 챗의 규칙

**서버가 매 턴 KB를 조회해 프롬프트에 넣습니다.** 모델은 도구를 부르지 않고, 조회 조건에도 관여하지 않습니다. 조립 규칙은 [11-chat-context.md](../backend/08-16-chat-context.md), 조회 우선순위는 [09](../backend/08-16-data-model.md) §11.2.

**인용 허용 집합은 이번 요청 프롬프트에 실제로 들어간 KB 항목입니다.** 그 목록이 `message.kb_context_refs`에 저장됩니다. **프롬프트에 없던 항목을 인용하면 서버가 거부합니다** → [09](../backend/08-16-data-model.md) §9.1

**「절차를 언급했는지」를 판정하지 않습니다.** 그 판정에 근거가 없기 때문입니다 → [11](../backend/08-16-chat-context.md) §6.1. 대신 **모든 문장이 `ref`로 출처를 밝히거나 `null`로 정보 없음을 밝힙니다.**

**서버가 확인하는 것은 셋입니다** → [11](../backend/08-16-chat-context.md) §6.2.

| # | 확인 | 어기면 |
| --- | --- | --- |
| 1 | `ref`가 이번 턴에 발급한 번호인가 | 지어낸 참조 → `KB_CITATION_MISSING`, 재시도 |
| 2 | `citations`의 각 항목에 `why`가 채워져 있는가 | 형식 위반 → 같음 |
| 3 | `insufficient`가 `true`인가 | **되묻기.** 에러 아님 |

**1·2번은 형식 위반이라 재시도합니다. 3번은 재시도하지 않습니다.**

> **2026-08-18 「인용 바꿔치기」 검사가 빠졌습니다.** 모델이 `kb_entry_id`·`kb_version` 을
> 아예 받지 않게 되어 바꿔칠 대상이 없어졌습니다 → [11](../backend/08-16-chat-context.md) §5.

**2번은 형식 검사일 뿐입니다.** `why`의 내용이 실제 답변과 맞는지는 기계로 확인할 수 없습니다. **과잉 인용은 억제만 하고 검사로는 잡지 못합니다** — 이유를 쓰게 하면 관련 없는 항목은 쓸 말이 없어 스스로 걸러지지만, 그럴듯하게 지어 쓰면 통과합니다.

**조회 결과가 0건이면 절차를 말하지 않습니다.** 이때는 `citations`가 비어도 위반이 아닙니다 → [10-errors.md](../backend/08-16-errors.md) §4.1

```jsonc
{
  "reply": "말씀하신 경우에 대한 확인된 절차를 아직 갖고 있지 않습니다. 금융감독원 1332로 연락하시면 상담받으실 수 있습니다.",
  "citations": [],
  "kb_result": "empty"
}
```

**조회 자체가 실패하면 챗을 멈춥니다.** `KB_UNAVAILABLE`(503)입니다. 공통 안전 절차로 폴백할 수 없습니다 — **§3.1에서 보듯 T0 단계에도 `citation`이 붙어 있어, T0 자체가 KB 항목**이기 때문입니다.

#### 응답 형식 — 판단 근거를 함께 받습니다

**모델 출력을 판단 근거와 응답 둘로 강제합니다.**

```jsonc
// 모델이 내놓는 것 (서버 안에서만)
{
  "reasoning": "사용자가 지급정지를 이미 걸었다고 했고 freeze_requested_at 이 confirmed 다. 다음 단계는 relief-application 인데 3영업일 기한이 걸려 있어 이걸 먼저 안내한다. 기한 날짜는 프롬프트에 계산돼 들어온 값을 그대로 쓴다.",
  "reply": "다음은 피해구제 신청서 제출입니다. …",
  "citations": [ /* … */ ]
}
```

**`reasoning`은 사용자 응답에 나가지 않습니다.** 서버가 `message.reasoning_masked`에 저장하고 응답 본문에서는 뺍니다.

#### 스트리밍을 쓰지 않습니다

> 2026-08-16 확정.

**응답을 다 받은 뒤 검사를 통과한 것만 내려보냅니다.** 글자가 한 자씩 나타나는 방식을 쓰지 않습니다.

챗 응답에는 **내보내기 전에 통과해야 하는 검사가 셋** 있습니다.

| 검사 | 무엇 | 정의된 곳 |
| --- | --- | --- |
| 인용 검증 | 절차를 언급했는데 `citations`가 비었는가 | [10](../backend/08-16-errors.md) §4 |
| 판단 근거 분리 | `reasoning`을 응답 본문에서 뺐는가 | 위 |
| 잔여 PII | 송출 직전 원문이 남았는가 | [04](08-14-pii-boundary.md) |

**스트리밍이면 이 검사들이 응답이 끝난 뒤에야 가능합니다.** 근거 없는 절차 문장이 화면에 먼저 뜬 다음 지워지는데, **잘못된 절차 안내가 곧 금전 손실인 서비스에서 그 한 번의 노출을 되돌릴 수 없습니다.** 사용자는 이미 읽었습니다.

`reasoning`이 앞에 오는 것도 문제입니다. 모델이 판단 근거를 먼저 내놓는데 스트리밍이면 그게 먼저 흘러갑니다. 화면에 안 띄우려면 어차피 구분자까지 기다려야 해서 스트리밍의 이득이 사라집니다.

**체감 속도는 다른 방법으로 확보합니다** — 응답이 2~4문장으로 짧고, 대기 중 진행 표시를 띄웁니다.

**API 응답 본문에 넣지 않는 이유**는 화면이 실수로 표시할 수 있기 때문입니다. 판단 근거에는 "이 사용자는 아직 신고를 안 한 것으로 보임" 같은 내부 판단이 들어가는데, 그게 화면에 뜨면 사용자가 불필요하게 불안해집니다.

관리자는 §5의 별도 경로로 봅니다.

**날짜는 서버가 계산해 프롬프트에 넣습니다. 모델이 세지 않습니다** → `CLAUDE.md` 불변 규칙 7.

```
프롬프트에 넣는 것:   기한: 2026년 8월 20일까지 (본 기한)
                           2026년 9월 3일까지 (추가 기간)
모델이 하는 것:       위 날짜를 문장에 넣기
모델이 하지 않는 것:  "3영업일 뒤" 를 계산하기
```

**`reply` 안의 토큰은 종류별로 부분 복원됩니다** → [04](08-14-pii-boundary.md) 「복원 위치와 범위」

| 종류 | 화면에 뜨는 것 |
| --- | --- |
| 계좌 | `국민 ****7890` |
| 이름 | `김O수` |
| 전화 | `010-****-5678` |
| **주민번호** | **복원 안 함** |

계좌가 둘 이상일 때 어느 건인지 구분하기 위해서입니다. **주민번호는 사건에 하나뿐이라 구분할 대상이 없고, 생년월일이 그대로 나가므로 제외합니다.**

```jsonc
// 인젝션 시도가 있었을 때
{
  "reply": "요청하신 값은 국민 ****7890, [주민번호-1] 입니다.",
  //                      ^^^^^^^^^^^^^^  ^^^^^^^^^^^^
  //                      뒷 4자리만       복원 안 됨
  "citations": []
}
```

**전체 계좌번호와 주민번호는 나가지 않습니다.** 그리고 모델이 지어낸 토큰은 이 사건 매핑에 없어 복원되지 않습니다.

### 3.10 `GET /api/cases/{case_token}` — 재방문 진입

> 2026-08-21 신설. 엔드포인트 목록에는 있었으나 **계약이 없었습니다** →
> [API 라우트 착수](../../docs/plans/08-20-api-routes.md) blocker ①.

**`/c/{token}` 첫 로드의 유일한 입구입니다.** 이것이 없으면
[ADR-021](../../decisions/021-reentry-and-identity.md)이 약속한 **「며칠 뒤 링크를 열면
곧장 플랜으로」**가 성립하지 않습니다.

```jsonc
// 응답 200
{
  "case_id": "01J8XKR5...",
  "track": "victim",                          // victim | frozen_account
  "created_at": "2026-08-14T15:02:00+09:00",
  "last_activity_at": "2026-08-20T09:11:00+09:00",
  "purge_after": "2027-02-16",                // ADR-016 · 마지막 활동일부터 180일

  "slots":     { /* §3.4 응답 그대로 — slots · tier_status · next_question */ },
  "plan":      { /* §3.6 응답 그대로 — is_superset · channels · steps */ },
  "deadlines": { /* §3.7 응답 그대로 */ }
}
```

#### 구조를 다시 정의하지 않습니다

**세 덩어리는 **§3.4 · §3.6 · §3.7 의 응답 그대로****입니다.
모양을 여기 다시 적지 않습니다 — `next_question` 을 한 곳에만 정의한 것과 같은 이유입니다.
**갈라지면 프론트가 같은 것을 두 번 구현합니다.**

**그래서 이 엔드포인트는 새 계약이 아니라 합본입니다.** 세 개를 따로 부르면
첫 화면이 뜨기까지 왕복이 넷이고, 패닉 상태의 사용자가 그 시간을 빈 화면으로 봅니다.

#### 초기 화면을 **서버가 지목하지 않습니다**

`focus`·`side` 를 응답에 넣지 않습니다. **`case-opener`(층 C)가 아래 규칙으로 고릅니다** —
[ADR-035](../../decisions/035-screen-state-axes.md)가 이미 그 소관으로 정했습니다.

```
focus   plan.steps 가 비어 있지 않으면  → 'plan'
        그 밖                          → 'chat'

side    plan.steps 에 지금 할 단계가 있으면 → 'work'
        그 밖                              → 'casefile'
```

**화면 구조가 바뀔 때마다 서버를 고치게 두지 않으려는 것입니다.** 화면은 프론트 소관이고,
서버는 **사실만** 줍니다. 되돌리기도 쉽습니다 — 필드 하나를 더하면 됩니다.

> **`focus: 'evidence'` 로는 열지 않습니다.** 증거함은 사용자가 눌러서 가는 곳이지
> 재진입의 도착지가 아닙니다. [화면 설계](../frontend/08-14-screens.md)의
> 「`focus: "evidence"` 시그널이 없다」는 TODO 는 **없는 것이 맞다**로 닫힙니다.

#### 찾지 못하면 404 하나입니다

| 상황 | 응답 |
| --- | --- |
| 없는 사건 | `CASE_NOT_FOUND` 404 |
| **파기된 사건** | `CASE_NOT_FOUND` 404 — **같습니다** |

**둘을 구분하지 않습니다.** 「있었는데 지웠다」와 「없었다」를 가르면
**그 토큰이 한때 유효했다는 사실**이 밖으로 나갑니다. 익명 링크에서는 그것 자체가 정보입니다.

**대신 화면이 둘 다 설명합니다** — 「이 주소의 사건을 찾을 수 없습니다.
마지막 활동일부터 180일이 지나면 자동으로 파기됩니다.」 API 를 나누지 않아도
사용자는 답을 얻습니다.

#### ⚠️ 경로 파라미터는 아직 미정입니다

**`{case_id}` 가 URL 의 `{token}` 과 같은 값인지 정해지지 않았습니다**
([ADR-021](../../decisions/021-reentry-and-identity.md) 「남은 것」).

> ⛔ **같다면 문제가 있습니다.** `case_id` 는 ULID 인데
> [ULID 는 앞자리가 시간순](../backend/08-16-data-model.md)이라, 하나를 알면
> **비슷한 시각에 만들어진 사건을 좁혀서 찔러볼 수 있습니다.**
> 익명 링크는 **토큰이 곧 인증**이라([ADR-021](../../decisions/021-reentry-and-identity.md))
> 추측 가능성이 그대로 접근 위험입니다.
>
> **이 계약은 그 결정과 무관하게 그대로 섭니다** — 경로에 무엇이 오든 응답은 같습니다.
> 다만 **라우트를 붙이기 전에 정해야 합니다.**

### 3.11 `POST /api/cases/{case_token}/vault` — 복원 매핑 맡기기

> 2026-08-21 신설. [ADR-009](../../decisions/009-restore-mapping-location.md)가
> 「암호화해 서버 볼트에」로 정했는데 **넣는 경로가 없었습니다** —
> [API 라우트 착수](../../docs/plans/08-20-api-routes.md) blocker ③.
> 볼트 포트가 **파기용 둘(`delete`·`remains`)뿐**이었습니다.

**브라우저가 봉한 토큰↔원문 대응표를 맡기는 자리입니다.**
이것이 없으면 `[계좌-1]` 이 영영 `[계좌-1]` 이고, **서류 기재 안내(S-10)가 통째로 빈칸**입니다.

```jsonc
// 요청
{
  "entries": [
    { "token": "[계좌-1]", "ciphertext": "base64(iv‖암호문)" },
    { "token": "[이름-1]", "ciphertext": "base64(iv‖암호문)" }
  ]
}

// 응답 200
{ "stored": 2 }
```

**모양은 `key-handler` 의 `VaultEntry` 그대로입니다** — 브라우저가 `sealAll()` 로 만든 것을
그대로 보냅니다. 서버가 다시 정의하지 않습니다.

#### 서버는 이것을 읽을 수 없습니다

`ciphertext` 는 **AES-GCM** 결과이고 **복호화 키는 브라우저에만** 있습니다
([ADR-027](../../decisions/027-session-key-storage.md) — `extractable: false` 로 IndexedDB 에).
서버가 하는 일은 **받아서 보관하고, 파기일에 지우는 것**뿐입니다.

**`token` 은 평문입니다.** `[계좌-1]` 자체는 개인정보가 아니고, 조회 키로 써야 합니다.

#### ⛔ 매핑을 **먼저** 올리고, 값을 **나중에** 씁니다

**순서가 계약입니다.**

```
① POST …/vault           매핑을 맡긴다
② PATCH …/slots          그 토큰이 든 값을 쓴다
```

**거꾸로 하면 안 됩니다.** ②가 성공하고 ①이 실패하면 **아무도 못 푸는 토큰**이 사건에
남고, 사용자는 서류 화면에서 빈칸을 보게 됩니다. **그리고 그게 왜 빈칸인지 알 방법이 없습니다.**

반대 순서의 실패는 안전합니다 — ①만 성공하면 **쓰이지 않는 매핑**이 남을 뿐이고,
파기일에 함께 지워집니다.

#### 같은 토큰을 다시 보내도 됩니다

**`(사건, token)` 기준으로 덮어씁니다.** AES-GCM 은 매번 다른 IV 를 쓰므로 같은 값이라도
암호문이 달라집니다 — **다르다고 해서 다른 값이 아닙니다.**

**같은 값에는 같은 토큰이 붙습니다** → [PII 격리 경계](08-14-pii-boundary.md)
「같은 값이 다시 나오면 같은 번호」. 그래서 덮어쓰기로 충분합니다.

#### 저장 위치는 볼트입니다 — 관계형 DB 가 아닙니다

`KV_URL` 쪽입니다. [ADR-016](../../decisions/016-retention-and-datastore.md)의 **세 층**
중 「복원 매핑 암호문」 층이고, 파기일에 **세 층이 함께** 사라집니다.
**DDL 이 바뀌지 않습니다.**

#### 왜 별도 엔드포인트인가

| 검토한 것 | 왜 아닌가 |
| --- | --- |
| `POST /api/cases` 에 한 번에 | **매핑은 계속 생깁니다** — 챗 발화마다, 슬롯 입력마다. 한 번으로 안 끝납니다 |
| 쓰기 요청마다 얹어 보내기 | 왕복은 줄지만 **볼트 쓰기가 모든 엔드포인트에 흩어집니다.** 한 곳이 아니면 순서 규칙을 지키는지 볼 자리가 없습니다 |

#### 오류

| 상황 | 응답 |
| --- | --- |
| 없는 사건 | `CASE_NOT_FOUND` 404 |
| `entries` 가 비었거나 `token`·`ciphertext` 가 빠짐 | `INTERNAL` 500 — ⬜ **아래 TODO** |
| 볼트가 안 붙었거나 쓰기 실패 | `STORE_ERROR` 503 |

> ⬜ **TODO(미정)** — **요청 형식 오류를 낼 코드가 없습니다.** 코드 표에 `BAD_REQUEST`(400)이
> 없어서, 지금은 `INTERNAL`(500)로 나갑니다. **이 엔드포인트만의 문제가 아닙니다** →
> [API 라우트 착수](../../docs/plans/08-20-api-routes.md) 「정본에 없어 채워야 하는 것」.

> ⬜ **TODO(미정)** — 한 번에 보낼 수 있는 `entries` 개수와 `ciphertext` 길이 상한.
> **상한이 없으면 볼트가 사건 하나로 채워질 수 있습니다.**

## 4. LLM 호출과 API의 관계

이 서비스가 LLM에 시키는 일은 넷이고, **각각 다른 엔드포인트 뒤에 있습니다.**

| LLM 호출 | 어디서 | 출력 | 인용 필요 |
| --- | --- | --- | :---: |
| 수법 판별·위험도 (`F-04`) | `POST .../evidence/.../complete` 이후 | 분류 + **근거 스팬** | 근거 스팬 |
| 슬롯 추출 (`F-05b`) | 같음 | 슬롯 값 + 확신도 | — |
| 플랜 생성 (`F-05`) | `PATCH .../slots/...` 이후 | 단계 목록 | **KB 인용** |
| 챗 응답 (`F-07`) | `POST .../messages` | 문장 | **KB 인용** |

**넷 다 서버가 필요한 것을 다 채워 넣는 단발 호출입니다. 도구를 쓰지 않습니다.**

**언어모델은 Grok(xAI)입니다.** OpenAI 호환 API를 씁니다 (`https://api.x.ai/v1`). 키는 `XAI_API_KEY` → §1.2

챗도 예외가 아닙니다. **서버가 KB를 조회해 프롬프트에 넣고 모델을 한 번 부릅니다.** 조회 조건(`track`·`channel_id`·`org_id`·조회 기준일·KB 버전)을 서버가 전부 알고 있어, 모델에게 물어볼 것이 없습니다 → [09](../backend/08-16-data-model.md) §11.2

**모든 호출이 `pii-tokenizer` 를 통과한 페이로드로만 이루어집니다.** 우회 경로를 만들지 않습니다.

**기한 계산은 이 넷 어디에도 없습니다.** 코드의 규칙입니다.

## 5. 관리자 조회 — 왜 이런 응대가 나갔는지

**응답 하나를 놓고 "무엇을 보고 그렇게 답했는지"를 재현할 수 있어야 합니다.**

### 5.1 엔드포인트

| 메서드 | 경로 | 기능 |
| --- | --- | --- |
| `GET` | `/api/admin/cases/{case_token}/messages/{message_id}` | 그 턴의 프롬프트 전문·판단 근거·KB 항목 |
| `GET` | `/api/admin/cases/{case_token}/trace` | 사건 전체 턴의 요약 |

**일반 경로와 분리합니다.** `/api/admin/` 아래에만 둡니다.

#### 인증 — 관리자 계정 하나

**MVP 범위에서는 계정을 하나만 둡니다.** 사용자 계정 체계를 만들지 않습니다.

| 항목 | 값 |
| --- | --- |
| 계정 | 하나. 아이디·비밀번호를 환경변수로 받음 |
| 환경변수 | `ADMIN_USERNAME` · `ADMIN_PASSWORD_HASH` |
| 인증 방식 | 로그인 후 세션 쿠키 |
| 헤더 | `X-Session-Id`(사용자용)와 **별개** |
| 쿠키 이름 | `__Host-fin_ally_admin` |
| 수명 | **8시간** |
| 담는 것 | **만료 시각 하나.** 아이디도 개인정보도 넣지 않습니다 |
| 서명 | `ADMIN_PASSWORD_HASH` 에서 파생한 키로 HMAC |

> 2026-08-21 확정.

**비밀번호를 평문으로 저장하지 않습니다.** 해시만 환경변수로 받습니다.

**`__Host-` 접두사를 씁니다.** 브라우저가 가장 엄격하게 다루는 형식입니다 — 하위 도메인이
같은 이름의 쿠키를 밀어넣을 수 없고, 경로가 `/` 이며 보안 연결에서만 오갑니다.

**서명 키를 새 환경변수로 만들지 않습니다.** `ADMIN_PASSWORD_HASH` 에서 고정 라벨로 한 번 더
HMAC 해 만듭니다. 표에 이름을 하나 더 늘리면 배포마다 빠뜨릴 자리가 생기고, 덤으로
**비밀번호를 바꾸면 기존 세션이 전부 끊깁니다** — 그게 맞는 동작입니다.

**저장된 해시를 그대로 서명 키로 쓰지 않습니다.** 용도가 다른 두 곳이 같은 값을 쓰면 한쪽이
새면 다른 쪽도 같이 무너집니다.

**담는 것이 만료 시각 하나뿐인 이유**는 계정이 하나라 누구인지 담을 것이 없기 때문입니다.

**`/api/admin/` 아래 모든 경로에 인증을 겁니다.** 인증 없이 접근하면 `401`입니다. 미들웨어에서 경로 접두사로 일괄 처리하고, **엔드포인트마다 개별로 확인하지 않습니다** — 새 관리자 경로를 추가할 때 인증을 빠뜨리는 것을 막기 위해서입니다.

> 사용자 계정 체계는 대회 범위 밖입니다. 서비스가 실제로 운영되면 관리자 여럿·권한 분리가 필요하고, 그때는 이 결정을 뒤집는 새 ADR을 씁니다.

### 5.2 응답

```jsonc
// GET /api/admin/cases/{case_token}/messages/{message_id}
{
  "message_id": "01J8XKRE...",
  "turn_no": 4,
  "created_at": "2026-08-16T14:40:00+09:00",

  "prompt": "…이 턴에 실제로 보낸 프롬프트 전문 (토큰화 상태)…",
  "reasoning": "사용자가 지급정지를 이미 걸었다고 했고 freeze_requested_at 이 confirmed 다. 다음 단계는 relief-application …",
  "reply": "다음은 피해구제 신청서 제출입니다. …",

  "kb_context": [
    { "kb_entry_id": "bank-freeze-request", "kb_version": "2026.08.1", "group": "applied" },
    { "kb_entry_id": "easypay-freeze",      "kb_version": "2026.08.1", "group": "reference" }
  ],
  "citations": [
    { "kb_entry_id": "relief-application", "kb_version": "2026.08.1" }
  ],

  "model": "…", "token_in": 3200, "token_out": 480, "latency_ms": 2100,
  "masked_counts": { "account": 1, "name": 2 },
  "audit_id": "01J8XKR2..."
}
```

**`kb_context`의 `group`이 진단의 핵심입니다.** "은행 이체 사건인데 왜 간편송금 절차를 안내했나"를 조사할 때, 그 항목이 `reference`였다면 **모델이 조건 라벨을 빠뜨린 것**으로 원인이 바로 좁혀집니다.

`group` 값의 정의와 프롬프트 조립 규칙은 [11-chat-context.md](../backend/08-16-chat-context.md).

### 5.3 관리자도 원문 개인정보를 볼 수 없습니다

**이 설계의 핵심입니다.**

```
관리자가 보는 것:   "[계좌-1] 로 300만원을 보냈다고 하셨으니…"
관리자가 못 보는 것: 110-234-567890
```

프롬프트·판단 근거·응답이 전부 **토큰화된 상태로 저장**돼 있고, 복호화 키는 사용자 브라우저에만 있습니다 → [04](08-14-pii-boundary.md) 불변 규칙 1

**관리자에게도 키가 없습니다.** 관리자 화면에서 토큰을 복원하는 경로를 만들지 않습니다.

**감사 가능성과 개인정보 최소 취급이 보통 상충하는데, 이 구조에서는 둘이 동시에 성립합니다.**

### 5.4 판단 근거는 사용자 응답에 절대 넣지 않습니다

**이유가 둘인데, 두 번째가 더 급합니다.**

**첫째, 화면이 실수로 표시할 수 있습니다.** 판단 근거에는 "이 사용자는 아직 신고를 안 한 것으로 보임" 같은 내부 판단이 들어갑니다. 화면에 뜨면 사용자가 불필요하게 불안해집니다.

**둘째, 판단 근거에는 인용 강제가 걸리지 않습니다.**

인용 검증은 최종 응답의 `citations`에 대해서만 돕니다. 그런데 모델이 생각하는 도중에는 이런 문장이 나올 수 있습니다.

```
판단 근거: "이 사용자는 지급정지를 걸었으니 3영업일 안에 신청서를 내야 한다.
            아마 은행 앱으로도 될 것이다."
                ^^^^^^^^^^^^^^^^^^^^^ KB 근거 없음. 검증 안 받음
```

**최종 응답에서는 `CLAUDE.md` 불변 규칙 1이 지켜지는데 판단 근거에서 새는 상태**가 됩니다. 사용자는 둘을 구분해 읽지 않습니다.

**그래서 관리자 전용 경로 분리는 선택이 아니라 필수 조건입니다.** 일반 사용자 응답 본문에 어떤 형태로도 판단 근거가 들어가면 안 됩니다.

### 5.5 감사 로그와의 관계

관리자 조회 자체도 기록에 남깁니다.

| `event_type` | `detail` |
| --- | --- |
| `admin.message_viewed` | `{"message_id": "…", "viewer": "…"}` |

**누가 무엇을 열어 봤는지가 남아야** 관리자 권한이 통제 밖으로 나가지 않습니다. `detail`에 개인정보를 넣지 않는 규칙은 그대로입니다 → [09](../backend/08-16-data-model.md) §10.1
