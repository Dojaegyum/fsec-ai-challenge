# 슬롯 티어링 (F-05b)

> **출처** — [서비스 기획서 v1.2](../../assets/artifacts/plans/08-13-service-plan.html) §2

> **설계 원칙: 미확정 슬롯이 있어도 절대 멈추지 않는다.**
> 패닉 사용자는 정보를 못 주는 게 정상입니다. 정보 요구로 사용자를 막지 말고,
> T0부터 시작해 슬롯이 채워질 때마다 플랜을 점진적으로 구체화합니다.

## 3티어

| --- | --- | --- |

| **T2 · 정밀화** | 문진으로 채우는 다섯 — 기관명·금액·시각·경과시간·상대 연락수단 (금액을 「모름」이라 하면 구간을 한 번 더, 이미 밟은 절차의 날짜 둘은 → 구현 주의). 상대 계좌·사칭 기관·부산물이 남기는 기산점처럼 **묻지 않고 채우는 T2 도 있어**, 전체 목록·티어·타입의 정본은 [09 §5.1](08-16-data-model.md)이고 코드는 `slot-checker/check.ts` 의 `T2_KEYS`·`ASK_ORDER` 가 같은 표를 듭니다 | **증거에서 자동 추출 우선** (이체내역 OCR → 은행명·금액·시각). 실패 시에만 질문. 미확정은 플랜에 '미확인' 배지로 명시, 나중에 채우면 **플랜 자동 재생성**. ⬜ 자동 추출은 **구현 전** — 아래 「구현 상태」 |

> **구현 상태 (2026-09-04)** — 표와 아래 흐름이 코드와 다른 자리 셋입니다.
>
> - **T0 는 KB 항목이 아닙니다.** `src/kb/` 에 1332·추가 송금 금지·비행기모드 항목은 없고, 넷은
>   브라우저의 상수입니다 — `src/app/c/[token]/safety.tsx` 의 `T0`(「KB 가 아니라 상수인 유일한 절차」).
>   사건을 만들 때 §3.1 응답이 함께 실어 보냅니다([ADR-046](../../decisions/046-case-and-plan-together.md)).
> - ~~**「증거에서 자동 추출 우선」은 구현 전입니다.**~~ → **배선됐습니다** (2026-09-04 ·
>   [ADR-069](../../decisions/069-evidence-slot-extraction.md)). `flows/read-evidence.ts` 가 토큰화 뒤에
>   기관명 사전 대조([ADR-056](../../decisions/056-transcript-org-normalization.md))에 이어 `slot-extractor` 를 불러
>   **금액 · 시각 · 상대 계좌 · 사칭 기관 · 연락 수단** 다섯을 `extracted` 로 둡니다. 뽑힌 값은 문진 자리에서
>   **한 번의 탭**(「맞아요」)으로 확인받고, 「아니에요」면 그 문항이 원래 형식으로 나옵니다. 값은 절대 표기만
>   받습니다(`lib/extracted-value.ts` — 「어제」는 사람에게 묻습니다). T1 둘은 여전히 사람의 답으로만 옵니다.
>   **본인 계좌·성명**(둘 다 토큰일 때만)도 같은 길로 뽑아 기재 안내의 신원 칸에 미리 채웁니다 —
>   묻지는 않습니다([ADR-070](../../decisions/070-prefill-identity-from-evidence.md)).
> - **슈퍼셋의 조건 라벨이 KB 에 하나도 없습니다.** `planner/plan.ts` 의 `supersetSteps` 는 `body.conditional`
>   이 있는 단계만 넣게 되어 있는데, KB 32 항목이 전부 `"conditional": null` 이라 슈퍼셋 플랜에 다른 유형의
>   조건부 단계가 하나도 붙지 않습니다. 라벨은 KB 가 씁니다 — 코드가 유형 이름으로 지어내면 절차 지식을
>   코드에 굽는 셈입니다([RFC-002](../../rfc/002-kb-authoring.md)).

## 흐름

```
인입(파일/텍스트/문진)
  → 슬롯 자동 추출 (전사·OCR에서 LLM 추출)      뽑힌 값은 `extracted` → 문진 자리에서 「맞아요」 한 탭 (ADR-069)
  → 슬롯 체커: T1 충족?
       ├ 미충족 → 우선순위 최상 슬롯 1개만 버튼 질문 ("모름" 포함)
       │            ├ 응답 → 다시 추출
       │            └ 모름 → 보수적 슈퍼셋 플랜
       └ 충족   → 유형별 맞춤 플랜 생성 (KB 근거 인용)
  → 실행 보드
       └ 증거 추가·슬롯 보완 시 → 추출부터 다시 (플랜 재생성)

T0 공통 안전 절차는 인입 즉시, 슬롯과 무관하게 실행 보드에 상시 노출
```

## 규칙

### 최소 질문 원칙

- **한 번에 한 슬롯만.** 버튼으로 담을 수 있는 질문은 전부 버튼으로, 담을 수 없는 것
  (날짜·기관명·정확한 금액)은 [API](../common/08-14-api.md) §3.4 의 `input`
  (`text`·`date`·`amount`)으로 — 어느 쪽이든 「모름」 자리는 상시입니다
  → [ADR-061](../../decisions/061-question-input-kinds.md).
- 질문 순서는 **플랜을 가장 크게 바꾸는 슬롯부터** (정보 이득 순).
- T2는 증거 자동 추출이 우선이므로 실제 질문은 보통 1~2개로 끝나야 합니다.

### "모름"의 처리

"모름"은 실패가 아니라 **정상 상태**입니다.

- 슈퍼셋 플랜은 모든 분기의 안전 단계를 포함하되, 조건부 단계에는 `"카카오페이로 보냈다면"` 식 라벨을 붙입니다.
  라벨은 KB 항목의 `body.conditional` 이 쓰고 코드는 짓지 않습니다 — 지금은 전부 비어 있어 조건부 단계가
  하나도 붙지 않습니다(위 「구현 상태」).
- **낫게 안내하지 못할 바에 넓게 안내하고, 절대 창작하지 않습니다.**

### 재생성

슬롯이 나중에 채워지면 플랜을 다시 만듭니다. 이때 **이미 완료된 단계의 상태(부산물 포함)는 보존**해야 합니다 → [05](08-14-completion-hook.md).

## 구현 주의

- 슬롯 미충족을 이유로 실행 보드 진입을 막는 흐름을 만들지 마세요 — T0가 있는 이유입니다.
- 모달로 정보를 강제 입력받는 UI는 이 원칙에 어긋납니다.
- 자동 추출 실패는 정상 경로입니다. 예외로 처리하지 말고 질문 경로로 흘려보내세요.
- **이미 밟은 절차의 날짜(`freeze_requested_at`·`relief_applied_at`)는 처음부터 질문입니다.**
  이체내역에도 전사에도 「언제 지급정지를 요청했나」는 없어 추출할 원본 자체가 없고,
  부산물에 있는 것은 **올린 날**이라 늦게 올리면 기한이 그만큼 늦게 잡힙니다
  ([ADR-054](../../decisions/054-notice-anchor.md)와 같은 이유). **이 둘이 비면
  3영업일도 14일 유예도 서지 않습니다** — 화면에 기한이 하나도 안 뜹니다.
