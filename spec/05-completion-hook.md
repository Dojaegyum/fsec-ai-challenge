# 50 · 완수 검증 Completion Hook (F-06b)

기획서 §5.

> **문제** — 체크리스트는 "체크는 됐는데 행위는 안 된 상태"를 막지 못합니다.
> 은행·경찰 시스템 API가 없으므로 완수를 직접 조회할 수도 없습니다.
>
> **원리** — 모든 공식 절차는 완수 시 반드시 **부산물**(접수번호·통지 문자·접수증)을 남깁니다.
> 이 부산물을 완료 조건이자 **다음 단계의 필수 입력**으로 삼으면,
> 인위적 잠금이 아니라 **절차 자체의 의존관계**로 완수가 강제됩니다.

## ① 증거 연쇄 (Evidence-Chained Workflow)

각 단계의 완료 = 부산물 입력/업로드.

| 단계 | 부산물 | 다음 단계에서의 쓰임 |
| --- | --- | --- |
| 112 신고 | 사건접수번호 | **피해구제신청서의 필수 필드** |
| 지급정지 | 은행 접수 문자 캡처 | 진행 상태 근거 |
| 서면 신청 | 접수증 | **환급 타임라인의 기산점** |

**부산물이 없으면 다음 산출물이 물리적으로 완성되지 않는 구조가 가장 강한 훅입니다.**

## ② 검증 3단계

| 레벨 | 방식 | 결과 상태 |
| --- | --- | --- |
| **L1 자동 검증** | 접수번호 포맷 체크, 접수증 OCR로 이름·날짜·사건 정보 대조(사건 파일과 일관성 검사) | 완료(증빙됨) |
| **L2 증빙 확인** | 캡처·서류 업로드 (**PII 스크러버 통과**) | 완료(증빙됨) |
| **L3 자기 신고** | 최후 수단 — 허용하되 상태가 '완료'가 아님 | **미확인** |

### 상태 머신

```
미시작 → 진행중 → 완료(증빙됨)
                └→ 미확인   (L3 자기신고)
```

`미확인`은 종결 상태가 아닙니다 — 리마인더 추적 대상으로 남습니다.

## ③ 통화 동반 모드

전화는 웹이 관측할 수 없는 블랙박스이므로 **관측 가능한 앞뒤를 잡습니다.**

1. 발신 버튼 클릭 → 통화 스크립트 + 예상 질문 표시
2. 통화 타이머 작동
3. 종료 직후 → **"접수번호를 지금 받아적으세요" 캡처 프롬프트 즉시 표시**

부산물 확보를 통화 경험 안에 심는 설계입니다.

## ④ 소프트 게이트 + 리마인더 + 사회적 훅

패닉 사용자를 막아 세우면 이탈합니다.

- **"나중에 입력"은 항상 허용**합니다.
- 단, `미확인` 상태를 **3영업일 D-day 트래커와 연동**해 리마인더(웹 알림·이메일)가 계속 추적합니다.
- **보호자 공유** — 진행 현황을 가족이 열람. 완수 책임을 사회화하는, 완수율을 올리는 가장 강한 비기술적 훅.

## 구현 주의

- 사용자의 체크만으로 `완료(증빙됨)`가 되는 경로를 만들지 마세요 — 이 기능의 존재 이유가 사라집니다.
- 업로드된 접수증도 PII 스크러버를 통과해야 합니다 → [04](04-pii-boundary.md).
- 플랜이 재생성되어도(슬롯 보완 시, [02](02-slot-tiering.md)) **이미 확보한 부산물과 완료 상태는 보존**해야 합니다.
- L1 자동 검증이 실패했다고 사용자를 막지 마세요. L2 → L3으로 내려가는 경로가 항상 열려 있어야 합니다.
