# RFC — 제안과 논의

구현 방식이 갈리는 문제를 **spec을 고치기 전에** 글로 정리하는 곳입니다.

## 언제 RFC를 쓰나

- 선택지가 둘 이상이고 되돌리기 비싼 것 (저장소·인증·상태 관리 구조 등)
- spec의 `TODO(미정)`을 채우려는데 정하는 데 근거가 필요한 것
- 이미 채택된 결정을 뒤집자는 제안

반대로, **정답이 하나뿐인 것은 RFC 없이** 그냥 spec에 쓰고 구현하세요.

## 흐름

```
rfc/NNNN-제목.md (초안)
   ↓ 논의
결론이 나면 → decisions/NNNN-....md 로 옮기고 (+ spec/ 갱신)
              rfc/ 의 파일은 지운다
```

**결론이 난 제안은 `rfc/`에 남기지 않습니다.** 같은 주제가 두 폴더에 있으면 어느 쪽이 정본인지
헷갈리고, ADR과 역할이 겹칩니다. 채택이든 폐기든 결론은 `decisions/`에 기록합니다
(폐기도 결정입니다 — "이건 검토했고 안 하기로 했다"를 남길 가치가 있습니다).

지운 RFC는 git 히스토리에 남으므로 논의 과정이 필요하면 거기서 꺼내면 됩니다.

**`rfc/`에 파일이 있다 = 아직 안 정해졌다.** 폴더만 봐도 미결 목록이 됩니다.

RFC는 **제안**이고 ADR은 **결정**입니다. 하나의 RFC가 여러 ADR을 낳을 수 있습니다.

## 파일명

`NNNN-제안을-한-문장으로.md` — 예: `0001-사건-스토어-선택.md`

번호는 순번이며 재사용하지 않습니다. 템플릿은 [0000-template.md](0000-template.md).
