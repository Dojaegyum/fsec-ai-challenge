# RFC-0007. 챗 답변의 근거를 문장 단위로 붙이고, 근거가 없으면 에러 대신 되묻는다

- 상태: **채택됨(→ `decisions/0009`)**
- 작성일: 2026-08-16
- 관련: `spec/11-chat-context.md` §5 §6 §9 · `spec/10-errors.md` §4.1 · `spec/08-api.md` §3.9 · [RFC-0006](0006-챗-컨텍스트-조립.md)

## 무엇을 정해야 하나

`spec/11-chat-context.md` §6.2에 미정 항목이 하나 남아 있습니다.

> TODO(미정): **절차를 언급했는지의 판정 방법.** `10-errors.md`가 "절차를 언급한 응답에 `citations`가 비면 안 된다"고 정했는데, 언급 여부를 서버가 어떻게 판정할지는 정해지지 않았습니다.

이게 안 정해지면 **인용 강제를 구현할 수 없습니다.** 양쪽 다 문제가 됩니다.

```
인용이 비면 무조건 거부   →  "네, 접수 문자 오면 올려주세요" 에도 근거를 요구
인용이 비어도 통과        →  근거 없이 "3영업일 안에 하세요" 라고 해도 안 잡힘
```

두 번째가 실제 위험입니다. **이 서비스에서 잘못된 기한 안내는 사용자가 권리를 잃는 것으로 이어집니다.**

그리고 이 문제를 파고들면서 **두 번째 문제**가 드러났습니다. 지금 스펙은 인용을 못 붙였을 때 재시도 두 번 뒤 502로 끝냅니다. 그게 맞는지 다시 봐야 합니다.

## 문제 1 — 절차를 언급했는지 누가 판정하는가

### 선택지

#### A. 서버가 응답 문장을 규칙으로 검사한다

"3영업일", "신청하세요" 같은 표현 목록을 만들어 대조합니다.

**탈락입니다.** 그 목록에 근거가 없습니다. 한국어 표현은 다양해서 빠뜨리면 못 잡고 과하게 넣으면 정상 응답이 막힙니다. `CLAUDE.md` 작업 규칙이 가장 강하게 막는 것이 **근거 없는 규칙을 지어내는 일**입니다.

#### B. 모델이 스스로 표시한다

응답에 "이번 답변은 절차를 말했다/아니다"를 함께 내게 합니다.

**탈락입니다.** 불변 규칙 1의 확인 장치를 모델 판단에 맡기는 것이 됩니다. 모델이 틀리거나 업로드 문서에 심어진 문장에 넘어가면 **검증이 통째로 비켜갑니다.**

#### C. 판정 자체를 없앤다

**모델이 자유 문장을 낼 때는 근거가 하나 이상 반드시 있어야 합니다.** 되묻기라는 예외를 두지 않습니다.

근거는 이 서비스의 구조에 있습니다. **되묻는 것은 원래 모델의 일이 아닙니다.** `spec/02-slot-tiering.md`가 빠진 정보를 물을 때 **서버가 버튼 한 문항으로 만든다**고 정해뒀습니다.

```
슬롯이 비었을 때  →  서버가 next_question 을 만든다 (버튼)
모델이 자유 문장을 쓰는 자리  →  절차를 설명하는 자리뿐
```

그래서 "절차를 언급했는가"라는 판정이 애초에 필요 없습니다.

### 권고 — C

**판정을 없애는 것이 판정 방법을 잘 만드는 것보다 낫습니다.** 규칙을 지어내지 않아도 되고, 모델 판단에 기대지도 않습니다.

## 문제 2 — 근거를 못 붙였을 때 무엇을 할 것인가

### 지금 스펙

`spec/10-errors.md` 예시 (3)입니다.

```
1차 생성: LLM이 절차를 설명했으나 citations 가 빔  → 재시도 1/2
2차 생성: 여전히 빔                                → 재시도 2/2
3차:      실패                                     → 502 "안내를 만들지 못했습니다"
```

### 이게 왜 문제인가

**근거를 못 붙였다는 것은 지금 조회된 절차가 이 질문에 안 맞는다는 뜻입니다.** 그리고 조회 조건은 사건 정보에서 나옵니다. 즉 **사건 정보가 부족하다는 신호이지 시스템 실패가 아닙니다.**

`CLAUDE.md` 불변 규칙 5가 이렇습니다.

> **"모름"은 실패가 아니다.** 정보가 없어도 플랜 생성은 멈추지 않습니다. 정보 요구로 사용자를 막는 흐름을 만들지 마세요.

충격 상태의 사용자에게 "안내를 만들지 못했습니다"라는 화면을 띄우는 것은 이 규칙과 어긋납니다. **사용자는 자기가 무엇을 더 알려줘야 하는지 모른 채 막힙니다.**

### 제안 — 원인을 둘로 가른다

| 원인 | 무엇을 뜻하나 | 처리 |
| --- | --- | --- |
| **KB 조회 결과 0건** | 해당 절차가 KB에 없음. 되물어도 안 나옴 | **현행 유지.** 절차를 말하지 않고 1332 안내 |
| **조회는 됐는데 인용을 못 붙임** | 조회된 절차가 질문에 안 맞음. **정보 부족 가능성** | **되묻기로 넘긴다** |

되묻기 경로입니다.

```
인용 없음
  → 형식 실수를 감안해 재시도 1회
  → 여전히 없으면 슬롯 체커로 넘긴다
      → 아직 안 채워진 슬롯 중 정보 이득이 가장 큰 것 하나를 버튼으로 질문
      → 채워지면 조회 범위가 좁아진 상태로 다시 답변
      → 채울 슬롯이 더 없으면 그때 1332 안내
```

이러면 `KB_CITATION_MISSING`은 **조회 0건**과 **슬롯을 다 채웠는데도 여전히 인용 불가**에만 남습니다. 일반 경로에서는 **에러가 아니라 질문이 나갑니다.**

`spec/10-errors.md` §4의 「에러가 아닌 실패」 분류와 결이 맞습니다. 그 표에 이미 "슬롯 자동 추출 실패 → 질문으로 흘려보냅니다"가 있습니다.

## 문제 3 — 근거를 어떻게 표시할 것인가

### 지금 스펙

`citations`가 `(kb_entry_id, kb_version)` 쌍만 담습니다. **답변 전체에 하나로 붙습니다.**

이러면 **과잉 인용을 막지 못합니다.** 허용 집합 대조는 조회된 항목을 전부 넣어도 통과합니다. 어느 문장이 어느 근거에서 나왔는지도 알 수 없습니다.

### 제안 — 문장 단위로 붙이고, 항목마다 이유를 쓴다

```jsonc
{
  "reasoning": "지급정지가 done_verified 이고 freeze_requested_at 이 confirmed 다. …",
  "citations": [
    { "ref": 1,
      "label": "국민은행 지급정지 요청",        // 사람이 읽는 이름. 서버가 붙임
      "kb_entry_id": "kb-bank-freeze-request",
      "kb_version": "2026.08.1",
      "why": "지급정지를 이미 걸었으므로 다음 기한이 적용되기 때문" }
  ],
  "reply_segments": [
    { "text": "다음은 피해구제 신청서 제출입니다.", "ref": 1 },
    { "text": "접수 문자가 오면 올려주세요.", "ref": null }
  ]
}
```

**프롬프트 쪽에는 이렇게 들어갑니다.**

```
[1 · 국민은행 지급정지 요청]
  통신사기피해환급법 제4조 …

[2 · 피해구제 신청서 제출]
  …
```

**얻는 것 둘입니다.**

**과잉 인용이 줄어듭니다.** 왜 인용했는지를 쓰게 하면 관련 없는 항목은 쓸 이유가 없어 스스로 걸러집니다. 그리고 **선언한 근거를 어느 문장에도 안 붙이면 서버가 잡을 수 있습니다.**

**관리자 조회가 항목 단위로 답합니다.** `spec/08-api.md` §5의 관리자 경로가 "왜 하필 이 절차를 골랐나"에 답할 수 있게 됩니다.

### 태그는 번호와 이름을 함께 씁니다

**둘 다 서버가 붙입니다.** 모델은 지어낼 자리가 없습니다.

| | 무엇에 쓰나 |
| --- | --- |
| `ref` (번호) | **대조용.** 모델은 이 번호로만 인용하고, 없는 번호는 그 자리에서 걸립니다 |
| `label` (이름) | **사람용.** 관리자 화면과 판단 근거에서 무엇을 가리키는지 읽힙니다 |

**이름만 쓰면 모델이 그럴듯한 이름을 지어내기 쉽습니다.** 허용 집합 대조에서 걸리기는 하지만 재시도가 늘고, **재시도 소진은 사용자 실패로 이어집니다.**

**번호만 쓰면 판단 근거가 읽히지 않습니다.** "1번을 인용했다"보다 "국민은행 지급정지 요청을 인용했다"가 관리자 조회에서 훨씬 빨리 읽힙니다.

## 문제 4 — 대괄호가 겹칩니다

`spec/04-pii-boundary.md`의 토큰이 `[계좌-1]`·`[이름-1]` 형식입니다. 근거 표시를 같은 대괄호로 본문에 넣으면 **두 표기가 겹치는데 처리 방향이 정반대입니다.**

| | 최종 답변 본문에 |
| --- | --- |
| PII 토큰 | **남아야 합니다** — 브라우저가 부분 복원 |
| 근거 표시 | **없어야 합니다** — `spec/11` §5.1이 내부 식별자의 노출을 금지 |

**문장 단위 구조가 이 문제를 없앱니다.** 근거 번호가 본문 안이 아니라 문장 바깥의 별도 칸(`ref`)에 붙기 때문에 두 표기가 만나지 않습니다.

## 이 검증이 못 막는 것

**문서에 명시해 둡니다.** 인용 검증이 정확성까지 보장하는 것으로 읽히면 안 됩니다.

| | |
| --- | --- |
| **막습니다** | 없는 절차를 지어내는 것 · 이 사건에 해당하지 않는 절차를 근거 없이 끌어 쓰는 것 |
| **못 막습니다** | **맞는 항목을 인용해 놓고 본문에 내용을 틀리게 옮기는 것** |

뒤쪽에서 가장 위험한 것은 날짜인데, 그건 `spec/11` §3.3이 이미 막고 있습니다. **날짜는 서버가 계산해 프롬프트에 넣고 모델은 계산하지 않습니다.**
