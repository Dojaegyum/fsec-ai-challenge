# RFC-0005. 바뀌는 절차 지식을 어디서 가져와 어떻게 저장할 것인가

- 상태: **채택됨(→ `decisions/0006`)**
- 작성일: 2026-08-16
- 관련: `spec/07-kb-operations.md`, `spec/09-data-model.md`, `research/`

## 무엇을 정해야 하나

보상 제도와 신고 기한은 계속 바뀝니다. **어디서 가져와서 어떻게 저장할지**가 안 정해지면 다음을 못 만듭니다.

- `F-11` 매뉴얼 KB 운영 파이프라인 — 무엇을 감시할지 모름
- `kb_entry` 채우기 — 원천이 없음
- Staleness Guard — 무엇과 비교해 "낡았다"고 판정할지 모름

`spec/07-kb-operations.md`가 소스 셋을 이름으로만 적어 뒀고 `TODO(근거 필요): 국가법령정보 API 사용 조건 확인`이 남아 있었습니다. **이 문서가 그것을 실측으로 채웁니다.**

## 1. 실측 결과 — 소스 셋 다 살아 있습니다

2026-08-16에 직접 호출해 확인했습니다.

### 1.1 국가법령정보 Open API — **기대 이상**

```
검색:  https://www.law.go.kr/DRF/lawSearch.do?OC=<키>&target=law&type=XML&query=<법령명>
본문:  https://www.law.go.kr/DRF/lawService.do?OC=<키>&target=law&MST=<일련번호>&type=XML&efYd=<시행일>
```

**통신사기피해환급법으로 실제 호출한 결과입니다.**

| 항목 | 값 |
| --- | --- |
| 법령ID | `011359` |
| 시행일자 | `20260804` |
| 공포일자 | `20260203` |
| 소관부처 | 경찰청, 금융위원회 |
| 응답 크기 | 법률 47KB · 시행령 223KB |
| 조문 수 | 법률 31개 · 시행령 27개 |

**핵심 발견 셋입니다.**

**첫째, `efYd`(시행일) 파라미터로 그 시점 기준 본문을 조회할 수 있습니다.** 과거 시점 조문을 그대로 재현할 수 있다는 뜻입니다.

**둘째, XML이 조문·항·호 계층으로 구조화돼 있습니다.** 시행령에 항 68개, 호 101개가 개별 태그로 들어 있어 **조문 단위 비교가 가능합니다.**

**셋째, `<조문시행일자>`가 조문마다 따로 있습니다.** 법령 하나 안에서도 조문별로 시행일이 다를 수 있고, 그걸 읽을 수 있습니다.

> ⬜ **[근거 필요]** 이용 조건. 안내 페이지에 "상업적 이용이 허용되지 않는 서비스에 상업적으로 이용하는 경우 제한될 수 있다"는 취지의 문구가 있으나 **정확한 조건을 확인하지 못했습니다.** 대회 제출물은 비상업이라 문제없을 가능성이 높지만, 신청 시 확인해야 합니다. 승인은 1~2일. 문의 02-2109-6446.

### 1.2 금융위원회 RSS — 본문까지 내려옵니다

| 게시판 | 주소 |
| --- | --- |
| **보도자료** | `https://www.fsc.go.kr/about/fsc_bbs_rss/?fid=0111` |

## 2. 실측이 바로 잡아낸 것 둘

**소스가 살아 있다는 것보다 이게 더 중요합니다.** 원문을 읽자마자 우리 자료의 오류가 나왔습니다.

### 2.1 기한 기산점이 틀렸습니다

시행령 제3조 원문입니다.

> ① … 피해구제신청서에 피해자의 신분증 사본을 첨부하여 해당 금융회사에 제출하여야 한다. **다만, 긴급하거나 부득이한 사유가 있는 경우에는 전화 또는 구술로 신청할 수 있다.**
>
> ② … **피해구제를 신청한 피해자는 그 신청한 날부터 3영업일 이내에** 제1항 본문에 따른 신청서류를 해당 금융회사에 제출하여야 한다.

**기산점은 「피해구제를 신청한 날」입니다.** 우리 자료(`research/01-환급절차-기한.md`)는 `freeze_requested_at`(지급정지 요청 시각)으로 적어 뒀습니다.

실무에서는 전화 한 통으로 지급정지와 피해구제를 같이 신청해 같은 날이 되는 경우가 많겠지만, **법적 기산점은 다릅니다.** 지급정지만 걸고 피해구제 신청을 안 한 경우 3영업일이 아직 시작 안 된 것일 수 있습니다.

**`case_slot`에 `relief_applied_at`을 추가하고 기산점을 그것으로 바꿔야 합니다.**

### 2.2 30영업일의 정체를 찾았습니다

`research/05-미확인-목록.md`의 **U-05**로 남겨 뒀던 항목입니다.

> ④ 법 제3조제3항에서 "대통령령으로 정하는 기한"이란 **30영업일**을 말한다.
> [본조신설 **2023.11.7**]

**수사기관이 피해자·피해금을 금융회사에 통지하는 기한**입니다. 대면편취형이 적용 대상에 들어온 시점(2023-11)에 신설됐습니다.

**사용자 기한이 아닙니다.** `deadline.kind = 'info'`로 넣어야 합니다.

## 3. 소스 3층은 성격이 달라 처리도 달라야 합니다

| 층 | 소스 | 형식 | 변경 빈도 | 신뢰도 | 감지 방식 |
| --- | --- | --- | --- | --- | --- |
| **1. 법령** | 국가법령정보 API | **구조화 XML** | 낮음 | 최고 | **조문 단위 비교** |
| **2. 정책 공지** | 금융위 RSS | 자연어 HTML | 중간 | 높음 | 항목 추가 감지 + LLM 분석 |
| **3. 기관 실무** | 기관 공지 | — | **높음** | 낮음 | **사람이 주기 확인** |

**1층만 기계적으로 정확한 비교가 됩니다.** 조문 텍스트가 한 글자라도 바뀌면 잡힙니다.

**2층은 감지만 자동이고 해석은 사람·모델의 일입니다.** "피해구제 신청 절차 개선" 보도자료가 떴다는 건 알 수 있지만, 그게 우리 KB의 어느 항목에 영향을 주는지는 자연어를 읽어야 압니다.

**3층은 자동화를 포기합니다.** 콜센터 번호가 바뀌었는지 알 방법이 없습니다. `spec/07-kb-operations.md`가 이 층을 "깨지기 쉬워 Staleness Guard(90일 재검증)의 주 대상"이라고 이미 지목했습니다.

## 4. 저장 — 원천과 가공을 나눕니다

### 4.1 지금 빠진 것

`spec/09-data-model.md`에는 **가공된 결과(`kb_entry`)만 있고 원천을 담을 자리가 없습니다.**

원천이 필요한 이유가 셋입니다.

**비교를 하려면 이전 것이 있어야 합니다.** 저장 안 하면 매번 전체를 다시 읽고도 무엇이 바뀌었는지 모릅니다.

**사람이 검수하려면 원문이 필요합니다.** `spec/07-kb-operations.md`가 "사람 검수는 생략 불가"라고 정했는데, 검수하려면 "무엇이 어떻게 바뀌었는지"를 봐야 합니다.

**감사 가능성 때문입니다.** "이 안내의 근거가 무엇이냐"에 답하려면 그 시점 원문이 있어야 합니다. 금융보안원 거버넌스 언어와 직접 이어집니다.

### 4.2 제안하는 테이블 둘

```sql
-- 원천 스냅샷: 가져온 것 그대로
CREATE TABLE source_snapshot (
  snapshot_id   CHAR(26)     NOT NULL,
  source_type   ENUM('law','press','manual') NOT NULL,
  source_key    VARCHAR(255) NOT NULL
                             COMMENT 'law: 법령ID:조문번호:efYd / press: 게시글 URL',
  fetched_at    DATETIME(3)  NOT NULL,
  content       MEDIUMTEXT   NOT NULL COMMENT '원문 그대로',
  content_hash  CHAR(64)     NOT NULL COMMENT 'SHA-256. 변경 감지용',
  meta          JSON         NOT NULL COMMENT '시행일·공포일·부처 등',
  PRIMARY KEY (snapshot_id),
  UNIQUE KEY uk_source_hash (source_key, content_hash),
  KEY idx_source_time (source_key, fetched_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

`uk_source_hash`가 핵심입니다. **같은 내용을 다시 가져오면 삽입이 실패하고, 성공하면 그것이 곧 변경입니다.** 별도 비교 로직 없이 데이터베이스 제약으로 감지됩니다.

```sql
-- 검수 큐: 변경이 감지되면 여기 쌓임
CREATE TABLE source_change (
  change_id       CHAR(26)    NOT NULL,
  source_key      VARCHAR(255) NOT NULL,
  snapshot_before CHAR(26)    NULL COMMENT '최초 수집이면 NULL',
  snapshot_after  CHAR(26)    NOT NULL,
  detected_at     DATETIME(3) NOT NULL,
  impact          JSON        NULL
                              COMMENT 'LLM 영향 분석: 어느 kb_entry 에 영향? 개정 초안',
  review_status   ENUM('pending','approved','rejected','deferred')
                              NOT NULL DEFAULT 'pending',
  reviewed_by     VARCHAR(64) NULL,
  reviewed_at     DATETIME(3) NULL,
  review_note     TEXT        NULL,
  released_version VARCHAR(32) NULL COMMENT '승인 후 반영된 KB 버전',
  PRIMARY KEY (change_id),
  KEY idx_status (review_status, detected_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**`review_status = 'pending'`인 행이 곧 사람 검수 큐입니다.** `spec/07-kb-operations.md`가 요구한 "절차 지식은 자동 반영 금지"가 이 칼럼으로 강제됩니다. `approved` 없이는 `kb_entry`에 안 들어갑니다.

### 4.3 전체 흐름

```
[1층] 법령 API ─┐
[2층] RSS ──────┼─► source_snapshot   (원문 그대로. 해시 중복이면 무시)
[3층] 사람 ─────┘         │
                          │ 새 해시 = 변경
                          ▼
                   source_change (pending)
                          │
                          │ LLM 영향 분석 → impact 채움
                          ▼
                   👤 사람 검수
                          │ approved 만
                          ▼
                   kb_entry 새 버전 릴리스
                          │
                          ▼
                   런타임 조회 (시행일 분기)
```

**`kb_entry`는 이 흐름의 끝에만 있습니다.** 수집기가 `kb_entry`를 직접 쓰지 않습니다.

무엇을 가져올지 고정해 둡니다. 목록이 없으면 수집기가 무엇을 볼지 매번 정해야 합니다.

| 법령 | 왜 |
| --- | --- |
| 전기통신금융사기 피해 방지 및 피해금 환급에 관한 특별법 | 절차·기한의 근거 전부 |

**시행령이 실질적으로 더 중요합니다.** 구체적 기한이 전부 시행령에 있습니다.

사기이용계좌 · 통장묶기 · 자율배상 · 책임분담 · 간편송금 · 가상자산

> ⬜ **[미정]** 키워드 필터로 충분한지, 아니면 제목·본문을 LLM에 넣어 판정할지. 놓치는 것과 비용의 절충입니다.

## 5.4 수집 주기 — 하루 1회

**자동 스케줄로 하루 1회 실행합니다.**

> 초안에서는 주 1회로 잡았다가 **하루 1회로 바꿨습니다.** §8.2 의 「겹칠 때까지 읽기」 덕분에 주 1회로도 게시물은 안 놓치지만, **제도 변경을 최대 7일 늦게 알게 됩니다.** 수집 뒤에 사람 검수가 붙으므로 실제 반영은 그보다 더 늦습니다. 호출·저장 비용이 사실상 같아 지연을 줄이는 쪽을 택했습니다.

| 소스 | 주기 | 놓칠 위험 |
| --- | --- | --- |
| 법령 API | **하루 1회** | **없음.** 전체 이력을 주므로 언제 호출해도 다 나옴 |
| 입법예고 API | **하루 1회** | 낮음. 예고 기간이 보통 수십 일 |
| 금융위 게시판 | **하루 1회** | **있음 — §8.2의 겹칠 때까지 읽기로 해소** |
| 기관 연락처 | 사람이 90일 | 해당 없음 |

**법령은 주기가 문제되지 않습니다.** 실측에서 2011년 제정부터 22건이 한 번에 다 나왔습니다. 언제 호출해도 전체 이력을 주므로 놓칠 수 없습니다. 월 1회로 줄여도 되지만 같은 스케줄에 묶는 편이 단순합니다.

**게시판만 주기에 민감합니다.** RSS가 4일치밖에 안 담습니다. §8.2의 방식으로 해소합니다.

> ⬜ **[미정]** 실행 수단. Vercel 환경에서 예약 실행을 붙이는 방법을 정해야 합니다. 대회 기간에는 수동 실행으로도 시연이 되므로 착수 후순위입니다.

## 6. 대회 기간의 범위

기획서가 이미 줄여 놨습니다.

> **MVP 범위 조정** — 대회 기간엔 **KB 수동 구축**(8유형 × 검증 출처) + Watcher는 **수동 트리거 시연** 수준. 자동 수집 전체 구현은 P2(`F-11`).

**이 제안서는 그 범위를 바꾸지 않습니다.** 다만 수동 트리거 시연을 하려면 수집 스크립트가 실제로 동작해야 하고, 이 문서가 그 명세입니다.

| 만들 것 | 대회 기간 | 이후 |
| --- | --- | --- |
| 법령 API 수집 스크립트 | **만듦** (수동 실행) | 일 1회 자동 |
| RSS 수집 스크립트 | **만듦** (수동 실행) | 일 1회 자동 |
| `source_snapshot`·`source_change` 테이블 | **만듦** | 그대로 |
| LLM 영향 분석 | **만듦** (시연용) | 그대로 |
| 사람 검수 화면 | **안 만듦.** 데이터베이스 직접 조작 | 화면 |
| 자동 스케줄 | **안 만듦** | 만듦 |

### 6.1 데모에서 보여줄 수 있는 것

수집 스크립트가 실제로 도니까 **이 장면이 가능합니다.**

```
1. 법령 API 호출 → 시행령 조문 27개 수집
2. 조문 하나를 일부러 바꿔 다시 넣음
3. 해시 불일치 → source_change 에 pending 행 생성
4. LLM 이 "이 변경은 CH-bank 의 relief-application 단계에 영향" 판정
5. 사람이 승인 → KB v1.1 릴리스
6. 같은 질문에 다른 답이 나감
```

**"제도가 바뀌면 코드 배포 없이 반영된다"를 말이 아니라 동작으로 보입니다.**

## 7. 선택지 — 저장 방식

원천을 어디에 둘지가 갈립니다.

### A. 관계형 DB (권고)

위 §4.2 그대로. 사건 데이터와 같은 데이터베이스에 테이블만 추가합니다.

**좋은 점** — 검수 큐 조회가 쉽고, `kb_entry`와 조인됩니다. 인프라가 안 늘어납니다.

**나쁜 점** — 시행령 본문이 223KB입니다. 스냅샷이 쌓이면 커집니다. 다만 변경이 드물어(연 몇 회) 실제 증가는 작습니다.

### B. 파일 + 형상 관리

수집 결과를 저장소에 파일로 커밋합니다.

**좋은 점** — 변경 이력이 형상 관리에 남아 사람이 보기 좋습니다. 비교 도구가 이미 있습니다.

**나쁜 점** — 서버리스 환경에서 저장소에 커밋하는 경로를 만들어야 합니다. 검수 상태(`pending`/`approved`)를 파일로 관리하기 어렵습니다.

### C. 객체 저장소

원문은 객체 저장소, 메타·검수 상태만 관계형 DB.

**좋은 점** — 큰 본문을 데이터베이스 밖에 둡니다.

**나쁜 점** — 조회가 두 번 일어나고, 대회 규모에서 얻는 게 없습니다.

**A를 권합니다.** 변경 빈도가 낮아 B·C의 장점이 실현되지 않습니다.

## 8. 누락 방지 — 이 설계의 진짜 목표

**소스를 찾는 것보다 빠뜨리지 않는 것이 어렵습니다.** 빠뜨리면 틀린 안내가 나가는데, **빠뜨렸다는 사실 자체를 모릅니다.**

누락은 다섯 곳에서 생깁니다. 각각 방어가 다릅니다.

### 8.0 커버리지 검사 테이블 — 검토했으나 뺐습니다

「있어야 할 항목」을 테이블로 선언하고 실제 지식베이스와 대조해 빈칸을 찾는 방안을 검토했습니다.

**뺀 이유** — 8유형 × 필수 단계면 수십 행이라 **손으로 관리해도 되는 크기**입니다. `research/05-미확인-목록.md`가 이미 사람이 읽는 형태로 그 역할을 합니다. 대회 기간에 테이블과 조회를 만들 값이 안 나옵니다.

**나중에 필요해지면** 기존 구조를 안 건드리고 추가할 수 있습니다. `kb_entry`와 `LEFT JOIN` 하는 표 하나면 됩니다.

### 8.1 구멍 1 — 소스 자체를 안 보고 있음

**이건 가정이 아니라 실측으로 확인된 구멍입니다.**

법령 이력을 전부 조회하면 2011년 제정부터 22건이 나오는데, **가상자산 2026년 10월 1일 개정이 그 안에 없습니다.** 최신이 2026-08-04입니다.

**공포되기 전에는 법령 API에 안 뜨기 때문입니다.** 우리가 10월 개정을 아는 이유는 금융위 보도자료를 봤기 때문입니다.

즉 **법령 API만 보면 예정된 변경을 전부 놓칩니다.** 그런데 이 서비스에서 가장 중요한 것이 "곧 바뀐다"는 정보입니다.

**방어 — 소스를 넷으로 늘립니다.**

| 층 | 소스 | 무엇을 잡나 |
| --- | --- | --- |
| 1 | 국가법령정보 API | **공포된** 개정 |
| **1.5** | **법제처 입법예고 API** (공공데이터포털) | **공포 전 예고 중인 개정** ← 빠져 있던 것 |
| 2 | 금융위 RSS | 정책 발표·해설 |
| 3 | 기관 공지 | 연락처·창구 |

> ⬜ **[미확인]** 법제처 입법예고 API (`data.go.kr/data/15090734`). 존재는 확인했으나 실제 호출은 안 해 봤습니다. 인증키 신청이 필요합니다.

**방어 — 근거를 역검증합니다.**

`kb_entry.source_url`이 우리가 감시하는 소스 목록에 속하는지 검사합니다. 속하지 않으면 **그 항목은 바뀌어도 우리가 모르는 항목**입니다.

```sql
CREATE TABLE source_registry (
  source_key_prefix VARCHAR(255) NOT NULL COMMENT '예: law.go.kr/DRF · fsc.go.kr/no010101',
  source_type       ENUM('law','pre_notice','press','manual') NOT NULL,
  watch_method      ENUM('api','rss','human') NOT NULL,
  interval_hours    INT NULL COMMENT 'human 이면 NULL',
  last_success_at   DATETIME(3) NULL,
  last_error        VARCHAR(500) NULL,
  PRIMARY KEY (source_key_prefix)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**감시 목록에 없는 출처를 근거로 삼은 KB 항목은 경고 대상입니다.** 기관 콜센터가 대표적입니다 — 감시할 방법이 없으므로 `watch_method = 'human'`으로 등록하고 사람이 주기 확인합니다.

### 8.2 구멍 2 — 소스는 보는데 게시물을 놓침

**RSS 하나만 쓰면 수집이 며칠만 멈춰도 그 사이 게시물이 영구히 사라집니다.** 실측으로 확인했습니다.

**측정 1 — RSS는 최근 10건만 줍니다.** 그 10건이 담는 기간이 이렇습니다.

| 날짜 | 건수 |
| --- | --- |
| 2026-08-14 | 1 |
| 2026-08-13 | 2 |
| 2026-08-12 | 4 |
| 2026-08-11 | 3 |
| **합계** | **10건 = 4일치** |

하루 평균 2.5건입니다. **4일이 지나면 RSS 에서 밀려나 다시 못 받습니다.** 하루 1회로 돌려도 수집이 나흘 멈추면 그 구간이 사라집니다.

**측정 2 — 게시글 번호로는 구멍을 못 잡습니다.** 번호가 게시판별 연속이 아니라 전체 게시판이 공유합니다. 실제 간격이 22·4·4·1·2·3으로 불규칙했습니다.

**측정 3 — 게시판 목록 페이지는 쪽 번호로 과거를 줍니다.**

| 쪽 | 건수 | 날짜 범위 |
| --- | --- | --- |
| 1쪽 | 10 | 2026-08-11 ~ 08-14 |
| 2쪽 | 10 | 2026-07-31 ~ 08-11 |

**두 쪽이면 2주치입니다.** 수집이 한동안 멈췄다 재개돼도 복구할 수 있습니다.

#### 방어 — RSS는 감지에만 쓰고, 본 수집은 목록 페이지에서 합니다

**고정 쪽수를 읽지 않습니다. 이전 수집 지점과 겹칠 때까지 읽습니다.**

```
last_seen_date = 지난번 수집에서 가장 최신 게시물의 날짜
page = 1

반복:
    items = 게시판 목록 페이지(page) 읽기
    새 항목을 source_snapshot 에 저장
    if items 중 가장 오래된 날짜 <= last_seen_date:
        중단          ← 겹쳤다. 구멍 없음이 확인됨
    page += 1
    if page > 20:
        경고 남기고 중단   ← 안전장치
```

**겹칠 때까지 읽는 것이 핵심입니다.** 이렇게 하면 수집이 한 달 멈췄다가 재개돼도 그 구간이 자동으로 복구됩니다. 고정 쪽수였다면 못 채웁니다.

#### 방어 — 수집 자체의 생존을 감시합니다

`source_registry.last_success_at`이 주기의 두 배(하루 1회면 2일)를 넘으면 경고합니다.

**조용히 멈춘 수집기가 가장 위험합니다.** 아무 일도 안 일어나므로 아무도 모릅니다.

### 8.2.1 이 설계로 감시되지 않는 층이 있습니다

**중요한 한계입니다. 「우리는 다 감시한다」고 말할 수 없습니다.**

지식베이스 조회 우선순위(`spec/09-data-model.md` §11.2)의 3층 중 **1순위만 자동 감시가 불가능합니다.**

| 순위 | 내용 | 근거의 출처 | 자동 감시 |
| --- | --- | --- | :---: |
| 3순위 (전 유형 공통) | 112 신고, 명의도용 점검 | 법률 | **가능** |
| 2순위 (유형 기본) | 3영업일·14일 기한, 환급법 적용 여부 | **시행령** | **가능** |
| **1순위 (기관 전용)** | **콜센터 번호, 앱 메뉴 경로, 창구** | **은행 재량** | **불가능** |

**법령은 "금융회사에 요청한다"까지만 정합니다.** 어느 번호로 어떤 메뉴에서 하는지는 은행이 정하고, 법령·보도자료 어디에도 안 나옵니다.

구체적으로 이렇게 갈립니다.

```
2026-07 비대면 신청 시행

  제도가 바뀌었다는 사실       → 법령·보도자료로 잡힘   ✓
  "은행 앱에서 신청 가능"      → 보도자료로 잡힘       ✓
  국민은행 앱의 실제 메뉴 경로  → 어디에도 없음         ✗
  그 메뉴가 나중에 개편되는 것  → 어디에도 없음         ✗
```

**제도 변경은 잡는데, 그 제도를 실제로 이용하는 경로는 못 잡습니다.**

#### 왜 크롤링으로 해결하지 않나

은행 15곳 + 간편송금 4곳 + 거래소 5곳의 홈페이지를 각각 크롤링하는 방안을 검토했습니다.

**버린 이유** — 구조가 전부 다릅니다. 24개 크롤러를 3주 반에 만들 수 없고, 만들어도 홈페이지가 개편되면 깨집니다. 깨진 것을 감지하려면 또 다른 감시가 필요합니다.

#### 대신 하는 것 넷

**1. 낡았을 수 있다는 것을 사용자에게 보여줍니다.** `spec/07-kb-operations.md`가 이미 정한 신선도 표시를 씁니다.

> 모든 절차 안내에 "KB v2.3 · 출처: … · **최종 검증 2026-08-01**"을 표기

**2. 확인 주기를 층마다 다르게 합니다.** 지금 Staleness Guard가 전부 90일인데, **자동 감시가 되는 1·2순위는 90일이 무의미하고, 안 되는 기관 정보만 짧아야 합니다.**

| 층 | 자동 감시 | 사람 확인 주기 |
| --- | :---: | --- |
| 3순위 공통 | 가능 | 불필요 (자동으로 잡힘) |
| 2순위 유형 기본 | 가능 | 불필요 |
| **1순위 기관 전용** | **불가능** | **⬜ 미정. 90일보다 짧아야 함** |

**3. 안 되면 쓸 대체 경로를 같이 줍니다.** 번호만 주고 끝내지 않습니다.

```
"국민은행 고객센터 ○○○-○○○○ (최종 확인 2026-08-16)
 연결이 안 되면 은행 홈페이지 고객센터 메뉴에서 확인하세요"
```

틀렸을 때 사용자가 막히지 않습니다.

**4. 사용자 신고를 받습니다.** "이 번호로 연결되던가요?"가 가장 정확한 신호입니다. **다만 사용자가 있어야 동작하므로 대회 기간에는 의미가 없습니다.**

#### 검토했으나 버린 안 — 번호를 아예 안 주기

"국민은행 고객센터로 연락하세요"까지만 하고 번호를 안 쓰면 **틀릴 일이 없습니다.**

**버린 이유** — 골든타임에 사용자가 번호를 검색하게 만듭니다. 이 서비스가 하려는 것과 반대입니다.

> 이건 판단입니다. 「틀린 번호를 주느니 안 주는 게 낫다」는 반대 의견도 성립합니다. 확정 전 논의가 필요합니다.

### 8.3 구멍 3 — 변경은 잡았는데 영향을 못 알아봄

보도자료 제목만으로는 우리 KB에 영향이 있는지 모릅니다. 키워드 필터가 놓칠 수도 있습니다.

**방어 — 판정을 기록하고, 애매한 것은 사람에게 넘깁니다.**

키워드에 안 걸려 버린 것도 **버렸다는 기록을 남깁니다.** 나중에 "왜 이걸 못 봤나"를 추적할 수 있어야 합니다.

```
source_change.impact = {
  "affected": ["relief-application"],
  "confidence": 0.4,
  "reason": "…"
}
```

**확신도가 낮으면 `review_status = 'pending'`으로 사람에게 갑니다.** 자동으로 버리지 않습니다.

### 8.4 구멍 4 — 알았는데 반영이 안 됨

검수 큐에 쌓였는데 아무도 안 보면 소용없습니다.

**방어 — 큐의 나이를 감시합니다.** `review_status = 'pending'`인 행이 N일 넘으면 경고합니다.

**이게 3주 반짜리 대회에서 실제로 일어날 가능성이 가장 높은 누락입니다.** 다른 일에 밀려서 검수를 안 하게 됩니다.

### 8.5 누락 점검을 한 화면에 모읍니다

위 다섯을 매번 따로 확인하면 결국 안 하게 됩니다. **한 번의 조회로 다 나와야 합니다.**

| 점검 | 무엇을 보나 | 정상 |
| --- | --- | --- |
| 커버리지 구멍 | `coverage_requirement` 중 `kb_entry` 없는 것 | 0건 |
| 감시 안 되는 근거 | `source_registry`에 없는 `source_url` | 0건 |
| 죽은 수집기 | `last_success_at`이 주기 2배 초과 | 0건 |
| 날짜 구멍 | 마지막 수집일과 최신 배치 사이 빈 구간 | 없음 |
| 밀린 검수 | `pending` 상태가 N일 초과 | 0건 |
| 낡은 항목 | `verified_at` 90일 초과 | 0건 |

**이 여섯이 전부 0이어야 "빠진 게 없다"고 말할 수 있습니다.** 하나라도 0이 아니면 그만큼이 우리가 모르는 부분입니다.

발표에서 이 화면 자체를 보여줄 수 있습니다. **"우리는 무엇을 모르는지 알고 있다"가 근거 인용 강제와 같은 성격의 통제입니다.**

## 9. 중복 제거 — 같은 내용을 여러 벌 갖지 않습니다

누락 방지와 반대 방향의 문제입니다. **빠뜨리지 않으려고 넓게 모으면 같은 내용이 여러 벌 쌓입니다.**

중복이 생기는 곳이 넷입니다.

### 9.1 원문 스냅샷 — 조문 단위로 저장합니다

**가장 큰 낭비 지점입니다.**

시행령 본문이 **223KB**입니다. 조문 하나가 바뀌었는데 법령 전체를 새로 저장하면 223KB가 통째로 늘어납니다.

| 저장 단위 | 개정 1회당 증가 | 연 4회 개정 시 |
| --- | --- | --- |
| 법령 전체 | 223KB | 약 892KB |
| **조문 단위** | **약 8KB** | **약 32KB** |

**약 28배 차이입니다.**

**조문 단위로 저장합니다.** `source_key`를 `법령ID:조문번호:조문가지번호` 로 잡습니다.

```
source_key = "011359:3:0"          시행령 제3조
content_hash = SHA-256(조문 본문)
```

제3조만 바뀌면 **제3조 행 하나만** 새로 생기고 나머지 26개 조문은 기존 행을 그대로 씁니다. §4.2의 `(source_key, content_hash)` 유일 제약이 그대로 동작합니다.

**저장 절약보다 더 큰 이득이 있습니다.** 변경 지점이 정확해집니다.

| 저장 단위 | 변경 감지 결과 |
| --- | --- |
| 법령 전체 | "시행령이 바뀌었다" — 어디가 바뀌었는지 사람이 다시 찾아야 함 |
| **조문 단위** | **"제3조가 바뀌었다"** — 검수자가 바로 그 조문만 봄 |

그리고 `kb_entry`가 조문 단위로 근거를 가리키므로(`legal_basis`가 "시행령 제3조 제2항") **대응 관계가 맞아떨어집니다.** 제3조가 바뀌면 제3조를 인용한 KB 항목만 골라낼 수 있습니다.

**초기 적재는 조문 수만큼 행이 생깁니다.** 법률 31행 + 시행령 27행 = 58행입니다. 부담이 아닙니다.

> 앞선 열린 질문 「조문 단위 저장 vs 법령 전체 저장」을 **조문 단위로 확정합니다.**

### 9.2 같은 사건이 여러 게시판에 뜨는 경우

금융위는 게시판을 넷 운영합니다. **같은 제도 변경이 보도자료·보도설명자료·공지사항에 함께 올라올 수 있습니다.** 각각 본문이 달라서 내용 해시로는 안 걸립니다.

**방어 — 변경 건을 묶는 키를 둡니다.**

```sql
ALTER TABLE source_change
  ADD COLUMN dedupe_key VARCHAR(255) NULL
      COMMENT '같은 제도 변경을 묶는 키. 예: law:011359:3 · topic:crypto-relief-202610';
```

LLM 영향 분석이 "이 변경은 어느 KB 항목에 영향을 주는가"를 판정하는데, **그 결과가 같으면 같은 건으로 묶습니다.** 검수자가 세 번 보지 않고 한 번 봅니다.

**묶되 지우지 않습니다.** 원문 스냅샷은 셋 다 남습니다. 근거가 여럿인 것이 오히려 낫습니다.

### 9.3 지식베이스 안의 중복 — 이미 해결돼 있습니다

같은 절차가 기관마다 복사되는 문제입니다. 은행 15곳에 "3영업일 안에 신청"을 각각 넣으면 15벌이 되고, 법이 바뀔 때 15곳을 고쳐야 합니다.

**`spec/09-data-model.md` §11.2의 조회 우선순위가 이걸 이미 막고 있습니다.**

```
3순위 (전 유형 공통)   112 신고            → 한 번만
2순위 (CH-bank 기본)   3영업일 신청         → 한 번만
1순위 (국민은행 전용)  콜센터 번호만        → 그 기관에만
```

**각 정보가 한 곳에만 있습니다.** 기관 항목은 "다른 것"만 갖습니다.

### 9.4 조사 문서와 지식베이스의 중복

`research/`의 사실과 `kb_entry`의 내용이 같아 보일 수 있습니다. 실제로는 역할이 다릅니다.

| | `research/` | `kb_entry` |
| --- | --- | --- |
| 읽는 대상 | **사람** | **기계** |
| 담는 것 | 사실 + 출처 + **신뢰도** + 왜 그렇게 판단했는지 | 사용자에게 나갈 절차 문장 |
| 미확인 항목 | **포함** (그게 목적) | **제외** (확인된 것만) |

**`research/`에는 확인 못 한 것이 들어가고 `kb_entry`에는 안 들어갑니다.** 이 차이가 있어서 둘이 필요합니다.

다만 **확인된 사실은 `research/`에 두 번 쓰지 않습니다.** 조문 원문은 `source_snapshot`에 있고, `research/`는 그것을 가리키며 판단만 적습니다.

### 9.5 모델 호출의 중복 — 이미 해결돼 있습니다

지식베이스 전체를 프롬프트에 넣으면 매 호출마다 토큰이 낭비됩니다.

`spec/09-data-model.md` §11.2의 조회가 **`track` + `channel_id` + `org_id` + 시행일로 먼저 좁히므로**, 모델에는 해당하는 몇 건만 들어갑니다. 전체를 넣지 않습니다.
