# RFC-0002. 복원 매핑을 클라이언트 세션이 아니라 서버 볼트에 둔다

- 상태: **채택됨(→ `decisions/0003`)**
- 작성일: 2026-08-16
- 관련: `spec/04-pii-boundary.md`, `CLAUDE.md` 불변 규칙 3, `decisions/0002-프로젝트-이름.md`

## 무엇을 정해야 하나

토큰(`[계좌-1]`)과 원문의 대응표를 **어디에 보관할지** 정해야 합니다.

현재 `spec/04-pii-boundary.md` 불변 규칙 1은 이렇습니다.

> **복원 매핑(토큰↔원문)은 서버에 저장하지 않습니다.** 클라이언트 세션에만 보관하고, 화면 표시 시점에 브라우저가 복원합니다.

`CLAUDE.md` 불변 규칙 3도 같은 내용입니다.

**이 규칙이 서비스의 포지셔닝과 충돌합니다.** 이게 안 정해지면 다음을 못 만듭니다.

- 재방문 화면 (`F-06` 실행 보드) — 며칠 뒤 들어온 사용자에게 무엇을 보여줄지
- 서류 도우미 (`F-08`) — 첫 방문 이후에도 신청서를 만들 수 있는지
- 사건 스토어 설계 (`RFC-0003`) — 무엇을 어디에 저장할지가 여기서 갈림

## 문제 — 스펙 안의 모순

`CLAUDE.md`가 서비스를 이렇게 정의합니다.

> 기한과 서류를 **몇 달에 걸쳐** 대신 관리합니다.

`spec/04-pii-boundary.md`가 이렇게 정합니다.

> 복원 매핑은 **클라이언트 세션에만** 보관
> 사건 파일은 세션 단위 격리 스토어에만 존재하고, 종료 또는 **24시간** 후 원문·파일이 자동 파기됩니다.

**둘이 동시에 성립할 수 없습니다.** `spec/03-channel-matrix.md`의 표준 절차 기한을 그대로 따라가면 이렇게 됩니다.

| 시점 | 사용자가 하려는 것 | 클라이언트 세션만 있을 때 |
| --- | --- | --- |
| 1일차 | 사건 등록, 지급정지 요청 | 정상 동작 |
| **3영업일 내** | **피해구제 신청서 작성** (`F-08`) | 브라우저 세션 만료 시 계좌번호가 `[계좌-1]` 로만 보임 → **서류를 못 씀** |
| 2개월 | 채권소멸공고 진행 확인 | 사건 자체가 24시간 규칙으로 파기됨 |
| 3~6개월 | 환급 여부 확인 | 같음 |

`spec/03-channel-matrix.md`가 지목한 **"가장 많이 놓치는 두 지점"** 중 첫째가 "전화로 지급정지를 걸어놓고 3영업일 신청을 안 해서 효력이 날아가는 것"입니다. 그런데 현행 규칙대로면 **바로 그 3영업일 시점에 서비스가 무력해집니다.**

### 왜 이렇게 됐나

`spec/README.md`에 원인이 이미 적혀 있습니다.

> 포지셔닝 전환 — 112 이후를 맡는 사건 관리, 상담 종료 후 링크 유입 | `06-screens.md` 전반 | **미반영**

기획서 v1.2는 구 명칭(골든30) 시점 문서라 **"30분 긴급 대응"** 을 전제했습니다. 한 번의 세션 안에서 모든 일이 끝난다면 클라이언트 세션 보관으로 충분합니다.

[ADR-0002](../decisions/0002-프로젝트-이름.md)에서 포지셔닝이 **사건 관리**로 바뀌었는데, PII 경계 규칙은 그대로 남았습니다. 이 RFC는 그 미반영분을 정리하는 것입니다.

## 제약

이미 정해져 있어 못 건드리는 것입니다.

| 제약 | 출처 | 이 결정에 어떻게 걸리나 |
| --- | --- | --- |
| 외부 LLM API에는 토큰화 텍스트만 | `CLAUDE.md` 2, `spec/04` 규칙 2 | **어느 선택지에서도 유지됩니다.** 이 RFC는 LLM 경계를 건드리지 않습니다 |
| 1차 마스킹은 브라우저에서 | `spec/04` 2중 스크러빙 | 유지. 원문이 네트워크를 타기 전에 걸러지는 구조는 그대로입니다 |
| 서류 완성본을 서버가 만들어 내려주지 않는다 | `spec/04` 규칙 6, `F-08` | 유지. 복원은 여전히 브라우저에서 일어납니다 |
| 학습·통계 활용 없음 | `spec/04` 규칙 5 | 유지 |
| 감사 로그는 토큰화 기준 | `spec/04` 감사 | 유지 |

**바뀌는 것은 규칙 1(매핑 저장 위치) 하나입니다.** 나머지 다섯은 그대로입니다.

## 선택지

### A. 현행 유지 — 클라이언트 세션만

브라우저 메모리 또는 `sessionStorage`에 매핑을 두고, 탭을 닫으면 사라집니다.

**좋은 점**

- 개인정보 측면에서 가장 강합니다. 서버가 대응표를 아예 모릅니다.
- 발표에서 **"서버 어디에도 누구의 어떤 계좌인지 완성된 정보가 없다"** 를 그대로 주장할 수 있습니다. 이게 현재 스펙이 내세우는 신뢰 근거입니다.
- 구현이 가장 단순합니다. 볼트도 키 관리도 필요 없습니다.

**나쁜 점**

- **재방문이 불가능합니다.** 위 표의 3영업일 시점 문제가 그대로 남습니다.
- 다른 기기에서 볼 수 없습니다. 가족이 함께 대응하는 경우(`spec/00-glossary.md` 전제)에 특히 문제입니다.
- 브라우저 사고(탭 닫힘·새로고침·크래시)로 매핑이 사라지면 복구 방법이 없습니다.
- **"몇 달 관리" 문구를 서비스 설명에서 빼야 합니다.**

**일정** — 추가 작업 없음.

### B. 서버 볼트 + 클라이언트 세션키

매핑을 **암호화해 서버에 보관**하되, 복호화 키는 클라이언트가 가집니다.

```
[브라우저]                        [서버]
원문 보유                         암호문만 보유
1차 마스킹 ──────────────────►    2차 스크러버
세션키 보유 (localStorage)         볼트: {토큰 → AES-GCM 암호문}
                                  키를 모르므로 복호 불가
복원: 볼트에서 암호문 받아
      브라우저에서 복호
```

- 볼트 키: `vault:{case_id}:{token}`
- 값: AES-256-GCM 암호문
- 인증 부가 데이터(AAD): `case_id ‖ token ‖ kind` — 다른 사건의 암호문을 옮겨 심는 시도가 인증 실패로 막힘
- 세션키: 브라우저가 생성·보관. **서버로 보내지 않음**

**좋은 점**

- **재방문이 가능합니다.** 같은 브라우저로 돌아오면 세션키가 있어 복원됩니다.
- 서버는 여전히 원문을 모릅니다. 암호문만 있고 키가 없습니다.
- 복원은 여전히 브라우저에서 일어나므로 `spec/04` 규칙 6이 유지됩니다.
- 세션키를 지우면 남은 암호문이 영구히 복호 불능이 됩니다.

**나쁜 점**

- **주장이 약해집니다.** "서버가 아예 모른다"에서 "서버가 암호문은 갖고 있지만 키가 없다"로 내려옵니다. 발표에서 한 단계 더 설명해야 합니다.
- 다른 기기에서는 여전히 못 봅니다. 세션키가 그 브라우저에만 있기 때문입니다.
- 키 관리가 생깁니다. 사용자가 브라우저 데이터를 지우면 매핑이 죽습니다 — A와 같은 상황이 되지만, 그때가 "탭을 닫을 때"가 아니라 "브라우저를 초기화할 때"로 미뤄집니다.
- 볼트 저장소가 하나 늘어납니다 (`RFC-0003`과 연동).

**일정** — 볼트 저장소 도입 + 암복호 코드. 2~3일 예상.

### C. 서버 볼트 + 복구 키를 사용자에게

B와 같되, 세션키를 사용자가 직접 보관할 수 있게 합니다(복구 코드 발급·재입력).

**좋은 점**

- **다른 기기에서도 볼 수 있습니다.** 가족 대응 시나리오가 완전히 해결됩니다.
- 브라우저 데이터를 지워도 복구됩니다.

**나쁜 점**

- **충격 상태의 사용자에게 복구 코드를 보관시키는 것이 현실적이지 않습니다.** `spec/00-glossary.md` 전제가 "사용자는 패닉 상태이고 정보를 못 주는 것이 정상"입니다.
- 복구 코드를 잃으면 A·B와 같은 상황인데, 사용자는 "복구할 수 있다고 했는데"라고 느낍니다.
- 복구 코드가 유출되면 서버 볼트와 합쳐져 원문이 드러납니다. 새 공격면입니다.

**일정** — B + 복구 흐름 UI. 4~5일 예상. 데모 일정에 부담.

## 권고

**B(서버 볼트 + 클라이언트 세션키)를 권합니다.**

근거는 셋입니다.

**첫째, A는 서비스 정의와 모순됩니다.** 이 서비스의 존재 이유가 "3영업일을 놓치지 않게 하는 것"인데, 정작 3영업일 시점에 서류를 못 만듭니다. 개인정보 보호가 아무리 강해도 서비스가 동작하지 않으면 의미가 없습니다.

**둘째, B가 잃는 것은 생각보다 작습니다.** "서버가 아예 모른다"와 "서버가 암호문만 갖고 키가 없다"는 실질 보안 수준이 크게 다르지 않습니다. 서버가 유출돼도 원문은 안 나옵니다. 오히려 **키 분리 구조를 설명하는 것이 발표에서 더 설득력 있을 수 있습니다** — 아무것도 저장 안 하는 것은 쉽지만, 저장하면서도 못 읽게 만드는 것은 설계가 필요합니다.

**셋째, C는 일정에 안 맞고 사용자 전제와 어긋납니다.** 패닉 상태 사용자에게 복구 코드를 맡기는 것은 `spec/02-slot-tiering.md`의 "정보 요구로 사용자를 막지 말라"는 원칙과 같은 결의 문제입니다.

### 판단이 갈린 지점 — 숨기지 않습니다

**`spec/04-pii-boundary.md` 머리말이 "이 문서의 규칙은 협상 대상이 아닙니다 — 서비스의 신뢰 근거이자 심사 차별점입니다"라고 못 박고 있습니다.** 이 RFC는 그 문서의 규칙 하나를 바꾸자는 제안입니다.

바꾸자는 이유는 규칙이 틀려서가 아니라, **그 규칙이 쓰인 시점의 서비스와 지금의 서비스가 다르기 때문**입니다. 30분 안에 끝나는 서비스라면 규칙 1이 옳습니다.

그리고 **"신뢰 근거이자 심사 차별점"이라는 판단 자체는 유지됩니다.** B에서도 서버는 원문을 못 읽습니다. 다만 주장 문장이 바뀝니다.

| | 주장 문장 |
| --- | --- |
| A | 서버·LLM 어디에도 "누구의 어떤 계좌"인지 완성된 정보가 존재하지 않는다 |
| B | 서버는 암호문만 보관하고 복호화 키를 갖지 않는다. 키는 사용자 브라우저에만 있다 |

## 열린 질문

- **세션키 보관처.** `localStorage`인지 다른 방법인지. `sessionStorage`는 탭을 닫으면 사라져 A와 같아지므로 안 됩니다.
- **볼트 보관 기간.** 현행 규칙 3의 24시간은 "30분 대응" 전제에서 나온 값입니다. 사건 관리 기간(3~6개월)과 맞출지, 별도 값을 둘지 정해야 합니다. → `RFC-0003`에서 함께 다룹니다.
- **세션키를 잃었을 때의 화면.** 매핑 없이도 기한·진행 상태는 보여줄 수 있습니다(토큰 상태로). 이때 무엇을 보여주고 무엇을 안내할지 정해야 합니다. → `spec/06-screens.md` 개정 시.
