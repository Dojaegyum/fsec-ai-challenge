# RFC-0003. 사건 상태를 어디에 어떤 형태로 저장할 것인가

- 상태: **채택됨(→ `decisions/0004`)**
- 작성일: 2026-08-16
- 관련: `spec/04-pii-boundary.md`, `rfc/0002-복원-매핑-보관-위치.md`, `spec/05-completion-hook.md`, `spec/02-slot-tiering.md`

## 무엇을 정해야 하나

사건(`Case`)의 상태를 **무엇에 저장할지**와 **어떤 스키마로 둘지** 정해야 합니다.

`CLAUDE.md`의 「아직 정해지지 않은 것」에 "저장소 선택"이 올라 있고, 이게 안 정해지면 다음을 못 만듭니다.

| 못 만드는 것 | 이유 |
| --- | --- |
| `F-06` 실행 보드 | 체크리스트·기한·타임라인 상태를 어디 둘지 모름 |
| `F-06b` 완수 검증 엔진 | 부산물(`Artifact`) 저장 위치가 없음 → `spec/05-completion-hook.md` |
| `F-05b` 슬롯 체커의 재생성 | "이미 완료된 단계의 상태는 보존"해야 하는데 보존할 곳이 없음 |
| `spec/08-api.md` | 응답에 무엇이 담기는지 정의 불가 |

## 제약

| 제약 | 출처 | 걸리는 방식 |
| --- | --- | --- |
| 관계형 DB에 원문 PII 금지 | `spec/04` 규칙 1·2 | **스키마 전체를 규정합니다.** 모든 PII 칼럼은 토큰만 담습니다 |
| 사건 파일은 세션 단위 격리 스토어, 24시간 파기 | `spec/04` 규칙 3 | `RFC-0002`에서 재검토 중. **이 RFC는 그 결과에 의존합니다** |
| 감사 로그는 토큰화 기준 | `spec/04` | 로그 테이블도 토큰만 |
| 학습·통계 활용 없음 | `spec/04` 규칙 5 | 분석용 사본을 만들지 않습니다 |
| 기한 계산은 코드의 규칙으로 | `CLAUDE.md` 7, `spec/03` | 계산 결과를 저장하되 **근거를 함께** 남겨야 재현 가능 |
| LLM은 KB 근거 없이 절차 창작 금지 | `CLAUDE.md` 1, `spec/07` | 플랜에 인용한 KB 버전을 저장해야 함 |
| 배포는 Vercel | `spec/00-glossary.md` §9 | **서버리스 환경.** 상시 켜진 프로세스나 로컬 파일 저장을 전제할 수 없습니다 |

### `RFC-0002`와의 의존 관계

`RFC-0002`(복원 매핑 위치)가 A(클라이언트만)로 결론나면 **이 RFC의 상당 부분이 불필요합니다.** 사건이 24시간 안에 끝나므로 영속 저장소가 필요 없습니다.

B(서버 볼트)로 결론나면 이 RFC의 선택지 B·C가 유효합니다.

**`RFC-0002`를 먼저 정하고 이 RFC를 정해야 합니다.**

## 선택지

### A. 저장소 없음 — 브라우저에만

사건 상태를 전부 `localStorage`에 두고 서버는 상태를 갖지 않습니다.

**좋은 점** — 구현이 가장 빠릅니다. `spec/04` 규칙을 전혀 안 건드립니다. Vercel 서버리스와 잘 맞습니다.

**나쁜 점** — `RFC-0002`의 A와 같은 한계입니다. 재방문·다기기가 안 되고, `F-06b` 완수 검증의 부산물을 오래 못 들고 있습니다. 그리고 **감사 로그를 남길 수 없습니다** — `spec/04`가 요구하는 "모든 LLM 호출을 감사 로그로 기록"이 불가능합니다.

**일정** — 추가 작업 없음.

### B. 관계형 DB + 볼트 저장소 (권고)

사건 상태는 관계형 DB에, 토큰↔원문 암호문은 별도 볼트에 둡니다.

```
[브라우저]        [서버]                      [저장소]
세션키 보유  ──►  API                    ──►  관계형 DB (토큰만)
                  게이트웨이(스크러버)   ──►  볼트 (암호문, 키 없음)
                                         ──►  객체 저장소 (업로드 원본)
```

**좋은 점**

- 재방문·기한 추적·감사 로그가 전부 가능합니다.
- 사건 구조가 명시적이라 `spec/05-completion-hook.md`의 상태 머신을 그대로 표현할 수 있습니다.
- 스키마가 곧 `spec/08-api.md` 응답 정의가 됩니다.

**나쁜 점**

- 저장소가 셋이라 운영 부담이 늘어납니다.
- 서버가 사건 구조를 알게 됩니다. **원문은 모르지만 "언제 얼마를 어느 은행으로 보냈다"는 압니다** — 금액·시각·기관명은 토큰화 대상이 아니기 때문입니다(→ `RFC-0004`).
- Vercel 환경에서 관리형 DB를 붙여야 합니다.

**일정** — 스키마 정의 + 접근 계층. 3~4일 예상.

### C. 문서 저장소 하나로 통합

사건 하나를 문서 하나(JSON)로 저장합니다.

**좋은 점** — 스키마 변경이 자유롭고, 슬롯·플랜처럼 형태가 유동적인 데이터를 담기 쉽습니다. 저장소가 하나로 줄어듭니다.

**나쁜 점** — 기한 조회(`status='open' AND due_at < ?`)가 비효율적입니다. 그리고 **볼트를 같은 저장소에 두면 `spec/04`의 분리 원칙이 무너집니다.** 결국 둘로 나눠야 해서 B와 비슷해집니다.

**일정** — B와 비슷.

## 권고

**B를 권합니다.** 단 `RFC-0002`가 B로 채택된 경우에 한합니다.

근거는 셋입니다.

**첫째, `spec/05-completion-hook.md`의 완수 검증이 영속 상태를 요구합니다.** 부산물(사건접수번호·접수 문자·접수증)로 완료를 판정하는데, 이건 사용자가 실제로 절차를 밟은 뒤에 생깁니다. 며칠 뒤입니다.

**둘째, 감사 로그가 스펙 요구사항입니다.** `spec/04`가 "모든 LLM 호출을 감사 로그(토큰화 텍스트 기준)로 기록"하고 "금융보안원 생성형 AI 가이드라인의 통제 항목에 매핑"한다고 정했습니다. **이 매핑 자체가 발표의 근거가 됩니다.** 브라우저에만 두면 못 합니다.

**셋째, 기한 재현이 필요합니다.** `spec/03-channel-matrix.md`의 기한(3영업일·14일·2개월·5영업일)을 계산해 저장하는데, **계산 근거를 함께 남기지 않으면 나중에 그 날짜가 맞는지 확인할 방법이 없습니다.** KB가 개정되면 더욱 그렇습니다.

### 판단이 갈린 지점

**B는 서버가 사건 구조를 알게 됩니다.** 원문 PII는 모르지만, `RFC-0004`에서 기관명·금액·시각을 토큰화 대상에서 빼기로 하면 서버 DB에 "2026년 8월 15일 19시에 국민은행 계좌로 300만원"이 남습니다. 여기에 `[계좌-1]` 만 붙어 있습니다.

이게 개인을 특정하지는 않지만, `spec/04` 머리말의 **"서버·LLM 어디에도 '누구의 어떤 계좌'인지 완성된 정보가 존재하지 않는 구조"** 라는 문장은 **"누구의"가 빠진 상태로만 참**입니다. 문장을 정확히 고쳐야 합니다.

## 제안하는 스키마 개요

전체 DDL은 채택 후 `spec/09-data-model.md`에 씁니다. 여기서는 구조만 봅니다.

```
case ─┬─ case_channel     경유 서비스 (N개. 혼합형 지원)
      ├─ case_slot        슬롯 값과 티어 상태 (spec/02)
      ├─ plan_step        플랜 단계와 진행 상태
      ├─ artifact         부산물 (spec/05 완수 검증)
      ├─ deadline         기한 (계산 근거 스냅샷 포함)
      ├─ message          대화 이력 (토큰화 상태)
      └─ audit_log        감사 로그 (해시 연결)

kb_version               인용한 KB 버전 (plan_step 이 참조)
```

`spec/00-glossary.md`의 코드 식별자와 맞춥니다.

| 스펙 용어 | 테이블 |
| --- | --- |
| 사건 `Case` | `case` |
| 경유 서비스 `Channel` | `case_channel` |
| 슬롯 `Slot` | `case_slot` |
| 플랜 `Plan` | `plan_step` |
| 부산물 `Artifact` | `artifact` |
| 증거 `Evidence` | 객체 저장소 + `evidence` |

### 핵심 규칙 셋

**1. PII 칼럼은 토큰만 담습니다.**

```sql
counterpart_account VARCHAR(64)  -- '[계좌-1]'. 원문 금지
```

**2. 기한에는 계산 근거를 함께 저장합니다.**

```sql
rule_snapshot JSON  -- 계산에 쓴 KB 항목 전체 + 반영한 공휴일
```

KB가 개정돼도 과거 계산을 재현할 수 있어야 합니다. `spec/07-kb-operations.md`가 KB를 버전드로 관리하므로, 어느 버전으로 계산했는지가 남아야 합니다.

**3. 본 기한과 유예를 별도 행으로 둡니다.**

`spec/03-channel-matrix.md`의 "3영업일 이내, 넘기면 금융회사가 14일을 추가로 주고"는 **두 시점**입니다. 하나로 합치면 사용자에게 둘 다 안내할 수 없습니다.

## 열린 질문

- **DB 제품.** Vercel 환경에서 쓸 관리형 관계형 DB를 정해야 합니다. 무료 한도와 지역(국내 처리 여부)이 판단 기준입니다.
- **볼트 저장소 제품.** 만료와 원자적 갱신을 지원해야 합니다.
- **보관 기간.** `spec/04` 규칙 3의 24시간은 "30분 대응" 전제 값입니다. 사건 관리(3~6개월)와 맞출지 정해야 합니다 — **`RFC-0002`의 열린 질문과 같은 항목입니다.**
- **업로드 원본 보관 방침.** 녹음·캡처에는 PII가 그대로 있습니다. ① 텍스트 추출 후 즉시 파기 ② 사건 종료까지 ③ 사용자 선택. ①이 가장 안전하지만 추출 오류를 되돌릴 수 없습니다.
